# Status

Proposed in response to the human's question about implementing the September19
knowledge decisions before moving the curated knowledge and five expert souls.
The recommendation is a bounded alignment-and-cutover phase before the next
Desktop implementation wave. This is not yet approval of new contract fields,
repository visibility, source-export identities, a live migration or a helper API.

The accepted direction is [flexible knowledge and situated expertise](/decisions/flexible-knowledge-and-instance-expertise.md).
The earlier [expert rebuild](/decisions/expert-souls-and-knowledge-rebuild.md) and
[source-edition proposal](/decisions/portable-role-editions-and-bootstrap.md)
remain relevant, with their separate approval boundaries intact.

# Sequence clarification

The human subsequently directed workspace/portable adoption first, followed by
centralised knowledge and the five expertise souls. This proposal's default
profile, curation and learning checks now fit phase2 of the
[execution plan](https://github.com/awebai/oats/blob/main/docs/design/2026-09-20-workspace-and-portable-adoption-plan.md).
Only demonstrated generic contract/provider readiness gaps needed for workspace
adoption belong in phase1. Do not start the corpus move before that foundation
works, or interpret the plan as approval for every future knowledge mechanism.

# Context

The 0.24.0/2.1.0 release supplies substantial retained execution, provider binding,
capture and delivery machinery. The later canonical knowledge explanation
clarifies defaults and alternatives; publishing that explanation does not change
installed instructions, adopted templates or live knowledge bindings.

A dedicated knowledge repository and expertise-oriented roster should exercise
the accepted model, rather than preserve an old model under new folder names.
However, neither the new wording nor an unimplemented alternative proves the
existing generic kernel interface needs wholesale replacement. Identify concrete
mismatches before adding fields or changing authority.

# Options

1. **Move the curated corpus immediately.** Fastest superficially, but risks
   moving stale ownership/read edges, provider instructions and acceptance rules
   into a destination that will need another cutover.
2. **Implement every knowledge ambition first.** Co-located profiles, alternate
   providers, automatic speciation, redirects and safe context cloning would
   delay the useful default and mix separately undecided mechanisms into rollout.
3. **Align and qualify the chosen default, preserving alternative freedom.**
   Audit the boundary, correct actual gaps at their owning layer, and prove the
   centralised per-soul path before activating the successor roster. Recommended.

# Recommended scope

## 1. Classify gaps before changing contracts

Review existing binding, invocation, helper and lifecycle interfaces against
[the provider-neutral boundary](/decisions/provider-neutral-knowledge-and-harvest.md).
Classify each finding as already supported, documentation/resource drift,
provider behavior, deployment/source setup, or a genuinely missing generic seam.

- Organisation, placement, reading, promotion and maintenance belong to the
  capability. The kernel must not impose an OKF taxonomy, memory filenames,
  external-only mutable placement or a universal harvesting algorithm.
- Accepted knowledge, task-local evidence/state and retained execution artifacts
  have distinct custody. Allowing mutable knowledge never makes a retained
  source or executable artifact writable.
- A long-running instance needs supported consultation/refresh and capture
  behavior; sharing a soul or updating a base is not automatic active-context
  synchronisation or curriculum replacement.
- Source independence, exact executable approval, truthful readiness/outcomes
  and required capture/handoff remain enforced. Do not remove a declared plugin,
  binding or lifecycle requirement merely to make a deployment qualify.

A newly required generic field or authority change gets its own explicit proposal.
Reuse the existing resolver and provider contracts; do not invent a second
knowledge dispatcher or bootstrap owner as a shortcut.

## 2. Make the reference profile coherent

Align the default OKF runtime instructions, skills, source declarations and
applicable config templates with the selected centralised per-soul model:

- Stable knowledge homes and explicit cross-reads, with one canonical home per
  concept and no dependence on a disposable instance or display-name spelling.
- `owns` as routing and `reads` as context selection, not implicit access rights
  or direct-write authority for every working instance.
- Independent judgment, reference promotion doctrine and PR-only Git delivery;
  distinguish a proposed PR from merge-visible acceptance and fresh-reader access.
- Explicit state/store bindings and honest readiness. Adopted local templates and
  running instances do not silently change when a package is updated.
- Human-accepted decisions preserve their scope and acceptance evidence; tasks,
  transcripts, code descriptions and procedures are not bulk-promoted as knowledge.

Publish only the corrected components that need changing, with compatible version
pins and updated guidance. An old deployed version is not itself proof that its
operator should upgrade without a deliberate cutover.

## 3. Curate and stage the five-role cutover

Reuse the preserved audit and candidate corpus; perform a focused freshness and
semantic pass for decisions and lessons added since that audit, not a new bulk copy.
The five expertise roles remain overall OATS, kernel, Desktop, market research and
user-facing assistant. The optional knowledge-theory authoring expert is not a
sixth mandatory runtime role.

- Confirm knowledge repository visibility/access before publishing any corpus.
  Public knowledge and a separate knowledge repository are compatible choices;
  neither implies that deployment-specific material is suitable for publication.
- Agree the exact portable source/export identities, owner/read mapping and
  immutable compatible revisions. Do not advertise the preserved legacy shapes
  as already valid portable exports.
- Deliver the curated corpus through reviewed changes, preserving original
  sources, pending inputs, work and recovery evidence until cutover is proven.
- Enable new bindings deliberately; do not rename live homes, overwrite identities
  or leave conflicting old/new writers. Repository bootstrap is separate from
  accepting knowledge, and does not grant a new operator-root helper protocol.

## 4. Prove the useful result, then cut over

Use a small representative end-to-end path: an expert reads its accepted
foundation and relevant cross-role material; an instance captures a useful new
finding; an independent worker proposes a Git change; authorised review/merge
accepts it; a different or fresh instance obtains the accepted learning through
the supported reader/refresh path. Do not seed the answer and call that learning.

Check each of the five roles' declarations, reading context and representative
questions without repeating full infrastructure matrices. Confirm practical
assistant onboarding separately from a merely valid source declaration. Retained
source behavior and any required messaging/provider readiness keep their existing
qualification boundaries; no model or GUI action on another operator's machine
is implied by this plan.

After that acceptance, activate the new roster and bindings. Decommissioning old
sources/writers is a separate, evidence-backed cleanup, not an automatic part of
copying concepts. Desktop parity can then reflect the qualified model.

# Deliberately not prerequisites

Automatic speciation, a permanent maintenance service, automatic redirects,
whole-session cloning, a production graph provider and a full co-located OKF2.x
profile are not required for this chosen default cutover. Their architecture must
remain possible and their limits honest. They can be separately prioritised;
none should be presented as shipped merely to finish the deployment.
