# Status and canonical explanation

Accepted in the founder's September19 discussion and approved for canonical
repository documentation before further implementation. The public explanation is
[Knowledge, instances and evolving expertise](https://github.com/awebai/oats/blob/main/docs/knowledge-theory.md),
introduced by the [README](https://github.com/awebai/oats/blob/main/README.md).
Those documents are the conceptual source of truth; this concept records the
scope and supersession rather than duplicating the full theory.

# Decision

- A soul defines reusable expertise, boundaries and curriculum. An instance is a
  situated working continuity, not necessarily a short task or single chat session.
  Ephemeral developers/reviewers and long-running expertise instances are both
  legitimate. Duration alone does not establish a new soul.
- Distinguish skills/capabilities, accepted knowledge, working understanding and
  ongoing state. Valuable instance context is not automatically shared knowledge;
  harvesting accepted concepts does not necessarily reproduce an experienced
  instance's whole working picture.
- Default to centralised, per-soul knowledge within the adopter's chosen base.
  It is a simple initial routing model, not permanent silos or implicit publication
  to an upstream soul publisher. Knowledge can grow, move, merge or support a
  reviewed split of the specialisation.
- Knowledge capabilities own their complete procedures and ways of working and
  learning, not merely storage under a kernel-owned judge. Other capabilities may
  support topic/project organisation, co-located OAS-style knowledge, multiple
  stores or different reading/promotion/maintenance models.
- The kernel owns identity, lifecycle, resolution, approvals and custody, not a
  mandatory knowledge taxonomy or learning pipeline. Mutable knowledge requires
  explicit supported write authority; co-location does not make retained source
  or executable artifacts writable.
- The reference doctrine still preserves behavior-changing judgment not quickly
  recoverable from repository code/docs. Rationale, discoveries and maintained slow
  state can qualify; code descriptions, raw task residue and copied procedures do
  not. Ownership routes harvests, not authorship, ACLs or a working soul's duty to
  keep the base honest.
- Speciation follows evidence of sustained reusable skill/read/work differences,
  with human acceptance of structural changes. Repeated spawning is evidence, not
  a requirement: one long-running instance may expose recurring specialisation.
  Widening, merging or retaining the existing soul are valid outcomes too.

# Why

A mandatory topic model would force users to design a taxonomy before gaining
basic shared learning. A permanently one-soul/one-folder model would couple
knowledge identity to a changing roster. A capability-owned model allows a simple
default and deliberate evolution without a universal kernel mode switch.

# Supersession and limits

This narrows the placement statement in
[external knowledge custody](/decisions/external-knowledge-custody.md) to the
default integration. It also supersedes a mandatory topic-first reading of the
September16 exploration. The existing
[provider-neutral knowledge boundary](/decisions/provider-neutral-knowledge-and-harvest.md)
is reaffirmed, not replaced.

The architectural choices are accepted; automatic per-soul provisioning,
co-located OKF profiles, topic redirects, incarnation profiles, automatic
maintenance/speciation and safe context cloning need implementation and acceptance.
No API fields, capability behavior, existing bindings or live writers change by
publishing these documents. Bootstrap/helper-entry and source-export layout
proposals keep their separate decision boundaries.
