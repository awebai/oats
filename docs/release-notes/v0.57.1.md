# OATS 0.57.1

2026-10-15

## Upgrade

- **Either order of Desktop and CLI works:** a 0.57.0 Desktop accepts a
  0.57.1 CLI, and the other way round. The 0.57.1 Desktop accepts OATS CLIs
  `>=0.26.0 <0.58.0`.

- **Upgrade the hosts a Desktop reaches over `--server`, too.** A routed
  attach runs its viewer on the host, so the viewer fixes (it ends with the
  agent's window under `detach-on-destroy off`, and a late hang-up no longer
  leaves an `oatsview-*` session behind) hold for a remote terminal only once
  that host runs 0.57.1. See Fixed
  ([#1237](https://github.com/awebai/oats/issues/1237),
  [#1243](https://github.com/awebai/oats/issues/1243)).

- **`oats tui`: the whole-screen open is gone.** `Enter` opens an agent's
  terminal in a panel beside the list; `z` gives it the whole body. The panel
  needs tmux 3.2 or later. `open.detachKey` in `tui.json` keeps its name and
  the keys it accepts, and now means the back key to the list; a key outside
  them is refused when `tui.json` is read. See Changed
  ([#855](https://github.com/awebai/oats/issues/855)).

- **pi homes: run `oats update`** to move the `@awebai/oats-pi` bridge in
  your pi folders to this release (by hand: see [Upgrading](../upgrading.md));
  the kernel alone doesn't change it. A freshly spawned pi home then no
  longer starts by "continuing" from an empty `STATE.md`. See Fixed
  ([#1251](https://github.com/awebai/oats/issues/1251)).

- **To get the new framework skills,** pin `oats.framework: v1.12.0` in your
  workspace and run `oats sync`: `/oats-host-delivery` and `/oats-git-setup`
  in oats.setup 2.7.0. Instances already running keep what they were spawned
  with. See Provider updates.

- **The official catalog's versions in this release** are oats.framework
  1.12.0, oats.okf 5.2.0, oats.aweb 1.27.3, oats.engineering 1.10.0,
  oats.cloning 1.0.1, oats.authoring 1.0.3, oats.jira 1.0.1, oats.linear 1.0.1
  and oats.apps 1.0.0.

## Changed

- **A spawn runs in a process session of its own.** The `oats spawn` child of
  a confirmed spawn now runs in a process session of its own, so a hang-up or
  a Ctrl-C in the terminal that started the client does not reach a spawn
  while its worktree hooks run. The deadline the confirmed preview implies
  still interrupts it, and the kernel rolls it back.

- **`oats tui` opens an agent's terminal in a panel beside the list**
  ([#855](https://github.com/awebai/oats/issues/855)). `Enter` on an
  instance that runs shows its terminal where the detail was, with the list
  still on screen and the focus in the terminal: everything you type goes to
  the agent but the back key (`Ctrl+\`, or `open.detachKey` in `tui.json`),
  which gives the focus to the list while the terminal stays open and live.
  From the list, `Enter` on its row goes back to it, `z` gives it the whole
  body and `c` closes it; `Enter` on another instance opens that one
  instead. A terminal whose viewer ends closes with a line that says why,
  and is never opened again by itself. **The whole-screen open of the
  previous version is gone**: `z` replaces it. The viewer now runs in a tmux
  server private to the run (tmux 3.2 or later), ended on every way out, a
  `kill -9` of `oats tui` included; a later run removes what a killed one
  left. `open.detachKey` keeps its name
  and the keys it accepts, and now means the back key; a key outside them is
  refused when `tui.json` is read, and an older OATS on another machine is
  opened like a newer one. See [the TUI page](../tui.md#open-an-agents-terminal).
- **The header's second row reads as navigation:** `Instances   Souls
  Capabilities`, the open view in reverse video and the views not built yet
  dim. The keys `1`, `2` and `3` are in the help, not beside the names, and
  the footer names them as one hint, `1-3 views`; `2` and `3` say what to
  run instead. Every frame is now one
  synchronized update (`CSI ?2026h` … `CSI ?2026l`).

## Fixed

- **Desktop: a team card's warning can be copied.** On the Teams board, the
  text of a team's warning or blocking problem, with its fix, can be
  selected and copied, and a click on that box no longer opens the team's
  page. A click anywhere else on the card still opens it, and the card is
  still one Tab stop.
- **Desktop: a Make default confirmation closes with the team's page.** A
  confirmation opened on a team's page no longer stays open after Back, Esc,
  a tab change or the team going away, and the Teams board updates again
  when your instances change.
- **Desktop: a failed read shows on an open team page.** When the teams on
  this computer can't be read, the open team's page says so in its card, in
  the board's words, instead of showing facts that may be out of date.

- **Desktop: a retired instance's tabs close**
  ([#1237](https://github.com/awebai/oats/issues/1237)). When a roster read
  shows an instance retired, whether the Desktop, the CLI, another agent or
  another machine retired it, every tab of that instance closes, in every
  split. The next tab becomes active, and the focus moves only if it was in
  a closed tab. A remote instance's tabs close only when its server answers
  without it, never because the server can't be reached. Stopping an
  instance still leaves its tab open, and an instance respawned under the
  same name opens a new tab.
- **Desktop: a tab no longer shows another instance's terminal**
  ([#1237](https://github.com/awebai/oats/issues/1237)). With tmux's
  `detach-on-destroy off` in your configuration, retiring an instance moved
  its tab to another session, often another tab's agent: the tab kept its
  name, and what you typed went to that agent. The tab's terminal now ends
  ("session ended") when its instance's window goes. Only the Desktop's own
  viewer sessions are set this way; your global option and your own
  sessions are untouched.

- **`oats session attach`: the viewer ends with the agent's window, even under
  `detach-on-destroy off`**
  ([#1237](https://github.com/awebai/oats/issues/1237)). When an attached
  instance was retired, a tmux configured with `set -g detach-on-destroy off`
  moved the viewer's client to another session, so the terminal went on
  showing, and typing into, another agent. The viewer session now sets
  `detach-on-destroy on` for itself alone, and the viewer ends as it does
  under tmux's default. Your own sessions keep your setting. A routed attach
  (`--server`) runs the viewer on the host, so this holds there once the host
  runs this release. Remote Desktop terminals use that viewer.

- **`oats session attach`: a late hang-up no longer leaves the viewer session
  behind** ([#1243](https://github.com/awebai/oats/issues/1243)). A hang-up,
  termination or interrupt can reach `oats session attach` late, for example
  under a wrapping shell or a terminal profile, where it arrives once the
  wrapper has died and goes to the whole process group. If it arrived just
  after the viewer's client had exited, or while the viewer was still being
  prepared, it could end `oats` before its cleanup, or kill the cleanup's
  tmux call, and leave the `oatsview-*` session (and a keyed viewer's key
  table) on the agents' tmux server. `oats` now handles these signals from
  before it creates the viewer until its cleanup has finished, and runs its
  tmux calls outside its own process group, so the viewer is always removed.
  Exit statuses are unchanged. A routed attach (`--server`) runs the viewer on
  the host, so this holds there once the host runs this release.

- **pi: a freshly spawned home no longer starts by "continuing" from an empty
  `STATE.md`**
  ([#1251](https://github.com/awebai/oats/issues/1251)). At session start the
  `@awebai/oats-pi` bridge sends the nudge "Read ./STATE.md … then continue
  from STATE.md's Next section". It held the nudge back only while `STATE.md`
  still held template text that no package writes any more, so every fresh
  home got it, ahead of its opening task. A startup now gets the nudge only
  when pi kept an earlier session of the home (pi keeps one once it holds a
  message) and
  `STATE.md` exists, whatever a knowledge capability seeded into it. Sessions
  of an earlier instance with the same name, at the same path, don't count.
  The bridge writes nothing in the home to tell. Run `oats update` to move
  the bridge in your pi folders to this release (by hand: see
  [Upgrading](../upgrading.md)); the kernel alone doesn't change it.

## Provider updates

- **oats.framework 1.11.0: oats.setup 2.6.0. Onboarding now makes a host's two
  delivery choices and checks them**
  ([#1224](https://github.com/awebai/oats/issues/1224)).
  - **Why.** A host could finish onboarding with `oats doctor` clean and still
    have two problems nobody had chosen:
    - its Claude homes ran in development channel mode, because
      `claudeChannelMode` was unset;
    - no host wake broker ran, so every joined team was poll-only, and Codex
      and `delivery: session` homes were not woken at all.
  - **A new skill, `/oats-host-delivery`,** is the one place that teaches both
    choices. `/oats-workspace-config` now points to it, instead of holding
    the approved-route steps itself:
    - **Choice 1, Claude channel delivery:** the approved route (the
      managed-settings file, `claudeChannelMode: approved`, the plugin in the
      launch's `CLAUDE_CONFIG_DIR`, respawning homes, the banner check) as the
      default for unattended hosts. The development fallback is written
      explicitly, with its costs stated. Session delivery is the third
      option.
    - **Choice 2, the host wake broker:** when a host needs it (a joined
      team, Codex, `delivery: session`); how the operator installs `aw wake
      run` as a per-user systemd or launchd service, with `AW_WAKE_OATS_BIN`
      and a `PATH` that reaches `oats`, `node` and `tmux`; the restart after an aw upgrade; the check (`aw wake status
      --json`, and readiness free of `wake-daemon-*` and
      `joined-team-poll-only`); and the false `wake-status-stale` of oats.aweb
      1.27.2 ([oats-aweb#116](https://github.com/awebai/oats-aweb/issues/116),
      fixed in 1.27.3).
  - **`/oats-onboarding`:**
    - card 4 requires both choices to be made and recorded: the broker is
      installed once aw meets its floor, before the first spawn;
    - card 8 checks each recorded choice, and the hand-back records both;
    - card 4 also requires Git that works without a terminal on a macOS
      host that another machine drives, linking
      [Git on a macOS host](../servers.md#git-on-a-macos-host).
  - **`/oats-setup-model`** names both host facts and answers “why didn't my
    agent wake”. `/oats-teams` reopens Choice 2 at a host's first joined
    team.
  - Instruction text and one new skill: there is no hook, command, schema or
    provider contract change, and the capability floors are unchanged
    (oats.setup `>=0.30.0`).
  - A deployment gets it by pinning `oats.framework: v1.11.0` and running
    `oats sync`. Instances already running keep the skills they were spawned
    with.

- **oats.framework 1.11.1, oats.setup 2.6.1: `/oats-host-delivery` teaches
  `oats aweb wake install` (oats.aweb 1.28.0)**
  ([#1224](https://github.com/awebai/oats/issues/1224)).
  - Choice 2 now leads with the oats.aweb 1.28.0 command: `--plan`,
    `install`, `status`, `uninstall`, and rerunning `install` after an aw
    upgrade.
  - The hand-written systemd and launchd units remain as the fallback, for
    older providers or an operator's own unit.
  - It names the migration from the hand-written `ai.aweb.wake` unit that
    oats.setup 2.6.0 taught: that unit carries no install marker, so `install`
    refuses it with `E_WAKE_UNIT_CONFLICT`. Retire it with the printed steps,
    then rerun.
  - On macOS, `install` runs at the desktop login. Over ssh, `launchctl
    bootstrap` can fail after the plist is written (`E_WAKE_UNIT`); rerun it
    at the desktop.
  - The broker is installed before onboarding card 6. From oats.aweb 1.28.0,
    card 6's readiness fails without it for a soul with `delivery: session` or
    a join.
  - Choice 1 and the checks name the new readiness warning
    `claude-channel-mode-default`, and the soul-scope broker check.
  - Instruction text only; the floors are unchanged.
  - A deployment gets it by pinning `oats.framework: v1.11.1` and running
    `oats sync`. Instances already running keep the skills they were spawned
    with.

- **oats.framework 1.12.0: oats.setup 2.7.0. A guided Git and GitHub setup
  for a person who isn't a developer**
  ([#1233](https://github.com/awebai/oats/issues/1233)).
  - **Why.** OATS reads its workspace with Git, and agents commit as the
    person who runs them, but nothing taught that person to set Git up. The
    kernel never prompts: it reads `git:` references over `https://` with
    the credential helper and runs ssh in batch mode. A host could reach
    onboarding with no GitHub credentials for Git, no known `github.com`
    host key, or commits that GitHub shows as Unverified.
  - **A new skill, `/oats-git-setup`,** walks through it on macOS and
    Linux. Each step says what to run, what you should see, and what to do
    when you see something else:
    - installing `git` and `gh`, and checking that `gh` has the flags the
      steps use;
    - one SSH key, registered on GitHub both as an authentication key and as
      a signing key, with the admin scopes removed from gh's token again
      afterwards;
    - `gh auth setup-git` for `https://` remotes, and the first `ssh -T
      git@github.com` checked against GitHub's published fingerprint;
    - the identity, with an email verified on GitHub, and SSH commit signing;
    - a DCO sign-off on every commit through a global `core.hooksPath` hook
      that still runs each repository's own hooks;
    - a check: SSH auth, a signed and signed-off commit that GitHub's API
      reports as `verified: true`, and `gh auth status`.
  - **The macOS credential helper.** On macOS, a Git process run without
    `HOME` skips `~/.gitconfig` and uses the system file, where Homebrew's
    Git sets `credential.helper osxkeychain`. That raised repeated keychain
    popups on one host. The skill leaves credentials to gh and SSH, checks
    which helper a Git without `HOME` would use, and says why it matters.
  - **`/oats-onboarding`:** card 2, which makes the first Git reads, starts
    with `/oats-git-setup` when the person's Git and GitHub setup is missing
    or unchecked. `/oats-setup-model` and
    `/oats-workspace-config` name where these facts live.
  - Instruction text and one new skill: there is no hook, command, schema or
    provider contract change, and the capability floors are unchanged
    (oats.setup `>=0.30.0`).
  - A deployment gets it by pinning `oats.framework: v1.12.0` and running
    `oats sync`. Instances already running keep the skills they were spawned
    with.

## Documentation

- [Configuration](../configuration.md), “Claude channel delivery: the approved
  route”:
  - an unset `claudeChannelMode` is development mode, so set it explicitly;
  - the host wake broker is the other host delivery choice;
  - the operator's procedure for both is oats.setup's `/oats-host-delivery`
    ([#1224](https://github.com/awebai/oats/issues/1224)).
- [Servers](../servers.md), “Git on a macOS host”, adds four things:
  - which remedy applies to an `https://` remote and which to a
    `git@github.com:` one;
  - that SSH commit signing has the same requirement;
  - the `--insecure-storage` trade-off;
  - when to set it up, and how to verify it from a session without a
    terminal ([#1224](https://github.com/awebai/oats/issues/1224)).

- [Servers](../servers.md), “Git on a macOS host”, points to `/oats-git-setup`
  for the person's whole Git and GitHub setup
  ([#1233](https://github.com/awebai/oats/issues/1233)).
