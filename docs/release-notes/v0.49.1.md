# OATS 0.49.1

Unreleased

## Added

- **`oats doctor` lists what retires left behind (#703, part 2a).** These are
  information lines only, with no new key. Doctor prints one
  `retained-recovery:` line per recovery copy under each instances directory's
  `.oats-retirement/recovery/`. Each line gives the path, the instance, `phase`
  and `classes` from `recovery.json`, the size and whether `after-hooks/` is
  there. A copy whose `recovery.json` is missing or unreadable is listed and
  says so. Doctor also prints one `retained-worktree:` line per retained
  worktree under `.agents/worktrees/<repo>/`, giving its repository, its
  branch (or detached commit), and whether it is clean, with the uncommitted
  classes when it isn't. Each line ends with the reachability fact for the
  HEAD commit: whether a ref of the source repository other than the tree's
  own branch reaches it, or how many commits no other ref reaches. A
  recovery line also names a retained worktree on its branch. These are
  facts to decide with, never "safe to delete". Each kind starts with a line
  giving its total, then at most 50 items, then `… and N more`. In
  `oats doctor --json` they are elements of the existing `information[]`, one
  line each. The reads are read-only and run Git without helpers, so doctor
  refreshes no index and follows no link. It doesn't ask for the status of a
  repository that configures a content filter, and never enters a
  submodule's work tree; the line says so. See [After a retire: inspect,
  restore, dispose](../souls-and-instances.md#after-a-retire-inspect-restore-dispose).

- **Capability-declared trigger sources, feature `trigger-sources` (#669).**
  A trigger can now watch more than GitHub pull requests. A capability
  declares **trigger sources** in its manifest (`triggerSources`): each is
  one of its own commands that, at each poll, lists the events due now. A
  trigger names one as `on.source: "<capability>:<source>"`, with `on:
  { source, params?, events, poll? }`, and the kernel keeps everything after
  the list on the same pipeline `github.pull_request` runs on: keys,
  at-least-once recording, pending events, concurrency by subject, the
  instance name, the event file and the spawn. Templates may name
  `{trigger} {source} {subject} {event} {key} {url} {fields.<name>}`, and the
  default purpose is `{trigger}-{subject}`; a `github.pull_request` template
  may now also name `{subject}` and `{key}`. What a trigger means is checked
  against the capability its soul composes at `trigger add`, at every poll
  (before the source runs) and by `trigger test`: a failure is
  `E_TRIGGER_SOURCE {capability, source, pointer?}` or
  `E_TRIGGER_INVALID {field}`, and a poll that finds one shows it as the
  trigger's `invalid: {code, message, field?, at}` in `list` and `status`.
  A param value carrying a control, bidi or invisible character is refused
  (`E_TRIGGER_INVALID`, `on.params.<name>`), and a stored one is printed by
  `trigger list`, `status` and `show` with those characters replaced or
  escaped.
  - **The wire.** One JSON request on stdin, exactly one JSON answer on
    stdout, killed at 30 s, in the environment a `readiness --soul` check
    gets: ambient `OATS_*`, `OAS_*` and `PI_*` removed, no instance, no
    credential from the kernel. A wire failure is `E_TRIGGER_POLL` with
    `details.cause` (`exit`, `result`, `too-many-events`, `timeout`,
    `refused`, `resolution`), records nothing and drops nothing. Each event
    is checked alone (key, subject, event, an `https:` `url` on one of the
    manifest's `urlHosts`, declared `fields`); an invalid one is dropped
    alone and listed in `invalidEvents`. A `url` must be printable ASCII
    with no space as written. A field value longer than 200 characters, or
    carrying a control, bidi or invisible character, is invalid whatever its
    pattern admits. The source's own text (a skipped item's `why`, a refusal's code and message) is capped, has every control,
    bidi and invisible character replaced with U+FFFD, is never composed into
    a task, and is printed only under `source says:`.
  - **How a pending event ends.** By the current state: a good poll that no
    longer lists a pending key drops it; a failed poll drops nothing.
    Retention keeps 500 fired keys per trigger as before, but never evicts a
    key the last good poll listed.
  - **The tick stays inside its minute.** Capability-source polls run after
    the schedules, most overdue first across every deployment the host
    ticks, and only while they can end within 50
    s of the tick's start; the rest are `poll-deferred` and go first next
    tick, so no schedule is missed because of them.
  - **`oats trigger poll <id> --run-source [--max-age <s>]`**, a new read
    verb (on the `--max-age` allow-list), runs a trigger's source once and
    records nothing. It and `oats trigger test <id> --run-source` **execute
    the capability's source command**: "read verb" means records nothing,
    not runs no provider code.
  - **A manual run takes `--run-source`.** Without it, `trigger test` and
    `trigger poll` of a capability source's trigger are refused with
    `E_TRIGGER_SOURCE_RUN` (`details: {capability, source, flag}`, a
    non-zero exit, the command to run again in the message): nothing of the
    capability has executed and nothing has been written. A definition that
    is invalid or whose meaning fails answers that first, flag or no flag.
    The flag is caller intent, never trust consent: with it both run the
    source whatever this host's `automations.trust` and the trigger's
    `runsOn` say, which gate the host tick exactly as before (the tick
    passes the flag to its own child). On a `github.pull_request` trigger
    the flag is accepted and inert. `test` names the placement in `problems`
    ("run manually with --run-source; the tick will not run it here: …") and
    always warns that the source's credential may not be visible to the host
    timer.
  - **Contained.** A malformed `triggerSources` never refuses the
    capability: spawn, preview, readiness, discovery and the lock ignore it.
    It is validated where a source is used, per source, and `oats
    capabilities show --json` adds `triggerSources` as declared and
    `triggerSourceProblems`. A provider declaring `triggerSources` does not
    need to raise `compatibility.oats`: every workspace-model kernel ignores
    the key, and only the host that runs a trigger naming the source needs
    this release. An older kernel reading the same deployment refuses such a
    trigger with `on.params: unknown key`, not with a message about
    `on.source`: `trigger add` stores `on.params` (`{}` when none is given),
    and that kernel checks the keys of `on` first.
  - **Schema tooling.** Until this release the published
    `docs/capability-manifest.schema.json` is closed at the top level
    (`additionalProperties: false`), so any tool that validates a manifest
    against an older copy of the schema flags `triggerSources`: this
    repository's own `validate-project`, the package dry-run checks, a
    provider's CI that pins the schema. The runtime ignores the key;
    schema-validating tooling does not. Validate against this release's
    schema, or declare the key once your tooling uses it.
  - **Output keys are additive and `triggerApi` stays 1.** On a capability
    source's rows only (absent, not `null`, on a `github.pull_request` row,
    whose outputs are unchanged): `status` gains `source`, `invalidEvents`,
    `skipped` and `invalid`, with `lastPoll` counting `events`,
    `invalidEvents`, `skipped` and `filtered` (or `{ok: false, cause, error,
    source?}`); `test` gains `source`, with `repo: null`; `instance.json.trigger`
    gains `fields`, with `repo` and `number` `null`. Readers tell rows apart
    by `on.source` and gate on `trigger-sources`.
  See [schedules.md](../schedules.md#capability-sources),
  [capabilities.md](../capabilities.md#trigger-sources-triggersources) and
  [desktop-cli-api.md](../desktop-cli-api.md#oats-trigger).

## Changed

- **The workspace pins oats.aweb 1.24.0** (tag on a7d976d4). Retire's
  recovery copy no longer keeps an instance's aweb private keys, and retire
  exits nonzero when leaving a joined team fails (except `team_not_hosted`), so
  the home and the key that can still leave the team are kept. Readiness and
  an approved Claude channel launch read the machine's Claude Code managed
  settings and warn whether they admit the aweb channel plugin; the skill
  documents the approved channel route as the recommended unattended setup.
  The package's OATS floor rises to `>=0.42.0`. Homes spawned before this
  version keep what they were spawned with; deployments adopt it with
  `oats sync`.

- **The official catalog and `mirrors/oats-aweb` carry oats.aweb 1.24.0.** The
  catalog's ref is `v1.24.0`, and the mirror is the package at that tag
  (a7d976d4), byte for byte, so the workspace pin, the catalog and the mirror
  agree.

- **oats.framework 1.9.0: oats.core 2.5.0 and oats.setup 2.5.0.** Instruction
  text only; no kernel, schema or provider contract changes. It also carries
  the skill text for 0.49.0's worktree commands and trigger names, which
  0.49.0 shipped in the kernel while the package stayed at 1.8.0.
  - **oats.core 2.5.0:** `oats-operate` covers the extra trees an instance
    makes in its home with `oats worktree add|remove` (from OATS 0.49.0,
    #801), that retiring an instance stops its recorded children first
    (#782), what `oats doctor` lists of what retires left (#836), and the
    event a triggered run reads: its `subject` (#798) and an event from a
    capability's trigger source (#845).
  - **oats.setup 2.5.0:** `oats-automations` covers triggers on a
    capability's source, with `--run-source` for trying one by hand (OATS
    0.50.0, #845), and how trigger instance names are cut to fit (from OATS
    0.49.0, #798). `oats-workspace-config` gains the host step "Claude
    channel delivery (approved route)", and `oats-onboarding` points to it
    (#844).
  - Both skills name the kernel version in which each of these starts, so
    the package's floors do not move.
  - A kernel release whose pull requests touched `oats-package/` now ships a
    framework release with it:
    [release-lane.md](../release-lane.md#releasing-oatsframework).

## Fixed

- **Retire: a worktree on a long branch is re-homed instead of refused
  (#821).** A retire keeps a worktree (`work/`, or an extra `.work-*` tree) by
  moving it to `<deployment>/.agents/worktrees/<repo>/<leaf>`, the leaf being
  the whole branch name as one path component. A branch whose flattened name
  went over NAME_MAX made `git worktree move` fail with ENAMETOOLONG. The retire
  then refused with `E_WORK_PRESERVATION_FAILED`, until the branch was renamed
  or the worktree discarded with `--discard-worktree`. The leaf is now at most 231 bytes before its `-N`. A
  longer one is cut, its trailing `-` trimmed, and followed by `-` and 6 hex of
  the SHA-256 of the full branch name, so it stays readable and unique per
  branch. A leaf that already fits is unchanged, and the retire plan's
  `movedTo` names the same path the retire uses
  ([souls-and-instances.md](../souls-and-instances.md#extra-trees-at-retire)).

- **Retire: a failed recovery copy is cleaned up even when a read-only
  directory in it has a name that isn't UTF-8 (#827).** When a recovery copy
  fails, the retire makes each directory of its staging copy writable and
  removes it. It listed names as text, so it couldn't reach a read-only
  directory (a Go module cache, `0555`) whose name isn't valid UTF-8, and the
  staging directory was left in recovery storage. The refusal was still the
  original `E_WORK_PRESERVATION_FAILED` and named the leftover to remove by
  hand. Nothing was lost. Names are now listed and joined as bytes, as the
  copier writes them, and the staging directory is removed. The refusal text is
  unchanged.

- **The process scan reads `/proc` on Linux, and doctor names a host with no
  scan (#625).** Whether a live process works in an instance home came only
  from `lsof`, which many Linux hosts lack. There retire refused whenever it
  needed the scan (a home without its session receipt, a missing recorded
  tmux socket, a Herdr home), and nothing said why before the refusal. Now
  the scan reads `/proc` on Linux (each process's `cwd` link, `comm` and
  `stat`) and runs `lsof` elsewhere, as before; the answer is unchanged: a
  pid and a program name, never an argument list. A process that ends during
  the scan is skipped. A `/proc` that cannot be read fails the scan, never
  answers "none". `oats doctor` (text, and `--json` in `information`, no new
  key) adds a `process-scan-unavailable` line only on a host with neither,
  saying what it blocks and to install `lsof`. A refusal for a missing `lsof`
  now says to install it. The stated limit is unchanged: neither mechanism
  sees a process this user may not inspect (another user's, or a
  non-dumpable one such as `ssh-agent`), so such a process working in a home
  does not stop a retire; refusing whenever one exists would refuse on every
  host. The harness OATS launches runs as the user and is seen. See
  [souls and instances](../souls-and-instances.md#the-process-scan).

- **A tmux server whose socket file was removed no longer reads as stopped
  (#624).** A tmux server keeps running when its socket file is removed, and
  tmux then answers as it does after a reboot (`No such file or directory`).
  `oats status` showed such an instance as not running, `oats session
  start`/`restart` created a second server at the recorded socket path and
  launched a second harness in the same home, and `oats instance stop`
  reported it idle. Now a missing socket file counts as stopped only when no
  process works in the home, as retire already required (#622). Otherwise,
  or when the process scan cannot run, status shows the row `running: null`,
  `runtimeState: "unreachable"` with a `runtimeError` that names the
  processes (existing values), start and restart refuse with
  `E_SESSION_UNKNOWN` and create nothing, and stop refuses with
  `E_SESSION_UNAVAILABLE`. Retire, which already scanned, now also scans
  when an older tmux words a missing socket file as `failed to connect to
  server: No such file or directory`; it took that as stopped. The message
  names tmux's own remedy: the server
  recreates its socket file when its process receives `SIGUSR1`. OATS never
  sends it. A socket file that no server listens on is still stopped, with
  no scan, and after a reboot (no process in the home) nothing changes. Any
  process working in the home blocks start and stop while the socket file
  is missing, a shell left in that directory included; the message names its
  pid and program. See [Sessions](../execution-targets.md#missing-socket).

## Documentation

- **Claude channel delivery: the approved route, as a host setup step.**
  Claude seats on aweb channel delivery no longer need to stop at Claude's
  “WARNING: Loading development channels” prompt. With the `oats.aweb` setting
  `claudeChannelMode: approved` (host-only) and `delivery: channel`, Claude
  starts with `--channels plugin:aweb-channel@awebai-marketplace` and admits
  the plugin when a root-owned managed-settings file on the machine lists it
  (`/etc/claude-code/managed-settings.json` on Linux,
  `/Library/Application Support/ClaudeCode/managed-settings.json` on macOS,
  with `channelsEnabled: true` and the `aweb-channel` /
  `awebai-marketplace` entry in `allowedChannelPlugins`). It does not depend
  on the Claude version and needs no launch-prompt consent. A human admin
  with sudo writes that file; OATS never does. Setting `allowedChannelPlugins`
  replaces Anthropic's default channel allowlist on the host, and on an
  account governed by server-managed settings or MDM the file is ignored (the
  organization admin sets the keys there). Existing homes keep the mode they
  were spawned with: respawn one to adopt the route. The contract is
  [Claude channel delivery: the approved route](../configuration.md#claude-channel-delivery-the-approved-route);
  the operator's ordered steps, with the banner checks, are the `oats.setup`
  host step “Claude channel delivery (approved route)” in
  `/oats-workspace-config`, which also names the file in its
  where-each-fact-lives table; `/oats-onboarding` card 4 calls the step. No
  kernel or CLI behaviour changes.
