# OATS 0.56.0

2026-10-14

## Upgrade

- **Install the Desktop first and the CLI second,** as
  [Upgrading](../upgrading.md) says: a 0.55 Desktop refuses a 0.56.0 CLI. The
  0.56.0 Desktop accepts OATS CLIs `>=0.26.0 <0.57.0`; a CLI of the 0.25 line
  is no longer accepted. `oats update` now prints this order itself when it
  installs a CLI of another minor.

- **A script that matched `E_HARNESS_PACKAGE`** matches
  `E_HARNESS_RESOURCE_MISSING` now. **A script or capability that read
  `E_SPAWN_FAILED` from `oats spawn` as "the spawn failed"** now gets the
  kernel's own code: match on the exit status or on `ok: false` instead, and
  read `details.unconfirmed` for how far a spawn got. See Changed
  ([#1047](https://github.com/awebai/oats/issues/1047)).

- **A `tui.json` that names the action `open-workspace`** is refused with
  `open-workspace is called open now; rename it`: rename it to `open`. See
  Added ([#855](https://github.com/awebai/oats/issues/855)).

- **To get the new provider versions,** pin `oats.framework: v1.10.1` and
  `oats.okf: v5.1.0` in your workspace and run `oats sync`. oats.okf 5.1.0
  needs OATS 0.49.0 or later: upgrade the kernel first, then re-spawn your
  harvesters for the new hook. Instances already running keep what they were
  spawned with. See Provider updates.

- **The official catalog's versions in this release** are oats.framework
  1.10.1, oats.okf 5.1.0, oats.aweb 1.27.3, oats.engineering 1.10.0,
  oats.cloning 1.0.1, oats.authoring 1.0.3, oats.jira 1.0.1, oats.linear 1.0.1
  and oats.apps 1.0.0.

- **A launch now gets exactly its capabilities' declared environment**
  ([#1123](https://github.com/awebai/oats/issues/1123)). An instance that
  relied on an ambient value of a variable one of its capabilities declares
  (in the tmux server's or the session's environment, the login shell's, the
  Desktop's) and that the capability's hooks do not return now starts without
  it. Nothing is required of you. An ambient value set before stays in the
  tmux environment until the server or the session is recreated, but no
  longer reaches a launch whose capabilities declare it; an instance already
  running keeps the environment it started with until it is restarted. To
  clear a stale value: `tmux -L oats set-environment -t <session> -u NAME`
  for a session, `tmux -L oats set-environment -g -u NAME` for the server,
  or recreate the server; then restart the affected instances.

## Added

- **Feature `spawn-kernel-codes` (#1047).** `oats spawn` answers the
  kernel's own code; a kernel without the word may answer `E_SPAWN_FAILED`
  where a kernel code was raised. See
  [spawn errors](../desktop-cli-api.md#spawn-errors).

- The Desktop's [Install](../desktop.md#install) section states what Linux the installers need: glibc 2.34 or later (for example Ubuntu 22.04, Debian 12, RHEL 9 or later), and the Linux installer build fails when any file of the DEB or the AppImage needs a newer glibc, GLIBCXX or CXXABI than that.

- **Desktop: the Start and Restart dialog offers the bare harness**
  ([#1079](https://github.com/awebai/oats/issues/1079)). The Launch
  configuration list has a second entry, "No launch configuration (the harness
  as installed)". It runs the harness itself, with no configuration's
  executable, arguments or environment, and without the default configuration
  the host declares for that harness. The Harness list stays usable with it:
  alone it starts the recorded harness bare, and beside a picked harness, that
  one. "Preview invocation" shows the same choice. It is what
  `--launch-config none` does on the command line.
  - **For an instance on a server** the entry is offered only when the host
    is known to read it: a host on OATS 0.49.0 or later, read through an OATS
    here that relays the hosts' feature lists. On an older host, pick a
    configuration, or use the command line there.
  [Starting an existing instance](../desktop-instance-start.md) has the
  whole of it.

- **`oats server roster --workspace-key <key>`** (feature
  `roster-workspace-key`, repeatable) probes and returns only the groups that
  can belong to the given workspaces: a registration recorded for one of
  them, a registration whose workspace is not known yet, and a server known
  only from saved routes, which is always probed because its workspace is
  unknown. A host registered for another workspace is not asked, so a
  switched-off host no longer delays the roster of every other workspace's
  window. The answer's shape is unchanged; without the flag it is exactly as
  before. A key is compared exactly with the registration's `workspaceKey`;
  an empty, missing or malformed value is `E_BAD_ARGS`
  ([the flag](../desktop-cli-api.md#roster-workspace-key),
  [#1124](https://github.com/awebai/oats/issues/1124)).

- **Forget… on an instance its server no longer lists.** In the Desktop, a
  remote instance that is gone from its server now offers **Forget…** in its
  roster row's actions menu and in the context panel. After a confirmation,
  the Desktop runs `oats server forget <server> --instance <instance>` for
  that row, which removes only this computer's saved route and nothing on the
  server, then reads the roster again. Before, the only remedy was to type
  that command
  ([`oats server forget --json`](../desktop-cli-api.md#forget-a-saved-route-oats-server-forget---json),
  [#1131](https://github.com/awebai/oats/issues/1131)).

- **A soul's own skills on its soul page.** In the Desktop, the soul page's
  Instructions card has a Skills group between "This soul" and "Instance": each
  skill from the soul's own `skills/` (not those its capabilities bring), with
  its description, expands to its files, and each file reads in place under its
  repository path, through the same strict reader as a capability's Contents.
  The Desktop asks only a CLI that reports them (feature `soul-skills`,
  `oats inspect --soul <name> --skills`), and for a soul on another machine
  only when that host reports them too; otherwise the group says this OATS
  doesn't report a soul's skills.

- **A soul's own skills, before a spawn.** `oats inspect --soul <soul>
  --skills --json` adds `souls[0].skills`: the skills a spawn of the soul
  copies (not its capabilities' skills), each with its `description` and
  every file's text, by the rules of `oats capabilities show`. The whole
  field carries at most 1 MiB of text; the files past that are listed with
  `omitted: true`. Nothing is read without the flag. No symbolic link is
  followed, and a skill whose files cannot all be listed and read has
  `files: null` with a problem. `--skills` combines with `--instructions`,
  refuses `--home`, and is routed with `--server` to a host that advertises
  the new feature `soul-skills`
  ([`oats inspect`](../desktop-cli-api.md#oats-inspect---home-----soul----dir----json--operationsapi-2),
  [#1144](https://github.com/awebai/oats/issues/1144)).

- **`oats tui` opens an agent's terminal**
  ([#855](https://github.com/awebai/oats/issues/855)). `Enter` on an
  instance that runs, on this machine or on a registered one, gives your
  terminal to the agent through `oats session attach`; `Ctrl+\` brings
  `oats tui` back and the agent keeps running. `tui.json`'s
  `open.detachKey` changes the key. After the return one line says what
  happened, and `Enter` on an instance that cannot be opened says why. An
  agent on a machine whose OATS is older than 0.51.0 is not opened: it has
  no key to leave a viewer. The action `open-workspace` is now `open`, and a
  `tui.json` that names `open-workspace` is refused with
  `open-workspace is called open now; rename it`.

## Changed

- **`oats retire --server` prints the receipt's warnings
  ([#1006](https://github.com/awebai/oats/issues/1006)).** The routed
  retire's text (without `--json`) printed the recovery and extra-tree lines
  of the host's receipt and none of its `warnings`. It now prints them as a
  local retire does, one `WARNING:` line each, after the extra-tree lines:
  what a retire left an attached child with, which repository it read from
  Git, where a link at `work/` led. The JSON is relayed as it was.
- **More text lines spell what a terminal would act on
  ([#1006](https://github.com/awebai/oats/issues/1006)).** The `note:`
  lines of `oats retire --plan`, `oats instance stop --plan`,
  `oats instance git` and `oats readiness`; the `WARNING:` lines of
  `oats spawn` (local and with `--server`), of the `oats session` commands
  and of `oats doctor`; and the retire's recovery and extra-tree lines, local
  and with `--server`, spell a control character (an escape, a newline), a
  line separator or a bidi override as `\u{<hex>}`, as the local retire's
  warnings have since 0.53.0. A line that holds no such character is printed
  as it was. No JSON answer changes. See
  [Text output](../desktop-cli-api.md#text-output).

- **`oats spawn` answers the kernel's own code (#1047).** Apply and
  `--preview`, text and `--json`: an error with a kernel code is answered
  with that code, as the lifecycle commands have done since 0.52.0, and
  `E_SPAWN_FAILED` is what an error with no kernel code is answered with,
  with `details.cause` for one that has a system code or is a defect (its
  stack on stderr). Until now the spawn's kernel stage passed a list of
  codes and answered every other one as `E_SPAWN_FAILED`, so a refusal with
  a remedy, such as a missing harness package (`E_HARNESS_RESOURCE_MISSING`)
  or a tmux server that cannot be read (`E_RUNTIME_ENDPOINT_UNKNOWN`),
  reached a client as a failure of the spawn mechanism. An operator's script
  or a capability that matched `E_SPAWN_FAILED` to mean "the spawn failed"
  now sees the specific code: match on the command's exit status, or on
  `ok: false`, to mean "it failed". A code is not a stable signal of how far
  a spawn got: `details.unconfirmed` is. The details of each code are what
  they were: a code that carried details keeps exactly those, and every
  other one carries the error's details only when `unconfirmed` is true. In
  text mode an error with no kernel code that a spawn meets outside its
  kernel stage prints `oats: <message>` where it printed Node's trace (a
  defect still prints its stack on stderr). See
  [spawn errors](../desktop-cli-api.md#spawn-errors).
- **The harness-package gate has one name, `E_HARNESS_RESOURCE_MISSING`
  (#1047).** A start or a restart refused for a missing harness package
  answers `E_HARNESS_RESOURCE_MISSING` where it answered
  `E_HARNESS_PACKAGE`, and so does the `harness-packages` check of a launch
  plan (`oats launch-config preview`); the message is unchanged, and a spawn
  answers the same code. A script that matched `E_HARNESS_PACKAGE` matches
  `E_HARNESS_RESOURCE_MISSING` now. A preview in which the gate itself
  faults (an error that is no verdict on a package) now fails as a fault,
  where it showed a row that called the fault a missing package.

- **Every retire plan has a new `planRevision`, once (#1065).** A retire
  plan's revision now binds everything the plan shows, except the facts
  that move by themselves, in every home (the defect is under Fixed). So a
  plan read under an older kernel is stale under this one: its guarded apply is refused
  with `E_PLAN_STALE` and the fresh plan in `details.plan`, nothing is
  stopped, run or removed, and the person confirms again. The revision's
  form is unchanged (24 lowercase hex characters), a client treats it as
  opaque as before, and there is no feature word and no change of
  `lifecycleApi`. A repeated apply with the idempotency key of a retire
  that did run is answered from its stored receipt as before, whatever
  revision it carries. A changed recovery exclusion changes the revision:
  the declared roots a recovery leaves out are part of it, as the spawn's
  receipt gives them, where since 0.42.0 they changed the plan's note and
  not its revision. A stop plan's revision is unchanged. See [the retire
  plan](../desktop-cli-api.md#retire-revision-work), which also names what
  is left out of the revision and why.
- **A guarded retire after the record was rewritten is refused as stale
  (#1065).** These went through, or were refused late, on a plan that no
  longer said what the kernel read:
  - with nothing at `work/`, a plan read under a record that said
    `worktree` and applied after the record said `attached` went through;
  - a plan applied after the record's `branch` was rewritten went through;
  - a plan applied after the record's `repo` was rewritten to a path that
    is no repository was refused only after the retire hooks had run
    (`E_WORK_PRESERVATION_FAILED`).

  Each is now `E_PLAN_STALE` with the fresh plan, before anything runs.
  Where such an apply was refused for the retire's own reason before
  anything ran (`E_WORK_INSPECTION_FAILED`: a file at `work/`; an own tree,
  or a link, under a record rewritten to `directory`), the answer is now
  `E_PLAN_STALE` first, and the fresh plan's revision meets that refusal as
  before.

- A failed or unparseable Git version probe now refuses the remote read with
  `E_REMOTE_UNREADABLE` and an existing reason instead of falling back to a
  whole-tree fetch. Only a successfully parsed version below Git 2.45 triggers
  a version-driven rebuild of a partial cache. Existing full caches stay full.

- **Desktop: the Start and Restart dialog says in its own words a start that
  OATS refuses for want of a configuration**
  ([#1079](https://github.com/awebai/oats/issues/1079)). When OATS refuses a
  start or a restart with `E_LAUNCH_CONFIG_AMBIGUOUS` (the start names a
  harness and no configuration, several configurations are declared for that
  harness, and none is the default), the dialog's status reads "More than one
  launch configuration is declared for the chosen harness, and none is the
  default. Choose one under Launch configuration, or choose "No launch
  configuration" to run the harness as installed.", and under it "OATS says:
  `<message>`" as one line, in place of OATS's message, written in
  command-line flags, as the status. A message that looks like a credential
  reads "[withheld]", with no name before it.
  - **"Preview invocation"** refused with that code reads the same sentence,
    then "Preview only. No agent was started or stopped.", with OATS's line
    under it. That refusal's message is no longer cut at 300 characters.
  - **Unchanged:** every other refusal of a start, a restart or a preview
    reads as before, and after any refusal Start is offered again once
    "Refresh status" is pressed.

- Roster rows whose state is unknown now stand after the running rows and
  before the stopped ones, in a fixed order by name, where they used to keep
  the order the read gave them.

- **The Desktop no longer accepts an OATS CLI of the 0.25 line: it accepts
  `>=0.26.0 <0.57.0`.** A 0.25 kernel is told so once, in the card
  "Compatible `oats` CLI required", with its version and the required range,
  where it was told at each workspace and deployment read to update OATS.

- **Desktop: an OATS Desktop older than the installed `oats` CLI says so, and
  offers no downgrade** ([#1107](https://github.com/awebai/oats/issues/1107)).
  When the CLI it finds is a released version above the range the Desktop
  works with (usually because the CLI was updated first), the card reads "This
  Desktop is older than the installed `oats` CLI" and names the OATS Desktop
  version to install. It no longer offers `npm install -g @awebai/oats@<the
  Desktop's version>`, which would have downgraded the CLI. **Choose oats…**,
  **Retry** and the docs link stay, and reads and terminals keep working
  meanwhile. For a CLI below the range, a prerelease, or any other refusal, the
  card is as before. [OATS Desktop](../desktop.md#troubleshooting) has the
  card's states.

- `oats update` now says, in one line under its steps, that the Desktop goes
  first when its plan installs a CLI of another minor or major version: `OATS
  Desktop refuses a CLI newer than its own minor version: if you use it,
  install OATS Desktop <version> first.` It prints the line with `--check`,
  before it asks, and without a terminal. A patch update, or a prerelease to
  its own release, prints nothing. Nothing detects an installed Desktop, so
  the line also shows on hosts without one ([Upgrading](../upgrading.md#the-steps),
  [#1107](https://github.com/awebai/oats/issues/1107)).

- Direct callers of `lib/remote.mjs` must select `displayRepoRef` for
  repository-reference display or `displayDiagnosticText` for kernel-authored
  diagnostic prose; Git lines continue to use `scrubGitLine`. The implicit
  `redactUrl` export is removed without a compatibility shim. These entries
  share the existing private renderer and preserve diagnostic output and
  disclosure rules. `lib/remote.mjs` is not in the package export map; this
  migration affects internal and direct-module callers. See the
  [entry-point signatures](../implementation.md#remote-diagnostic-display).

- With an OATS CLI that lists `roster-workspace-key`, the Desktop's roster read
  contacts only the machines of the workspaces its windows show, plus those
  whose workspace is not known yet and those known only from a saved route. A
  machine registered for another workspace is no longer contacted, so one
  that is switched off no longer slows every window's roster. Opening a window
  on another workspace reads its machines at once; with an older CLI every
  machine is read, as before ([Which machines the Desktop
  reads](../desktop.md#a-workspaces-machines),
  [#1124](https://github.com/awebai/oats/issues/1124)).

- **The Desktop's Forget… runs only for an instance the last roster read
  showed gone from its server
  ([#1170](https://github.com/awebai/oats/issues/1170)).**

- **The Desktop accepts OATS CLIs `>=0.26.0 <0.57.0`**
  ([#1188](https://github.com/awebai/oats/issues/1188)). The compatibility band
  admits 0.56; a 0.55 Desktop refuses a 0.56 CLI. No new gate on the band.
  `oats tui` runs the kernel it ships with and is held to the same band.

- **`oats spawn --server <id> --preview --json` no longer carries
  `snapshot`.** The field named a saved-route file that a preview should never
  have written. The answer is now the server's preview plus `server` and
  `target`, the two fields a routed spawn adds
  ([servers.md](../servers.md#run-there)).

- The context panel offers Stop for a stopped instance and for one whose state is unknown, as the roster menu does. Stop also stops an instance's children, so it is how a stopped parent's running children are stopped. When it offers no lifecycle action, as for an instance its server does not report addressable, it says why.

- A stop, retire or start runs in a process session of its own, so neither closing the Desktop nor interrupting the terminal that started it interrupts it. When a stop or retire takes longer than ten minutes, the Desktop stops waiting and says the result is not confirmed; the command keeps running, and Check again reads its result. When a start or restart takes longer than 60 seconds, the Desktop stops waiting and says the start is not confirmed; the start keeps running, and the roster shows its result. Another stop or retire asked meanwhile names the one still running.

- When the Desktop cannot run the OATS CLI for a start or restart, the dialog now says the start could not be confirmed and to refresh the instance's status, instead of showing the system's error.

- **A launch whose harness package cannot be checked in its pane's account
  is refused, where it passed before
  ([#993](https://github.com/awebai/oats/issues/993)).** The check of a
  required harness package now runs with the `PATH`, `HOME` and harness
  folder the launch's tmux pane will have. When a server runs and one of
  those cannot be read from it, a spawn or a start whose capabilities require
  a package is refused before anything is probed. That first check comes
  before anything is created. A spawn whose pane differs from the one it
  checked (another creator started the server first) checks again on the
  pane it got, once its home, work and hooks exist, and a refusal there rolls
  the spawn back. The case that
  passed until now: a launch configuration that declares an absolute
  `executable`, in a session whose `PATH` is cleared or cannot be read as
  data. A launch with no package requirement is not affected.
  - **What you do:** the message names the name, where it was read and what
    makes it readable. Either set that name in the launch configuration's
    `env`, or give the session or the server a value OATS can read (`tmux -L
    oats set-environment -g PATH <value>`), or start the OATS tmux server
    from your own shell.
  - **The code** is `E_RUNTIME_ENDPOINT_UNKNOWN` at `oats spawn`,
    `oats session start` and `restart`, and in a preview's
    `harness-packages` item, with the same message
    ([#1047](https://github.com/awebai/oats/issues/1047)).
- **`oats harness trust` writes for the file launches read, and refuses when
  it cannot tell which.** Its ambient file is the one a launch with no launch
  configuration reads: the server's or the session's `CLAUDE_CONFIG_DIR` or
  `CODEX_HOME`, else the default file under their `HOME`, where it was the
  operator's own shell's before. `--plan` shows the file and what selects
  it. With no server running it is the operator's own, as before, and
  `warnings` says so. When a server runs and its environment cannot be read,
  or tmux could not say whether one runs (`tmux -L oats list-sessions`
  refused or cut off),
  nothing is written and the answer is `E_RUNTIME_ENDPOINT_UNKNOWN`
  (`E_CONFIG_BROKEN` when a launch configuration's target is refused as
  well).
  - **What you do:** run it where `tmux -L oats list-sessions` answers.
    With no tmux on its `PATH` the command makes no read and writes the
    operator's own file, as before, and `warnings` says so.
  - **One more target.** A launch configuration that sets `HOME` and no
    `CLAUDE_CONFIG_DIR` or `CODEX_HOME` gets the default file under that
    `HOME` written, when the session and the server set no such variable
    either: that is the file its launch reads. It had no target before.
- **The `harness-trust` item of `oats readiness` is `unknown` when no OATS
  tmux server runs** and the launch configuration does not set the harness
  folder: the file it can read is the calling process's, not known to be the
  one a launch will read, and `reason` says so. The item is optional, as
  before, and `ready` does not change with it. It is also `unknown`, with
  `file` null, when a server runs and its environment cannot be read.

- **The Desktop's command palette lists instances by last focus.** With an
  empty query, ⌘K / Ctrl+Shift+P starts with a **Recent** group: every
  instance of the window's workspace whose terminal you have focused, most
  recent first, each with its parent as quiet text. The instances you have
  not focused follow in the sidebar's tree order. When the most recent is the
  terminal in front, the palette opens on the one before it, so ⌘K then Enter
  returns to the previous agent. With a query, recent matches come first. The
  sidebar roster keeps its stable order. The record stays on this machine, in
  the Desktop's own storage (the 200 most recent per workspace), and survives a
  restart; it is never written to a deployment.

- **Desktop: the active terminal tab's instance is always shown in the
  sidebar.** When another terminal tab becomes active (a click on a tab,
  Ctrl+Tab, go to tab, closing a tab, focusing another split group), the
  instance list scrolls just enough to show that instance's row and marks it
  selected at once. A click on the tab that is already active does the same.
  Focus stays where it was. The list does not move while the sidebar is hidden
  or in focus mode, or when your filter hides the row. A row under a collapsed
  parent shows its parent's row instead, and the parent stays collapsed.

- **Desktop: the sidebar's instance list no longer shows a scrollbar.** On
  Linux the list showed the platform's heavy classic scrollbar when the roster
  overflowed. It now scrolls like the tab strips, with the wheel or the
  touchpad. Moving through the rows with the keyboard (the arrows, Home/End,
  Down from the filter, F6) scrolls the list just enough to show the whole
  focused row, its tools included.

- **The Desktop's keyboard shortcuts editor is searchable and easier to
  read.** A search at the top, focused when the editor opens, filters by an
  action's name, its group or its keys: `shift+b` or `ctrl shift b` finds
  Ctrl+Shift+B. Down moves from the search into the list, and Esc clears the
  search before it closes the editor. Each shortcut shows as keycaps. A quiet
  "terminal" marks the ones that work while a terminal has focus, and
  "changed" marks the ones that differ from the default, next to their Reset.
  Group headings stay in view while their shortcuts scroll. See
  [Desktop keyboard](../../packages/desktop/docs/desktop-keyboard.md).

- **Desktop: the instance panel starts closed and stays as you leave it.**
  Opening an instance's terminal (from the sidebar, the palette, the overview,
  Quick Open or a tab switch) no longer opens the panel on the right. Whether
  it is open is remembered on this computer: open it once (its shortcut, the
  palette's **Instance panel: show / hide**, or **Show instance panel**) and
  it stays open for every instance until you close it. The Workspace view's
  soul inspector still opens when you select a soul.
- **Desktop: a closed sidebar or panel leaves nothing behind.** The thin strip
  left by a hidden sidebar and the narrow rail of a collapsed panel are gone:
  the terminal gets the whole width. To open them again, besides their
  shortcuts and the palette, the top bar has **Show sidebar** at its start
  while the sidebar is hidden or focus mode is on, and **Show instance panel**
  at its end while the panel is closed. Show instance panel carries the
  Developer page's dot when that page has changes.

- **Desktop shortcuts work from a focused terminal on Linux and Windows.**
  Three defaults moved so they no longer take a key a program reads: the
  sidebar is Ctrl+Shift+B (was Ctrl+B, the tmux prefix), the instance panel
  Ctrl+Shift+I (was Ctrl+I, the Tab key) and filter instances Ctrl+Shift+F
  (was Ctrl+F). These three, the stages (Ctrl+1, Ctrl+2, Ctrl+3), the
  shortcuts editor (Ctrl+,) and terminal zoom (Ctrl+= Ctrl+- Ctrl+0) now work
  while a terminal has focus. Plain Ctrl+B, Ctrl+I and Ctrl+F reach the
  program, and a shortcut you set yourself is kept. Ctrl+3 from a terminal now
  opens Automations instead of sending ESC: use Esc. macOS is unchanged. See
  [Desktop keyboard](../../packages/desktop/docs/desktop-keyboard.md).

- OATS Desktop shows `[withheld]` where it showed `[Detail withheld]`, the
  word the terminal client already uses: both clients now show one word for
  any text they withhold.

## Fixed

- **A path, a branch name or a hook's words could rewrite the terminal
  through these lines
  ([#1006](https://github.com/awebai/oats/issues/1006)).** A hook's warning,
  a pi folder's path, an extra tree's path or a branch name printed as it is
  could clear the screen, add a line of its own or reverse what followed it.
  It is now spelled (see Changed).

- The kernel's check that keeps a value carrying a URL with credentials out
  of the parsed cache now takes time in proportion to the value's length.
  Before, a long run of dotted, hyphenated or plus-joined words in a
  repository value (such as `a.b.c.…`) made the check take time growing with
  the square of the run: a fraction of a second at 16 KiB, several seconds at
  64 KiB, on every read that wrote that value to the cache. Which values are
  kept out of the cache is unchanged.
  ([#1036](https://github.com/awebai/oats/issues/1036))

- **A retire plan's revision did not bind what the plan showed of the
  record (#1065).** A plan's revision is hashed from the facts that make
  the retire safe, and a guarded apply is refused when one of them moved.
  The record is a file the instance can write, and the revision held
  little of it: not its work mode, its repository or its branch, and of
  the session only the state. So the record could be rewritten between a
  plan and its apply without the revision moving, and two plans that
  differed in `facts.ownWorktree`, `defaults.retainWorktree`,
  `facts.repo`, `facts.recordedBranch`, a note or the text's `defaults:`
  line shared one `planRevision`. So did two plans that differed in what
  Git says of `work/` beyond its commit, branch and counts (the reason it
  gives no answer, a detached `HEAD`, whether the tree is on the recorded
  branch, the branch's upstream, the remote),
  and in the reason of an edge that could not be followed. The revision now
  holds everything a retire plan shows but the facts that move by
  themselves: the instant, the counts against the upstream and the default
  branch with that branch's name, and a child's session. 0.55.0 and every
  release before it have the defect: it is older than 0.53.0.

- Git version probe failures preserve existing partial remote caches and all
  their commit pins. Failed probes are not cached, so later reads can retry;
  each caller may stop waiting on its own timeout or cancellation, including
  reads without a session. A shared probe still uses the launching caller's
  timeout and signal, whose failure reaches every remaining waiter.

- **A failed write of the scheduler's, the triggers' or an extra tree's
  files leaves no private file behind
  ([#1076](https://github.com/awebai/oats/issues/1076)).** The kernel writes
  each of these files through a private file beside it, renamed into place:
  the automations snapshot (`.agents/automations/snapshot.json`), the
  schedules (`oats-schedules.json`), their run state and the triggers' state
  (`.agents/schedules/state.json`, `triggers.json`), the host scheduler's
  `~/.oats/schedules/registry.json` and `state.json`, an extra tree's record
  (`.oats/trees/<purpose>.json`) and the step `oats worktree add` records in
  its claim (`.oats/trees/<purpose>.lock`). On a file system with no space
  the private file was created, its write failed, and nothing removed it:
  each failed attempt left one more empty `<name>.tmp-<pid>` (for a claim,
  `<name>.tmp-<pid>-<nonce>`) beside the file. Each of them now removes its
  private file when the write or the rename fails, as the two writers of a
  stop have since 0.53.0, and every such write goes through one writer in
  the kernel. The error answered is the one answered before. An upgrade does
  not remove the files an earlier version left.

- **A session command's refusal names the file it could not read
  ([#1092](https://github.com/awebai/oats/issues/1092)).** For a home whose
  `instance.json` is not JSON, `oats session inspect`, `attach` and `input`
  said `cannot read session receipt for <home>: <the parser's words>`, though
  the receipt was intact: the file that could not be read was the record, and
  nothing in the sentence said so. The receipt and the record are now read
  apart, and each refusal names its own file by its path:
  `cannot read <home>/instance.json: <why>` for the record (`it is missing`
  for one that is not there, `it holds no JSON object` for one that is JSON
  and no object), `cannot read session receipt for <home> at <path>: <why>`
  for the receipt. The code is `E_RUNTIME_ENDPOINT_UNKNOWN` for either, as
  before. The same sentences reach the error a schedule records for a job
  whose instance's session cannot be inspected, and the row of `oats instance
  stop` for a home without its `instance.json`. `oats session start` and
  `restart` are unchanged: they refuse such a home earlier, with their own
  sentence.

- When `oats harness trust` refuses a configuration file, the refused row now
  says which check refused it (for example a macOS extended-attribute marker,
  more than one hard link, another owner, or an unsupported format), without
  repeating the file's content. A refused row no longer prints an empty current
  value and "missing" digests, which read as if the file had no trust, and the
  error message lists every refusal (#1109).

- **An instance no longer inherits another instance's provider settings
  through the tmux session or server**
  ([#1123](https://github.com/awebai/oats/issues/1123)). OATS set only the
  variables a capability's hook returned; a variable the capability declares
  in its manifest `environment` but left out of its answer kept whatever the
  pane's environment held. A Claude Code instance on the aweb channel path
  started with `AWEB_DELIVERY=session` that way, so its channel delivered
  nothing and it was never woken. Now, for every capability, a declared
  variable its hooks leave out is removed from the launch: each window's
  command unsets it (for a spawn, a start, a start in place and a restart),
  and the checks of the launch read it as not set. A launch configuration's
  explicit `env` still applies. The persisted launch command does not
  change. See
  [a declared name is the provider's](../capabilities.md#a-declared-name-is-the-providers).

- `oats harness trust` names the right reason when a launch configuration that
  sets only `HOME` points at a path that is not a usable directory (a file, or
  a path under one): it says the `HOME` does not select a usable configuration
  directory, where it used to say the path is not absolute (#1171).

- Desktop terminals draw text again after the computer wakes from sleep or
  after a switch of Spaces or windows. When the graphics process restarted,
  every terminal pane went blank, showing only its background and the cursor,
  for old output and new alike, until the app was reloaded. Now, once the
  graphics contexts are back, the app redraws the text of every open terminal,
  hidden tabs included.
  ([#1190](https://github.com/awebai/oats/issues/1190))

- **`oats session attach` asks tmux for synchronized output
  ([#1193](https://github.com/awebai/oats/issues/1193)).** Every `oats session
  attach` client, the Desktop's remote terminals and the TUI included, now
  starts its tmux client with the `sync` terminal feature when the host's
  tmux is 3.2 or later. tmux then wraps each redraw in DEC mode 2026, so a
  terminal that supports the mode no longer paints a half-drawn redraw (in
  the Desktop, the cursor flickering while you type in a remote instance's
  input box). A terminal without the mode ignores it. The feature is the
  viewer's client's alone: the agent's session, other clients and the tmux
  server's options are unchanged. With tmux before 3.2, or a `tmux -V` the
  kernel cannot read, the client starts as before.
  [Inspect, input and attach](../execution-targets.md#inspect-input-and-attach).

- **Desktop: the cursor no longer flashes while you type in a terminal tab**
  ([#1193](https://github.com/awebai/oats/issues/1193)). Each keystroke in a
  program like Claude Code reaches the tab as one redraw that hides the cursor,
  repaints the line and shows the cursor again; a redraw that arrived in two
  pieces was sometimes painted half done, with the cursor hidden. The Desktop
  now attaches its tmux viewer with synchronized output (on tmux 3.2 and later)
  and paints each redraw only once it is whole. Local terminal tabs have the fix
  now; a tab on another machine has it once that machine's oats has the
  matching viewer change.

- **A routed spawn preview no longer saves a route.**
  `oats spawn <soul> --server <id> --preview` used to print
  `Spawned <instance> on <id> … — not launched` with a remote home, a route
  snapshot and an attach hint, and saved a route under
  `~/.oats/remote/<id>/`, though the server had only answered a preview and
  created nothing. That stale route then showed in `oats status --server` and
  `oats server roster`, made `oats retire --server` fail with
  `E_HOME_MISMATCH`, and, after `oats server add --replace`, made the next
  `oats spawn --server` fail with `E_ROUTE_CHANGED`. A routed preview now runs
  the spawn's own checks here, asks the server for its preview, and prints the
  local preview's line with the server named
  (`preview <soul> → <instance> on <id> …; nothing was created`). It saves
  no route or other state on this machine. A server that does not advertise
  `spawn-preview-2` is refused with `E_REMOTE_INCOMPATIBLE` before the spawn
  is sent. Drop a route an earlier preview saved with
  `oats server forget <id> --instance <instance>`.

- **The checks of a launch read the environment its pane will have, not the
  one of the process that spawns
  ([#993](https://github.com/awebai/oats/issues/993)).** A harness runs in a
  tmux pane, with the session's and the server's `HOME` and harness folder
  (`CLAUDE_CONFIG_DIR`, `CODEX_HOME`, `PI_CODING_AGENT_DIR`). The folder-trust
  check and the harness package check read those names from the process that
  ran the spawn instead, so the two disagreed whenever that process had
  another account than the server: a spawn was refused for a package that
  the pane's account has, or passed and then launched without it; folder
  trust was reported for a file the launch never reads, and a codex launch
  trusted its home by that file. Now the lookup of the harness, the
  folder-trust check, the package check and the command its refusal names,
  the `harness-trust` item of `oats readiness`, a preview and `oats harness
  trust` read one answer: the launch configuration's `env`, else the
  session's entry, else the server's, else what the server is created with.
  - **Who sees a different answer after upgrading:** a host whose OATS tmux
    server or session holds `CLAUDE_CONFIG_DIR`, `CODEX_HOME` or
    `PI_CODING_AGENT_DIR` (the checks now read that account, and no longer
    the shell's), and agents that spawn from a session with a folder of their
    own (their own folder is no longer the one checked: the launch's is). A
    host where the spawning process and the server have the same account sees
    the same answers.
  - **No selector is an answer.** A session or a server that sets none, or a
    session that clears it, launches with the default folder under the
    pane's `HOME`: the checks read that file, and the package check's command
    starts with no selector.
  - **Folder trust never guesses.** When the pane's environment cannot be
    read, the warning is `<harness> folder trust: the configuration file this
    launch will read could not be established (…); nothing is said about its
    trust`. Otherwise the warning names where the launch gets the file from:
    `… is not established in <file> (the CLAUDE_CONFIG_DIR of tmux session
    <name>): oats harness trust --dir <deployment>`.
  - **A preview says what it could not know.** With no server running, a
    preview, `oats readiness` and `oats harness trust` do not start one, and
    do not start your login shell. They read the launch configuration's
    value, else the calling process's, and say so, for `PATH` as well: `the
    pane's environment is not established until a spawn starts the OATS tmux
    server (none runs); read instead: this process's PATH`. A preview carries
    it in the `executable` item's `detail`, a spawn preview in `warnings`.
    The package check does not refuse on that alone.
  - **A spawn with `--no-launch`** checks against the calling process, as
    before, and the start that follows checks again on its own session. It
    now says whose values it read where it already says something: in the
    folder-trust warning and in a refusal for a missing package.
  - **The package check runs the program the lookup selected**, by its
    full path, with the pane's `PATH` as the pane reads it. With a relative
    entry in that `PATH`, the check could run another program, found from
    the directory the command ran in, than the one the launch starts.
  - **A spawn judges again on the session it gets**, as the lookup already
    did: when another creator won the race to start the server, the package
    check and the folder-trust check are made on that server's account.

  [Every check of a launch reads the environment its pane will have](../execution-targets.md#the-checks-read-the-pane).

## Removed

- **`E_REQUIREMENT_INACTIVE` (#1047),** documented as an answer of
  `oats spawn` and of `oats inspect --soul`, and never raised since 0.26.0:
  no OATS from 0.26.0 raises this code. It leaves the contract page and the
  kernel. Nothing a released kernel answers changes.

## Provider updates

- **oats.framework 1.10.1: oats.setup 2.5.3.** Instruction text in two
  oats.setup skills; no hook, command, schema or provider contract changes,
  and the capability floors are unchanged (oats.setup `>=0.30.0`).
  - `oats-onboarding` and `oats-workspace-config` say that from OATS 0.56.0 a
    failed or unparseable Git version probe keeps the remote cache and its
    pins, as the entry under Fixed says
    ([#1074](https://github.com/awebai/oats/issues/1074)): fix the local Git
    failure and retry, without deleting the cache. A `cannot-read` is now
    fixed in the operator's Git environment, not only its Git access.
  - `oats-onboarding`'s knowledge section names oats.okf 5.1.0 and the kernel
    it needs, OATS 0.49.0 or later (the instance-event lookup after a source
    retires), as the oats.okf entry says.
  - A deployment gets it by pinning `oats.framework: v1.10.1` and running
    `oats sync`. Instances already running keep the skills they were spawned
    with; new spawns get the new ones.

- **oats.okf 5.1.0** (from 5.0.5), mirrored from the published `v5.1.0`
  tag at `40265ac79eca54a76ae648462dbfc83ac370dbbe`. The mirror, catalog and
  workspace pin move together; the mirror and inventory are generated by
  the parity checker from that tag.
  - **A harvest survives its proposer's retirement.** The required spawn
    hook verifies the source's live record or event-named retirement recovery,
    then atomically captures the proposal, source declarations/bindings and
    only named backing notes in the harvester's own home. Later retirement
    or recovery disposal cannot remove captured input. Missing/ambiguous
    provenance still refuses; soul opt-out, unrelated harvesters, the no-wait
    rule and reviewed acceptance remain unchanged.
  - **Requires OATS >=0.49.0**, where the public source-event lookup first
    works after home removal. Upgrade the kernel before the provider pin;
    re-spawn harvesters for the new hook and instructions. Restarting keeps
    a home's copied provider. The onboarding skill now names 5.1.0 and this
    kernel floor; that skill change ships with the next framework release.
  - **Binding URL sequencing:** change a binding's `repository` to the plain
    URL only after every reading seat has been re-spawned on oats.okf 5.0.4
    or later; a session restart does not upgrade its copied modules.
  - Source capture refuses reused/ambiguous source incarnations and incomplete
    event histories. Legacy note references are preserved or explicitly
    refused, never silently dropped or replaced by a shorter filename.

  Provider changes: [oats-okf#82](https://github.com/awebai/oats-okf/pull/82).
  The generated mirror/pin change is not evidence of deployment adoption or
  a model-run harvest; existing homes and deployments remain unchanged until
  explicitly upgraded.
