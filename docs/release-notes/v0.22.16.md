# OATS v0.22.16

The same reviewed content as the unpublished v0.22.15 tag, whose hosted
run failed in frozen test data (retirement goldens still carrying the
removed `harvested` field, and a Desktop harvest fixture predating the
operations gate) before anything was published; only tests changed.

Souls and capabilities become something you inspect and manage, through
one kernel contract, and knowledge providers declare what they can do.

## Provider operations and inspection (kernel)

`oats inspect --json` answers everything a GUI needs in one envelope for a
scope, a selected soul or a running home: souls with runtime defaults,
editability and instructions; installed capabilities with health from the
package engine, separately from their effective activation, provenance and
settings; effective layer bindings; and the operations each provider
declares, with availability and the reason when unavailable. For a home the
answer is its captured bindings (with current manifests and trust), the live
config beside it, and the drift between them. Same-named souls in member
repositories are addressed by name plus agents root; a home selects its own
soul under its own root.

`oats operation run <layer>:<name>` resolves the provider that fills a layer
for a home or a soul, checks declaration, trust and host requirements, runs
the provider's own command in the right place with the right identity, and
relays its receipt; a view answers labeled documents. Unconfirmed outcomes
carry what was observed and a scheduled operation keeps its slot until
reconciled. Manifests declare `operations`. Schedules gain kind
`operation`. `oats use --json` answers receipts and `--inherit` returns a
level to inheritance; `oats soul set` edits an editable soul's defaults and
instructions in place. All four route to a registered server through the
saved route; the probe advertises `operations` and `operationsApi: 1`. The
retire receipt no longer implies a harvest. See
docs/design/operations-contract.md.

## oats.okf 1.6.0

The official knowledge provider declares `inspect` (a view of STATE.md,
log.md and pending notes) and `harvest` (the existing action); the catalog
pins v1.6.0. Existing scopes keep their locked 1.5.2 until their owners
update them; the GUI then shows no operations for those providers, which is
the truthful state.

## Desktop

Souls & capabilities replaces the launch-centric roster: select a soul to
inspect it, Launch and Schedule are explicit, defaults and instructions are
editable where the kernel says so, installed capabilities are shown apart
from activation with enable, disable and inherit at an exact scope, an
instance's menu opens Knowledge & capabilities, provider views render as
text, and schedules run declared provider operations. See
docs/design/2026-09-07-desktop-souls-capabilities.md.
