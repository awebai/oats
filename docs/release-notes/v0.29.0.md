# OATS 0.29.0

## Added

- **Workspace triggers and schedules** (feature `automations`). A trigger or a
  schedule can now be declared in Git, in any confirmed member, and shared with the
  team. It is named `<member>/<id>`, and a machine's own ones are named
  `local/<id>`. See
  [schedules.md#workspace-triggers-and-schedules](../schedules.md#workspace-triggers-and-schedules).
  - Triggers and schedules stay separate:

    | | triggers | schedules |
    | --- | --- | --- |
    | folder | `oats-triggers/` | `oats-schedules/` |
    | file name anywhere in the member | `*.oats-trigger.yaml` | `*.oats-schedule.yaml` |
    | `kind:` | `oats-trigger` | `oats-schedule` |
    | commands and list | `oats trigger …` | `oats schedule …` |
    | opt-out | `triggers.disabled` | `schedules.disabled` |

    `oats-package/`, `.git/` and `node_modules/` are never scanned.
  - Every file carries `kind`, `schemaVersion: 1`, `runsOn` (the host that runs it)
    and `owner` (the GitHub account it acts as). The wrong kind is
    `E_AUTOMATION_SCHEMA`, and a duplicate id is `E_AUTOMATION_DUPLICATE`.
  - A host runs one only when `runsOn` is its new `oats-local.yaml` `host.name`
    **and** its `gh` is logged in as `owner`. Otherwise the item is listed as
    `assigned-elsewhere`, `owner-mismatch` or `host-unnamed`.
  - `oats trigger disable <member>/<id>` and `oats schedule disable <member>/<id>`
    stop it on this host without a commit, by writing `triggers.disabled` or
    `schedules.disabled` in `oats-local.yaml`.
  - `oats sync` takes a snapshot of them. The host tick reads the snapshot and
    refreshes it every ten minutes (`oats automations refresh`).
  - `oats trigger add … --workspace <member> --runs-on <host> --owner <host>/<login>`
    writes the file in a checkout of the member, or prints it. `oats schedule add`
    takes the same options.
  - `oats trigger list --json` and `oats schedule list --json` answer the Desktop's
    rows for both levels: the owner, where it runs and why (not), the soul and
    where it comes from, the task verbatim, the event or cron, and the last and
    next run. Local schedule rows keep their bare `id` and add `qualifiedId`. See
    [desktop-cli-api.md](../desktop-cli-api.md).
  - Each row's `origin` carries `url` (the file on GitHub at its commit) and
    `localPath` (the file in this machine's clone of the member), each `null` when
    there is none. Both lists carry `host.ghUser` (who `gh` is logged in as, per
    GitHub host) and the host `scheduler`. "When it next runs" is `nextDue`
    everywhere.
- **Desktop facts** (feature `desktop-facts`): kernel facts the Desktop's Workspace
  view shows, so it never derives them. Every field is an addition. See
  [desktop-cli-api.md](../desktop-cli-api.md#desktop-facts-feature-desktop-facts-oats-0290).
  - `oats inspect --soul --json`: each capability's `composedFrom` (`workspace`,
    `team:<label>` or `soul`), and `capabilitiesOff[]`, the defaults the soul
    turned off (`<id>: off` or `<slot>: none`).
  - `oats souls --json` rows: the default `harness`/`model` a spawn starts with,
    and `spawnable` and `problem`, the refusal a spawn would meet (it spawns
    nothing). Also `file`.
  - `oats capabilities --json` rows: `layer` on package rows too, `description`,
    `skills`/`commands`/`hooks` by name, `file`, and a member capability's `tree`
    (its Git tree id).
  - `oats workspace status --json`:
    - the workspace and team `defaults` as rows;
    - this computer's member `clones` and the rule that found each;
    - `disabledSouls`;
    - `lock` (`path`, `lockfileVersion`);
    - `packages[].latest` when the shipped catalog has a newer version;
    - file locations (`workspace.file`, `members[].url`,
      `members[].membershipFile`).
  - `oats status --json` instance rows: `startedAt` (the last start or restart),
    `modelFrom` (also recorded in `instance.json`) and `identityAddress`. A member
    module's drift `current` gains `version`.
  - URLs are GitHub pages at the row's commit, `null` for any other host.
  - `oats help` lists `spawn --provider`.
- **`oats schedule test <id>`**: where a schedule runs, whether its soul resolves
  (a spawn preview) and when it is next due. It spawns nothing, like
  `oats trigger test`.
- **`launchConfig`** on a trigger's `spawn` and on a spawn schedule: the soul starts
  on that launch configuration of the running host (`oats-local.yaml`
  `launch-configs`). A package trigger template can expose it as a parameter.
- `oats trigger status --json` rows add `nextDue`, `concurrency` and `liveCount`;
  `oats trigger test --json` `wouldFire` items add `repo`.

## Changed

- **A local trigger's id is `local/<id>`** in `oats trigger` rows, in its dedup keys
  and state, and in a triggered instance's `instance.json.trigger.id` and event
  file. It was the bare id in 0.28.0. Every `oats trigger` verb still accepts the
  bare id.

## Fixed

- Concurrent spawns of the same instance: a spawn that loses the race now refuses
  with `E_PLACEMENT_TAKEN` (it created nothing). It used to fail with an uncoded
  "instance already exists" error, surfaced as `E_SPAWN_FAILED`.
- Disabled-here messages name the per-kind key (`triggers.disabled`,
  `schedules.disabled`).

## oats.okf 4.0.0 (catalog pin and bundled mirror)

The official catalog now pins `oats.okf` to `v4.0.0` (tag object `239f2885`,
commit `1f0ba12f`). The copy bundled in this package is its byte mirror.

**BREAKING:**
- The package requires `oats >=0.29.0`; an older kernel refuses it
  (`E_CAPABILITY_INCOMPATIBLE`).
- The `okf` and `memory-harvest` skills are gone from `oats.okf`.

- **Three capabilities.** The package now exports:
  - `oats.okf`: the knowledge slot;
  - `oats.okf-harvest`: the harvester's completion and status commands;
  - `oats.okf-maintenance`: the maintainer's review context.

  The catalog maps `oats.okf-harvest` and `oats.okf-maintenance` to the
  `oats.okf` package.
- **Working souls get two skills and the inject.** A soul with `oats.okf` in
  its knowledge slot gets `okf-consultation` and `okf-instance-knowledge`, and
  the okf inject.
- **The harvester is a package soul.** `oats okf run-source` (and `oats okf
  harvest`) spawns `oats.okf/knowledge-harvester`. It is named
  `okf-harvester-<run>` and homes under
  `agents/oats-okf--knowledge-harvester/`. It is no longer the `memory-harvest`
  capability agent. After a successful completion it stays alive in the `okf`
  team until its PR is merged or closed. `oats.okf/knowledge-maintainer` is the
  package's second soul.
- **The harvest-review trigger.** The package ships the trigger template
  `harvest-review` (`triggers/harvest-review.json`). It watches the labelled
  harvest PRs.
- **`harvest: on|off`** (default **off**). Harvest is a host switch in
  `oats-local.yaml` `settings.oats.okf.harvest` (`oats okf setup --harvest
  on|off`). Off means no source registration, capture or custody. A soul can
  only opt out (`knowledge: { harvest: off }`).
- **`oats okf read` is removed** (`E_REMOVED`). Use `oats okf cat --base
  <alias> <path>`, which takes the same path and gives the same text and
  receipt.

The bundled mirror now covers the three capability directories
(`capabilities/oats-okf`, `capabilities/oats-okf-harvest`,
`capabilities/oats-okf-maintenance`). The package's souls and trigger are
checked byte for byte in `scripts/okf-source-inventory.json` (schemaVersion 2).
The npm package does not ship them, because the kernel reads a package's souls
and triggers from Git at its locked commit.
