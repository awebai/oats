# OATS v0.25.0 — the workspace model (breaking)

Kernel/Pi **0.25.0**. Tag `v0.25.0` → the commit carrying these notes; the
version-bump commit lands after the tag. Consumers gate on `oats version --json`
`features[]` names and API integers — never on the version.

**This is the 0.25 line: a new deployment model, not a patch to the old one.**
0.24.x keeps spawning 0.24.x deployments; there is no converter. The rebuild
guide is `docs/rebuild-to-v2.md`. Design: `docs/design/2026-09-23-simplified-workspace-model.md`;
decision record (26 decisions): `agents/oats-expert/soul/knowledge/decisions/workspace-model-v2.md`;
normative module contracts: `docs/design/2026-09-23-workspace-module-contracts.md`.

## The one idea

An organisation has **one workspace**: a Git repo hosting `oats-workspace.yaml`
that lists its **member repositories**, pins its **packages**, names its
**teams** and declares **defaults**. Every member carries an
`oats-membership.yaml` back-link; the handshake is confirmed over the Git
remotes in the operator's own access context and **membership is the trust**.
A member exports **souls** (`souls/<name>/soul.yaml`) and **capabilities**
(`capabilities/<name>/oats.json`) at its latest commit; a soul says where each
capability comes from (`from: <member repo> | here | package`). Packages are
consumed only through `packages:` + `oats-lock.json` v3, with **per-version
executable approval**. A spawn **resolves** the soul (`lib/resolve.mjs`) and
**materializes** every capability whole into the instance
(`<home>/.oats/modules/<cap>/`, skills under `<home>/.agents/skills/<cap>/`);
the harness starts normally. Nothing is installed anywhere.

## Kernel — `workspace-v2` (`workspaceApi: 2`), `instance-modules`, `spawn-provider-payload`

- **Declarations** (`docs/*.schema.json`, all `schemaVersion: 2`):
  `oats-workspace.yaml` (members, packages, teams, defaults incl. `byTeam`,
  stores, `messaging` incl. `byTeam.<label>`, external souls),
  `oats-membership.yaml` (`workspace`, `team?`), `soul.yaml` v2
  (`capabilities: { <cap>: { from } | off }`, `team`, `private`,
  `compatibility`, slot payloads), `oats-local.yaml` (the ONLY per-machine
  file: `workspace:` or `standalone:` ref, `clones`, `settings.<cap>`,
  `souls.disabled`).
- **`oats sync`** — discover → confirm membership → resolve packages → write
  `oats-lock.json` v3; unapproved executables listed, exit 2 non-TTY / prompt
  on a TTY. `oats package add|remove`, `oats workspace status`,
  `oats capabilities`, `oats souls` (origin + team columns).
- **`oats spawn`** — discovers and resolves over the remotes, fetches the soul
  from its member repo (refreshed per commit), materializes, launches.
  `--preview` works before any apply and reports `modules[]` (with
  `changedSince`), `team`, `resolution`, `workspace`, `soulFetched`; the
  decision binds the resolution revision (a member that moved between preview
  and apply → `E_DECISION_STALE`). `--provider <cap> k=v` records a per-spawn
  provider payload (`instance.json.providers`) — the third payload home after
  the soul and `oats-local.yaml settings`.
- **`instance.json`** carries `modules{}` (name → from/commit/digest),
  `providers{}`, `workspace{ key, commit, resolution, standalone, soul }`,
  `capabilities[]`.
- **`oats status`** shows drift per instance (`member moved since …`,
  `capability no longer present`); `--json` `instances[].modules[]`.
- **`oats onboard [<dir>] --workspace <ref>`** — writes `oats-local.yaml`,
  runs the sync path, prints the taught layout and the **hosting rule** for
  mixed public/private organisations (`onboardApi: 2`). Creates no soul,
  spawns nothing.
- **Standalone case** — a member whose workspace cannot be read (access
  failure only, never network/timeout) still offers its souls with `from: here`
  capabilities **plus `oats.core`** from the official catalog through the
  operator's own lock; marked `standalone: true` in sync/status/spawn output.
- **Teams** are labels; per-team provider payload is `messaging.byTeam.<label>`
  (merged by the kernel, stripped before the provider). A store names a
  repository; the root inside it is the provider's binding key.
- **Scheduled spawns** on a workspace deployment materialize exactly like
  `oats spawn` (the scheduler delegates to the CLI).
- **Security** (found by adversarial review, all pinned): remote tree names
  fsck'd (no traversal), tag naming a blob refused as a commit, symlinks in
  fetched trees refused except the soul's `CLAUDE.md → AGENTS.md` alias,
  `__proto__`/`constructor`/`prototype` refused at every payload layer and in
  `--provider` flags, `byTeam` reserved outside `workspace.messaging`, package
  executables gated on per-version approval, atomic staging with full
  rollback (no half homes).

## Removed

`oats init`, `use`, `install`, `trust`, `list`, `remove`, `migrate`, `catalog`,
`update`, `config`, `inject` → typed `E_UNKNOWN_COMMAND` naming the
replacement. `oats-config.yaml` is no longer read as configuration (a leftover
one is harmless); the `installed/` tier, `oats.yaml`, `lockfileVersion` 2,
per-soul `source: git:…` lines, `stores.inherit`, `imports`. The `catalog`
feature name is gone from `version --json`. `docs/configuration.md` now
describes `oats-local.yaml` only.

## Desktop

The Desktop server's `oats catalog` reader now surfaces `E_USAGE` (the verb is
removed); the Capabilities view's package acquisition flow will follow the new
DTOs in a later release (Phase F). Everything else in the Desktop is unchanged.

## Known follow-ups

- The classic (no `oats-local.yaml`) spawn path still runs the pre-v2 compose
  in `lib/core.mjs`; folding it into the one pipeline removes the remaining v1
  modules (residue table in `docs/design/2026-09-23-workspace-v2-implementation-plan.md`).
- The OATS framework repositories themselves convert to the model (six expert
  souls, `oats.core`/`oats.setup` rewritten for the new architecture) in 0.26.
