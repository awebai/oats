# OATS 0.40.0

## Added

- **"Needs input": an instance can say it is blocked on a human** (feature
  `waiting-on-you`). The `waitingOnYou` fact that `oats instance events` has
  carried since 0.24.12 finally has producers. It shows on every running
  instance row of `oats status --json` and on `oats session inspect --json`
  as `waitingOnYou: {since, producer, reason, message} | null`, and plain
  `oats status` prints `! needs input (<reason>): <message>` under the row.
  Claims are display-only: nothing in the kernel acts on them, and
  `oats session input` is unchanged. See docs/desktop-cli-api.md, "Waiting
  on you".
  - `oats instance waiting <set|clear> --producer <id> [--reason
    permission|question|attention] [--message <text>]` records a producer's
    claim as a `waiting` event, appended only when the claim changes.
  - `oats instance attention [--message "<one line>"] [--clear]` is the
    agent's own claim, run from its home (`$OATS_INSTANCE_HOME` only). The
    oats.core instructions now teach it: when an agent has asked a human
    something and cannot continue without the answer, it runs
    `oats instance attention --message "…"` and ends its turn, then
    `--clear` once it has the answer. Only the agent or a session boundary
    clears an agent claim.
  - `--message` is one line of 1 to 200 characters. Refused, at write and
    again at read (a refused stored message reads as `null`): control
    characters, U+2028/2029, the bidi controls U+202A–202E and
    U+2066–2069, U+200B, U+2060, U+FEFF and the tag characters
    U+E0000–E007F. Everything else is allowed, ZWJ/ZWNJ (U+200C/D) and
    LRM/RLM/ALM (U+200E/F, U+061C) included. The Desktop uses the same set.
  - A claim is live only after the incarnation's latest kernel `launched`,
    `restarted` or `stopped` row, so a crashed or restarted session never
    shows a stale claim. `waitingOnYou` and `waitingClaims[]` entries gain
    `message` (a string or `null`); the shape is otherwise unchanged.

- **oats.core 2.4.0 (oats.framework 1.6.0) reports Claude Code permission
  prompts and questions.** For a Claude instance, oats.core manages its own
  hook entries in `<home>/.claude/settings.json`. A permission prompt sets
  `waitingOnYou` with reason `permission`; AskUserQuestion or an MCP
  elicitation sets `question`; the claim clears when the session moves on.
  The hooks always exit 0, print nothing and time out in seconds, so a failing
  emitter means "unknown", never a blocked tool. Every other key and entry in
  that file is left alone. oats.core now requires OATS 0.40.0. See
  docs/capabilities.md, "oats.core: needs input".

## Changed

- **oats.engineering 1.8.1** (catalog and workspace pin, and the bundled
  mirrors): a PR is reviewed only after its owner says the developer's review
  loop converged. `/pr-review` starts on the owner's hand-over (the loop's
  final verdict and rounds, the exact head, CI green on it), and a head that
  moves afterwards waits for the next hand-over, after which only the delta is
  reviewed and the verdict re-bound; a PR with no owning expert is ready when
  its author marks it ready or asks for review at a named head.
  Experts verify only converged branches and hand PRs over with all three
  facts; developers report convergence, with the head, instead of
  intermediate heads.
- **The Desktop accepts OATS CLIs `>=0.25.8 <0.41.0`**, so it runs against
  this release's kernel; the Desktop 0.39.x refuses a 0.40 CLI.
- **`oats session start` and `restart` now record a `launched` event**
  (`data.phase: "start"` or `"restart"`, `data.startId`), as spawn already
  did, once per start and in each log: a start recovered from an interrupted
  one's receipt adds none, copies the same row into a log that missed it, or
  writes one with `phase: "recovered"` dated at its launch when the
  interrupted start had written it to neither log. A consumer that counts a home's
  events sees one more row per start.

## Notes

- **Claude Code honours only the last `--settings` flag.** On Claude Code
  2.1.288 a second `--settings` replaces the first wholesale, even when it
  has no hooks. That is why oats.core writes the project
  `<home>/.claude/settings.json`, which composes with the user's settings and
  with a `--settings`. Any capability that needs Claude settings must manage
  its own entries in that file, under its own marker, and never pass
  `--settings`.
- **Claude instances spawned before the upgrade get the emitter only on
  respawn.** A home's launch hook comes from its recorded module copy, so a
  restart keeps the old oats.core. The `attention` verb works on any harness
  as soon as the kernel is upgraded.
- If a user's Claude configuration sets `disableAllHooks` or
  `allowManagedHooksOnly`, the emitter never runs and the field stays `null`.
- Refusing a Claude Code permission prompt fires no hook (Claude Code
  2.1.288), so after a "No" the claim stays, labelled `permission`, until the
  human's next prompt; Claude is waiting for that prompt anyway.
- The emitter debounces only the per-tool-call clears; `UserPromptSubmit`,
  `Stop` and `SessionEnd` always call the CLI. That bounds what an unfenced
  kernel write can leave wrong ([#568](https://github.com/awebai/oats/issues/568)):
  after a hook suspended past 5 s mid-call (the machine slept) or a reaper
  killed at a precise instant, a claim wrongly shown lasts until the turn
  ends at the latest, and a hidden question until the human answers it. See
  docs/capabilities.md, oats.core: needs input, Limits.
- Tool calls by background or parallel subagents in the same Claude session
  do not clear the claim: the emitter skips tool events that carry a
  subagent's `agent_id`. A permission prompt never says who asked, so after
  a human approves a subagent's prompt the claim stays until the next
  main-thread event (its next tool call, the subagent's completion, a stop or
  a prompt). For a foreground subagent the main thread makes no call until
  the subagent finishes, so the claim can last the whole subagent run: too
  long, never hiding a real block.
