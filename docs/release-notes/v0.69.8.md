# OATS 0.69.8

Unreleased

0.69.8 is the first slice of the onboarding redesign. `oats.framework` 1.18.0
ships the setup expert as a package soul, with a capability that tailors a new
workspace; `oats onboard` names it, the kernel records who spawned each
instance, and the Desktop can open on an instance. A waiter now sets a
checkpoint before it waits on a child, and a pi home that may have no provider
gets a warning. The catalog moves to oats.framework 1.18.0 and oats.engineering
1.18.0.

## Upgrade

- **Either order of the Desktop and the CLI works.**
  [Upgrading](../upgrading.md) installs the Desktop first, and a host that
  installed the CLI first is fine too: the 0.69.8 Desktop accepts OATS CLIs
  `>=0.26.0 <0.70.0`, and so does the 0.69.7 Desktop.
- **Package move:** the official catalog pins oats.framework 1.18.0 and
  oats.engineering 1.18.0, with no change to their OATS floors. A deployment
  takes them with `oats sync`. Running instances keep the modules they were
  spawned with: new spawns get the new ones, and a stopped home moves with
  `oats instance upgrade`.
- **Optional:** a waiter's checkpoint is a wake job, so it needs the host's
  schedule timer (`oats schedule host install`). On a host without the timer,
  the waiter tells its parent instead.

## Added

- **Desktop opens on an instance: `--instance <name>` beside `--dir <deployment>`.** The deployment's window selects that instance in the roster as **Show in roster** does, on a first launch and on a launch while Desktop runs (`open -a "OATS Desktop" --args --dir <deployment> --instance <name>`). It only selects: nothing starts, attaches or is written. Only the `--dir` deployment's own instances count. A name not there yet (a spawn still finishing) is waited for about 30 seconds, then the window says "No instance <name> in this workspace". A value that isn't an instance name, or a name two instances share, selects nothing and says so. Selecting, typing or clicking while it waits drops it ([Opening on an instance](../desktop.md#opening-on-an-instance); [awebai/oats#1665](https://github.com/awebai/oats/issues/1665)). An older Desktop ignores the argument and opens the workspace.

- **`oats.framework` 1.18.0 ships the setup expert as a package soul, and a capability that tailors a new workspace.** The package soul `oats-setup-expert` holds `oats.setup` and the new `oats.onboarding`. It works in its own folder (`work: directory`), takes no knowledge slot and takes the workspace's messaging default. `oats.onboarding` 1.0.0 has one skill, `/oats-tailor-workspace`: for a new workspace, it discovers how the team works, authors the workspace's own coordination, knowledge and tasks capabilities from OATS's defaults, takes the person through the deployment-agent step their messaging capability offers (instances spawned after it carry a chain to them; earlier ones stay `unknown` until respawned), offers the approved channel route and briefs the person. The catalog maps `oats.onboarding` to `oats.framework` ([awebai/oats#1665](https://github.com/awebai/oats/issues/1665); [The official OATS catalog](../official-catalog.md)).

- **The kernel records who spawned each instance, and status rows show the human an instance's identity is attributed to.** The feature probe is `spawn-attribution`. Everything here is additive: a home, provider or client without these fields behaves as before.
  - **`spawnedBy`.** A new instance records `spawnedBy: {instance, home}` in `instance.json` and in the `spawned` event, or `null`. Status rows, local and remote, carry it in that shape only: anything else reads `null`. The caller is the instance that the `spawnOrigin` check confirms, so `spawnedBy` non-null implies `spawnOrigin: "instance"`. `spawnOrigin: "instance"` with `spawnedBy: null` means the spawner's session was found gone. A spawner whose session can't be read (tmux unreadable, its session receipt unusable) is kept, and the spawn is never refused. A person's shell, the Desktop, an automation and another deployment's home give `null`, and so does a `--server` spawn whose caller is not a live home on that host. `spawnedBy` is separate from `parentInstance` and `relation`, so an instance's `--relation unrelated` spawn still has a spawner. It is written once, at spawn: retire's lineage repair doesn't touch it, and it can name a home that no longer exists.
  - **`OATS_SPAWNER_HOME`.** Spawn hooks get the spawner's absolute home in this new reserved variable, unset when the spawner is `null`. It selects who signs the new identity. An inherited value is always dropped, and it never reaches the harness's pane. A capability should treat a missing value as a person's spawn only when the kernel lists `spawn-attribution`. The kernel reads the caller from its environment only, so a harness that strips its session's environment reads as a person's spawn.
  - **`attributedHuman`.** Status rows, local and remote, gain `attributedHuman`. It is the label of the human that the messaging capability attributed its served identity to, through an optional `identity.attribution` (`{mode, human: {id, label}|null, parent: {id}|null}`). Otherwise it is `null`. Only the messaging-layer capability's identity counts. The label is untrusted text, held to a waiting claim's message rule: one line of 1 to 200 characters with no refused character, else `null`. A malformed `attribution` reads as absent and never fails a row. `oats inspect` passes the identity through unchanged.
  - `spawnedBy` and `attribution` report: no kernel decision reads them.

  See [awebai/oats#1665](https://github.com/awebai/oats/issues/1665), [Spawned by](../desktop-cli-api.md#spawned-by), [Attributed human](../desktop-cli-api.md#attributed-human) and [Commands and hooks](../capabilities.md#commands-and-hooks).

## Changed

- **`oats onboard` names `oats.framework`'s setup expert, with a name for the workspace.** `next.spawn` picks the workspace's own `<workspace>-oats-setup-expert`, then the package soul `oats-setup-expert`, then the first soul by name that declares `oats.setup`; a soul is never chosen by its name alone. For the package soul it carries `--name <workspace>-oats-setup-expert`, or `<workspace>-oats-setup` when a soul of the workspace already holds that name, or no `--name` when that is taken too or the name would pass the 64-character instance-name limit; the text output says why. `next.spawn` stays a command string, and a long workspace name never makes onboarding fail ([awebai/oats#1665](https://github.com/awebai/oats/issues/1665); [`oats onboard`](../desktop-cli-api.md)).
- **`oats.setup` 2.10.0: SSH, signing and the DCO sign-off are optional.** `/oats-setup-expert` and `/oats-onboarding` no longer send every onboarding through `/oats-git-setup`: GitHub over https is enough for onboarding's reads, pushes and pull requests, and `/oats-git-setup` runs when Git access is broken or the person wants an SSH key, signed commits or the sign-off. For a new workspace whose setup expert carries `oats.onboarding`, `/oats-setup-expert` routes the use case, the first souls and knowledge to `/oats-tailor-workspace` ([awebai/oats#1665](https://github.com/awebai/oats/issues/1665)).

- **`/oats-agent-permissions` treats a checkpoint as an instance's own act.** A wake job on an instance's own home is no longer listed as an operator act. `oats schedule show` and `oats schedule host status` join the allow list as reads, and the `autoMode` entry tells the classifier that adding or removing such a job is normal. Installing the host's timer stays the operator's, and `--wake-*` on a spawn stays `ask`.

- **The macOS installers are built on `macos-15`.** GitHub retires `macos-14` on 2026-11-02, so `release.yml`, `build-installers.yml`, the macOS test run and the TUI's macOS tests move to it. The installers' targets and signing don't change, and the x64 installer is still cross-built and smoke-tested under Rosetta.

- **oats.engineering 1.18.0: a waiter sets a checkpoint before it waits on a child.** A developer, expert or maintainer that ends its turn to wait now sets a wake job on its own home, due when the result is overdue, so a stalled child no longer stalls it indefinitely. It sets one only where `wakeHold` reads `on-claims` or `not-exposed`, on a kernel with the feature `wake-hold`. Otherwise it hands the wait up, and where no level can set one the wait has no bound and the maintainer tells its human. See its [changelog](https://github.com/awebai/oats-engineering/blob/v1.18.0/CHANGELOG.md).

## Fixed

- **A pi home that may have no provider now gets a warning at spawn and start.** pi starts with no provider, takes its prompt and shows no error, so the home read as running while nothing happened. oats.core 2.12.0 warns when pi finds no provider in the environment of the command, and names the fix: log in, set a provider's API key, or pin the soul to another harness. The warning never refuses a start, and a slow or failed check says nothing. The check sees the calling process's environment, not the pane's, so a pi folder (`PI_CODING_AGENT_DIR`) or key that only the launch or the pane has can warn on a pi that works.
