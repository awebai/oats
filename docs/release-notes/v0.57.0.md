# OATS 0.57.0

2026-10-15

## Upgrade

- **Install the Desktop first and the CLI second,** as
  [Upgrading](../upgrading.md) says: a 0.56 Desktop refuses a 0.57.0 CLI. The
  0.57.0 Desktop accepts OATS CLIs `>=0.26.0 <0.58.0`.

- **A script that runs `oats worktree remove`** may now get
  `E_CHILDREN_RUNNING`: the tree is the work of an attached instance whose
  session is running or cannot be read. Nothing is removed, and no flag
  removes anyway: stop that instance (`oats instance stop <instance>`) or
  retire it, then remove again. **A script that attaches a spawn to a tree of
  no known instance** gets one `E_BAD_ARGS` naming every flag still missing,
  where it got a repository refusal and then `E_SPAWN_FAILED` on the retry.
  See Changed ([#958](https://github.com/awebai/oats/issues/958),
  [#964](https://github.com/awebai/oats/issues/964)).

- **A retire plan taken before the upgrade** is refused once by the 0.57.0
  kernel with `E_PLAN_STALE` and the fresh plan: the plan's revision now also
  binds the instances attached to each tree. Read the fresh plan and retire
  with it. See Changed ([#964](https://github.com/awebai/oats/issues/964)).

- **On Linux and Windows the Desktop's palette is Ctrl+Shift+K,** and
  Ctrl+Shift+P now opens Quick Open, from a focused terminal too. macOS keeps
  ⌘K and ⌘P. See Changed
  ([#1217](https://github.com/awebai/oats/issues/1217)).

- **To get the new provider versions,** pin `oats.framework: v1.10.2` and
  `oats.okf: v5.2.0` in your workspace and run `oats sync`. Instances already
  running keep what they were spawned with. See Provider updates.

- **Pin `oats.okf: v5.2.0` and run `oats sync`; only new spawns get the
  capability-owned harvest duty.** Existing homes keep their copied provider
  and instructions, including across session restarts. Deployments whose
  task briefings never mentioned harvests now propose eligible knowledge at
  finished tasks or PR hand-overs. Souls not ready for that must declare
  `knowledge: { harvest: off }`; consultation and working-memory upkeep
  remain. OATS >=0.49.0 is still required.

- **The official catalog's versions in this release** are oats.framework
  1.10.2, oats.okf 5.2.0, oats.aweb 1.27.3, oats.engineering 1.10.0,
  oats.cloning 1.0.1, oats.authoring 1.0.3, oats.jira 1.0.1, oats.linear 1.0.1
  and oats.apps 1.0.0.

## Added

- **`oats tui` stops, starts, restarts and retires an agent**
  ([#855](https://github.com/awebai/oats/issues/855)). With an instance
  selected, `X` stops it, `D` retires it, `S` starts it and `R` restarts it,
  each after a confirmation that opens with the focus on `Cancel`: the act
  takes a move (`Left`/`Right` or `Tab`) and a press of `Enter`, and pasted
  text never acts. The rules and the words are the Desktop's: a stop or a
  retire shows the kernel's plan first and applies exactly that plan, on
  this machine or on a registered one; a start or a restart uses the launch
  recorded for the agent. An act you sent runs to its end whatever
  `oats tui` does: closing the confirmation, quitting, a suspend or a signal
  never ends it, and when you leave while one runs a line on standard error
  says so. `tui.json` changes the keys (`stop`, `retire`, `start`,
  `restart`). See [the TUI page](../tui.md#stopping-starting-restarting-and-retiring).

- **Desktop: each team has its own page, with your instances on it.** Click
  a card under Workspace › Teams, or press Enter on its name, to open it. The
  page shows the team's card at the top (its default, description, who may
  join, address, problems and actions), then **Your instances on this team**:
  how many there are, how many run, how many are stopped or need attention,
  and on how many machines. Below that, each machine gets a card, with a
  table of its instances: the name, the soul, the state, when it was created
  and a Terminal button when it can be opened. A click on the name shows the
  instance in the roster. The page lists only your instances, the ones on
  this computer and on the machines you added to this workspace. Instances
  other people run on the team are not listed. Back or Esc returns to the
  board, on that team's card.

## Changed

- **The Desktop accepts OATS CLIs `>=0.26.0 <0.58.0`**
  ([#1211](https://github.com/awebai/oats/issues/1211)). The compatibility band
  admits 0.57; a 0.56 Desktop refuses a 0.57 CLI. No new gate on the band.
  `oats tui` runs the kernel it ships with and is held to the same band.

- **Desktop on Linux and Windows: the palette is Ctrl+Shift+K, and Quick Open
  is Ctrl+Shift+P and works from a focused terminal**
  ([#1217](https://github.com/awebai/oats/issues/1217)). Quick Open was
  Ctrl+P, which a focused terminal keeps for the program in it (shell
  history), so it did not open from there. **Ctrl+Shift+P changes meaning:**
  it has opened the palette since 0.30.3 and now opens Quick Open; the
  palette moves to Ctrl+Shift+K. While the palette is open, Ctrl+Shift+K
  moves down its rows and ArrowUp moves up. xterm sends nothing for either
  chord, so plain Ctrl+K and Ctrl+P still reach the program. A shortcut you
  set yourself is kept; when it is one of these two chords, the shortcuts
  editor shows the clash. A Quick Open shortcut you set yourself now works
  from a terminal too: if it is a plain Ctrl+letter, such as Ctrl+P, the
  program no longer gets that key, so choose a Ctrl+Shift chord. macOS is
  unchanged (⌘K, ⌘P). See
  [Desktop keyboard](../../packages/desktop/docs/desktop-keyboard.md).

- **An attached spawn on an extra tree derives its owner and its repository
  (#958).** `oats spawn <soul> --work attached --work-dir
  <home>/.work-<purpose>` was refused twice: first for the repository
  (`pass --repo`), then, with that given, for the owner (`--parent
  <instance>`). For `<home>/work` the kernel derived both. An extra tree of
  a home is that home's tree too, so the same command now spawns with
  neither flag: the owner is the instance in whose home the tree is, the new
  instance is its child, and its repository is the repository of the tree
  it is attached to (for an extra tree the one Git names for it, which can
  be another member repository than the owner's own). `--parent <owner>`
  and `--repo` given explicitly still work, so a command that passes both
  runs on this kernel and on earlier ones. The tree is an extra tree by the
  kernel's own test (a registered linked worktree in a home), never by the
  shape of its path. Nothing changes for `<home>/work`, and no flag, key or
  field changes.

  A tree of no known instance still needs both flags. Its refusal is now
  one, `E_BAD_ARGS`, and names every flag still missing: `attached workDir
  <path> is not a known instance's <home>/work or an extra tree of a known
  instance's home (<home>/.work-<purpose>), so neither its owner nor its
  repository is derived — pass both: --parent <instance> (the owning
  instance) and --repo <repository>`. With one of the two given it names
  the other. Before, the missing repository was refused first (`no
  repository for a attached instance — pass --repo (the work tree's owner
  records none)`), and the missing owner only on the retry, under the code
  `E_SPAWN_FAILED`. See
  [`attached`](../souls-and-instances.md#attached--another-instances-tree).

- **A tree that goes away says what it leaves its attached instances with
  (#964).** An instance can be attached to an extra tree of its owner as to
  the owner's `work/` (#958). Four things change for such a tree:

  - **A retire that re-homes an extra tree repoints its attached children**
    to the tree's new path, as it does for `work/`: only the recorded
    children the retire stopped, only once the tree is seen at its new path
    with nothing left at the old one, and only a link that is still the one
    the retire found. One that cannot be repointed is a warning in the
    receipt, with the command to do it by hand.
  - **A retire that removes a tree names the attached children it leaves
    without one.** A clean extra tree is removed, as before, and so is
    `work/` with `--discard-worktree`. The plan's note for the tree now
    names its attached children and says that their `work` link would then
    point at a path that is gone, and the receipt's `warnings` (and the
    summary) say so afterwards, naming each child, the tree and the link.
    Before, the plan and the receipt said nothing of them.
  - **An attached instance the retire does not act on is named too.** An
    instance that records the owner as its parent under a name that is not
    unique is listed under the plan's `ambiguous` and is never stopped, so
    its link is not repointed either. The plan's note for the tree it is
    attached to (an extra tree, or `work/`) now names it and says that its
    `work` link would then point at a path that is gone, and the receipt's
    `warnings` say so for each tree that was moved or removed, with the
    command to repoint the link by hand where the tree was re-homed. A
    `--self` retirement's receipt does not carry those warnings.
  - **`oats worktree remove` refuses a tree under a running session.** When
    an instance attached to the tree has a session that is running, or that
    cannot be read, the command answers `E_CHILDREN_RUNNING` before Git is
    asked anything: nothing is removed and the record is kept. `details` is
    `{purpose, path, children: [{instance, home, session}]}`, `session` being
    `"running"` or `"unknown"`. The message names each instance and the
    step: stop it (`oats instance stop <instance>`) or retire it, then remove
    again. The command stops nobody, and no flag removes the tree anyway. An
    attached instance whose session is stopped does not refuse: the tree is
    removed and the answer's `warnings` name the instance and its link.

  The new sentences are strings in arrays the plan and the answers already
  have (`notes`, `warnings`): no key, field or flag is new, and a tree with
  no attached instance is handled as before. `E_CHILDREN_RUNNING` is the code
  a retire already answers, there for a child it asked to stop and that did
  not; `oats worktree remove` answers it with `details` of its own and no
  `childrenStopped`. See
  [extra trees at retire](../souls-and-instances.md#extra-trees-at-retire)
  and [extra trees](../souls-and-instances.md#extra-trees).

- **Desktop: the Workspace › Setup tab reads as one column.** The List view
  puts what the workspace shares through Git above what lives only on this
  computer. It shows the same facts as before.
  - **Under the workspace's name**, a summary counts the members (and those
    that need attention), the packages and the state of the lock. The line
    under it says where the workspace is declared, for example "Declared in
    agents's oats-workspace.yaml at 1a2b3c4."
  - **An Overview** says that the host repository defines the workspace: its
    members and its packages. **For developers**, folded, explains the two
    links that make a repository a member: the host's workspace file lists
    it, and its membership file names the workspace back. It also says what
    each member state means. The Graph view shows the Overview too. The
    legend of badges is gone.
  - **Shared through Git** holds Members, Packages and Defaults. Only the
    host's row carries a tag, **Host** with its workspace file; the Member
    tag is gone from every row. A confirmed member shows a check and
    "confirmed". Any other state keeps its warning chip. In a wide enough
    window every row takes one line.
  - **This computer** holds the deployment's folder, settings, lock, lock
    file, CLI, instances and disabled souls, then the member clones, then the
    Machines box. Instances reads "3, 1 running". The Machines box no longer
    carries a "Not shared" tag; the zone says it.
  - **The Graph view** labels read "Shared through Git", "Members, latest"
    and "Packages, pinned", in sentence case.

- **Desktop: the Teams board is one calm column.** Shared teams, local teams
  and which teams each soul may join each have a heading and one line saying
  what they are. A team's card no longer lists its instances: it shows the
  team's facts in labelled rows (Default for, May join, Address), any
  warning with its fix, and a summary line at the bottom ("3 of your
  instances, 1 on other machines"). A click anywhere on the card opens the
  team's page, and each card is one Tab stop. Which teams each soul may join
  is now a table: the pattern, its default team, and the other teams it may
  also join. The type is calmer: fewer sizes and styles, no uppercase labels,
  and the facts that matter stand out by size and weight, not by new colours.

## Fixed

- **Released in 0.56.0, not noted there: the Desktop's terminals draw again
  after a GPU process restart
  ([#1190](https://github.com/awebai/oats/issues/1190), #1192).** After the GPU
  process restarted, xterm's shared glyph store went stale and terminals
  stopped drawing. They now draw again. A 0.56.0 or later Desktop has the
  fix.

- **A retire's recovery of a worktree carries a stopped cherry-pick, revert,
  rebase or merge, and the stash, in both ref formats
  ([#1038](https://github.com/awebai/oats/issues/1038)).** The recovery
  copied an operation's state as files of the Git directory. Three things
  were missing from it, and nothing said so:
  - where the repository stores its refs in the reftable format,
    `CHERRY_PICK_HEAD`, `REVERT_HEAD`, `REBASE_HEAD` and `AUTO_MERGE` are not
    files. The recovery had none of them, and its `git status` no longer said
    a cherry-pick or a revert was in progress. The stash's log is not a file
    there either: the recovery's `git stash list` was empty;
  - in both formats, the commit or tree those refs and `MERGE_HEAD` name is
    often in no branch (a commit reset away, a conflict's tree). The recovery
    named it without holding it, so `git cherry-pick --continue`, `git merge
    --continue` or a diff against `AUTO_MERGE` failed there;
  - a link at one of the copied names was left out when it led nowhere.

  The recovery now writes those four refs through Git at the same ids and
  holds every object they and `MERGE_HEAD` name. It stores the stash's
  entries again, oldest first, with their messages, so `git stash list`
  reads the same. A link is copied as the same link. A ref the source holds
  in the reftable format without its object cannot be written, and refuses
  the retire with `E_WORK_PRESERVATION_FAILED`, the home kept, as any
  recovery that cannot be made does. Which homes a retire recovers, the
  receipt and every code are unchanged.

## Provider updates

- **oats.okf 5.2.0:** the IMPORTANT inject block requires current instance
  knowledge and compulsory reading of `okf-propose`. The skill holds the
  bounded checkpoint procedure, promotion/search checks, proposal format and
  memory/concurrency gates. No harvest or proposal direction remains in the
  working instance's TASK brief. At most one proposal per completed task or
  PR hand-over, one harvester per instance, and no spawn under memory pressure
  or below 8 GB available; most checkpoints propose nothing. An unrelated
  harvester can outlive its proposer. These limits are instructions, not a
  scheduler or resource reservation.
- `oats okf status` exposes the duty written by the provider at spawn (`on`,
  `off`, or missing-state `unknown`). An unknown answer or failure permits no
  proposal. Shared inject/skill text explicitly exempts opted-out souls, and
  the harvester independently refuses their recorded source material. No
  kernel composition mechanism is added.

- **oats.framework 1.10.2: oats.core 2.6.1 and oats.setup 2.5.4.**
  Instruction text in two skills; no hook, command, schema or provider
  contract changes, and the capability floors are unchanged (oats.core
  `>=0.40.0`, oats.setup `>=0.30.0`).
  - `oats-operate` (oats.core) says that from OATS 0.57.0 `oats worktree
    remove` refuses a tree that is the work of an attached instance whose
    session is running or cannot be read (`E_CHILDREN_RUNNING`): stop that
    instance or retire it, then remove again, as the entry under Changed
    says ([#964](https://github.com/awebai/oats/issues/964)).
  - `oats-onboarding` (oats.setup) pins `oats.okf: v5.2.0` in its knowledge
    section and describes the harvest duty that oats.okf 5.2.0 gives every
    working soul: the compulsory `okf-propose` skill, `oats okf status`, and
    the soul's own opt-out, as the oats.okf entry says.
  - A deployment gets it by pinning `oats.framework: v1.10.2` and running
    `oats sync`. Instances already running keep the skills they were spawned
    with; new spawns get the new ones.
