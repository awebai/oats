# OATS 0.69.7

Unreleased

0.69.7 stops a scheduled wake from answering a dialog nobody saw: a wake now
holds while a permission prompt or a question is known to be open. A turn that
ends in a provider error now shows on the instance, every session start and
restart holds the home's lifecycle claim, and a spawn and a retire no longer
leave a half-written `instance.json` for a reader to catch. It is also the
bridge for the move to the `oats-project` organisation: the two spellings of a
moved repository are one repository, and a deployment that changes no string
behaves as before. The catalog moves to oats.framework 1.17.0.

## Upgrade

- **Either order of the Desktop and the CLI works.**
  [Upgrading](../upgrading.md) installs the Desktop first, and a host that
  installed the CLI first is fine too: the 0.69.7 Desktop accepts OATS CLIs
  `>=0.26.0 <0.70.0`, and so does the 0.69.6 Desktop.
- **Package move:** the official catalog pins oats.framework 1.17.0, with no
  change to its OATS floors. A deployment takes it with `oats sync`. Running
  instances keep the modules they were spawned with: new spawns get the new
  ones, and a stopped home moves with `oats instance upgrade`. A Claude home on
  an older oats.core reads `wakeHold: "unknown"`, which a waiter treats as not
  covered, until it moves. Its wakes still hold on its claims, but its
  `permission` claim comes from `Notification` alone, about 6.5 s after the
  dialog opens.
- **Until a deployment runs this kernel, run no wake jobs on a home that can open an approval or question dialog.** A wake's Enter can approve a command or answer a question nobody saw. This release holds those wakes where claims exist; it doesn't reach the gaps listed under Fixed, so the same care applies to them afterwards.

- **Keep `@awebai/oats` installed: this release installs over it, under the same name.** OATS is moving to the `oats-project` organisation in stages, and this release is the bridge. Nothing asks you to change a string, and a deployment that changes none behaves as before. `npm rm -g @awebai/oats` leaves running sessions without their kernel until they restart, when a start rewrites each home's `.oats/bin/oats` and hooks, and the host's schedule unit stays on the old path until `oats schedule host install` runs ([The move to the oats-project organisation](../upgrading.md#the-move-to-the-oats-project-organisation)). Installing the other name with `--force` and then removing the old one also deletes the `oats` command.

## Added

- **Spawn and launch hooks get `OATS_HARNESS_EXECUTABLE`.** This is additive, for every harness: the absolute real path of the executable the pane will run, found the way the pane finds it, and set the same way in a preview. It is reserved, so a launch configuration's `env` or a trigger cannot set it, and it is absent where that lookup has no answer, including a bare harness name on a spawn with `--no-launch`. A bare name can still be replaced on the session the launch gets, and a symlink can move under any path; that launch warns, in its answer and as a `launch-warning` event in the home, naming both real paths. oats.core uses it for the Claude Code version check of the failed-turn report (Fixed, below), so on a kernel without it Claude's failed turns stay unreported ([awebai/oats#1667](https://github.com/awebai/oats/issues/1667)).

- **`wakeHold` on `oats session inspect --json` says whether this home is covered.** Feature `wake-hold` says the kernel holds; `wakeHold` says whether this home's dialogs become claims: `on-claims`, `not-exposed`, or `unknown`, which a waiter treats as not covered. It's on every successful result, a stopped, never-launched or missing home included, and it covers the kernel's wake delivery only, not mail ([Inspect, input and attach](../execution-targets.md#inspect-input-and-attach)). A spawn or launch hook gives the answer as `dialogClaims: "reported" | "none"`, recorded per capability as `instance.json.dialogClaims`; the kernel names no harness, and a hook that runs and answers nothing removes its entry ([Commands and hooks](../capabilities.md#commands-and-hooks)). oats.core 2.11.0 answers `reported` only when it wrote its hooks and the Claude Code this launch runs fires them. An older kernel ignores the key, and a home on an older oats.core reads `unknown` until it's upgraded or respawned.

- **The old and the new spelling of a moved repository are one repository.** Seven repositories are moving, and wherever the kernel compares two keys it now treats both spellings as the same repository: the backlink, `clones:`, a clone's remotes, a home's recorded soul and modules, `from:`, a `git:` package source and a server's `workspaceKey`. The Desktop does the same for its machines, schedules and catalog rows, and the release lane's okf mirror check accepts a clone repointed to the new URL. It compares and never rewrites: every key stays as declared or recorded, in each JSON answer, cache directory and lock ([Moved repositories](../workspaces.md#moved-repositories)). The table is closed at these seven, and the old names are never reused: a repository at one ends GitHub's redirect for good.
- **`oats version --json` has a `package` field**, the npm name this kernel was installed under. `name` stays `@awebai/oats` under either name, because released readers refuse any other value.
- **The kernel knows its own npm name.** `oats update`, `oats server connect` and the pi bridge use the name the kernel was installed under, so an update never crosses from one name to the other. Clients and the pi bridge accept `@awebai/oats` and `@oats-project/oats`.

## Changed

- **Every session start and restart now holds the home's lifecycle claim, so it can no longer race a retire.** `oats session start`, `oats session restart` and a scheduled start take the claim that a retire, a stop, an upgrade and a resume already hold, for the whole start. A restart holds one claim from before its stop to after its launch, so no retire runs between the two. Before this, a start could begin beside a retire and leave a session running in a home being removed. New answers, each given before anything is stopped or started:
  - A start or restart beside a retire answers `E_INSTANCE_RETIRING`. Beside a stop or an upgrade it answers `E_LIFECYCLE_BUSY`, with `details.holder` and `details.action`.
  - A retire, a stop apply or an upgrade apply that arrives while a start runs answers `E_LIFECYCLE_BUSY` with a new value, `details.action: "start"`.
  - A scheduled start refused this way is recorded as a skip. It holds no launch slot and is retried at the job's next due minute.
  - A start or restart whose claim cannot be written answers `E_LIFECYCLE_FAILED` before any effect, where it used to go on. The answer names the claim and the reason; the remedy is to make the claims directory (`<instances>/.oats-retirement/claims/`) writable.

  A path with no `instance.json` it can read is no home to hold: a start or a resume of it takes no claim and writes nothing beside it. A resume of one now answers `E_RUNTIME_ENDPOINT_UNKNOWN` or `E_UNIDENTIFIED_INSTANCE_HOME`, where it left `.oats-retirement/` in the parent directory, or answered `E_LIFECYCLE_FAILED` when it could not. Two starts of one home still answer `E_SESSION_START_BUSY`, and a resume beside a resume still answers `E_LIFECYCLE_BUSY`. A client gates on the new feature probe, `lifecycle-claim-start`. A kernel without it reads a `start` holder as a retire, so its stop or upgrade beside a new start answers `E_INSTANCE_RETIRING`, still before any effect ([awebai/oats#1602](https://github.com/awebai/oats/issues/1602); [Commands that meet on one home](../desktop-cli-api.md#lifecycle-pairs)).

- **The development-prompt guidance names the approved route.** `/oats-host-delivery` and the configuration and integrations guides now name `settings.oats.aweb.claudeChannelMode: approved` as the way to stop Claude's development-channel prompt. `delivery: session` stays a supported value.

- **The `launchPromptAnswers` messages name one way to stop Claude's development-channel prompt.** They now advise `settings.oats.aweb.claudeChannelMode: approved` alone, matching [oats-aweb#162](https://github.com/awebai/oats-aweb/issues/162). `settings.oats.aweb.delivery: session` stays supported.

- **`E_SOUL_UNKNOWN` names the members it could not confirm:** how many, each key with its reason and detail, and what to do. `details` gains `unconfirmed`, only when there are any.
- **`E_CLONE_MISMATCH` gives the fix** for a Git repository with the wrong remotes, if it is a clone of that member: the `git remote` command to run, and that a second remote passes too.

## Fixed

- **A spawn no longer shows a half-written `instance.json`.** `oats spawn` wrote the home's record in place, the last time after the session had started, so a status, a Desktop listing or a start reading it at that moment could report the home as unreadable. Every write of the record during a spawn now goes through a private file renamed over it, so a reader sees the record before or after a write, never part of one. The record's bytes and mode are unchanged. A spawn killed during such a write leaves `instance.json.tmp-<pid>` beside the record, which a retire does not count as a change to the home ([awebai/oats#1659](https://github.com/awebai/oats/issues/1659)).

- **A retire no longer leaves another home's `instance.json` half written for a moment.** A retire's lineage repair rewrote the records of the retiree's orphans in place, and a sibling's session may be running, so a status, a Desktop listing or a start reading the record at that moment could report the home as unreadable. It now replaces the record whole, and a record that cannot be written refuses the retire with the same answer as before. One exception stays: on any failure of the atomic write (a home that refuses the private file, a refused rename, a full disk), the repair writes in place as it always did, and that write's own failure is the answer. So a retire works wherever it did before, and a reader in that case can still catch a torn record. Every kernel write of a home's record now keeps that record's mode: under a umask of 002 a start or a restart no longer moves it from 0644 to 0664 ([awebai/oats#1660](https://github.com/awebai/oats/issues/1660)).

- **The Desktop and the TUI now say that nothing was started when a stop, an upgrade, a retire or unfinished cleanup refuses a start or restart.** A kernel answers `E_LIFECYCLE_BUSY` beside a stop or an upgrade, and `E_INSTANCE_RETIRING` beside a retire or for a home with cleanup to finish. Both clients read those answers as uncertain, though the kernel gives them before any launch and before a restart's stop. They now read them as refused and word them for a start, with the kernel's own line under the sentence. A restart says that nothing was stopped or started. Only a holder that is running is offered waiting. This needs the answering kernel to list `lifecycle-claim-start`: a local kernel or a server's host without it, or a host whose features aren't known, keeps the uncertain reading ([awebai/oats#1666](https://github.com/awebai/oats/issues/1666); [Commands that meet on one home](../desktop-cli-api.md#lifecycle-pairs)).

- **A turn that ends in a provider error now shows on the instance.** A refusal, an exhausted rate limit or a dead credential ended the turn with the error in the pane and nothing anywhere else, so an instance could sit idle for days while whoever waited on it heard nothing. On Claude Code 2.1.78 and later (oats.core 2.11.0, its `StopFailure` hook) and on pi (`@awebai/oats-pi`), the instance now sets a needs-input claim, `Turn failed: <the error>`, on `oats status`, Desktop and the terminal UI. It shows only once the harness has stopped retrying, so a transient error it recovers from raises nothing, and it clears on the instance's next turn. On Claude, a provider's refusal, a dead credential and a server error raise an `attention` claim. Error class `rate_limit`, and any class not known to be free of a dialog, including one Claude adds later, raises `question`, because Claude's usage-limit screen is a menu an Enter answers. An API-key home has no such menu, but its `rate_limit` reads `question` too. A claim doesn't cover every Claude dialog: the limit menu fires no hook of its own, and choosing "Stop and wait" leaves the claim until the next prompt. The claim uses the existing `oats instance waiting` path; pi's producer id is `oats.pi`. Codex still reports nothing: a provider error fires neither its `Stop` hook nor `notify`, so no hook can see it. A pi before 0.80.4 reports nothing either, and neither does a Claude Code before 2.1.78: that version refuses a settings file naming the hook, so oats.core asks the executable the launch will run and writes the hook only on a clear answer of 2.1.78 or later ([awebai/oats#1667](https://github.com/awebai/oats/issues/1667)).

- **A scheduled wake holds while a permission prompt or a question is known to be open.** A wake's Enter could approve a prompt or answer a question nobody saw. A wake reaches a running session as a paste and an Enter, and an open dialog took that Enter: the message never reached the model, and the schedule recorded `delivered`. A wake now reads the home's claims immediately before it types, and sends no key while the home has a live `permission`, `question` or unknown-reason claim, or while the claims can't be read and trusted. An `attention` claim alone holds nothing. A held wake stays pending and tries again at every tick until nothing holds it, then delivers once. It takes no slot, and it has no expiry: the kernel never sends a key, and never drops the message, because a hold ran long. `lastRun` shows `reason: "waiting-on-you"`, `pending: true` and `held: {since, claimReason, producer, unreadable?}`, and one `wake-held` event marks the start of a hold ([A held wake](../schedules.md#a-held-wake); [awebai/oats#1670](https://github.com/awebai/oats/issues/1670)). `delivered` keeps its value and is now documented for what it means: submitted, which doesn't mean the model received the message. The kernel's rule changes with this: a claim authorizes nothing, and it may only withhold an automated keystroke. `oats session input` is unchanged.

  What this leaves open ([What a hold leaves open](../schedules.md#what-a-hold-leaves-open)):
  - Harnesses with no claims stay exposed. pi homes read `unknown`: an extension can open its own dialog, and the kernel can't see which load.
  - A dialog that opens before the Enter is still answered, whether it opens between the read and the Enter or in the lag between a dialog opening and its claim being written. A `permission` claim took 395 to 514 ms from the dialog on screen, median 433 ms over 10 samples, on Claude Code 2.1.308 on one host, against about 6.5 s from `Notification` alone. It's a window that still exists. Lag for an `elicitation_dialog` question, a subagent's dialog and other Claude Code versions isn't measured.
  - A dialog that fires no hook has no claim, so claims can't cover every Claude dialog: the `/rate-limit-options` menu fires no hook of its own (measured on Claude Code 2.1.308), and `pro-trial-expired` opens the same way at startup, with no failed turn behind it.
  - `oats session input` run by a script or an agent can answer a dialog. Don't run it at a session that may show one.
  - The aweb host wake broker types on its own path, joined teams included, and isn't held.

  A claim can also outlive its dialog, and there's no expiry. Claude Code fires no hook on Esc or "No" (measured on 2.1.308), so a refused dialog's claim stays until the next prompt, and on an idle home a wake holds behind it. A long hold is a reason to look: send a prompt in that session, or run `oats instance waiting clear --producer oats.core --home <home>`. An approved subagent's dialog can leave its claim until the main thread's next event.

  oats.core 2.11.0 also sets the `permission` claim from Claude Code's `PermissionRequest` as the dialog opens, where `StopFailure` is written too. `Notification` stays as the fallback.

## Provider updates

- **oats.framework 1.17.0: oats.core 2.11.0, oats.setup 2.9.6.** oats.core's Claude hooks report a turn that ends in a provider error, and set the `permission` claim as a permission dialog opens, on a Claude Code that fires those hooks. `/oats-operate` says what a wake's hold covers and what it leaves open. oats.setup's `/oats-host-delivery` names the approved route for the development prompt, and `session` leaves its hand-back choices for Claude seats; `delivery: session` stays supported. The hooks need OATS 0.69.7: on an older kernel oats.core writes neither of them. The floors and the other capabilities are unchanged.
- **Upgrade:** `oats sync` locks it once the workspace or the catalog pins `oats.framework: v1.17.0`. New spawns get it, and a stopped home moves with `oats instance upgrade`, from OATS 0.68.0.
