# OATS v0.24.0 — retained execution first cut

These notes describe the planned kernel/Pi/Desktop **0.24.0** cut. They do not
assert that its tag, packages, installed deployment or real-model acceptance have
already completed. The release owner publishes only the reviewed, packaged and
qualified combination; source commits and inert fixtures are not a usable-session
claim. No release version or provider pin is fabricated by these notes.

## Source-complete preparation and retained execution

- Public `prepare --request` accepts one bounded nonsecret JSON input through the
  shared strict reader and preparation validator. Source, deployment, work target
  and workspace/standalone context remain distinct; no inherited current config
  fills missing source authority. Exact executable approvals remain explicit.
- Fresh onboarding detects existing managed state without deleting it. Inspected
  deployment/work-directory replacement or later provisioning requires reinspection;
  ordinary project edits remain allowed. This is a point-in-time check, not a lock
  against concurrent writers or a general migration engine.
- Captured instructions/resources, source identity and provider bindings remain
  usable from retained bytes after the source is removed. Portable home/work
  boundaries preserve canonical aliases and immutable source custody.
- Captured primary/helper public start and restart use retained selections and
  indexed incarnation/intent custody. A helper is launched through its exact
  **SOURCE helper edge**, not by treating a dedicated helper ID as a persistent
  source. Same-ID uncertainty is held rather than redispatched; failure receipts,
  pending allocation, native history and cleanup obligations are preserved.
- Provider execution keeps generic invocation, same-owner binding and explicitly
  opted-in source-receipt inputs separate. Missing/invalid current transport does
  not silently become legacy authority. Source-owned completion is not transferred
  to a helper or invented instance.

## Backends and first-cut Pi profile

The shared native path supports the existing tmux and Herdr adapters. Herdr adapter
selection understands exact protocols20 and22; it does not negotiate an unknown
protocol, relabel a retained target or fall back to tmux. Public caller/schema support
and the actual explicit server endpoint must match the selected protocol. API2
availability/readiness-not-checked is not server, model or provider health.

The first-cut Pi host target is explicit print-mode retained execution, not unrestricted
interactive/plugin parity. Its packaged entrypoint, parser/native services, selected
curriculum eligibility and external session-directory identity witness must be complete
before that selected profile is usable. An absent/incomplete witness or required
runtime/bridge/plugin contribution remains a refusal, never a dummy success or a
silently dropped requirement.

The user's already-authenticated harness retains its normal native profile,
auth/helpers/OAuth/model configuration. This cut does not introduce an auth-file
selector, credential inspection/copy, provider/key allowlist, empty production store
or substitute profile. Strict selected curriculum and controlled native history are
separate from that authentication boundary.

## Desktop CLI compatibility

Desktop's released-CLI band extends to `>=0.22.0 <0.25.0`, including0.24.x. Desktop
CLI API remains **v1**; prereleases, wrong probe/API versions and failed probes still
refuse. Optional execution/remote capabilities are advertised separately—version
acceptance grants none of them. Observation-only degradation remains available when
no compatible CLI is verified.

This version-band update is not complete captured UI, Herdr0.9 terminal attachment,
plugin, scheduling, retirement/recovery or all-platform Desktop parity. The existing
release lane aligns kernel, Pi and Desktop manifests/locks together, retains package
and installed-artifact checks, and keeps Desktop artifact gates before tag-workflow
publication. Ad-hoc signing is not Developer ID notarization.

## Explicit limits and safe adoption

- No automatic reconstruction/in-place migration, old-state deletion, role-library
  adoption or new operator-root/bootstrap-helper grammar is introduced.
- Selected unsupported managed/plugin/bridge or interactive profiles stay held.
  Default-OKF worker/capture/learning claims require the actual selected launcher,
  real turn, captured result and accepted fresh-reader evidence—not seeded transcripts
  or a successful scaffold. Git knowledge delivery remains PR-only.
- Public captured retirement, wake and recovery remain separately bounded work;
  do not strip selectors, use a legacy/private fallback, or delete an uncertain home
  to simulate completion. Preserve old sessions, identities, work and receipts.
- No private-aweb human/admin/privacy qualification follows from backend/model
  success. External authority evidence cannot be fabricated by the framework.
- Provider versions, catalog refs and compatibility floors must identify real
  reviewed/published artifacts. This note does not finalize or repin them.

Use a new explicit deployment/source request and the actual installed public contract.
Do not assume parked source candidates or optional helper packages are published.
Final release evidence must distinguish package installation, native dispatch, actual
model/task completion, provider-worker behavior and learning; a narrow first-cut pass
must not be presented as full parity.
