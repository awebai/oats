# OATS 0.69.10

0.69.10 moves the official catalog to `oats.framework` 1.20.0 (the setup
expert talks to a newcomer in everyday words, and puts a local-only project on
GitHub on the person's yes) and `oats.aweb` 1.34.0 (messaging only: aweb tasks
are taught only where `oats.aweb-tasks` is composed; tested with aw 1.36.53).
Getting started now sets up a new workspace with no aweb sign-in, and gives its
agents aweb's task list unless they already use a tracker. A repository
reference may now be an `ssh://` address with a user. A local schedule accepts
any soul the workspace offers.

## Upgrade

- **Either order of the Desktop and the CLI works.**
  [Upgrading](../upgrading.md) installs the Desktop first, and a host that
  installed the CLI first is fine too: the 0.69.10 Desktop accepts OATS CLIs
  `>=0.26.0 <0.70.0`, and so do the 0.69.9 and 0.69.8 Desktops.
- **Package moves:** the official catalog pins oats.framework 1.20.0 and
  oats.aweb 1.34.0, with no change to their OATS floors (oats.aweb keeps aw
  >=1.36.33, and is tested with 1.36.53). A deployment takes each by raising
  its own pin (`/oats-package-pins`), then `oats sync`. Running instances keep
  the modules they were spawned with: new spawns get the new ones, and a
  stopped home moves with `oats instance upgrade`.
- **With oats.aweb 1.34.0, aweb tasks come only from `oats.aweb-tasks`.**
  oats.aweb no longer mentions task coordination in anything it puts into a
  home. A deployment that uses aweb tasks composes `oats.aweb-tasks` (for
  example `defaults: { tasks: { oats.aweb-tasks: { from: package } } }`);
  without it, its agents get no task guidance after the upgrade. The rule that
  `aw lock` and `aw roles` stay outside OATS moves with it.
- **An `ssh://user@host/...` repository reference is refused by older
  kernels.** Before any member uses the form in a shared `oats-workspace.yaml`,
  upgrade every deployment of that workspace to 0.69.10: an older kernel
  refuses the file.

## Changed

- **`oats.framework` 1.20.0 ships the setup expert's newcomer changes.** `oats.setup` 2.11.0's `/oats-setup-expert` talks to a newcomer in everyday words, and puts a project that lives only on the person's computer on GitHub when they say yes, after checking for secrets and for files GitHub refuses (#1710, #1711, #1712). `oats.onboarding` 1.1.1's `/oats-tailor-workspace` uses the same plain words, and keeps the tasks default a new workspace was given rather than adding a second tasks provider (#1710, #1716). No command they name needs a newer OATS than each capability already admits ([awebai/oats#1665](https://github.com/awebai/oats/issues/1665)).
- **`oats.aweb` 1.34.0: messaging only; aweb tasks by opt-in.** Nothing oats.aweb puts into a home names the task layer, `aw task`, `aw work`, `aw lock`, `aw roles` or task claims: not the inject, not the `Comms:` line, not its skills. `oats.aweb-tasks` teaches them, and its inject and skill open with the workspace's opt-in. The inject gives the whole messaging loop for mail and chat ([awebai/oats-aweb#186](https://github.com/awebai/oats-aweb/pull/186)).
- **`oats.aweb` 1.33.3: tested with aw 1.36.53.** `AW_TESTED` moves to 1.36.53, npm's `latest` now that aweb Cloud serves invite preview; the floor stays 1.36.33. A resident create whose API key is refused can be rerun under aw 1.36.53. The unread-count readiness warning follows whether health publishes now, inside readiness's time budget, and the alias-conflict refusal names its remedy without a ticket or kernel version ([awebai/oats-aweb#179](https://github.com/awebai/oats-aweb/pull/179), [#182](https://github.com/awebai/oats-aweb/pull/182), [#184](https://github.com/awebai/oats-aweb/pull/184)).
- **The setup expert talks to a newcomer in everyday words.** `oats.framework`'s `/oats-setup-expert` and `/oats-tailor-workspace` assume the person may not know what a repository, Git or a terminal is. They ask about the person's project, their code on GitHub and the group their agents talk in, each question with a recommended default, and avoid OATS's and Git's own words. A command, a change or a link is shown only where the person must act on it, introduced in a plain sentence; the setup briefing's rules on what the person types and on showing a change before a push come first. A newcomer test run found the setup expert's first question saying "agents can only work in a repository the workspace lists as a member" ([awebai/oats#1665](https://github.com/awebai/oats/issues/1665)).
- **The setup expert puts a project that lives only on the person's computer on GitHub, on their yes.** OATS reads a workspace's members over Git, so `/oats-setup-expert` step 3 now first handles a folder whose code is on no GitHub repository. A folder inside a repository that is already on GitHub is not copied: the person is asked whether that repository is the project to add. Before asking, it finds what would be pushed without changing the folder:
  - for a new repository, the files Git would take, without dependency and build folders or files too large for GitHub;
  - for a repository with commits, its current branch and its history, with its whole history searched for secrets.

  Files named like a secret or holding a private key are certain: left out of a new repository, and a reason not to push one whose history holds them. Other files whose content may hold a password or key are shown to the person by name, and they choose. The scans print file names only, never a secret's value. It shows the person the files, what it leaves out, and whether the project's own automations would start. It then proposes a private repository under their GitHub login, named after the folder. A new repository is created with the secrets left out and the staged files checked against what was shown. Where a secret is in a repository's history, nothing is pushed: the person chooses a fresh copy or keeping it local. On a no it creates nothing and says the agents can't work on that project until its code is on GitHub. A newcomer test run found the setup expert improvising this step ([awebai/oats#1665](https://github.com/awebai/oats/issues/1665)).
- **The local-only project step cleans up and checks a repository's history for files GitHub refuses.** `/oats-setup-expert` step 3's previews now remove their temporary scratch repository. For a repository with commits, it lists by name any file over 100 MiB in its branch's history, since GitHub refuses that push, and then pushes nothing and offers a fresh copy of the current files or keeping the project local ([awebai/oats#1665](https://github.com/awebai/oats/issues/1665)).
- **Getting started speaks to a newcomer and asks less.** These changes come from newcomer test runs of `oats-getting-started` on fresh machines.
  - **Wording:** the skill talks in everyday words (projects, code, folders, "the setup assistant") and keeps file paths, commands, error codes and raw output to itself.
  - **Step 1** first runs step 2's read-only checks, then asks three things: what the agents should help with, which projects, and whether this is a fresh start or joining someone's setup. It proposes everything else as defaults: the name (from the project's), where the shared setup lives and under which GitHub owner (from the project's repositories or the login), the messaging account, the folder where the agents live (default `<home>/Agents/<workspace>`) and the Desktop. It doesn't ask for the harness. When an answer changes a default, the skill derives them again and shows the final values.
  - **One confirmation covers every change to the person's computer** that the checks found needed: the installs, the PATH line, the Claude channel plugin, folder trust, the Desktop and any missing system package. The list names each change by what and where, Git's own settings included. A new private GitHub repository for a new workspace goes on the same list, and so does the name on the first commit when Git has none, so neither is asked again later. The skill never runs `sudo` for anything outside that list. When the agent's own permission check refuses a step, the skill never runs it another way: it asks the person once, by name, retries once, and otherwise says what is missing. The person never types a command with `!`, and types one in a terminal only for a password or login when no window can be opened for them.
  - **The Desktop downloads in the background** right after the GitHub login, with its checksum and attestation, while the CLI installs. It is installed only once all three have passed.
  - **Linux:** the Desktop's system libraries are checked before the install. A missing ALSA is a system package to confirm; a missing FUSE 2 installs nothing, and the Desktop starts with `--appimage-extract-and-run`.
  - **Minimums:** a new workspace needs `oats.framework` 1.19.0 or later, whose setup expert attaches the person to the workspace's messaging account (1.18.0 before), and its `oats.aweb` pin is never below 1.33.1, the release whose invite works after a no-sign-in setup.
  - **An existing workspace** names its setup expert and the machine's messaging root after the machine's short hostname, with a suffix hashed from the machine's id (never the id itself) for hostnames many machines share. From `oats.aweb` 1.33.1 the invite answer's `awebUrl` is the service URL the join needs; without it the join takes the service from the invite, and stops if it can't.
  - **The hand-off** tells the person to switch to the Desktop and click the setup assistant, since it has already started and will ask them its first question there. Attaching the person to the workspace's messaging account happens later in the setup, with the setup expert ([awebai/oats#1665](https://github.com/awebai/oats/issues/1665)).
- **Getting started creates a new workspace's aweb account and team with no sign-in.** By default, `oats-getting-started` no longer asks the person to sign in to aweb in their browser. Step 1 names the account `N` (default `<workspace>-oats`) and its root `A` (`<workspace>-root`). The skeleton's team is `default:N.aweb.ai`. Step 9 creates the account and team with `oats aweb setup --soul S --username N --name A --label L`, plan first, and goes on only when the answer's `result.team` equals that line and `result.membershipVerified` is true. When `N` is taken, the person picks another, the team line is changed, committed and synced, and the signup runs again. The person is told the team is on an aweb account created for the workspace, which they attach themselves to later in the setup, with the setup expert (`/oats-tailor-workspace`). Signing in with `aw auth login` and `aw team ensure`, for a team owned by their own aweb account from the start, is now the optional step 5 ([awebai/oats#1665](https://github.com/awebai/oats/issues/1665)).
- **Getting started: a new workspace's agents track work in aweb's task list by default, unless the person already uses a tracker.** With aweb, `oats-getting-started` now writes `tasks: { oats.aweb-tasks: { from: package } }` into a new workspace's `defaults`. It writes `tasks: none` when the person's projects already use a tracker, and the setup expert then connects that tracker with them. The skill finds a tracker rather than asking about one: a GitHub repository with an issue updated in the last 180 days and not opened by a bot (issues switched on but unused don't count), a tracker the person names, or ticket keys such as `ABC-123` in recent branch names or commit subjects. It asks one prefilled question only when unsure: ticket keys the person didn't name, a project kept somewhere other than GitHub, or an issues check that failed. The setup expert's tailor skill keeps that default rather than adding a second tasks provider. The hand-off names the choice and how to change it, and with a tracker asks the person to leave aweb's task list empty, because one task there opts the whole team in ([awebai/oats#1665](https://github.com/awebai/oats/issues/1665)).
- **Getting started: pi's aweb extension comes without its skills.** After `pi install npm:@awebai/pi`, `oats-getting-started` sets the extension's entry in pi's `settings.json` to `"skills": []`, so pi's aweb extension puts no machine-wide skills on the computer; each agent gets its skills from its own capabilities ([awebai/oats#1665](https://github.com/awebai/oats/issues/1665)).
- **An `ssh://` reference with a user is accepted wherever a repository reference is.** `oats-local.yaml` (`workspace`, `standalone`), `oats-membership.yaml` (`workspace`) and `oats-workspace.yaml` (`members`, `stores` and an external soul's pinned `source`) now accept `ssh://<user>@<host>[:<port>]/<path>`, with a user of letters, digits and `. _ ~ -` that doesn't start with `-`, the way the kernel already read it and the way `git@host:path` always was. Before, `oats onboard --workspace ssh://user@host/path` was refused with `E_WORKSPACE_SCHEMA`, while the refusal showed the reference without its user, so it looked valid. A password (`ssh://user:password@…`, percent-encoded or not), an empty user and a second `@` in the host or path stay refused, so in a pinned source the last `@` is always the pin. A package's `git:` reference keeps its own grammar. Existing files need no change ([awebai/oats#1665](https://github.com/awebai/oats/issues/1665)).
- **An operator command run without `--soul` says what the chosen soul is for.** `oats <namespace>` from a deployment directory, with no `--soul`, now prints `oats <namespace>: using the settings and teams of soul <member>/<soul>, the first soul by name in this deployment that provides "<namespace>"; pass --soul <name> to use another` on stderr, in place of `no --soul given; running as soul …`. Which soul is chosen is unchanged ([operator commands](../capabilities.md)). The old line read as if an unrelated soul were acting: a newcomer test run on a fresh workspace saw `oats aweb` say it was "running as" the knowledge-theory expert ([awebai/oats#1665](https://github.com/awebai/oats/issues/1665)).

## Fixed

- **A local spawn schedule accepts any soul the workspace offers.** `oats schedule add` and `update` refused a local spawn job whose `agent` is a member or package soul this deployment had never spawned (`agent: no soul named "<soul>" under <root>/agents`, `E_SCHEDULE_INVALID`), although `oats spawn` resolves it, and a run always resolves its soul as `oats spawn` does. Such a job is now checked by `oats spawn <agent> --preview` with the job's own `launchConfig`, `harness`, `model`, `backend` and `repo`: a job whose preview fails is still refused with `E_SCHEDULE_INVALID`, field `agent`, now carrying spawn's own message and its code in `details.code`; a soul already spawned here is accepted without the preview, as before. `oats schedule test` reports such a soul as resolving (and now passes the job's `repo` to its preview), and the job runs at its due minutes and through `run-now` ([Kinds](../schedules.md#kinds)).
- **`oats schedule reconcile` keeps a spawn attempt it cannot attribute.** When a spawn job's result was never recorded and its `agent` is a qualified or package soul, whose runs spawn names after the soul's stem, reconcile no longer takes the missing `<agent>-<purpose>-<minute>` home as proof that nothing launched: it answers `unknown` and keeps the attempt and its slot until you check by hand and run `reconcile <id> --clear`. Before, it recorded `launch-failed` and freed the slot while the run's instance could still be running. A local or workspace job whose `agent` is a member soul under `agents/` is reconciled as before ([What a run reports](../schedules.md#what-a-run-reports)).
- **Getting started: the steward's global address names the oats.aweb release that carries its route.** On a machine found-list, the skill gated the steward's global address on oats.aweb 1.34.0, which ships without the resident root route; it now names 1.35.0. On 1.34.0 the plan already fell back to a local team identity, so only the stated version changes.
