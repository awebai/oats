# OATS 0.49.0

2026-10-08

## Capabilities set up the Git trees the kernel creates (#796)

- **Capabilities can set up the Git trees the kernel creates: the
  `worktree` hook event, feature `worktree-event` (#796).** A capability
  manifest may declare `hooks.worktree`, as a command string or
  `{ command, required }`. It fires once for `./work` of a `work: worktree`
  spawn (after the spawn hooks succeed, inside the spawn's transaction) and
  once for each tree `oats worktree add` makes. It never fires for another
  work mode, for a tree made with raw Git, or at start, restart, resume or
  retire. It runs differently from other hooks, which are unchanged:
  - its cwd is the new tree, stdin is `/dev/null` and it has no terminal;
  - it runs detached, in its own process group, with a fixed 30-minute
    timeout that ends the whole group;
  - its output goes to `<home>/.oats/logs/worktree-<purpose|work>-<cap>.log`
    (0600, truncated per run), and on `oats worktree add` also to stderr,
    never stdout (a caller that closes its pipes only stops that copy: the
    add completes); receipts, records, markers and events carry the log's path
    only, never its content;
  - the result is the exit status; of its last JSON line only `warning` is
    read, and `env` is a contract error.

  `required: true` is now valid on `spawn` and `worktree`. A required
  `worktree` hook that fails or times out fails the spawn through the
  existing rollback, or makes `oats worktree add` remove the tree and delete
  the branch while it is still where `add` created it. A spawn's rollback
  deletes the home that held the hook's log, so its answer names no log path
  (`details.hooks[].log` is `null`); `add` keeps its logs. A non-required one
  warns, and the tree is kept. The kernel runs only the hooks of the
  instance's own capabilities: no file in the repository is run or trusted.
  See [capabilities.md](../capabilities.md#the-worktree-event).

- **The hook environment of the event.** Besides the standard hook variables,
  a `worktree` hook gets `OATS_TREE`, `OATS_TREE_CLONE`, `OATS_TREE_REMOTE`,
  `OATS_TREE_MEMBER`, `OATS_BRANCH`, `OATS_TREE_BASE`, `OATS_TREE_BASE_OID`,
  `OATS_PURPOSE` (empty for `./work`) and `OATS_TREE_ORIGIN` (`spawn` or
  `add`). `OATS_TREE_REMOTE` is `origin`'s URL without credentials: a
  URL-style remote loses its whole userinfo, an scp-style remote its `user@`.
  Only that form is ever recorded, printed, logged or passed on. The
  environment is otherwise inherited from whoever ran the command (inside a
  session, the session's own); the kernel adds no credentials.

- **`oats worktree add|remove`: extra trees made by the kernel.** From an
  instance home, `oats worktree add --purpose <p> --branch <b> --base
  <remote-branch> [--repo <member key|clone path>] [--preview] [--json]` makes
  `<home>/.work-<p>` with the same three Git steps the work-mode briefing
  taught (the clone's refs are not moved), fires the `worktree` hooks, records
  `<home>/.oats/trees/<p>.json` and appends a `worktree-added` instance event.
  Run again with the same arguments, it does nothing (`resumed: true`). An
  interrupted `add` rolls back; one killed outright leaves its record, and the
  next `add` or `remove` of that purpose completes the rollback. A rollback
  deletes the branch only when that `add` created it, no worktree has it
  checked out, and it still points where `add` created it. Otherwise the
  branch is kept and the answer says why (`branchKept`, `branchKeptReason`).
  Commands on one purpose are serialized by a claim,
  `<home>/.oats/trees/<p>.lock`. A claim left by a killed command is taken
  over by the next one once its holder is verified gone, and any git step
  the killed command left running is ended before the next one acts.
  `oats worktree remove --purpose <p>` runs `git worktree remove`, which
  refuses a tree with uncommitted work, keeps the branch and fires no hook. A tree `add` made is
  an ordinary extra tree to retirement. The `worktree` and `checkout`
  briefings and `/oats-operate` now teach these commands in place of the raw
  Git recipe, and tell agents that `add` may take minutes where a capability
  sets up the tree. New spawns get the new briefing.

- **Two error codes.** `E_INTERRUPTED`: SIGINT, SIGTERM or SIGHUP during
  `oats worktree add`'s hooks or a spawn's `worktree` hooks; the kernel ends
  the hook's process group, rolls back and exits 128 + the signal number.
  `E_WORKTREE_DIRTY`: `oats worktree remove` on a tree Git refuses as dirty,
  with Git's message; the record is kept. Commit and push, or discard, then
  retry. `add` otherwise reuses existing codes (`E_BRANCH_EXISTS`,
  `E_PLACEMENT_TAKEN`, `E_LIFECYCLE_BUSY`, `E_CLONE_MISSING`,
  `E_CLONE_MISMATCH`, `E_REMOTE_UNREADABLE`, `E_BASE_UNKNOWN`,
  `E_GIT_FAILED`, `E_REQUIRED_HOOK_FAILED`, `E_HOOK_ENVIRONMENT_CONTRACT`, `E_BAD_ARGS`,
  `E_INSTANCE_RETIRING`).

- **Additive JSON fields.** `spawn --preview` has a top-level `worktreeHooks`:
  `[{capability, required}]` for a `worktree` spawn, `null` for every other
  mode (the `worktree` path string is unchanged); the text preview prints
  `worktree hooks: …` or `worktree hooks: none`. The spawn result and the
  `spawned` event carry `worktreeHooks` (the hooks' receipt) only when
  `worktree` hooks ran. A spawn running its `worktree` hooks holds the
  quarantine marker `.oats-rollback-incomplete.json` with a new optional
  `inProgress: {pid, processStart, startedAt, branch, baseOid, hookPgid?, hookStart?}`; while
  that process is verifiably alive, its `oats status --json` row carries
  `spawnInProgress: true` and no `rollbackIncomplete`, and `oats retire`
  refuses with `E_LIFECYCLE_BUSY`. Whether a process exists is the operating
  system's answer (`kill -0`), on every host; only then is its start read,
  from `/proc`, or with `ps` in a fixed `LC_ALL=C`, `TZ=UTC` environment
  (macOS). A start
  that cannot be read is never taken for gone, nor shown in progress: the row
  carries `rollbackIncomplete` (its `inProgress` names the pid), and retire refuses, naming the pid and `oats retire
  <instance> --force`, which then keeps the branch. Once it is gone, `oats retire` ends the
  hook process group it left and completes the rollback (below). It
  signals that group only while the group's leader runs with its recorded
  start time. A group whose leader has exited is never signalled, and a
  warning names it. A group with members whose leader's start cannot be
  read is not signalled either: retire refuses, naming the group and
  `oats retire <instance> --force`, and so do `oats worktree add` and
  `remove` for a hook or git step an interrupted command left. A new instance
  event kind, `worktree-added`. See
  [desktop-cli-api.md](../desktop-cli-api.md#oats-worktree).

- **One exception to "no retire deletes a branch".** When a spawn was
  killed (SIGKILL, or its rollback cut short) while its `worktree` hooks ran,
  its marker's `inProgress` records the branch and the commit the spawn
  created it at (`inProgress.branch`, `inProgress.baseOid`). Once that
  process is verified dead, `oats retire` ends the leftover hook process
  group, runs the retire hooks, removes the worktree and verifies the
  removal, and only then deletes the branch with an atomic compare-and-delete
  (`git update-ref -d refs/heads/<b> <baseOid>`), finishing the spawn's own
  compensation. A branch still at its creation commit holds no work. If the
  tip moved, the branch is checked out in any worktree, or the ref cannot be
  read, the branch is kept and the retry stays incomplete with the usual
  "branch left" item naming it (the home is kept). Every other quarantine
  keeps its branch. The retire result keeps `branchDeleted: false` and
  reports the step in an additive `spawnCompensation`: `{branch,
  branchDeleted: true}` or `{branch, branchDeleted: false, reason}`, present
  only when the step was reached.

- **Limit: spawns from triggers and schedules.** A trigger or schedule spawn
  still runs as a child with a 5-minute timeout, which does not change. A
  `work: worktree` soul with a slow `worktree` hook is supported from a tick
  only if the whole spawn finishes in that time; otherwise the child gets
  SIGTERM, rolls back, and the tick records a failure.

- **Adopting the event.** A kernel before 0.49.0 refuses a manifest that
  declares `hooks.worktree`, and with it the whole capability. In order:
  1. Upgrade the kernel on every host that composes the capability.
  2. Only then declare `hooks.worktree`, with `compatibility.oats:
     ">=0.49.0"`, so an older host refuses with `E_CAPABILITY_INCOMPATIBLE`
     naming the release, not with a schema error.
  3. The blast radius is every soul that composes the capability, on every
     host below the release, as in lfx-oats-workspace#22, where one
     capability took down every developer soul.
  4. To limit it, put the hook in a small capability composed only by the
     souls that need the setup.
  5. Declare it `required` when the tree is unusable without the setup.

## oats.okf 5.0: proposals at checkpoints, not a harvest engine

0.48.1 was not released on its own: the oats.okf 5.0 pin it described ships
in 0.49.0, and its notes are these two sections.

The official catalog and reference workspace pin oats.okf 5.0.0. Working
instances update their notes at important checkpoints, write their own
proposal, and directly spawn `oats.okf/knowledge-harvester`. The harvester
checks the actual source, accepted knowledge and open/recent harvest PRs,
then opens a normal Git PR for maintainer review. No host harvest setting,
scheduled harvest jobs, source capture/worker/drain machinery or automatic
retirement harvest remains. Transcripts are not a default input.

The sole opt-out is in the soul: `knowledge: { harvest: off }`. Consultation
still works, no checkpoint-harvest direction is given, and the harvester
refuses that source in its required spawn hook. Directory bases remain
consultable, but harvesting requires a Git base with a reviewed PR path.

## oats.okf 5.0 cutover — order matters

1. **While still using oats.okf 4.2, finish or explicitly dispose of any
   registered 4.x sources.** Settle active harvesters and held drains, and
   decide the disposition of remaining private inputs and open PRs. Do not
   silently delete or re-import old custody. A registered old source retired
   after the pin can refuse with `E_HARVEST_CONSENT_UNKNOWN` and retain its
   home; finish that old-provider work before changing the pin.
2. **Pin and sync oats.okf 5.0.0**, using the deployment's normal reviewed
   package update and approval process. This makes the new administration
   command available; it does not replace modules in running homes.
3. **Before any new spawn, remove explicit legacy host settings** using the
   new, guard-exempt command, from the deployment directory and with a soul
   that selects oats.okf:

   ```sh
   oats okf setup --remove-legacy-settings --soul <soul> --plan --json
   oats okf setup --remove-legacy-settings --soul <soul> --json
   ```

   The plan writes nothing. Applying removes only the explicit host keys
   `settings.oats.okf.harvest`, `harvest-runtime` and `harvest-model`, keeps
   the file's permissions, and never changes the soul opt-out. Unsupported
   YAML shapes refuse without writing; report them to the deployment owner.
   **Between steps 2 and 3, a new spawn with those old host keys refuses
   with `E_REMOVED`; the refusal names this cleanup command as the fix.**
   The cleanup command did not exist in 4.2: it cannot run before step 2.
4. **Respawn homes that should propose knowledge.** Existing homes keep
   their copied modules, skills and briefings; their own commands, hooks and
   checks still run those old modules. A source record with an explicit
   host-origin legacy key continues to be refused by the 5.0 harvester even
   after host cleanup, until the source is respawned. A recorded 4.x
   `manifest-default` is nobody's decision and is ignored by the 5.0 reader;
   it alone does not require respawn, but the new proposal briefing does.

A proposal must contain exactly one `Source: instance <name>, home <path>,
soul <name>` line naming an actual recorded source. Spawn the harvester with
`--relation unrelated` alone, never with `--relative-to`; source-pair
consistency does not establish proposer authorship. Claims are untrusted
data and enter commit/PR message files, not shell command text.

This package pin changes no production kernel contract. Package mirrors are
generated from the exact pinned payload; the clean-room and provider-facing
tests exercise the 5.0 contract rather than restoring removed 4.x machinery.

## Added

- **Remote roster groups carry each host's kernel features, feature
  `server-probe-features`.** `oats status --json` now has a top-level
  `features`: the running kernel's own list, the same array as
  `oats version --json` `features` (emitted at output time, never from a
  reused `--max-age` observation; the human output is unchanged). `oats server
  roster --json` relays it from the status answer it already pulls, as each
  group's `probe.features`, so the Desktop can tell what a host supports
  without probing it: no extra ssh, no `version --json`, nothing stored. The
  host's answer is untrusted and is relayed only as an array of at most 256
  entries, each a string of at most 64 characters matching
  `^[a-z0-9]+(?:-[a-z0-9]+)*$`, in the host's order, duplicates kept;
  anything else, even one bad entry, is `null` (never a filtered list). `null`
  means unknown; `[]` is a valid answer, not unknown. A failed probe stays
  `{ok: false, error}` with no `features` key. A host before 0.49.0 answers no
  `features`, so its group reads `null`: a false negative for a host running
  0.46.0 to 0.48.0, whose `version --json` does advertise, for example,
  `soul-composed-instructions`. Its features are unknown until it runs
  0.49.0.

- **Desktop: a spawn whose capabilities set up its worktree finishes, and every
  outcome is reported for what it is (#802, feature `worktree-event`).** A
  `worktree` hook can run for up to 30 minutes, but the Desktop ended every
  spawn after 60 s, which made the kernel roll it back, and then reported
  "Outcome unknown". Now the deadline comes from the preview the operator
  confirmed (60 s, plus 30 minutes per hook and 60 s), the request answers
  within 50 s and the Desktop follows the spawn until it settles, and up to 4
  spawns run at once (one per workspace and soul). The spawn dialog's
  **Setup** fact names the capabilities that will set up the worktree. A
  spawn that was interrupted, or whose required hook failed, reads as rolled
  back with nothing created, and one whose cleanup was owed says to retire it.
  The roster shows a spawn running its hooks as **Setting up worktree…** with
  no actions, a home whose spawn or retire didn't finish as **Spawn didn't
  finish** or **Retire didn't finish** with only **Retire instance…**; the
  retire result names a branch an interrupted spawn left, and the events list
  gains **Worktree added**. A server spawn whose worktree hooks take more than
  about a minute is not yet supported from the Desktop: use the CLI on the
  server.

- **What to do with what a retire leaves behind (#703, part 1).** A new
  section, [After a retire: inspect, restore,
  dispose](../souls-and-instances.md#after-a-retire-inspect-restore-dispose),
  says what a recovery copy's `recovery.json` records (`phase`, `classes`,
  `afterHooks`), how to inspect one (`git -C <recovery>/repo status` and
  `log`, the copied home and outputs), how to restore from it (fetch the
  branch from the recovery's clone into the source repository under a new
  name, or copy files back) and how to remove one by hand; how to list and
  remove a retained worktree under `<deployment>/.agents/worktrees/`; and
  that the `retired` event keeps the recovery's path. The retire summary's
  recovery block ends with a line pointing to it. Nothing in the receipt or
  the plan changes, and nothing removes a recovery or a retained worktree
  for you.

- **Desktop: a soul's page shows its instructions.** A new **Instructions**
  section, after Capabilities, reads the soul's own `AGENTS.md` the way a
  capability's page reads its injected instructions: a navigation tree, then
  the file with its front matter as a table, its Markdown rendered strictly and
  its code highlighted. The path shown is the file's place in the soul's
  repository. It comes from the page's existing inspection (no new CLI call),
  and **Refresh** keeps the selection, focus and scroll position. The capability
  page's Contents and this section now share one reader and one keyboard model.
  With OATS 0.46.0 or later, the section also shows the soul's composed
  `AGENTS.md`, what a new instance spawned here would be given: the soul's own
  text, then each part OATS and its capabilities inject, each headed with where
  it comes from and its file, with **Open capability** on a capability's part
  and **Copy composed AGENTS.md** for the exact file. The page asks for it
  (`oats inspect --soul … --instructions`) only when the installed OATS
  supports it. For a soul on another machine (a server workspace), the page
  asks only when that server supports it, as the server reports in the remote
  roster (`probe.features`, feature `server-probe-features`): a server that
  reports nothing (older than 0.49.0, or not reached) shows only the soul's own
  `AGENTS.md`. The Desktop decides from the roster it already reads; it never
  probes a server for this.
- **Desktop: capability warnings and the new trigger fields are shown
  (#802).** A capability that declares a hook event this kernel does not run
  (`hook-event-unsupported`) now shows a **Warnings** list, in the kernel's
  own words, on the capability page, the soul page, readiness, the instance
  Soul tab, the spawn preview and Workspace › Sources. Each warning is marked
  by the word "Warning" and an icon, keeps its code and path under
  **Details**, and, on the soul page, in readiness and in Sources, has **Open
  capability**. A warning blocks nothing and changes no ready state or count;
  past 32, the list says how many more. A trigger's page now shows its last
  poll, the events waiting (newest first), the instances live now, and its
  last error with its code; events are named by their `subject`. Its **Test**
  card shows the instance each event would spawn and says when the name was
  shortened to fit. An older kernel sends none of these, and the pages read as before.

## Changed

- **The Desktop accepts OATS CLIs `>=0.25.8 <0.50.0`.** The compatibility band
  admits 0.49; existing feature gates remain unchanged.

- **Trigger events carry `subject` (#669).** Events carry `subject` (a PR's
  number); `perKey` counts by subject; added to the event file,
  `instance.json.trigger` and `trigger status`/`test`. `subject` is a string:
  `"42"` for PR 42. The keys are added beside the existing ones, and
  `triggerApi` stays 1: `trigger status` rows in `pending[]`, `fired[]` and
  `live[]`, `lastRun` in `trigger list`/`show`, and `trigger test`'s
  `wouldFire[]` (with `instance` and `nameCut`). A home spawned before 0.49.0
  has no `subject` in its record and still counts toward `perKey` by its PR's
  repo and number; a pending event an older kernel recorded is given its
  number as `subject` when it is read. See
  [desktop-cli-api.md](../desktop-cli-api.md).

- **Desktop: identity marks show two letters.** Soul, capability and workspace
  marks used the name's first letter, so every `oats-…` soul read "O". A mark
  now drops a package qualifier and, from three words, a leading namespace
  word, then takes two words' initials or a one-word name's first two letters:
  `oats-desktop-expert` is DE, `oats-okf--knowledge-harvester` KH, `oats.aweb`
  OA. Colours are unchanged, and the mark stays decorative beside the name.
  Where marks stack (a capability's *Used by*, a team's members), they now
  overlap by 1px, so no letter hides under the next mark.
- **A capability that declares a hook event this kernel does not run still
  composes (lfx-oats-workspace#22).** Until now an unknown event in `hooks`
  dropped the whole capability from discovery, and every soul composing it
  stopped on that host. From 0.49.0, an unknown event declared as a command,
  `{ command }` or `{ command, required: false }` is ignored and never runs;
  the capability composes and carries the warning `hook-event-unsupported`
  (`capability <id> declares hook "<event>", which this kernel does not
  run`). The warning appears, in JSON and in text, in `oats sync`, `oats
  workspace status`, `oats capabilities show`, `oats inspect`, `oats
  readiness` and `oats doctor`, each in a `warnings` array (new, and always
  present, in `capabilities show`, `inspect` and `readiness`; new in
  `doctor --json`), and as its message in the `warnings` strings of `oats
  spawn --preview` and `oats spawn`. Doctor without `--soul` reads the
  deployment's capabilities from this machine's cache, and names what it
  could not check (`hook-events-unchecked`). `oats capabilities` lists only
  the hook events this kernel runs. An unknown event declared
  `required: true` is still refused, exactly as before, since skipping a hook
  its author declared essential would fail open. The tolerance covers the
  event's name only: a malformed declaration (no or empty command, an unknown
  key, a non-boolean `required`, a script outside the capability) is refused
  as for a known event. Approved events are unchanged.
  `docs/capability-manifest.schema.json` accepts additional `hooks` keys with
  the same value shape. The limit: it helps from this release on only.
  Kernels before 0.49.0 still refuse every unknown event, so a capability
  that must load on them declares only the events they run.
- The text form of `oats spawn --preview` now prints its `warnings`
  (`WARNING: …`), including the launch-prompt notice that was JSON-only
  before.
- **`oats spawn --json`: a required spawn-hook failure answers its typed
  code, no longer `E_SPAWN_FAILED`.** A required `spawn` hook that fails
  used to answer `E_SPAWN_FAILED`, with no details. It now answers
  `E_REQUIRED_HOOK_FAILED`, or `E_HOOK_ENVIRONMENT_CONTRACT` when the hook
  answered an `env` outside its contract, with `details.hooks` (the hooks'
  receipt, paths only), as a required `worktree` hook's failure does.
  Anyone matching `E_SPAWN_FAILED` for that case must update.
  `details.unconfirmed: true` still means the rollback could not confirm the
  spawn's effects; `details` never carries `home`. See
  [desktop-cli-api.md](../desktop-cli-api.md).
- **The release-workflow test no longer runs the Desktop suite nested inside
  a root shard.** `test/release-workflow.test.mjs` ran Desktop's `npm test`
  as a third, unsharded copy of a suite that already runs twice; it used
  about 270 s of its 300 s budget and timed out on trees where every test it
  reached passed. It now checks that the Desktop scripts the release invokes
  exist. The Desktop suite's release gate is the `desktop-standalone` CI job,
  which runs the release's `npm ci && npm test` inside `packages/desktop`, and
  the root shards also run it. The failure-message helper from #644 (also
  reported as #750 and #794) stays for any nested `node --test` run.

- **A detached checkout or attached spawn records no branch, never `"HEAD"`
  (#641).** `oats spawn` of a checkout or attached instance whose tree is on
  a detached HEAD, or on a branch whose name is not valid UTF-8, records
  `branch: null` in `instance.json`, where it recorded the word `"HEAD"`
  (or the name with replacement characters). The Desktop now sees `branch:
  null` instead of `"HEAD"` for such a new spawn in `oats status --json` and
  in the spawn result. A home spawned earlier may still record `"HEAD"`:
  `oats instance git` reports it as `recorded.branch: null` with `drift:
  false`, and the retire plan's `facts.recordedBranch` is `null`, so neither
  the plan's notes nor the Desktop's Remove dialog say any more that the
  worktree is "not the branch it was spawned on (HEAD)". See
  [desktop-cli-api.md](../desktop-cli-api.md#instancejson).

## Fixed

- **Desktop: the bundled server ends with the app that started it (#698).**
  On Linux, quitting or upgrading Desktop could leave the old app's server
  (`server/oats-web.mjs start --port 4820`) running in the old app's
  `app-…scope`, still answering on 4820 with the old version, while the new
  app served from 4821. The app stopped its server only at the end of a
  clean quit, so a crash, a kill or a failure earlier in the quit left it
  running. Now the app starts its server with its stdin as a pipe that only
  the app holds, and the server exits as soon as that pipe closes, which the
  operating system does when the app ends by any path. A server started by
  hand is unchanged. CLI commands the server is running when it exits get no
  signal and finish, as on a normal quit. The startup log also names the
  case: a server of this app at another version on the port is reported with
  the version found, this app's version, and that it was not started by this
  app and is left running, then the port this app uses instead (it was
  reported as "not the requested workspace"). The app never stops a server
  it did not start. **One-time cleanup:** a server left running by an
  earlier Desktop does not have this tie and stays until it is stopped once
  by hand: stop the process listening on 4820 (Linux: `ss -ltnp 'sport =
  :4820'`, or `systemctl --user stop` its `app-…scope`; macOS: `lsof
  -iTCP:4820 -sTCP:LISTEN`), then restart Desktop. See the Troubleshooting
  table in [desktop.md](../desktop.md#troubleshooting).

- **Desktop: a deployment attached to a workspace identity matches its own
  server (#807).** Desktop decides whether a running server serves its
  workspaces by comparing each workspace's directory with the views the server
  lists. An attached deployment is listed under its workspace's id
  (`ws:<hash>`), with its path among the view's deployments, and only the id
  was compared. So a server of the same version serving that deployment was
  not reused (logged as "not the requested workspace") and a second one
  started. If the attach was observed before the app's new server first
  answered, startup could also stop with "spawned backend serves … does not
  cover …". A directory now matches a view when it is, or lies under, the
  view's id or one of its deployments.

- **Desktop: the soul page's Teams card shows a server's refusal as the
  context panel does (#680).** For an instance on a registered server, a
  refusal of listing, refreshing, joining or leaving teams now reads the same
  in both views: a headline naming the server (for `E_REMOTE_INCOMPATIBLE`,
  the missing feature and the update), with the kernel's code and message
  under Details. The soul page showed the kernel's raw message.

- **A home's session receipt is found whatever the letter case of its path
  (#780).** On a case-insensitive filesystem (the macOS default),
  `.../agents/...` and `.../Agents/...` are one directory, but the receipt was
  keyed by the path as the caller spelled it. So a healthy home addressed with
  a different case was refused with `E_RUNTIME_ENDPOINT_UNKNOWN` by
  `session inspect`, `start`, `restart` and `stop`. Retire then read it as a
  home of unknown provenance, and a directory-work home was refused with
  `E_WORK_INSPECTION_FAILED`. A spawn now keys the receipt and records its home
  by the on-disk spelling, and every reader compares spellings on disk. A
  receipt a kernel before 0.49.0 wrote keeps working where it is (nothing is
  moved or rewritten). It is found from the spelling its spawn used, and from
  the on-disk spelling when the two are the same. Any other spelling of such a
  home still misses it: address the home as `oats status` prints it. The
  missing-receipt message names the on-disk receipt path, and the older path
  for the caller's spelling when that differs. Case-sensitive filesystems are
  unchanged: two spellings there are two directories.

- **Retire sees a session working in a home whatever the letter case of its
  path (#789).** Before it removes a home without a usable session receipt
  (and on a lost tmux server, or for a home opened in Herdr), retire checks
  that no tmux pane and no process works there. tmux and lsof report those
  working directories in their on-disk spelling, which was compared with the
  caller's spelling of the home. On a case-insensitive filesystem (the macOS
  default), a home addressed in another letter case therefore looked empty
  while a session still worked in it, and retire went on to remove it. Both
  checks now compare on-disk spellings. So do the checks that find a home's
  `.work-*` extra trees: under another spelling they were missed, so a
  detached extra tree's own commits could be left reachable from no ref.
  Such a tree is now kept as a worktree, as under the home's own spelling.

- **Paths given in another letter case no longer lead the kernel astray
  (#789).** On a case-insensitive filesystem (the macOS default), several
  checks compared a path that git, Claude or an operator had recorded in its
  on-disk spelling with the caller's spelling of the same directory. The
  serious one failed open: a deployment root inside a linked Git worktree,
  given in another letter case, was not mapped to the primary checkout, so a
  spawn created its home in the linked worktree, the misplacement that check
  exists to prevent. Now:
  - the root maps to the primary checkout whatever its spelling;
  - retire's check that a removed worktree is no longer registered compares
    on-disk spellings;
  - launch prompt consent recorded under one letter-case spelling of a home
    applies under another (an exactly spelled key still decides, and several
    case-variant keys with no exact one give no consent);
  - Codex's trust key is written in the home's on-disk spelling, which Codex
    compares with its working directory;
  - a project-scoped Claude plugin is found from any spelling of its project.

- **A triggered spawn no longer fails on the length of its instance name
  (#669).** A trigger asked spawn for `<stem>-<purpose>`, and spawn refuses a
  name over 64 characters and never rewrites one. For a soul with a long agent
  name (a package soul's is `<package>--<soul>`), every event of the trigger
  failed with `E_INSTANCE_NAME_INVALID`, stayed pending, and failed again at
  every poll. The trigger now fits the name itself, keeping three of the 64
  characters for spawn's `-2`, `-3`, … suffix. A triggered instance whose name
  would be 62–64 characters is now named with a cut purpose and a 6-character
  hash of the event key; a name over 64, which used to fail with
  `E_INSTANCE_NAME_INVALID` and stay pending, now spawns. Names of 61
  characters or fewer are unchanged. When a name needs cutting but the soul's
  stem leaves no room even for the hash (a stem over 54 characters), the event
  still does not spawn; it stays pending with `lastError.code:
  E_INSTANCE_NAME_INVALID`, which now says the soul name is too long for a
  triggered spawn and names the stem and its length. (A stem over 62
  characters fails already in the preview: the message says the same, then
  quotes the preview's refusal, which names `<stem>-1` and its length.)
  To find affected triggers: `oats trigger test <id> --json` shows each
  would-fire event's `instance` and `nameCut`; `oats trigger status <id>`
  shows a pending event with `lastError.code: E_INSTANCE_NAME_INVALID` for a
  trigger that was stuck. To learn the stem, the tick now runs one
  `oats spawn <soul> --preview` per trigger per tick in which that trigger
  fires, with the trigger's own `launchConfig`, `harness`, `model`, `backend`
  and `yolo` (before, only for a trigger with `spawn.teams`, once per event,
  and with none of them).
  See [schedules.md](../schedules.md#triggers).

- **Retire's Git reads no longer rewrite the index they inspect (#662).**
  Every `git status` a retire ran (the inspection, its classes, the copy's
  verification, the outputs listing) ran with optional locks on, so Git could
  refresh and rewrite the inspected worktree's index while reading it. Every
  Git command the retire runs on the work, its repository, a repository under
  it and a recovery clone now runs with `--no-optional-locks` and
  `GIT_OPTIONAL_LOCKS=0`, with fsmonitor, hooks, an external diff and lazy
  fetch (`GIT_NO_LAZY_FETCH=1`, Git 2.44 or later) turned off, and without the caller's repository-local Git variables (`GIT_DIR`,
  `GIT_INDEX_FILE`, `GIT_WORK_TREE`, `GIT_CONFIG_PARAMETERS`, …), so an
  inherited `GIT_DIR` or `GIT_INDEX_FILE` no longer redirects what the retire
  reads. The operator's global and system Git configuration are still read,
  so what status reports, and so the spawn baseline comparison, is unchanged.
  A filter driver that the repository's own configuration names and its
  `.gitattributes` select can still run during `git status`. See
  [souls-and-instances.md](../souls-and-instances.md).

- **Retire's `work/` step runs Git helper-free, and verifies a removal
  (#679).** The default re-home ran `git worktree move` with the ambient
  environment, and `--discard-worktree` (or a quarantine that owes the
  worktree) ran `git worktree remove --force` and `git worktree prune` through
  a shell, so a helper the repository's own configuration names (fsmonitor,
  hooks) could run during the retire. These commands, and a quarantine
  retry's checks, now run helper-free against the repository's common Git
  directory, as the `.work-*` extra-tree step already did. A removal was not
  verified: a `worktree remove` that failed was swallowed, recorded as
  `removed`, and `work/` was then deleted with the home, leaving a dangling
  admin entry. The removal is now verified (nothing at `work/`, not in
  `git worktree list`); one that did not happen refuses with
  `E_WORK_PRESERVATION_FAILED` and keeps the home, `--force` included. This
  changes what `--discard-worktree` does when Git refuses the removal (a
  locked worktree, for example): it now refuses and keeps the home instead. When nothing is at `work/` and its repository
  cannot be read, the worktree is recorded `absent`, never `removed`, and a
  quarantine retry keeps `could not verify removal` as an incomplete item.

- **Retire refuses a `work/` whose `core.worktree` names another directory
  (#648).** A worktree's per-worktree configuration can point Git at another
  directory: its status then described that directory, while the retire
  read, copied and removed `<home>/work`. A clean status there meant no
  recovery, and `--discard-worktree` removed a `work/` nobody had inspected.
  Before any status is trusted, each inspection now checks that Git's top
  level for `work/` is `<home>/work` (in its on-disk spelling, so a symbolic
  link or another letter case on a case-insensitive filesystem is the same
  path), and refuses with `E_WORK_INSPECTION_FAILED`, naming both paths. The
  first inspection does so before the session is stopped or any retire hook
  runs: nothing was stopped, run or removed.

- **Git reads of an instance's work never fetch a missing object.** A
  repository's own configuration can make it a promisor of another one: a
  read of an object it lacks then fetched it, running the remote helper, ssh
  command or credential helper that configuration names, and writing the
  object into the observed repository. `oats instance git`, `oats instance
  diff` (and the Desktop views that read them) and retire now run Git with
  `GIT_NO_LAZY_FETCH=1`. Visible effect: for a partial clone that lacks an
  object a read needs, `oats instance git` and the diff report a failure
  (`E_GIT_FAILED`) instead of fetching it, and a retire refuses
  (`E_WORK_INSPECTION_FAILED` or `E_WORK_PRESERVATION_FAILED`) and keeps the
  home. The protection needs Git 2.44 or later; an older Git ignores the
  variable, and nothing else changes for it.

- **A retire by name cleans its wake schedules again (#693).** Without
  `--home`, `oats retire <instance>` handed the wake-schedule cleanup the
  instance record instead of its home path. As soon as any wake schedule
  existed the cleanup threw, the retire printed `wake schedules not cleaned:
  The "paths[0]" argument must be of type string. Received an instance of
  Object`, and the retiree's wake schedules stayed. The cleanup now gets the
  home the retire selected, with or without `--home`; the receipt is
  unchanged.

- **A recovery holds every stash entry, not just the latest (#654).** The
  copy of a worktree and of each nested repository fetched `refs/stash` only,
  while it copied the stash's log whole: `stash@{1}` and older were listed in
  the copy and their commits were not there. Every commit the copied stash
  log names is now fetched into the copy and checked there.

- **A recovery holds the blobs of a resolved conflict (#655).** The index was
  copied whole, resolve-undo records included, but only its staged blobs were
  restored: a conflict side that is in no commit was missing, so
  `git checkout -m <path>` could not recreate the conflict in the copy. The
  blobs the copied index's resolve-undo records name are now restored and
  checked too.

- **The recovery copier reads the files Git reads (#647).** It trimmed white
  space off the paths Git printed for it (the Git directory, the common
  directory, `core.excludesFile`, the top level), so for a path that really
  ends in white space it read another file, or none; and it took the staged
  blobs to carry from Git's own index rather than from the index file it
  copied. It now reads each path exactly as Git prints it, takes the blobs
  from the index file it copies (`GIT_INDEX_FILE`), and reads a worktree's
  `.git` file as Git does (the `gitdir: ` prefix, the trailing line feeds
  and carriage returns removed, nothing else). A `.git` file that Git would
  not read (`gitdir:` without its space, or a path with a trailing space
  that does not exist) now reads as a worktree whose admin entry is gone:
  the retire keeps the directory and the home and does not complete.

- **A nested repository's recovery is on its branch, with its branches and
  reflogs (#657).** Its copy had a detached `HEAD` even when the source was
  on a branch, kept no other branch name, and lacked commits only a reflog
  reached. The copy's `HEAD` is now on the source's branch (detached only
  when the source's is), every local branch exists under its name at its
  commit, and the reflogs of `HEAD` and of each branch are carried, with
  every commit they name. Its local configuration is still not carried beyond
  the six status settings: remotes, `branch.*` upstreams, `user.*` and the
  rest are dropped, so that the recovery stays inert to inspect (its
  configuration could name hooks, an fsmonitor, a credential helper or a
  filter that would run there). See
  [souls-and-instances.md](../souls-and-instances.md).

  Each of these objects is collected, restored or fetched, and checked again
  before a copy is accepted; one the source cannot supply (a partial clone
  that lacks it) refuses the copy with `E_WORK_PRESERVATION_FAILED`, naming
  it, where before the copy went through without it.

- **A recovery of a worktree with an uncommitted top-level deletion or rename
  is verified (#656).** The copy is a clone with the worktree's files put
  over it, and only the top-level entries the worktree had were replaced. A
  tracked top-level file, directory or link the worktree had deleted or
  renamed stayed in the copy as the clone checked it out, so the copy's
  verification disagreed and the retire refused with
  `E_WORK_PRESERVATION_FAILED` until the deletion was committed or undone.
  Each top level of the copy (the worktree's, and each nested repository's)
  is now made the source's: what the source lacks is removed, `.git` aside,
  then what it has is copied.

- **A work copy's verification compares every `.git` it does not rebuild
  (#663).** It passed over every entry named `.git`, at any depth, so a
  dangling `.git` link, or the Git directory of a repository inside a nested
  one, was copied but never compared. It now leaves out only the worktree's
  own `.git` and those of the nested repositories the copy rebuilds from a
  clone, by their exact paths, and compares every other entry named `.git`
  as bytes.

- **A file whose name is not valid UTF-8 no longer stops a retire (#645).**
  The recovery copier read names as text, so such a file in the home (a
  scratch repository's ref or reflog, for example) or among a worktree's
  untracked or ignored files could not be opened by its decoded name, and the
  retire refused with `ENOENT` until someone removed the file by hand. The
  copier now reads, joins and writes names as bytes, and the copy holds such
  a file under its own name, and the receipt counts its bytes (it counted
  them as 0). Names shown to a person (a receipt's
  `paths`, a message) stay text, with replacement characters for such bytes.
  One case still refuses, now with a message that says what to do: a nested
  repository whose own path is not valid UTF-8, because Git cannot be given
  that path; rename the directory, then retire again. See
  [souls-and-instances.md](../souls-and-instances.md).

- **Desktop: starting or restarting an instance is held to its window's
  workspace (#818).** The app's main process pins every workspace-scoped
  request with no `?ws=` to the workspace of the window that sent it, and
  refuses one naming a workspace the server does not serve (404
  `E_WORKSPACE_NOT_SERVED`) without sending it. `POST
  /api/start/<instance>` and `/api/restart/<instance>` were not in that set,
  so they got neither. Nothing was ever started in the wrong workspace: the
  server resolves an instance only inside the workspace it is given, refuses
  an ambiguous bare name and finds nothing in a workspace it does not serve.
  The two routes now get the same pin and refusal as every other privileged
  instance request.

- **An untracked link or a name that is not UTF-8 is compared by what it
  holds (#660).** The spawn baseline's digest of a worktree's untracked and
  ignored paths took them from the status decoded as text and tested each
  with a call that follows links. So an untracked symbolic link whose target
  does not exist, and a path whose name is not valid UTF-8, read as missing
  at spawn and at retire whatever they held: a change to such a path alone
  added no class, and the retire wrote no recovery for it. A new spawn's
  baseline now takes the paths from the status's bytes and tests each
  without following a link, so a link is compared by its target and such a
  name by its file. Such a path that cannot be read (an entry under it
  without permission) refuses the retire with `E_WORK_INSPECTION_FAILED`,
  naming it, before anything is stopped, run or removed. A baseline written
  before 0.49.0 keeps the old digest until the instance is respawned. See
  [souls-and-instances.md](../souls-and-instances.md).

- **The spawn baseline's digests no longer depend on the locale, and two
  different trees no longer give the same digest (#661).** The digests a
  spawn baseline stores, of the home and of a worktree's untracked and
  ignored paths, ordered names by the locale and wrote file contents without
  their length, so a retire under another locale could read an unchanged
  home as changed (which adds a copy attempt), and a file whose bytes spell
  the entry after it read like those two entries. A new spawn records
  `digestVersion: 2` in its baseline and writes digests that order names by
  their bytes and frame every name, file and link target with its length.
  The home copy's verification uses them too. A baseline written before
  0.49.0 keeps the old digests until the instance is respawned, and is
  compared with them exactly as before. The baseline's own `version`, which
  also gates the start and retire authority of every existing instance, is
  unchanged.

- **A retire plan's notes fit what the Desktop reads (#658).** The Desktop
  refuses a plan with a note over 4096 characters or more than 64 notes, and
  Remove then failed with `E_CLI_PROTOCOL`. The recovery note's list of
  declared roots that are not copied is now bounded to about 1024 characters
  (the rest is `, and N more`), and a recovery path too long for the note is
  never cut: the note says the retire receipt (`workRecovery.path`) and the
  summary name it. An extra tree's note keeps the tree's path whole and leaves
  its longest other parts to `facts.extraWorktrees` in the plan JSON; more
  extra trees than fit in 64 notes end in `and N more extra worktrees`. A
  drift note with two long branch names, or a session note with a long
  reason, points to the plan JSON's field for what does not fit. The plan's
  shape is unchanged.

- **Retire refusals after the hooks say what has happened, and a failed copy
  keeps its cause (#659).** A recovery that cannot be completed after the
  retire hooks now ends, as a refusal before them does, with what the retire
  has done: the hooks have run; the home, its work and the pre-hook recovery
  (if any) are kept; and whether this retire stopped the session. A copy
  that fails verification while the work holds a read-only directory (a Go
  module cache, for example) used to end in a bare `EACCES` from its cleanup,
  losing the cause and leaving a partial copy in recovery storage: the
  cleanup now makes the staged directories writable before removing them,
  never replaces the original error, and names a staging directory it could
  not remove.

- **The manifest checks `retirement.disposable.work` as spawn does (#659).**
  A work root must be a relative path under `work/` with no empty, `.` or
  `..` segment (a leading `./` and a trailing `/` are dropped first, as spawn
  does). An absolute one, a Windows one such as `C:/x` included on any host,
  is refused where the manifest is read: in discovery (`E_WORKSPACE_SCHEMA`),
  package manifests (`E_PACKAGE_MANIFEST`) and the kernel's loader, at
  `/retirement/disposable/work/<i>`; so are two entries of one manifest that
  overlap. Before, any non-empty string loaded and the spawn failed later.
  Spawn still refuses a declared root that is a symbolic link in the work (a
  link whose target is missing too, which it used to accept) and roots of two
  capabilities that overlap, now with the code `E_CAPABILITY_BROKEN`; `oats
  spawn --json` still reports it as `E_SPAWN_FAILED`, with the same message.
  The published schema states the same grammar.

- **Attached children follow a retained worktree (#718).** Retiring an
  instance whose worktree is retained left each attached child's `work` link
  pointing at the removed home. Each attached child the retire stopped is now
  repointed to the retained worktree, atomically, as the last step before the
  home is removed; the summary says so per child, and a relink that fails is
  a warning with the command to repoint it, without undoing the retire. A
  child linked through an alias of the tree (its `--work-dir`) counts too. The
  retire plan names the attached children in one note, which also says that
  with `--discard-worktree` their link would dangle. No receipt or
  `instance.json` field is added; the child's AGENTS.md and TASK.md still
  name the old path.

- **`oats instance events` answers for a retired instance (#642).** An
  instance's rows outlive its home in
  `<deployment>/.agents/events/<agent>--<instance>.jsonl`, but the command
  looked only for a live home and answered `E_SESSION_UNKNOWN`. When no live
  home resolves, it now answers from that log, in the same shape, with the
  home source `absent` and `incarnation: null`. When the logs of two agents
  hold an instance of that name, it refuses with `E_AMBIGUOUS_INSTANCE` and
  lists the candidates; `--home <agents root>/<agent>/instances/<instance>`
  picks one. A removed `--home` answers only at that path and only when that
  agent's log exists; any other is still `E_HOME_MISMATCH`.

## Removed

- **Desktop: the unused transcript route of the local server (#627).**
  `GET /api/chat/<instance>` returned a parsed transcript of an instance's
  harness session log, read from under the user's home. Nothing in the
  Desktop used it: its terminals are viewers of the instance's session, and
  the separate chat view it served was dropped. The path now answers as any
  unknown route does (`404`, `not found`), behind the same Host and Origin
  guards, and the Desktop no longer pins a workspace onto it. The instance
  menu no longer sends an action it has no handler for to the server as
  `POST /api/<action>/<instance>`; no menu action took that path, and one
  would now be refused in the app. Closes
  [#627](https://github.com/awebai/oats/issues/627).

- **Desktop: the dedicated harvest route of the local server (#818).**
  `POST /api/harvest/<instance>` ran the knowledge provider's harvest for one
  instance. Nothing in the Desktop called it once the instance menu stopped
  sending actions it has no handler for (#627). Harvest is still available
  where a soul's capability offers it: the soul page runs any provider
  operation, `knowledge:harvest` included, through `/api/capabilities`, and a
  schedule can run it. The path now answers as any unknown route does
  (`404`, `not found`), behind the same Host and Origin guards. The Desktop's
  "no compatible CLI" card and log now say Spawn, Start and other changes
  need the CLI, instead of naming a Harvest action it no longer has.
