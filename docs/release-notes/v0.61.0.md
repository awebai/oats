# OATS 0.61.0

2026-10-16

## Upgrade

- **A pi instance stuck on its opening task: restart it after the update**
  ([#1322](https://github.com/awebai/oats/issues/1322)). On pi 1.2 and
  later, the 0.60.0 bridge (`@awebai/oats-pi`) held an instance's opening
  task forever, and everything typed after it stayed queued. Install the
  0.61.0 bridge (`oats update` moves it in every pi folder your launches
  use), then restart each pi instance that is stuck. Instances that already
  ran their opening task are unaffected. See Fixed.

- **Install the Desktop first and the CLI second,** as
  [Upgrading](../upgrading.md) says: a 0.60 Desktop refuses a 0.61.0 CLI. The
  0.61.0 Desktop accepts OATS CLIs `>=0.26.0 <0.62.0`.

- **The official catalog moves oats.framework 1.12.3 → 1.13.0** (oats.setup
  2.8.0, see Provider updates). The other packages are unchanged. A
  deployment takes it by changing its pin and running `oats sync`. Only new
  spawns use it.

- **OATS 0.61.0: `oats onboard`'s `next.spawn` can name a soul other than
  `oats-operator-expert`** ([#1314](https://github.com/awebai/oats/issues/1314)).
  Before OATS 0.61.0 it named `oats-operator-expert` whenever a soul had that
  name, and only then; from OATS 0.61.0 it names the soul that holds
  `oats.setup`, the workspace's setup expert, so a workspace without this
  project's soul is pointed at its own. The JSON shape is unchanged
  (`onboardApi` 2, text or `null`). A script that matched the old exact name
  sees a different answer: a soul named `oats-operator-expert` that does not
  declare `oats.setup` now gives `null`.

## Changed

- **OATS Desktop's command palette shows when two instances are siblings**
  ([#1312](https://github.com/awebai/oats/issues/1312)). An instance declared
  a sibling of a root, and that root, each say `sibling of <name>` beside
  the name, in the tree, as a match's context and in Recent, and assistive
  technology reads it once with the row. Siblings under one parent still read
  `under <parent>`. Matching, order and groups are unchanged
  ([keyboard reference](../../packages/desktop/docs/desktop-keyboard.md)).

- **The Desktop sidebar draws the sibling line apart from the lines to
  children** ([#1312](https://github.com/awebai/oats/issues/1312)). The
  dotted line joining sibling instances runs through their dots, and a
  parent's line to its children runs just to the right of it, so the two no
  longer share one line. The dotted line is darker in the White and Solarized
  themes, so it stands out on every row (3:1 contrast). See
  [the sidebar's instance tree](../desktop.md#the-sidebars-instance-tree).

- **OATS 0.61.0: `oats onboard` names the workspace's OATS setup expert**
  ([#1314](https://github.com/awebai/oats/issues/1314)). Its last next step,
  and `next.spawn` in `--json`, name a soul whose own `soul.yaml` declares
  `oats.setup` (from any source; `off` does not count): the one called
  `<workspace name>-oats-setup-expert`, else the first by name, else none,
  when the text suggests adding that conventional soul. A name alone never
  counts. Only the
  soul's own declaration is read: `oats.setup` given only through workspace
  defaults is not seen. A standalone view has no workspace name, so only
  the declaration counts there. `oats help` describes the step the same way
  ([the rule](../desktop-cli-api.md#oats-onboard-onboardapi-2)).

- **OATS Desktop accepts an `oats` CLI 0.61.x.** Its band is now
  `>=0.26.0 <0.62.0`. 0.61 adds no new gate on the band: `oats onboard`'s
  next step names the workspace's setup expert in the same text-or-`null`
  shape the Desktop already reads.

## Fixed

- **pi 1.2 and later run an instance's opening task again**
  ([#1322](https://github.com/awebai/oats/issues/1322)). From pi 1.2.0 a run
  counts as active before its `before_agent_start`, and the bridge's hold on
  the opening prompt waited for that same run. So on pi 1.2 and later, an
  instance's opening task never ran. That was the launch's `@TASK.md` in
  interactive mode, or the first default `session.prompt()` of an SDK
  session. Escape didn't release it, and every later prompt waited queued
  behind it, even after the aweb welcome's turn had finished. The hold now
  never waits for the prompt's own run, and a session that shuts down
  releases it. The task still runs once, after a welcome turn that started
  first. On pi 1.2 and later, a welcome sent while the task's run starts is
  queued by pi into that run, after the task. The bridge still sends and
  alters nothing. Restart a pi instance that hangs on its opening task once
  the updated `@awebai/oats-pi` is installed (`oats update`).

- **`oats tui` names a sibling at both ends of the link, and its palette
  names siblings** ([#1315](https://github.com/awebai/oats/issues/1315)).
  The detail's parent line named a sibling only on the instance that
  declared the link, and named it as written, even when no instance had
  that name or two had it. Now both ends say `sibling of <names>`, as the
  Desktop does, and a name that resolves to no instance, or to more than
  one, is not shown. The palette shows the same words, dim, after an
  instance's name; a query never matches them. See
  [the TUI page](../tui.md#the-palette).


## Provider updates

- **oats.framework 1.13.0, oats.setup 2.8.0: the setup expert runs the
  setup, and the person types only secrets**
  ([#1314](https://github.com/awebai/oats/issues/1314)).
  - **The setup briefing has one rule for what the person types:**
    passwords, tokens, API keys and interactive logins. It also keeps the two
    installs that capture their own shell, the host wake broker and the host
    timer (#922). Everything else the agent runs and reads back.
  - **A secret reaches its command by a route the agent never sees,** in
    this order:
    - a browser device flow the agent starts (`gh auth login --web` without
      a terminal);
    - a no-echo prompt in a split of the agent's own tmux pane, which closes
      when its command ends (while it is open, wakes and `oats session input`
      can't reach that instance);
    - the person's own terminal.

    Each route is checked with a read-only command.
  - **`/oats-git-setup` is run by the agent.** The person approves each gh
    login in the browser and chooses their name, email and passphrase
    option. The SSH key is made with no passphrase, because the kernel's ssh
    runs in batch mode; a passphrase key held in an ssh-agent is the
    alternative. The GitHub host key that was checked against its published
    fingerprint is the one recorded. Step 0 reads the global Git
    configuration's names only, and step 7's check runs as one block.
  - **`/oats-setup-expert` (new):** a workspace setup expert's first session.
    It starts from the intake that the `oats-getting-started` skill hands it
    from OATS 0.62.0,
    covers a new or an existing workspace, and ends at a first working soul.
    `/oats-onboarding` points to it.
  - **`/oats-agent-permissions` (new): Claude Code's permissions for OATS
    instances.** The setup expert writes the user settings of the Claude
    config the launches use, never the home's `.claude/settings.json`:
    - auto mode, by `permissions.defaultMode` or `--permission-mode auto` in
      a launch configuration's `args`;
    - an `autoMode` block naming what the workspace trusts;
    - narrow allow rules for the `oats` reads, `oats spawn` (with an `ask`
      rule on `--yolo`, `--server` and `--wake-*`), reading `aw` mail and
      chat, and `gh` reads.

    Retire and stop (except `--plan`), `aw` sends, `git` beyond Claude's
    built-in read-only forms, pushes, merges and the operator acts stay
    with the classifier, or an `ask` rule. The person approves the
    change. The check: no `waitingOnYou` with reason `permission` during the
    first working soul's task. Claude only; Codex and pi are named.
  - **`/oats-setup-model` explains the per-workspace setup expert,** and how
    `oats onboard` finds it from OATS 0.61.0.
  - Instruction text only; the floors are unchanged. A deployment gets it by
    pinning `oats.framework: v1.13.0` and running `oats sync`.

## Documentation

- **The README's opening reads at a skim.** One paragraph says what OATS is
  (a provider- and harness-agnostic framework for distributed agent teams,
  completely free and open source), then five short points: each agent
  keeps its harness's full power, capabilities shape the team over
  opinionated defaults, you keep control, the two clients, and what it
  builds on.
