# OATS 0.66.0

Unreleased

## Upgrade

- **Install the Desktop first and the CLI second,** as
  [Upgrading](../upgrading.md) says: a 0.65 Desktop refuses a 0.66.0 CLI. The
  0.66.0 Desktop accepts OATS CLIs `>=0.26.0 <0.67.0`.

- **Two package moves:** the official catalog pins oats.framework 1.13.4 and
  oats.aweb 1.30.0 (Provider updates, below). A deployment that pins them
  takes them with `oats sync`, and only new spawns use them. Neither floor
  changes.

- **`oats tui` moves its key file** to `~/.oats/config/tui.json` the first
  time it starts (Changed, below). If you keep the file in a dotfiles
  manager, point it at the new path first.

- **Coming from 0.61 or earlier:** do 0.62.0's Upgrade steps too (the capture
  service's `oats setup`, once per user on each host, from that user's shell).

- **`oats server connect` needs `--dir`, inside a deployment too**
  ([#1390](https://github.com/awebai/oats/issues/1390);
  [Connect a machine](../servers.md#connect-a-machine)). The folder on the
  host no longer defaults to `~/Agents/<this deployment's directory name>`:
  only you know where the deployment goes there. A script that ran `connect`
  without it now gets `E_BAD_ARGS` "--dir <path on the host> is required:
  the folder on `<host>` for this deployment (absolute, or ~/… resolved
  there)" before anything runs; add `--dir`. `--workspace-ref` still
  defaults from the deployment, and existing registrations are unchanged.

## Added

- **`oats tui` takes the OATS Desktop's Ctrl+Shift chords, where your
  terminal lets them through** ([Chords](../tui.md#chords)): `Ctrl+Shift+K`
  the palette, `Ctrl+Shift+P` a spawn, `Ctrl+Tab` and `Ctrl+Shift+Tab` the
  next and previous tab, `Ctrl+Shift+W` close the terminal, `Ctrl+Shift+F`
  the filter, `Ctrl+Shift+E` and `Ctrl+Shift+O` the splits. Each does what
  the leader then a key does, from every focus, an agent's terminal too,
  and never reaches the agent. They are extras: the leader stays the key
  that always works, and the cheat sheet does not name them.
  - **Only where the terminal says it can.** At start the TUI asks for the
    kitty keyboard protocol (flags 1 and 4) and asks the terminal which flags
    it has. Only when the terminal answers does it take the chords and list
    them in the help, with the keys your terminal may take first (foot's
    Ctrl+Shift+C, V, R, N, O, U, Z, X and Q). Without an answer everything
    is as before. foot, Ghostty, kitty, Alacritty and WezTerm answer; VTE
    terminals and Terminal.app do not. On macOS only `Ctrl+Tab` and
    `Ctrl+Shift+Tab` are chords: the Desktop's hold ⌘, which a terminal
    never passes on.
  - **`Alt+O` and `Esc` then `o` are told apart exactly** under the
    protocol, with no timing.
  - **An agent gets the same bytes as before:** every key typed into its
    terminal is turned back into the bytes it sends without the protocol,
    and no tmux setting is changed. With a terminal that confirms flag 1
    but not flag 4, Shift with Alt or Ctrl on a key that is not a letter
    is typed as the US layout makes it.
  - **The protocol is popped on every way out** and at a suspend, beside the
    terminal modes the TUI already restores.

## Changed

- **OATS Desktop's Add a machine dialog no longer suggests a folder**
  ([#1390](https://github.com/awebai/oats/issues/1390)). **Folder on that
  machine** starts empty and you have to fill it in. Its hint reads "A path on
  that machine, starting with / or ~/". If you click **Add machine** with the
  folder empty, the dialog says so beside the field and runs nothing. It used
  to fill in `~/Agents/<deployment folder name>`. The Name default
  (`<host>-<deployment folder name>`) is unchanged.

- **`oats deployments add` walks up to a regular `oats-local.yaml` only**
  ([#1397](https://github.com/awebai/oats/issues/1397);
  [This computer's deployments](../workspaces.md#this-computers-deployments)).
  A directory or a link of that name is passed over, as a client passes it
  over when it admits a deployment, instead of being listed and then shown
  as `not-a-deployment`.
- **A deployment under a temporary directory is no longer listed
  automatically** ([#1397](https://github.com/awebai/oats/issues/1397)). A
  kernel command run in one (`os.tmpdir()`, `/tmp`, `/private/tmp` or
  `/var/folders`, compared after realpath) leaves the list alone, so test
  fixtures no longer fill it with rows that turn `missing`. Such a
  deployment stays reachable: `oats deployments add`, `oats onboard` and a
  client opening it still list it.

- **`oats tui` reads its key file from `~/.oats/config/tui.json`**
  ([#1390](https://github.com/awebai/oats/issues/1390)), beside the kernel's
  own files: `$OATS_HOME_DIR/config/tui.json` when `OATS_HOME_DIR` is set.
  `XDG_CONFIG_HOME` is no longer read for it.
  - **An existing file is moved for you** the first time the TUI starts: it
    copies `~/.config/oats/tui.json` (or `$XDG_CONFIG_HOME/oats/tui.json`)
    to the new path and renames the old file `tui.json.migrated`, beside
    it. Nothing else changes.
  - **If both files are there, the TUI refuses to start** with
    `E_TUI_CONFIG`, naming both: copy what you need into
    `~/.oats/config/tui.json`, then remove the old file.
  - **If you keep `tui.json` in a dotfiles manager,** point it at
    `~/.oats/config/tui.json`. A manager that puts the old file back makes
    both files present, and the TUI refuses until you remove it.
  - When the move can't be made (the old file is a link to nothing,
    `tui.json.migrated` is already there, the file system has no hard links,
    or a step fails), the TUI says why and stops: move the file yourself.
    See [OATS TUI](../tui.md#the-move-from-configoats).

- **OATS Desktop accepts an `oats` CLI 0.66.x.** Its band is now
  `>=0.26.0 <0.67.0`. 0.66 adds no new gate on the band: the Desktop's Add a
  machine already passes the `--dir` that `oats server connect` now requires.

- **A new workspace gets messaging, a team and a first developer in its first
  commit, with no pull requests and no API key.** The `oats-getting-started`
  skill asks for an aweb username in its one round of questions, writes the
  workspace with `oats.aweb`, a team `default:<username>.aweb.ai`,
  `defaultTeam` and a developer soul beside the setup expert, then signs up
  the account with `oats aweb setup --username` before the spawn. Later
  changes follow oats.setup's push rule (the next entry). The skill also runs `gh auth setup-git` when gh is
  already logged in, so the first push and `oats onboard` no longer fail with
  "could not read Username". The README's Start here tells a coding agent
  exactly what to download and follow.

- **The setup soul that the `oats-getting-started` skill writes leaves when
  to push to `oats.setup`.** Its `AGENTS.md` states no push rule of its own.
  From `oats.setup` 2.8.3 (oats.framework 1.13.4), the setup expert checks
  before each push (`/oats-workspace-config`, "Change a shared file"): it
  pushes straight to the default branch only where nobody else can push and
  nothing guards that branch, and to a member repository only on the
  person's yes; otherwise it opens a pull request. An older `oats.setup`
  always opens one ([#1314](https://github.com/awebai/oats/issues/1314)).

## Fixed

- Capture setup now shares one checked publisher for hooks, service definitions
  and pending activation markers: it syncs file contents before rename, then
  the containing directory, and syncs newly created parent entries in order.
  Required sync failures exit nonzero; failures after publication name the
  affected target and stage without claiming rollback or established durability.

## Provider updates

- **oats.framework 1.13.4: oats.setup 2.8.3.** Text only: its floor
  (`compatibility.oats`) does not change.
  - **Straight pushes to a repository only the person can push to.** The
    briefing's rule for shared files was "only by pull request".
    `/oats-workspace-config`'s "Change a shared file" now has two routes. A
    commit goes straight to a repository's default branch, the workspace's
    host or a member repository alike, only when checks right before the
    push show that the person alone can push to it and nothing guards the
    branch:
    - they are its admin and its only collaborator with push access; for an
      organization's repository, an active member and its only owner;
    - no deploy key can write;
    - no branch protection or ruleset guards the default branch (a plan
      without rulesets counts as unguarded).

    For the host, the setup expert then pushes and tells them what changed.
    For a member repository, it first shows them the commit and says that
    the push runs that repository's push-triggered CI and deploys, and it
    pushes only on their yes. Otherwise the change is a pull request, and a
    refused push never takes another route. The briefing,
    `/oats-setup-expert`, `/oats-package-pins`, `/oats-teams`,
    `/oats-automations` and `/oats-setup-model` follow it
    ([#1314](https://github.com/awebai/oats/issues/1314)).
  - **`/oats-setup-model` on a capture setup that failed after
    publication.** When the setup summary says that publication may have
    occurred but durability was not established, inspect the named target
    and stage before rerunning, and keep that evidence. A sync or close
    failure after the rename does not mean that the old file was restored
    ([#1340](https://github.com/awebai/oats/issues/1340)).

- **oats.aweb 1.30.0: Codex readiness from the kernel's launch record.** The
  catalog and this workspace pin `oats.aweb: v1.30.0`
  ([#1345](https://github.com/awebai/oats/issues/1345)).
  - Readiness takes a home's runtime from the kernel's recorded
    `instance.json` `launch.harness` (or top-level `harness`), not from
    provider metadata. A home recorded as Codex needs the host wake broker:
    a missing Codex target or primary stream reports `wake-stream-missing`.
    Malformed or inconsistent kernel fields report
    `receive-record-unavailable`.
  - A malformed `status.updated_at` from `aw wake status` reports
    `wake-status-timestamp-unknown`, naming the aw client and daemon
    versions, instead of `wake-status-stale`.
  - The floors are unchanged (OATS >=0.52.0, aw >=1.36.33). A deployment
    gets it by pinning `oats.aweb: v1.30.0` and running `oats sync`; only
    new spawns use it.
