# OATS 0.69.11

0.69.11 lets a workspace give the tasks provider one shared setting in
`oats-workspace.yaml` (`tasks:`), and lets a capability mark a setting
`committedOnly`, so no deployment can override it locally. It moves the official
catalog to `oats.framework` 1.21.0 (`/oats-host-delivery` installs the pi
extension without its bundled skills, and `/oats-upgrade` covers a first Desktop
install) and `oats.aweb` 1.35.0 (`oats.aweb-tasks` gains a shared `team`
setting and a readiness check, and pi homes get a warning while the extension
still loads its skills). Getting started takes fixes from a second round of
newcomer runs on fresh machines.

## Upgrade

- **Either order of the Desktop and the CLI works.**
  [Upgrading](../upgrading.md) installs the Desktop first, and a host that
  installed the CLI first is fine too: the 0.69.11 Desktop accepts OATS CLIs
  `>=0.26.0 <0.70.0`, as the 0.69.10 and 0.69.9 Desktops do.
- **Package moves:** the official catalog pins oats.framework 1.21.0 and
  oats.aweb 1.35.0, with no change to their OATS floors (oats.aweb keeps aw
  >=1.36.33, and is tested with 1.36.53). A deployment takes each by raising
  its own pin (`/oats-package-pins`), then `oats sync`. Running instances keep
  the modules they were spawned with: new spawns get the new ones, and a
  stopped home moves with `oats instance upgrade`.
- **A pi home may warn `pi-extension-skills-loaded`** (oats.aweb 1.35.0) when
  its pi folder's `settings.json` lists `npm:@awebai/pi` without
  `"skills": []`. The warning names the file and the one entry to change; the
  extension still loads, and `pi install` and `pi update` keep the filter.
- **Where `oats.aweb-tasks` is composed, readiness gains one provider item.**
  With no `team` setting it passes and reads nothing.
- **Since oats.aweb 1.33.2 (pinned from 0.69.10 on), spawn and readiness warn
  `aw-newer-than-tested`** when the aw on PATH is newer than the aw the
  provider is tested with and the home's team root names a service other than
  the aweb Cloud: a server on an older aweb may refuse it. The fix it names
  first is upgrading that server's aweb. Cloud homes never warn, and it is
  never a refusal. (0.69.10's notes left this out.)
- **A workspace sets `tasks:` only once every deployment that reads it runs a
  kernel listing `workspace-tasks-payload`** (`oats version --json`
  features). An older kernel refuses the whole file, so every resolve and spawn
  on that deployment stops. A file without `tasks:` resolves exactly as before.
- **A capability's `committedOnly` setting is enforced only by kernels with
  `settings-committed-only`.** An older kernel ignores the flag and still merges
  the key from oats-local.yaml and `--provider`. A provider that relies on it
  sets its kernel range to this release or later.

## Added

- **A workspace `tasks:` payload** (feature `workspace-tasks-payload`). The
  workspace file may carry a top-level `tasks:`, an opaque payload for whichever
  capability fills the tasks slot, merged at the same layer as `messaging:`:
  the manifest's defaults, then the workspace's `messaging:` or `tasks:`, the
  soul's slot payload, oats-local.yaml `settings.<cap>`, then `--provider`. Its
  leaves' origin is `{kind: "workspace", at: "oats-workspace.yaml#/tasks"}`. A
  `hostOnly` key or `byTeam` in it is refused, as in `messaging:`. There is no
  workspace `knowledge:` payload
  ([Provider payloads have three homes](../workspaces.md#provider-payloads-have-three-homes),
  [awebai/oats#1719](https://github.com/awebai/oats/issues/1719)).
- **`committedOnly` settings** (feature `settings-committed-only`), the mirror
  of `hostOnly`. A manifest's `settings.<key>.committedOnly: true` makes the
  resolver refuse that key in oats-local.yaml `settings.<cap>` and in
  `--provider <cap>` with `E_WORKSPACE_SCHEMA`, reason `committed-only-key`. The
  key's presence is refused, even with the committed value. The refusal names
  the key, where it was set, where it may be set (`details.allowed`) and the
  fix. For a messaging or tasks capability, that is oats-workspace.yaml under
  `messaging:` or `tasks:`, or a soul's slot payload. A key marked both
  `hostOnly` and `committedOnly` is a manifest fault, `details.why`
  `settings-flag-conflict`
  ([Commands and hooks](../capabilities.md#commands-and-hooks)).
- **An unknown top-level key in oats-workspace.yaml says the workspace may be
  newer than the kernel.** Beside "unknown property", the problem adds "if this
  is not a typo, the workspace uses a feature newer than this kernel (OATS
  <version>): upgrade OATS", with reason `unknown-root-key`. Nested unknown keys
  are unchanged.

## Changed

- **`oats.framework` 1.21.0 ships two setup steps.** `oats.setup` 2.12.0's `/oats-host-delivery` gains the pi step of channel delivery: install `@awebai/pi`, then set its entry in the pi folder's `settings.json` to `{"source": "npm:@awebai/pi", "skills": []}`, so pi loads the extension without the skills it bundles (#1722). Its `/oats-upgrade` now covers a first Desktop install: on a host without the Desktop it asks whether the person wants it, and installs that release's Desktop (#1724). No command they name needs a newer OATS than `oats.setup` already admits ([awebai/oats#1665](https://github.com/awebai/oats/issues/1665)).
- **`oats.aweb` 1.35.0: one tasks team for every deployment; pi without its
  bundled skills.** `oats.aweb-tasks` gains `team: <label>`, the aweb team
  whose task list every deployment shares. It is set only in the workspace's
  or a soul's `tasks:` payload, and marked `committedOnly`. Its new readiness
  check refuses a home that has not joined the team, naming
  `oats aweb join --labels <label>` or `tasks: none`. Both pi `install` texts
  install `@awebai/pi` with `"skills": []`, and readiness warns
  `pi-extension-skills-loaded` where it still loads them. A joined team that has
  become the default is kept, with a warning, until the home is respawned
  ([awebai/oats-aweb#188](https://github.com/awebai/oats-aweb/pull/188)-[#191](https://github.com/awebai/oats-aweb/pull/191)).
- **Getting started: the steward's global address waits for a release that
  carries its route.** The skill named oats.aweb 1.35.0 as the first release
  with the resident root route, but 1.35.0 ships without it
  ([awebai/oats-aweb#147](https://github.com/awebai/oats-aweb/pull/147) is not
  merged). It now names no version and always takes the fallback, a local team
  identity, until a release carries the route. That was already the outcome on
  1.35.0, because the plan fell back; only the stated version changes.
- **Getting started: fixes from a second round of newcomer runs on fresh machines.** In `oats-getting-started`:
  - **The whole file:** its description and its first line tell the agent to download it whole with `curl -fsSL` and follow it as written; a summary of it, from a web fetch that summarises, is not the procedure.
  - **One change per command:** each change step 1's yes named runs as its own command, never batched with others, so a permission check that reads the conversation sees it by name. A refused command is never split into pieces or re-run in parts, `sudo` included: the agent asks the person once, naming the change, and retries once on their yes.
  - **The time budget:** the setup takes a few minutes and seconds of the person's time. The agent waits about a minute for the Desktop's background download once the CLI is installed; when it hasn't verified by then, it goes on without the Desktop and records that in the hand-over; the person can install it later with the setup expert, through `/oats-upgrade`. `/oats-upgrade` (oats.setup) now covers that first install: on a host without the Desktop it asks whether the person wants it, and its Desktop step installs that release's Desktop.
  - **A terminal window on Linux** that `systemd-run --user` can't open (no user session bus) is started directly and detached (`setsid -f xdg-terminal-exec` or `setsid -f x-terminal-emulator`, with the display variables the agent already has, never guessed) before the person is given a command to type.
  - **GitHub:** the skill always checks the login, even right after it installed `gh`, before starting a device login.
  - **A monorepo host:** step 1's one yes names the two setup files pushed straight to its default branch (which runs its automatic checks or deploys), and step 7 pushes them without asking again. A repository others can push to, a protected default branch or a refused push takes a pull request instead, and the hand-over records the skeleton as pushed or merged.
  - **The hand-off** names no versions, package sources or internal flags or codes, and the setup expert, when named as the Desktop lists it, only by its display form; anything the person may want later goes in the hand-over file.
  - **pi's skills filter** matches `npm:@awebai/pi` alone or with a version, never another `@awebai/pi-…` package. The skill now says that Claude's aweb channel plugin still carries one skill of its own until aweb ships it without one, a known gap ([awebai/oats#1665](https://github.com/awebai/oats/issues/1665)).

## Documentation

- **`/oats-host-delivery` installs the pi extension without its skills.** `oats.framework`'s host-delivery skill gains the pi step of channel delivery: the setup expert runs `pi install npm:@awebai/pi`, then makes the extension's entry in the pi folder's `settings.json` `{"source": "npm:@awebai/pi", "skills": []}`, so pi loads the extension and none of the skills `@awebai/pi` bundles. A home gets its skills through its OATS capabilities only. The filter is interim, until aweb publishes the extension without skills; oats.aweb's readiness warns `pi-extension-skills-loaded` while it is missing.
