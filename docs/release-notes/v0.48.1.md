# OATS 0.48.1

## oats.okf 5.0: proposals at checkpoints, not a harvest engine

The official catalog and reference workspace pin oats.okf 5.0.0. Working
instances update their notes at important checkpoints, write their own
proposal, and directly spawn `oats.okf/knowledge-harvester`. The harvester
checks the actual source, accepted knowledge and open/recent harvest PRs,
then opens a normal Git PR for maintainer review. No host harvest setting,
scheduled harvest jobs, source capture/worker/drain machinery or automatic
retirement harvest remains. Transcripts are not a default input.

The sole opt-out is in the soul: `knowledge: { harvest: off }`. Consultation
still works, no checkpoint-harvest direction is given, and the harvester
refuses that source in its required spawn hook. Directory bases remain
consultable, but harvesting requires a Git base with a reviewed PR path.

## Deployment cutover — order matters

1. **While still using oats.okf 4.2, finish or explicitly dispose of any
   registered 4.x sources.** Settle active harvesters and held drains, and
   decide the disposition of remaining private inputs and open PRs. Do not
   silently delete or re-import old custody. A registered old source retired
   after the pin can refuse with `E_HARVEST_CONSENT_UNKNOWN` and retain its
   home; finish that old-provider work before changing the pin.
2. **Pin and sync oats.okf 5.0.0**, using the deployment's normal reviewed
   package update and approval process. This makes the new administration
   command available; it does not replace modules in running homes.
3. **Before any new spawn, remove explicit legacy host settings** using the
   new, guard-exempt command, from the deployment directory and with a soul
   that selects oats.okf:

   ```sh
   oats okf setup --remove-legacy-settings --soul <soul> --plan --json
   oats okf setup --remove-legacy-settings --soul <soul> --json
   ```

   The plan writes nothing. Applying removes only the explicit host keys
   `settings.oats.okf.harvest`, `harvest-runtime` and `harvest-model`, keeps
   the file's permissions, and never changes the soul opt-out. Unsupported
   YAML shapes refuse without writing; report them to the deployment owner.
   **Between steps 2 and 3, a new spawn with those old host keys refuses
   with `E_REMOVED`; the refusal names this cleanup command as the fix.**
   The cleanup command did not exist in 4.2: it cannot run before step 2.
4. **Respawn homes that should propose knowledge.** Existing homes keep
   their copied modules, skills and briefings; their own commands, hooks and
   checks still run those old modules. A source record with an explicit
   host-origin legacy key continues to be refused by the 5.0 harvester even
   after host cleanup, until the source is respawned. A recorded 4.x
   `manifest-default` is nobody's decision and is ignored by the 5.0 reader;
   it alone does not require respawn, but the new proposal briefing does.

A proposal must contain exactly one `Source: instance <name>, home <path>,
soul <name>` line naming an actual recorded source. Spawn the harvester with
`--relation unrelated` alone, never with `--relative-to`; source-pair
consistency does not establish proposer authorship. Claims are untrusted
data and enter commit/PR message files, not shell command text.

This package pin changes no production kernel contract. Package mirrors are
generated from the exact pinned payload; the clean-room and provider-facing
tests exercise the 5.0 contract rather than restoring removed 4.x machinery.
