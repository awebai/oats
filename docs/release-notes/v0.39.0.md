# OATS 0.39.0

## Added

- **`oats server connect`: put this workspace on another machine and register
  it, in one run** (awebai/oats#517, feature `server-connect`). From a
  deployment, `oats server connect <id> --ssh <host>` takes a machine you reach
  over ssh, even one with no OATS and no deployment, to a registered, synced
  deployment of the same workspace. Six steps (`ssh`, `oats`, `git`,
  `deployment`, `register`, `readiness`) are re-checked on every run, and each
  does only what is missing. `--install-oats` installs exactly this kernel's
  version with npm on the host. The deployment goes to `~/Agents/<this
  deployment's directory name>` there unless `--dir` says otherwise; a
  non-empty directory is never written into. What only a person can do (Git
  credentials on the host, a provider's configuration) comes back as
  `needs-human` with the exact remedy; run the same command again afterwards.
  See docs/servers.md, "Connect a machine".

- **A registration knows which workspace it serves** (feature
  `servers-per-workspace`). `~/.oats/servers.json` registrations record
  `workspaceKey`, the canonical workspace key the host's deployment reports.
  It is learned from the host, never typed: `server add` records it when the
  host answers, `server check` fills it in when it is missing, and a host that
  reports a different key is refused with `E_SERVER_WORKSPACE_MISMATCH`
  without rewriting the registration. `oats server list --workspace-ref <ref>`
  lists one workspace's servers and reports `unknownWorkspace`.

- **Capability commands run on a server with `--server <id>`** (feature
  `capability-route`). For example, `oats aweb setup --join aweb
  --invite-stdin --soul dev --server altair-aweb` runs `oats aweb setup …` in
  the registered deployment on that machine, with stdin forwarded untouched
  and the host's output, exit status and `--json` envelope relayed. Invite
  values are redacted wherever the command line is printed.

- **macOS hosts say why a private remote is unreadable over ssh.** On macOS,
  in a session without a terminal (every routed command runs in one), Git
  cannot open the login keychain where its credential helper keeps the forge
  token. An `auth` failure there now carries `details.hint:
  "keychain-non-interactive"` and names the remedies: store Git credentials
  outside the keychain (`gh auth login --insecure-storage`, then `gh auth
  setup-git`) or use an SSH key. `oats server check` reports whether the
  host's Git reads the workspace remote (`workspaceReadable`).

- `oats onboard <dir> [--workspace <ref>] --check --json` answers, without
  writing anything, where `<dir>` is, what is there, and whether this
  machine's Git reads the workspace remote. `server connect` asks it of the
  host.

## Upgrading

- Install the CLI and the Desktop 0.39 together. An older kernel on the same
  machine refuses a `servers.json` holding `workspaceKey` (an unknown field),
  so don't downgrade once 0.39 has written registrations; removing the
  `workspaceKey` lines by hand makes the file readable to an older kernel
  again.
