# OATS 0.44.0

## Added

- **The launcher can answer one launch prompt for a home you opt in**
  ([#708](https://github.com/awebai/oats/issues/708)). `oats-local.yaml`
  gains the host-only strict boolean
  `launchPromptAnswers.homes.<canonical-home>.awebDevelopmentChannel`, default
  false: no existing home is opted in, and provider development mode is not
  consent. For an opted-in home, a spawn or start the kernel itself launches
  answers Claude Code's aweb development-channel confirmation with one Enter,
  and only on an exact match of a qualified fixture (Claude 2.1.289,
  `darwin-arm64`, 110x35, bound to the executable's SHA-256; completion frames
  with the aweb plugin absent or installed). Everything else is blocked:
  folder trust, API keys and any other or changed prompt. Session input and
  wake delivery gain no prompt authority.
  - The spawn preview reports the home's effective policy and its source
    (`launchPromptAnswers`), and an opted-in launch warns that a harness
    update can block it until fixtures are refreshed. There is never a
    fallback key or a broader matcher.
  - A blocked or uncertain launch keeps the home and pane and answers
    `E_SPAWN_INCOMPLETE` with additive `launchPrompts` details (`status`,
    `answers`, `reason`, `receipt`). Inspect the pane; never resend or
    relaunch automatically. A submitted answer is not readiness, and a
    retained `launched:false` is not proof the process is gone.
  - Every answer and every outcome is a checked `launch-prompt` instance
    event, including metadata or receipt failures after the controller
    finished. A replaced home is the one exception: nothing is written into
    the replacement.
  - `workspaceTrust` is refused with instructions to remove it; folder trust
    is [oats#712](https://github.com/awebai/oats/issues/712).
  - Other model, billing, effort or permission banners after a submitted Enter
    still block (`E_SPAWN_INCOMPLETE`, `blocked`).

  See [configuration](../configuration.md#exact-home-launch-prompt-consent)
  and [recovery](../execution-targets.md#launch-prompt-outcomes).
- **The Desktop shows launch-prompt consent and retained launches**
  ([#711](https://github.com/awebai/oats/issues/711)). The spawn dialog shows a
  home's development-channel consent and its source. A retained launch says
  why and gives one next step: inspect the existing pane, then
  `oats session start --home` (no new spawn, no retry). Activity shows
  `launch-prompt` events.
- A provider's readiness binding check and a layer operation
  (`oats operation run`) get `OATS_SOUL_ID`, and `OATS_AGENT` with the value
  the soul's hooks and dispatched commands get, from a home and with
  `--soul`: every provider surface now sees one soul identity
  ([#707](https://github.com/awebai/oats/issues/707)). The readiness answer is
  unchanged. See [Readiness check](../capabilities.md#readiness-check-bindingcheck).
- Readiness and doctor warn when a workspace has no operator soul
  ([#671](https://github.com/awebai/oats/issues/671)). An operator soul is a
  soul the workspace offers that composes `oats.setup`. The codes are:
  - `operator-soul-missing`: no such soul;
  - `operator-team-uncovered`: none is eligible for a team;
  - `operator-coverage-unknown`: coverage cannot be read. It never asserts
    absence.

  Detection is by composition, never by a soul's name. Disabled and
  unresolvable souls do not count, nor does one that empties a layer the
  workspace fills. These are warnings only (`required: false`): nothing
  refuses or spawns, and an eligible soul is not a launched seat.
  - Readiness reports the subject's own teams.
  - Doctor stays offline. It resolves from this machine's cache, which `oats
    souls` fills, and checks every declared team. When the cache cannot answer,
    it says coverage is unknown.

  See [Operator coverage items](../desktop-cli-api.md#operator-coverage-items).

## Changed

- **A team label is at most 64 characters**
  ([#726](https://github.com/awebai/oats/issues/726)). Both
  `oats-workspace.yaml` and `oats-local.yaml` now refuse a longer label. The
  refusal is `E_WORKSPACE_SCHEMA`, and the message names the label and the
  64-character limit. `oats teams add` and a trigger's `spawn.teams` apply
  the same bound.
  - **Who this breaks:** a workspace or deployment with a label over 64
    characters. The Desktop could never show such a label: it refused the
    whole readiness answer.
  - **What to do:**
    - Shorten the label wherever it is used: `teams:`, `defaultTeam:`,
      `souls:`, oats-local.yaml, and a trigger's `spawn.teams`.
    - Respawn any instance whose recorded default team had the long label.
      It keeps its spawn-time record, so readiness for it still reports
      the long label.

  See [Teams](../desktop-cli-api.md#teams).
- For `--soul` on a package soul, a readiness binding check and a layer
  operation get `OATS_AGENT` as `<package>--<soul>`, the value its hooks
  get, instead of the bare soul name.
- **Ordinary parent spawns refuse an edited anchor**
  ([#708](https://github.com/awebai/oats/issues/708)). A `relation: parent`
  spawn keeps its post-launch lineage timing but now refuses when the anchor's
  `instance.json` was edited or removed since the spawn read it, instead of
  overwriting the change with stale data.
- **Retirement keeps a recovery copy after a blocked spawn**: a blocked
  spawn's kernel metadata transition counts as a changed home, so retirement
  keeps a recovery copy even when no authored bytes changed.
- **The Desktop accepts OATS CLIs `>=0.25.8 <0.45.0`**, so it runs against
  this release's kernel; the Desktop 0.43.x refuses a 0.44 CLI. Upgrade the
  Desktop and the CLI together.

## Fixed

- **Readiness clips long item text**
  ([#725](https://github.com/awebai/oats/issues/725)). An item's `reason`,
  `remedy` and kernel `problems[].message` are at most 1000 characters,
  clipped with `…`. A provider's refusal code over 128 characters, or with
  control characters, is reported as `provider-unavailable`. Before, a long
  remote error made the Desktop refuse the whole readiness answer. One
  example is the workspace discovery error in the member and package-soul
  items. A provider's own `result` is still relayed verbatim.
- **A commit the read just fetched is no longer reported missing**
  ([#728](https://github.com/awebai/oats/issues/728)). When a read's deadline
  or git's own timeout ended the check that a commit is in the cache, the
  read reported the commit missing or "not a commit" (`not-found`), even one
  it had just fetched. git's timer can fire a moment before the wall
  clock reaches the deadline. Such a check is now the read's `timeout`
  (`E_REMOTE_UNREADABLE`, reason `timeout`, stage `fetch`), judged by git's
  own result. This covers a commit already in the cache, too: it is no
  longer refetched or reported missing after a timed-out check. No new codes
  or fields.

- **`oats sync --plan` previews; it used to apply**
  ([#731](https://github.com/awebai/oats/issues/731)). `sync` ignored
  `--plan`, so the "preview" wrote the lock. `--plan` now runs the same
  discovery and resolution and gives the same report (`plan: true` in JSON;
  the text says what a bare `oats sync` would change) and writes nothing: no
  lock, no `agents/`, no automations snapshot. `oats sync` also refuses a flag
  or positional it does not read with `E_BAD_ARGS`, naming it and the usage,
  instead of ignoring it. A script that passed an unknown flag to `sync` now
  fails: drop the flag. See [`oats sync`](../desktop-cli-api.md#oats-sync).

- **Schedule doctor distinguishes retained attempts from unknown observations**
  ([#584](https://github.com/awebai/oats/issues/584)). Offline workspace warnings
  describe saved placement exclusions or unverifiable authorization instead
  of promising a reconciliation command that cannot run. Unknown observations
  without an attempt no longer claim execution is blocked pending reconciliation.
  For a local schedule whose retained state doctor cannot vouch for (captured
  execution state, an invalid or mismatched stored definition or ID, unreadable
  lock custody, or invalid local configuration), doctor no longer prints a
  reconcile command and says why instead. This fixes diagnosis only:
  retained-state recovery outside current workspace placement remains
  unsupported, and attempts, locks and slot rules are unchanged.
- A restart no longer brings back older launch settings from the receipt of
  a start that had already completed
  ([#691](https://github.com/awebai/oats/issues/691)). A start keeps its
  launch receipt, and the next start replayed it over `instance.json` even
  when `instance.json` already recorded that start: an older launch recipe
  (hook env, contributions) and older provider metadata replaced newer ones
  before the launch hooks ran, and a plain `session start` on a running
  instance wrote them before answering `E_SESSION_RUNNING`. Now a receipt for
  a recorded start, on the recorded target, is never applied again. With
  such a receipt, a plain start on a running instance answers
  `E_SESSION_RUNNING` with nothing written and no hook run; a restart, or a
  start after the target is gone, starts from `instance.json` as it is, and
  its new receipt replaces the old one. An interrupted start (its metadata
  write failed) is still adopted as before, with no second launch. A receipt
  that names the recorded start on another, still running target is refused
  as ambiguous (`E_SESSION_UNKNOWN`); the message names that target, and a
  restart once it is stopped clears it. Nothing needs editing by hand. See
  [Start and restart](../desktop-cli-api.md#start-and-restart).
