# OATS 0.64.0

Unreleased

## Upgrade

- **Install the Desktop first and the CLI second,** as
  [Upgrading](../upgrading.md) says: a 0.63 Desktop refuses a 0.64.0 CLI. The
  0.64.0 Desktop accepts OATS CLIs `>=0.26.0 <0.65.0`.

- **The official catalog moves oats.framework 1.13.2 → 1.13.3** (oats.core
  2.6.5 and oats.setup 2.8.2, see Provider updates). The other packages are
  unchanged. A deployment takes it by moving its `oats.framework` pin and
  running `oats sync`. Only new spawns use it.

- **Coming from 0.61 or earlier:** do 0.62.0's Upgrade steps too (the capture
  service's `oats setup`, once per user on each host, from that user's shell).

## Changed

- **One way in: the README's "Start here" points to the
  `oats-getting-started` skill**, which a person's own coding agent
  downloads verbatim and follows ([#1314](https://github.com/awebai/oats/issues/1314)).
  - **The skill is rewritten.** It asks one round of questions: the use case,
    the existing repositories, the knowledge tools, new or existing
    workspace, messaging, harness and deployment directory.
  - **It installs what is missing,** then OATS Desktop and the CLI at the
    same version (with the pi bridge, `@awebai/oats-pi`, when the harness is
    pi). The Desktop comes from the release asset, downloaded with
    `gh` and checked against `SHA256SUMS.txt` and its attestation; on Linux it
    installs per user and shows in the app launcher.
  - **The GitHub login** is gh's device flow, which the agent starts and the
    person approves in their browser.
  - **A new workspace** becomes a private repository holding the workspace
    file, its membership and one thin soul,
    `<workspace>-oats-setup-expert`, which holds `oats.setup` and has no
    knowledge of its own, so it spawns on a machine before knowledge is set
    up there. It takes the workspace's messaging, so it stays the
    workspace's operator. **An existing workspace** is onboarded as it is;
    when it has messaging, the skill sets it up on the machine before the
    spawn, with an invite token the person types in their own terminal.
  - **Then** the skill spawns the setup expert with the person's answers as
    its task, and the expert does the rest (`/oats-setup-expert`,
    oats.framework 1.13.0). An existing workspace without a setup soul gets
    one first, from its owner, by pull request.
  - The Desktop is started on the new deployment, and the TUI is offered.
  - The person types only passwords, logins and tokens, and no secret passes through
    the agent.

- `spawnOrigin` now describes the caller independently of lineage: valid
  instance context in this deployment records `instance`; otherwise `operator`,
  including operator spawns with `--parent`. Existing instances keep their
  recorded values, whose older meaning followed the relation. Attribution is
  informational and does not change permissions (#1371).

- Desktop: the command palette (⌘K / Ctrl+Shift+K) now shows the sidebar's
  tree, with the sidebar's lines and state dots, ordered by the instance you
  focused most recently. A group or a parent moves up when you focus any
  instance under it, and a child stays under its parent. This replaces the
  flat Recent group. The palette still opens on the agent you were on before,
  and the sidebar keeps its own name order (#1383).

- **OATS Desktop accepts an `oats` CLI 0.64.x.** Its band is now
  `>=0.26.0 <0.65.0`. 0.64 adds no new gate on the band: `spawnOrigin` keeps
  its `instance`/`operator` values, which the Desktop passes through without
  reading, and the Desktop already shows a fallback shell as `shell` (#1387).

## Fixed

- Shared spawn help now lists the existing `--base <ref>` flag beside `--branch`
  and explains its worktree-only scope and default to the soul commit observed
  by spawn (#1370, #445).

- `oats spawn --help` and `oats help` now list the full existing spawn flag
  inventory, including decision replay, scope, launch, child policy and wake
  options, with compatibility and internal inputs labelled. Flag behavior is
  unchanged (#1373).

- Status and session inspection now recognize a fallback shell when tmux
  reports an empty or `unset` pane command, so a stopped harness no longer
  appears to be running in that case (#1381).

## Provider updates

- **oats.framework 1.13.3: oats.core 2.6.5 and oats.setup 2.8.2.** Text
  only: neither capability's floor (`compatibility.oats`) changes.
  - **`/oats-operate`** says what `spawnOrigin` records from OATS 0.64.0: the
    caller's context (`instance` from a valid instance environment in this
    deployment, otherwise `operator`), independent of the relation. It is
    attribution, not a permission check, and a remote spawn records the
    host side. The skill also says how `--branch` and `--base` choose a
    worktree's branch and start point
    ([#1371](https://github.com/awebai/oats/issues/1371),
    [#1370](https://github.com/awebai/oats/issues/1370)).
  - **oats.setup names the right OATS version for the getting-started entry
    path.** `/oats-setup-expert`, `/oats-setup-model` and the oats.setup
    briefing said the `oats-getting-started` skill writes the setup expert's
    hand-over and creates its soul from OATS 0.62.0. That skill first ships
    in 0.64.0, and they now say so
    ([#1314](https://github.com/awebai/oats/issues/1314)).
