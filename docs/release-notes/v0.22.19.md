# OATS v0.22.19

Version 0.22.18 was tagged but never published: its hosted gate failed on
four tests that pass on macOS and fail on Linux (two launch tests calling
the kernel directly resolved the real harness binary on the test process
PATH, one launch test spawned zsh, which the runner does not install, and
one capture-lock test where Linux reused the inode of an unlinked
directory). The tag stays fixed and unpublished. This release carries the
same content with the corrections below.

Choose how an agent runs without replacing its home. Desktop offers
**Start…** for stopped instances and **Restart with…** for running
instances, with harness, model, permissions and named launch
configurations. The kernel records what each home was started with and
starts it again the same way.

## Named launch configurations

Define a reusable configuration in a scope's `oats-config.yaml`, or use
**Manage launch configurations** in Desktop. A configuration chooses `pi`,
`claude` or `codex`, an optional executable or wrapper, literal arguments,
environment values or references, a default model and the shared `yolo`
setting.

```yaml
launch-configs:
  codex-personal:
    runtime: codex
    args: ["--profile", "personal"]
    yolo: true
```

Arguments are passed literally; native configuration files and account
settings stay under the harness's control. For environment credentials use
a reference such as `API_KEY: {fromEnv: PERSONAL_KEY}`: the execution host
resolves it each time the agent starts. The recorded recipe, receipts,
previews, roster answers and spawn answers do not expose the value (the
launch itself and its transport necessarily use it). A configuration cannot name the kernel's own launch
environment or override environment a capability owns.

An existing instance keeps its recorded launch configuration even if the
scope's definition changes or disappears. Select a named configuration
explicitly to apply its current definition. Changing only the model or
permissions keeps the rest of the recorded invocation; choosing a harness
without a configuration starts that harness's defaults, with no model
carried across harnesses.

`oats launch-config list | set | remove | preview` author and inspect
configurations; `oats spawn --launch-config` starts a new instance under
one; a soul may name a default (`launch-config:` in soul.yaml,
`oats soul set --launch-config`).

## Restart in place

`oats session start` with a selection validates the requested launch
(recipe, executable, references, capability preparation, runtime packages)
and starts a stopped instance; it never stops a running harness. Only
`oats session restart` does: it runs the same checks first, then sends
SIGTERM to the harness under the pane's launcher and waits a bounded time
for it to end; it does not escalate to a forced kill and refuses to launch
a second harness if it cannot confirm the first has stopped, reporting what
was signalled and observed. The instance keeps its home, identity, work and
notes; OATS does not transfer a native conversation between harnesses.
Save work before restarting.

Capabilities take part through what was captured for the home: a capability
may declare a `launch` hook to prepare another harness (under the settings
captured at spawn, with the scope's current manifest and trust); a
capability that contributed harness-specific arguments and cannot prepare
the new one refuses the switch. Homes that predate launch recipes are
converted narrowly from their recorded command when a selection asks for
it; unrecognized arguments are refused by name.

One limitation, stated rather than hidden: a runtime-package requirement is
verified with the package manager's controlled list command under the
launch's environment and executable, which cannot carry a configuration's
arguments. When such a requirement applies and the configuration passes
arguments, the launch is not reported verified (`E_LAUNCH_PROBE_UNSUPPORTED`):
put native configuration a required package must see in a wrapper
executable or the environment.

```sh
oats launch-config list --dir /path/to/team
oats launch-config preview --home /path/to/instance --runtime codex --json
oats session restart --home /path/to/instance --launch-config codex-personal
```

Local tmux and Herdr sessions use the same lifecycle operations. Registered
servers support configuration management and start/restart choices through
their installed OATS CLI (probe tokens `launch-config`, `session-restart`);
existing remote homes keep their saved route, and an older kernel is
refused after the compatibility probe, before any mutation or stop.

## Desktop fixes

Tabs from other workspaces stay hidden. Instance action menus are positioned
correctly when opened and remain stable through roster refreshes. Failed
launch preflight checks are shown in the invocation preview, and an accepted
launch is not presented as a running agent until the terminal is observed.

## Also in this release

- Capture lock (source only; the installed capture service is unchanged):
  nonce-checked ownership, cleanup of a failed initialization that respects
  a replacement, release outcomes reported as observed, and the privacy
  loader's exit no longer leaves a lock behind. The initializing directory
  is held open until its owner record is written or its cleanup finishes,
  preventing its inode from being reused during cleanup; a replacement
  directory is left alone.
- Test fixtures: the launch tests resolve their fake harness binaries on the
  test process PATH and exercise only the shells the host installs; no
  kernel change.
- A design proposal for managing agents from an iPhone over Tailscale
  (docs/design/2026-09-07-mobile-agent-management-proposal.md); no
  implementation ships.
