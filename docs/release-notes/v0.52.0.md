# OATS 0.52.0

Unreleased

## Upgrade

Steps 1 to 3 each stop a spawn that worked on 0.51, so do them on each host
before upgrading, in this order:

1. **Establish folder trust first**: `oats harness trust --plan`, then
   `oats harness trust`. On 0.51 a Claude start on a host without it reported a
   launched instance waiting at the trust prompt. On 0.52 every start with the
   development-channel flag is observed, so the same start ends as
   `E_SPAWN_INCOMPLETE`, `blocked: unexpected prompt`, with the pane retained.
   That is the loud miss working as designed, and it is new for every home that
   was never on the old `launchPromptAnswers` list.
2. **A host with several launch configurations for one harness** marks one
   `default: true` or names one in `souls.launch`. Until then, scheduled jobs,
   triggers and agents' own spawns that name no configuration are refused
   (`E_LAUNCH_CONFIG_AMBIGUOUS`).
3. **Remove `launchPromptAnswers`** from `oats-local.yaml`: a home entry
   `awebDevelopmentChannel: false` stops the deployment from loading.
4. **Pin oats.aweb 1.27.0.**

## Added

- **`oats tui` (preview): a terminal client (#855).** `oats tui` is a
  full-screen, keyboard-only client for people who work in terminals and on
  machines with no display. It ships inside the `oats` package: there is
  nothing else to install. **It is a preview, and this version draws the
  frame only**: it shows the frame, answers `?` (help) and `q` (quit), and
  reads nothing from the kernel yet. The views arrive in later releases, and
  while it is a preview its screens may change without notice. It leaves
  preview when the readers it shares with the Desktop are in their shared
  home, a person has used it for a working day and both maintainers agree.
  - **What it does to your terminal** is a closed list, restored on every way
    out a process can handle (quit, an internal error, SIGINT, SIGTERM,
    SIGHUP, SIGQUIT) and across `Ctrl+Z` and `fg`: raw mode, the alternate
    screen, the cursor hidden, autowrap off and bracketed paste on. It
    switches on no mouse or focus reporting and no keyboard protocol, writes
    no title, clipboard sequence or bell, and uses only your terminal's own
    sixteen colours (`NO_COLOR` is honoured). After SIGKILL no process can
    restore a terminal: `reset` is needed (inside tmux, `tput rmcup` too), and
    nothing is left in tmux.
  - **Text it did not write never reaches the terminal raw.** The screen
    draws only the TUI's own words and text that passed the display filter it
    shares with the Desktop, so a name or a message cannot write a control
    sequence.
  - **Without a terminal** on stdin and stdout, or with `TERM` unset or
    `dumb`, it exits 1 with one line on stderr naming `E_NO_TERMINAL` and
    draws nothing. `oats tui --json` is refused with `E_BAD_ARGS`: it is
    interactive, and `oats status --json` is the machine view.
  - `oats pane` still refuses, and its message now names `oats tui` beside
    the Desktop.
  - No JSON answer, configuration key, hook or lock changes, and
    `oats version --json` lists no new feature: nothing gates on this word.
    See [OATS TUI](../tui.md).

## Changed

- **The Desktop accepts OATS CLIs `>=0.25.8 <0.53.0`.** The compatibility band
  admits 0.52. Upgrade the CLI and the Desktop together: a 0.51.0 Desktop
  refuses a 0.52.0 CLI. No new gate on the band. The Desktop reads two of this
  release's features where the answering kernel names them, and makes the
  weaker claim for a kernel that does not: `lifecycle-claim-stop` (who holds
  the claim, on `E_LIFECYCLE_BUSY`) and `lifecycle-kernel-codes` (a failed stop
  row's `stillRunning: []` says the harness exited).

- **OATS confirms Claude's development-channel prompt on every start that
  launches Claude with the development-channel flag**
  ([#886](https://github.com/awebai/oats/issues/886)). When a spawn,
  `oats session start` or `session restart` (by hand or by an agent) starts
  Claude with `--dangerously-load-development-channels
  plugin:aweb-channel@awebai-marketplace`, the launcher confirms Claude's
  confirmation once, with one Enter, in the pane it created. Launching with the
  flag is the decision. There is **no consent setting and no list of homes**:
  every Claude home the messaging provider starts in development mode (the
  default `delivery: channel`, `claudeChannelMode: development`) is covered,
  existing homes included at their next start. This reverses the rule that no
  existing home is enabled automatically. To keep the prompt for a person, stop
  launching with the flag: `settings.oats.aweb.delivery: session` or
  `settings.oats.aweb.claudeChannelMode: approved`, then respawn the home. Each
  start that engages it says so in its warnings (`launch-config preview`, the
  spawn's warnings, `session start|restart`). `spawn --preview` does not yet:
  the argv comes from the provider's spawn hook, which a preview does not run (a
  kernel follow-up runs preview-aware launch hooks there).
  See [the development-channel confirmation](../configuration.md#the-development-channel-confirmation).

- **Accounts where Claude Code offers no channels, on the default
  `delivery: channel`: every start now says the instance gets no channel
  delivery.** Claude Code disables channels when telemetry is opted out (`DISABLE_TELEMETRY`, `DO_NOT_TRACK`, `CLAUDE_CODE_DISABLE_NONESSENTIAL_TRAFFIC`): a host or launch configuration that sets any of
  them is affected the same way, and oats.aweb's readiness warning names the
  three variables that do it. For such an account Claude 2.1.296 ignores
  `--dangerously-load-development-channels`, shows no confirmation, and starts
  the session with the notice `--dangerously-load-development-channels ignored
  (plugin:aweb-channel@awebai-marketplace) Channels are not currently
  available`. Before 0.52 that start reported launched and said nothing, and mail
  and chat never woke the instance. Now, when that notice block equals the new
  `flag-ignored` tolerance entry (which takes no input), OATS sends no key, the
  start succeeds, and the home records `launchPrompts: {status: "flag-ignored",
  reason: "channels-unavailable", signatureId, startId, at}`. The start's
  warnings replace the statement that OATS confirms the prompt with one that
  says what was seen and the causes to check, in order (next entry). It says so
  at every start until the cause is removed or delivery changes. The provider's readiness reports it; the kernel's
  `launch-prompt` readiness item does not. A notice in a wording no entry holds
  still ends `blocked`, like any unknown screen. **Known limit, on a first spawn:** a fresh Claude configuration can show
  another notice (auto mode becoming the default) and keep this one behind
  `1 more notice hidden`. OATS cannot see it, so that spawn ends
  `E_SPAWN_INCOMPLETE`, `blocked: unexpected prompt`, with the session running in
  the retained pane. The error and the readiness remedy then say Claude may have
  ignored the flag: look at the pane and, if the session is running, restart the
  instance; the restart sees the notice and records `flag-ignored`.

- **The flag-ignored words say what was seen, and a spawn's answer carries
  `launchPrompts`.** The start's warning reads `Claude reported that channels are not currently available and ignored the development-channel flag, so this instance gets no channel delivery: mail and chat will not wake it. Check first for a telemetry opt-out in the launch environment (DISABLE_TELEMETRY, DO_NOT_TRACK or CLAUDE_CODE_DISABLE_NONESSENTIAL_TRAFFIC: Claude Code disables channels when one is set), then whether this Claude account offers channels; otherwise change the messaging provider's delivery (its readiness warning says where the setting is). See docs/configuration.md#the-development-channel-confirmation.` The hidden-notice hint in the
  error and the readiness remedy names the same causes in the same order. Neither
  states that the account lacks channels, since a telemetry opt-out is the
  other cause, and neither names a provider setting. A successful `oats spawn
  --json` answer now carries `launchPrompts` exactly as a start's answer does
  (`completed`, `not-engaged` or `flag-ignored`), so a client learns a
  spawn's outcome from the answer, as it does a start's.

- **The match no longer depends on the Claude binary, platform or pane size.**
  The executable-hash pin, the platform gate and the 110×35 geometry pin are
  removed; the launcher never resizes a pane. The screen, with box-drawing rows
  dropped and whitespace collapsed (nothing else), must **equal** an entry of
  the tolerance list `lib/launch-prompt-fixtures/dev-channel-confirmation.json`:
  the confirmation's text, exactly one channel, the affirmative option selected,
  nothing else. One entry covers Claude 2.1.289 and 2.1.296 on macOS and Linux
  (captures and provenance in `test/fixtures/launch-prompts/`). Claude 2.1.288
  on linux-x64 at 194×50 and 80×24 is reported coverage, not a committed
  capture: the release review matched it on its own host
  ([review 5481510495](https://github.com/awebai/oats/pull/917#pullrequestreview-5481510495)).
  A new Claude wording is a new entry in a reviewed change. A screen still
  being painted is waited for, and so is a transient frame Claude paints while
  starting: an unknown screen blocks only once it has held unchanged for the
  settle window (`SETTLE`, 2 s), `blocked: unexpected prompt`, with no key, and
  the receipt says what `differed` from the nearest entry. A screen still
  changing at the 30 s bound never settled: `blocked: observation timeout`,
  with what differed kept, and an error and readiness remedy that say no prompt
  was established. A pane too narrow
  for Claude to wrap at word boundaries (about 40 columns) does not match.

- **Completion after the Enter is version-tolerant.** `SETTLE` (2 s) of
  consecutive clean captures (non-blank, no question marker, no entry; the screen
  free to change) completes. A question marker inside the window, or the
  confirmation coming back, blocks. A blank capture restarts the window. No
  complete window by the 30 s bound is `blocked: observation timeout`, and the
  error says the one Enter was sent. A question first painted more than 2 s
  after the session is working is the session's own, not a launch prompt. The footer-structure
  rule and the exact banner frames are gone, and so is their 110×35 condition.
  Private evidence is kept for every miss and every completion (recognition
  `stable-screen`). See [launch completion](../launch-prompt-completion.md).

- **The record always describes the last start.** A start that does not engage
  the confirmation writes `instance.json` `launchPrompts: {status:
  "not-engaged", startId, at}` and removes `launchPromptTarget`. A home whose last
  start was `blocked` shows a `launch-prompt` readiness warning with what
  differed and both remedies (add a tolerance entry, or press Enter after
  reading the prompt); a later start clears it.

- **Contract changes for readers.** Previews no longer carry
  `launchPromptAnswers`; `launch-prompt` events no longer carry `consentSource`
  and add `claudeVersion` and `claudeVersionSource` (read from the executable's
  real path, never by running it; `unknown` when Claude is started through a
  wrapper, whose path carries no version) and, on a miss, `differed`. A blocked
  `launchPrompts` carries `differed`, and `claudeSessionShown: true` when the
  blocked screen was Claude's running session. `launchPrompts.status` and the
  `launch-prompt` event add the value `flag-ignored`. After the Enter, a
  `blocked: observation timeout` error and readiness remedy now say the one
  Enter was sent. `oats version --json` lists the feature
  `launch-prompt-dev-channel`.

- **Folder trust for every configuration file a launch reads**
  ([#886](https://github.com/awebai/oats/issues/886)). `oats harness trust`
  writes the deployment-root trust entry into the ambient file (the operator's
  `CLAUDE_CONFIG_DIR` or `CODEX_HOME`, else the default) and into the file of
  each launch configuration whose `env` sets `CLAUDE_CONFIG_DIR` (claude) or
  `CODEX_HOME` (codex), as a literal or a `{fromEnv}` reference; files sharing a
  directory count once. `--plan` lists every file, which launch configurations
  use it and what it will write. A launch configuration whose directory is
  missing, whose reference is unset or whose path is relative is a named problem
  that refuses the command before any write. OATS never creates a harness
  configuration directory: a missing ambient one (a harness that has not run as
  this user) is `skipped` under `--harness all` and a problem when that harness is
  named; it used to be created.
  Spawn, `session start|restart`, `launch-config preview`, readiness and Codex's
  per-launch home trust read trust from the file the launch's own environment
  selects; before, they always read the ambient file. The spawn warning and the
  `harness-trust` readiness item say `<harness> folder trust is not established
  in <file>: oats harness trust --dir <deployment>`, because a missing entry does
  not prove that the harness will prompt; readiness also reports a passing item
  naming the file. OATS never answers a folder-trust prompt.
  See [harness trust](../harness-trust.md).

- **A spawn with an ambiguous launch configuration is refused**
  ([#886](https://github.com/awebai/oats/issues/886)). When the harness a spawn
  resolves to has more than one launch configuration in `oats-local.yaml`, none
  of them `default: true`, and the spawn names none, `oats spawn --preview` and
  the spawn refuse with `E_LAUNCH_CONFIG_AMBIGUOUS` (`details: {harness,
  configurations, fix}`) instead of starting the bare harness. Name one with
  `--launch-config <name>`, `--launch-config none` (the bare harness) or a
  `souls.launch` name, or mark one `default: true`. An inline `souls.launch`
  preference, the soul's own `launch:` and `--harness` alone do not count. A
  single configuration for the harness is not refused. `oats souls`, `oats
  inspect --soul` and readiness show it as the launch's `problem`. Known gap:
  `session start|restart` of an existing home, including `--harness` and
  `--reselect-launch`, keeps its behaviour and is not refused.

- **Desktop: the kernel readers moved to `packages/client/`.** The modules
  through which the Desktop reads the kernel's JSON (the CLI adapters and the
  contract decoders) now live in `packages/client/`, where a second client can
  import them. The Desktop behaves as before. In the installed app they are in
  `client/` beside `app.asar`, not inside it: `Contents/Resources/client/` in
  the macOS bundle, covered by its signature, and `resources/client/` on
  Linux. Installer CI now launches the packaged window on the Linux leg.
- **Desktop: the instance menu is built from one shared decision.** Which
  acts a roster row offers (inspect, start or restart, stop, retire) and why
  one is unavailable is now decided in `packages/client/`, where a second
  client can import it, with the roster's tree and its sections; the Desktop
  draws its menu from that answer. One thing differs: a remote row whose
  server does not report it as reachable has a menu with no items. That menu
  could not be opened before either (its button is disabled and says why), so
  the items it held were never reachable. A root test,
  `test/client-boundary.test.mjs`, pins what `packages/client/` may import
  and which of its modules and exports a second client may take.
- **Desktop: the panel is put together in `packages/client/`.** What the
  Desktop's backend makes of one deployment's observation (its rows, the
  answer when terminal status cannot be read, what a failed read becomes)
  and the workspace views over its deployments are now functions in
  `packages/client/` that keep nothing, where a second client can call them.
  The Desktop answers as before, apart from the two entries that follow. A
  test now holds that the window's page loads no module that needs Node.
- **Desktop: a row whose spawn is still setting up its worktree says that it
  can't be used until the spawn finishes.** It no longer says that it opens
  then, which was true only for a spawn started from this window.
- **Desktop: a local instance whose state OATS could not establish is shown
  as state unknown, with the reason, and no longer as stopped with a Start
  that is then refused.** Its Session card shows a tmux session only when
  OATS recorded one. A kernel read that failed once leaves the row unknown
  until the next roster read.
- **Desktop: Stop and Retire word the kernel's lifecycle answers from their
  data (#866).** **In 0.51.0 the Desktop's headline promised that waiting
  ends a busy answer also where nothing was running; from this release it
  words the answer by who holds the claim.** The 0.51.0 notes say that the
  Desktop "already words `E_LIFECYCLE_BUSY`, the answer a second retire of
  an instance now gets". That holds for a second retire. The same release
  answers the code where no command runs (a process whose start cannot be
  read, a home that changed while its claim was taken), and there the
  headline told the person to wait for another stop or retire to finish. The
  new wording needs a kernel that says who holds the claim (feature
  `lifecycle-claim-stop`, this release): against an older kernel the headline
  is unchanged, because that kernel does not say.

  Each sentence below is decided from fields of the answer and from the
  features of the kernel that gave it (for a routed command, the host's own
  list; a host whose list is not known counts as without the feature). No
  kernel message is parsed.
  - **A stop whose session stopped, and whose record failed, reads as stopped
    and not recorded.** With a kernel that lists `lifecycle-kernel-codes`, a
    failed row with `stillRunning: []`, in a stop's result or in a refused
    retire's child list, says that the harness exited and that what failed
    came after. Its line now reads "<name>: Stopped, but OATS couldn't record
    it" where it read "<name>: Didn't stop". When every failed row is such a
    row, the sentence above the rows says so. A stop: "<name> stopped, but
    OATS couldn't record it." for one target and "Every session stopped, but
    OATS couldn't record all of them:" for several, under the title "Stopped,
    but not recorded", where it read "Not every session stopped". A retire
    refused with `E_CHILDREN_RUNNING`: "The child instances stopped, but OATS
    couldn't record it for all of them, so nothing was retired." where it read
    "A child instance wouldn't stop, so nothing was retired. Other children
    may already have stopped." It is still a result that did not succeed: no
    check mark, and **Review again** is offered. Rows of mixed kinds keep the
    sentences they had. With a kernel that does not list the feature the
    Desktop shows what it showed before for every answer: there `[]` does not
    say stopped, and `/api/instance-lifecycle` carries it as `null`.
  - **A child that another command holds reads "Not stopped", with why.** In a
    refused retire's child list, and in a stop's result, a row the kernel
    answers `E_INSTANCE_RETIRING` now reads "<name>: Not stopped: it is being
    retired", and a row it answers `E_LIFECYCLE_BUSY` reads "<name>: Not
    stopped: OATS couldn't lock its home", with the kernel's own sentence for
    that row under it, shown as one line through the display filter. Both read
    "<name>: Didn't stop" before, which says that a stop was tried and failed.
    The kernel answers both codes only before any effect, so for that row
    nothing was tried. The two lines are keyed on the row's code and apply
    with every kernel: a kernel before 0.52.0 already answers an
    `E_INSTANCE_RETIRING` row for a child with a scheduled self-retire. The
    sentence above the rows is unchanged.
  - **`E_LIFECYCLE_BUSY` is worded by who holds the claim.** With a kernel
    that lists `lifecycle-claim-stop`, the kernel's busy answer to a stop, a
    retire or a plan read is read by its `error.details.holder`, and only
    `running` tells the person to wait:
    - `running`: "Another OATS command is already running. Wait for it to
      finish, then review again." (it no longer says "stop or retire": the
      holder can be a spawn), with the kernel's sentence in Details, as before;
    - `unknown`: "Nothing was done. OATS can't tell whether another command is
      still running." then "It says what to check:" and the kernel's sentence;
    - `none`: "Nothing was done, and there is no other command to wait for."
      then "OATS says what to do:" and the kernel's sentence;
    - the field absent, or a value outside that list: "Nothing was done: OATS
      refused this as busy." then "It says:" and the kernel's sentence.

    For the last three the kernel's sentence names the step that ends the
    refusal, so it is the main text under the headline, as one line through
    the display filter, and a screen reader gets it with the headline. When
    the filter withholds it, the introducing words are left out and Details
    shows that a detail was withheld. When a recursive stop is refused for the
    claim of a child, one line names it: "This is about <name>, which is in
    this plan." The name is the plan's own. With that feature the Desktop's
    own sentence for a home a spawn left ("… then retire it from the CLI with
    --force.") is no longer shown: the kernel's sentence names the check and
    the command where it offers one. Without the feature, or for a host whose
    features are not known, every busy answer reads as before, that sentence
    included, and the busy the Desktop raises itself keeps its sentence.
  - **An answer the kernel gave never reads "OATS couldn't be run for
    this."** That sentence was shown for every code the Desktop has no
    sentence for, with no kernel message. Two things change. A kernel error
    whose code the Desktop does not describe now keeps its own code and reads
    "OATS answered with an error that Desktop has no description for.", with
    the code and the kernel's message in Details, for a local answer and a
    routed one. And `E_RUNTIME_QUIESCE_FAILED` has its own sentence, "OATS
    tried to end a session or a process and couldn't confirm that it ended.",
    shown as the cause under "OATS didn't confirm the result. Check again
    before assuming nothing happened.", with the kernel's message in Details.
    Neither changes what is offered: which answers are a refusal and which an
    unknown outcome is decided as before. "OATS couldn't be run for this."
    stays for what it says: a command that could not be run, and a system
    code (`ENOENT`) from a kernel before 0.52.0.
- **Desktop: a Stop or a Retire of a home OATS cannot work from reads as a
  refusal (#866).** `E_UNIDENTIFIED_INSTANCE_HOME` is the kernel's answer for
  a home it cannot work from: its `instance.json` is there and cannot be
  read, its rollback marker cannot drive a retry, or it has neither a record
  nor a cleanup descriptor. In 0.51.0 the Desktop read that answer as "OATS
  couldn't be run for this.", with no kernel message, and an apply answered
  with it was an unknown outcome. It now reads "OATS couldn't find or read
  what it needs in this instance's home folder, so nothing was done.", with
  the code and the kernel's message in Details, for a local answer and a
  routed one. An apply answered with it is now a refusal: the kernel answers
  the code only before any effect, and the code joins the Desktop's list of
  the codes it reads so. "Nothing was done" is about the instance: its
  sessions and its home.
- <a id="lifecycle-claim-stop-changed"></a>**Stop and retire: the answers
  that changed with the claim a stop now holds (#866, #890, #895).** What
  changed, and what it fixes, is under
  [Fixed](#lifecycle-claim-stop). These answers are not what they were in
  0.51.0:
  - **A stop now needs to write its claim.** A stop whose claim cannot be
    written (a full disk is the likely case) is refused before anything is
    signalled: `E_LIFECYCLE_FAILED`, `the claim <lock> could not be taken
    (<the system's error>); nothing was done`, and the session runs as
    before. In 0.51.0 a stop took no claim: it signalled the harness
    whether or not it could write its marker, so it could fail afterwards,
    writing its own record, with the signal already sent. The way out:
    free space and stop again, or end the session by hand. See
    [A stop needs to write its claim](../desktop-cli-api.md#stop-claim-write).
  - A guarded retire whose extra trees no longer read as its plan said,
    found after the hooks, answers `E_WORK_PRESERVATION_FAILED`; it answered
    `E_PLAN_STALE`, which says that nothing happened (#895). The home and
    its work are kept, as before.
  - A retire that cannot end the worktree hook process group an interrupted
    spawn left (it survives SIGTERM and SIGKILL) answers
    `E_RUNTIME_QUIESCE_FAILED`, naming the group; it answered
    `E_LIFECYCLE_BUSY`, "nothing was retired", after two signals.
  - `oats instance stop --apply` with a `--grace-ms` that is not 1–300000
    answers `E_BAD_ARGS` as an error, before the plan is read and before the
    key is used. It answered a receipt with one `E_BAD_ARGS` row per target,
    stored under the key: a caller that read the receipt's rows for this
    now gets an error.
  - A recorded child whose claim is held when its parent is retired (a stop
    or a retire of that child is running) is a row of `childrenStopped`
    with `E_LIFECYCLE_BUSY` or `E_INSTANCE_RETIRING`, and the retire answers
    `E_CHILDREN_RUNNING`, as for any child that did not stop.
  - The message of `E_CHILDREN_RUNNING` says `still running after a bounded
    stop` only of a child whose processes were found running (its row's
    `stillRunning` lists them); of any other child that did not stop it
    says `<child> could not be stopped (<its row's code>)`. It said "still
    running" of every one. The code, `childrenStopped`, the exit status and
    the text form's line are as they were.
- **Desktop: the launch-prompt answers of this release are read and shown
  (#917).** The Desktop follows the contract above with every kernel it
  accepts. Each new field is read when the answer carries it: nothing is
  gated on `launch-prompt-dev-channel`, and no reader of a field that a 0.44
  to 0.51 kernel sends is removed, because a routed host can run one and a
  home keeps what an older kernel recorded. Against this release's kernel the
  Spawn dialog shows no "Launch prompts" note: a preview carries no
  `launchPromptAnswers`, and `oats spawn --preview` cannot report the
  confirmation (#912). What a person reads differently:
  - **When OATS could not keep its own evidence of a launch, the outcome
    shows its reason instead of "Launch requires inspection".** Four reasons
    the kernel writes join the Desktop's set: `private launch evidence
    retention failed`, alone and as the suffix of three blocked reasons.
  - **When OATS stops at a screen that is not the confirmation it answers,
    Desktop shows what OATS expected and what the terminal showed.** In the
    Spawn dialog, the Start dialog and the Activity row of the event. The
    terminal's text is shown as a quote with its speaker named, through the
    display filter, and is never compared or acted on. The notice of a
    background spawn says that Activity shows it.
  - **A launch-prompt row in Activity shows the Claude version and the
    screen OATS recognised.** "Consent source" stays on the rows an older
    kernel wrote.
  - **Readiness names the configuration file of the folder-trust check, also
    when it passes.** The reason of the new `launch-prompt` warning, which
    quotes a terminal, is shown through the display filter.
  - **When a machine has several launch configurations for a harness and no
    default, the Spawn dialog says so and points to the choice, instead of
    "OATS couldn't work out this soul's defaults".** While that refusal
    stands, the first entry of Launch configuration reads "No default: choose
    one" and Spawn stays disabled.
  - **A Start or Restart that stops at a launch prompt says what happened
    and what OATS saw, instead of showing the command-line message.** The
    dialog says that OATS could not confirm the instance finished starting,
    with the kernel's reason, whether an answer was submitted, and that the
    session was kept; the kernel's own message follows under "OATS says:".
  - **A slow Start or Restart waits for OATS's own answer, up to 70 seconds,
    instead of showing a timeout after 20 seconds while the start was still
    going on.** Giving up never ends a start: the server awaits the command
    whatever becomes of the request.
  - **When a Start or Restart works but Claude Code ignores the channel
    option, Desktop says after the start that mail and chat will not wake the
    instance, with what OATS reported.** The start is not shown as a failure:
    the dialog closes and the terminal opens. The notice is shown after a
    Start and a Restart only. After a spawn the Desktop of this release
    shows none: it does not yet read the spawn's answer for it.

## Fixed

- **Schedules: an instance whose tmux server is gone reads `stopped`, with
  what to do (#921).** After a reboot, scheduled spawn jobs whose instances
  are gone from tmux show `stopped`, with the command to resume or retire
  them, instead of a silent "still running". Before, a scheduled instance
  whose recorded tmux server was gone (a reboot, a crash) read `unknown`. Its
  spawn job kept its slot and skipped every due minute as `still running`,
  forever, with nothing saying why. Such an instance now reads `stopped`
  with the note `its tmux server is gone`. Its job still keeps its slot and is
  skipped with `previous instance stopped: retire it (oats retire
  <instance>) or start it again (oats session start --home <home>)`, and
  `oats schedule run-now` refuses with the same words (`E_SCHEDULE_RUNNING`,
  which used to say "is still running"). These words apply to every stopped
  instance, one whose harness exited included, not only one whose tmux
  server is gone. Gone is judged as `oats session start` and `stop` judge
  it: no server listens on the socket, or the socket file is missing and no
  process works in the home.
  When a process still works there, the instance stays `unknown`, with that
  reason. See [Schedules](../schedules.md#what-a-run-reports).

- **Schedules: wake jobs after a reboot (#921).** A wake job whose
  instance's tmux server is gone now starts that instance's session at its
  next due minute. Before, it waited forever, skipped as unable to observe
  the session. When a process still works in the home, nothing is started.
  See [Schedules](../schedules.md#what-a-run-reports).

- **A lifecycle command never answers with a code that is not a kernel code
  (#892, #874 item 3; the raw inner code of #891).** `oats retire`, `oats
  instance stop`, `oats session` and `oats worktree add|remove` answered any
  error that had a `code` with that code, so a file the system refused to
  read, an entry removed while a retire walked the home, a claim directory
  that could not be made or a home removed under a stop came back as `EACCES`,
  `ENOENT`, `EEXIST` or `ENOTEMPTY`, with no statement of what the command had
  done. Such an error is now answered with a documented kernel code
  (`E_WORK_INSPECTION_FAILED` for an entry a retire's inspection cannot read
  or no longer finds; `E_LIFECYCLE_FAILED` for the rest; `E_SESSION_FAILED`
  for `oats session`; `E_SESSION_STOP_FAILED` inside a stop receipt and a
  retire's `childrenStopped`), with the system's own code in the new
  `error.details.cause` (`{code, syscall}`; or `{name}` for a defect of the
  kernel, a `TypeError` and its like, whose stack goes to stderr). A refusal
  the kernel words without a code, and a `tmux` or `git` command that fails,
  are answered as before: the command's general code and the message alone.
  `unsafe-config-key` and `unsafe-config-value` keep their own names. A
  retire's message ends with
  what it had done when it failed, and every error of a retire apply says the
  same as data in the new `error.details.reached`: `{phase,
  sessionStopAttempted, hooksStarted, home, recovery}`. A removal that fails
  after a complete recovery names that recovery. One value of an existing
  field changes: in a failed row of a stop's `results` and of a retire's
  `childrenStopped`, `stillRunning` is `[]` only when the harness exited. A
  stop whose signalled processes are all gone while the session still does
  not read as idle (`… is still running after <n> ms; nothing was escalated`)
  answered `[]` there and now answers `null`: nothing is established, and a
  reader that takes `[]` as "stopped" no longer does so for it. The stop
  receipt file a kernel with the feature stores says that its rows follow
  these rules (`lifecycleKernelCodes: true`, in the file alone); the replay
  of a file without it answers `null` for a failed row's `[]`, and a kernel
  code for a system's. No existing kernel code
  changes its meaning, no exit status changes, and no receipt or plan a
  command answers gains a field. `oats version --json` lists the feature `lifecycle-kernel-codes`
  for all of this: the rule about codes, `details.cause`, `details.reached`
  and what its absence means. A client that matched on a system error's name
  in one of these answers reads `details.cause.code` instead when the probe
  lists the feature, and keeps its guard for a system code when it does not.
  See
  [The envelope](../desktop-cli-api.md#kernel-codes) and
  [`error.details.reached`](../desktop-cli-api.md#retire-reached).
- **A claim no longer refuses for ever, or spins, about a holder that will
  never act again (#870, #874 items 1 and 2).** The claim is the file that
  lets one `oats retire` of a home, and one `oats worktree add|remove` of a
  purpose, run at a time. Three of its edges are closed:
  - **A holder that has exited or was killed and that its parent has not
    reaped (a zombie) is gone.** It was read as running, so the command
    answered `E_LIFECYCLE_BUSY` "… is already running … wait for it to
    finish" until the parent reaped it, which a parent that never waits does
    not do. Its claim is now taken over as any dead holder's is. The same
    holds for the three other records that name a command by pid and start
    time: a tree record in state `creating` (the next `add` or `remove`
    recovers it), a self-retire's pending marker (the next retire does what
    the completion owed), and a spawn's `inProgress` marker. **A changed
    answer of `oats status --json`:** a spawn whose process is a zombie
    reads as `rollbackIncomplete`, no longer as `spawnInProgress: true`, and
    `oats retire` completes it. A process group that a killed command left
    is still proven by its leader while that leader is a zombie, and its
    members are still ended. The start token a record names (`proc:<ticks>`,
    `ps:<lstart>`) is unchanged, so a claim or a marker written by an older
    kernel still names its live holder.
  - **A path that exists and never reads as a claim is refused, not
    retried without end.** A dangling symbolic link where the claim belongs
    made `oats retire` and `oats worktree add|remove` loop without a pause
    and without an end. Every attempt now pauses, and the command answers
    `E_LIFECYCLE_BUSY` "`<file>` is not a readable claim; inspect it and
    remove it …; nothing was done": a retire, which does not wait, after
    five retries (a quarter of a second); a worktree command, and a
    self-retire's completion, the same five retries after its 3 s wait.
  - **A gone holder whose claim cannot be taken over is said to be gone.**
    A claim file whose holder is gone and whose `nonce` is not the 32
    hexadecimal digits a claim carries (written or damaged by hand) was
    answered as a live holder, to wait for. It, and the claim at the end of
    a chain of dead takeovers too long for the file system to name one
    more (answered until now as `E_LIFECYCLE_FAILED` with `ENAMETOOLONG`
    about a file that does not exist), now answer `E_LIFECYCLE_BUSY` "the
    process that held `<file>` (pid `<pid>`) is gone, and this file is not a
    claim this kernel can take over (`<why>`); nothing was done — inspect
    `<file>` and remove it if no oats retire holds it, then retry".
  `E_LIFECYCLE_BUSY` keeps its meaning (refused before any effect) and no
  JSON shape changes: what changes is when it is answered and, in the two
  cases above, its message. `details.lock` of a worktree command's "not a
  readable claim" and "this process's start time cannot be read" refusals
  now names the file the message names, as a retire's does; it was always
  the purpose's claim, which differs only for the claim of a takeover
  (`<purpose>.lock.reclaim-<nonce>`).
  **One changed answer in a rare race, `oats worktree` only:** a command
  whose takeover ended a dead command's git step and that was then refused
  the claim (another command took it first) answered `E_LIFECYCLE_BUSY`
  "… nothing was done". It now answers `E_LIFECYCLE_FAILED`, naming the git
  group it ended first and then the refusal, with "nothing else was done";
  `details` are the refusal's. The same holds when the system refuses to
  remove that dead command's claim: "… was ended, and the claim it left is
  kept; nothing else was done", where the answer said that nothing was done.
  See
  [`oats worktree`](../desktop-cli-api.md#oats-worktree) and
  [One retire of a home at a time](../desktop-cli-api.md#retire-one-at-a-time).
- **One instance home whose record cannot be read no longer breaks the others
  (#896, first half).** A home whose `instance.json` was there and could not
  be read as a JSON object (a write cut off, a file kept from the user, JSON
  that is not an object) made `oats status` end with a stack and no answer,
  and made every other instance's stop and retire fail, because the listing
  read every record without a guard. Now that home decides only for itself.
  `oats status` lists every instance, and that home's row has the fields of a
  home with no `instance.json`, with `running: null`, `runtimeState:
  "unreachable"` and `runtimeError: "E_UNIDENTIFIED_INSTANCE_HOME:
  <home>/instance.json cannot be read (<reason>)"`. Every command about
  another instance answers as if that home were not there. The home's own
  `oats retire` (`--plan` and `--force` included), `oats instance stop` and
  `oats session start|restart` are refused with
  `E_UNIDENTIFIED_INSTANCE_HOME` before anything is read, stopped, run or
  removed; a stop and a session start did not answer that code before.
  Restoring the file from a copy makes the home usable again. A home whose
  `instance.json` is there and cannot be read cannot be removed through OATS
  yet, `--force` included. A parent whose record cannot be read has no
  recorded children for a stop or a retire: they are listed and act on their
  own. **What an operator should know:** a home whose record cannot be read
  is never stopped as anyone's child. Its session may go on running under a
  parent that was stopped or retired, and the stop's or the retire's answer
  does not name it; `oats status` is where it shows. A spawn that names such
  a home as its parent or anchor is refused (`E_SPAWN_FAILED`); before, a
  parent record holding `null` let the spawn through as if no child-spawn
  policy were recorded. **One new value in a field the Desktop reads:** a
  stop or retire plan of a home the kernel cannot look into (the directory
  itself kept from the user) says `work: {observed: false, reason:
  "E_WORK_INSPECTION_FAILED"}`, where it said `"no-worktree"`. A home with no
  `instance.json` answers as before, and so does every command when every
  record can be read; no answer gains a field, and there is no new feature
  name. See
  [A home whose `instance.json` cannot be read](../desktop-cli-api.md#unreadable-record).

- **Linux: a tmux server first started from inside a systemd service runs in
  its own scope and survives the service** (#915). A tmux server lives in the
  cgroup of the process that started it. When the schedule tick, whose
  oneshot service ends after every tick, was the first to start the OATS tmux
  server, the server and every agent in it died with the tick within a second.
  The run was then recorded `unknown`, and the job was skipped as "still
  running" from then on. The same held for a Desktop run as a user service:
  the next restart of that unit (every Desktop upgrade) took the server and
  every agent with it. Now, on Linux, a creator inside a systemd service starts
  the server with the system's
  `systemd-run --user --scope --collect --quiet --unit oats-tmux-<hash>-<random>`, with
  the same tmux command and environment as before, less any `INVOCATION_ID`
  (the scope's own is removed with the system's `env -u`, so no pane gets it). The server is a sibling of
  the service and outlives it. When `systemd-run` is missing or fails (no user
  bus), the server starts as before, and the spawn or session start answer,
  and the tick's record of that run (feature `schedule-run-warnings`), say
  that it lives inside that unit. macOS, an operator's shell, an agent's pane
  and a server that already runs are unchanged. Nothing has to be reinstalled.
  See [Execution targets](../execution-targets.md#a-server-started-from-inside-a-systemd-service).

- <a id="lifecycle-claim-stop"></a>**A stop and a retire of one instance
  no longer run together, and a killed stop no longer strands the stops
  after it (#866, #890, #895).** Feature
  `lifecycle-claim-stop`. `oats instance stop <instance> --apply` now takes
  the claim that orders the retires of a home
  (`<instances>/.oats-retirement/claims/<instance>.lock`, beside the homes),
  for the instance and for every recorded child it would stop, before it
  stops the first one, and holds them until it has written its receipt.
  - **A stop beside a retire in flight is refused** with
    `E_INSTANCE_RETIRING`, "nothing was stopped", and **a retire beside a
    stop** with `E_LIFECYCLE_BUSY`, "nothing was done": at once, before any
    effect. Before, neither saw the other: the stop wrote its marker, its
    event and its receipt into a home the retire was inspecting or
    removing, which could fail the retire closed or leave a directory that
    no command removed. A stop of a parent is refused whole when any of its
    targets is held; two overlapping stops of one parent: one stops
    everything, the other is refused whole. `oats worktree add` in a home
    whose retire is running is refused too (`E_INSTANCE_RETIRING`, "no tree
    was made"): it reads the claim and takes nothing.
  - **A stop that was killed** (SIGKILL, SIGTERM, SIGINT or SIGHUP) left
    `<home>/.oats-stop-pending.json`, a file that named no holder, and every
    later stop of that instance answered `E_LIFECYCLE_BUSY` until someone
    removed it. The file is no longer written or read. A killed stop leaves
    its claim, which the next stop or retire takes over. The name stays
    reserved: a file an older OATS left refuses nothing, does not make a
    plan's `stopPending` true, and is removed by the next stop apply of
    that home.
  - **A holder is answered before a stale plan.** A stop apply compares the
    revision it was sent once, under its claims, as a guarded retire does:
    beside a retire or a stop in flight the answer is that one is running,
    whatever the plan would read by then. `stopPending` and `retiring` stay
    booleans on every target of a stop plan and are now read from the claim
    (`retiring` also from a scheduled self-retire's marker, as before).
  - **`error.details.action`**, the holder's verb (`"retire"`, `"stop"`), on
    these refusals, beside `lock`, `pid` and `since`; a claim without a verb
    (an older kernel's) reads as `"retire"`. `details.instance` and
    `details.home` are of the home whose claim refused: in a recursive stop
    that may be a child of the instance asked for.
  - **`error.details.holder` on every `E_LIFECYCLE_BUSY`** of `oats retire`,
    `oats instance stop` and `oats worktree add|remove`: `"running"` (a
    process with the recorded pid and start time is alive: waiting ends it
    when that process is the `oats` command its file names), `"unknown"`
    (whether one runs cannot be read) or `"none"` (nobody is running: do
    what the message says). A reader treats an unknown value, or the field's absence, as "do
    not promise that waiting ends it". For `"unknown"` and `"none"` the
    message names the step that ends it; four refusals gained one or were
    reworded for it (a claim file that cannot be read, a command whose own
    start time cannot be read, an interrupted add's rollback that could not
    be completed, a tree record written at the same moment).
    **`"running"` is a live process, not a verified command:** a file that
    names any live process reads as `running`, whoever wrote it. So the
    three sentences of a claim whose holder runs now also name the check
    for a holder that does not end, in the words the `unknown` refusal
    already had: `a retire of <name> is already running (pid <pid>, since
    <at>); nothing was done — wait for it to finish; if it does not end,
    check that pid by hand, and if it is not an oats retire, remove <lock>,
    then retry`; `another oats worktree add or remove of purpose <purpose>
    is running (pid <pid> holds <lock>); nothing was done — retry when it
    has finished; if it does not end, …`; and `<name> is being retired (pid
    <pid>, since <at>); nothing was stopped — if it does not end, …`, which
    does not say to wait. The codes and `details` are as they were.
  - **The codes a stop and a retire answer only before any effect are one
    list in the kernel**, by verb, and the docs table is checked against it:
    `E_BAD_ARGS`, `E_PLAN_STALE`, `E_INSTANCE_RETIRING`, `E_LIFECYCLE_BUSY`,
    `E_HOME_MISMATCH`, `E_SESSION_UNKNOWN`, `E_AMBIGUOUS_INSTANCE`,
    `E_UNIDENTIFIED_INSTANCE_HOME`, and the router's `E_REMOTE_INCOMPATIBLE`,
    `E_AMBIGUOUS` and `E_SNAPSHOT_UNKNOWN`. A listed code that a stop or a
    retire would answer after its first effect is a defect of the kernel,
    answered as one (`E_LIFECYCLE_FAILED`, its stack on stderr), never as
    "nothing happened".
  - **A claim that is taken again and again by commands that die ends in a
    refusal of its own.** A retire, a stop or a worktree command takes over
    the claim of a holder that is gone and tries again. Once its wait is
    over, when it has found the claim without a live holder five times and
    each time found it taken again, the last time by a process that is
    gone, it answers `E_LIFECYCLE_BUSY`, `holder: "none"`: `the claim <file>
    was found without a live holder 5 times and was taken again each time,
    the last time by a process that is gone (pid <pid>); nothing was done —
    run the command again` (a stop says `nothing was stopped`). Nothing is
    wrong with that file, and the next run takes it over. It is not the
    refusal of a file that cannot be taken over, which says to inspect the
    file and remove it.
  - **Text of a claim file is never part of an answer.** A claim is read
    back as whatever is in its file, and the claims of a deployment's homes
    are in a directory that every instance of it can write: an instance
    could put a sentence in `action`, `at`, `pid` or `processStart` and
    have it shown to whoever ran a stop or a retire. A refusal now names
    the holder's pid, its recorded start and the time it took the claim
    only when each has the shape the kernel writes; otherwise the message
    says `?` (`none` for the start), and `details.pid` and `details.since`
    are `null`. `details.action` is `"retire"` or `"stop"`, and anything
    else in the file reads as `"retire"`. The same for the claim of a
    purpose (`oats worktree add|remove`, whose refusal then has no
    `details.pid`), and for the recorded start of a process group whose
    leader cannot be read (a claim's git step, a tree record's or an
    interrupted spawn's hook group): `recorded start none`, and
    `details.gitStart: null`. No answer changes for a file the kernel
    wrote. See
    [`error.details` of a claim's refusal](../desktop-cli-api.md#claim-file-text).
  **The answers that changed** are under
  [Changed](#lifecycle-claim-stop-changed).
  Two kernel versions acting on one deployment at once are not covered: an
  older kernel takes no claim for a stop. Upgrade with no lifecycle command
  in flight. See
  [Commands that meet on one home](../desktop-cli-api.md#lifecycle-pairs),
  [the list](../desktop-cli-api.md#before-effect-codes) and
  [`details.holder`](../desktop-cli-api.md#busy-holder).

## Removed

- **`launchPromptAnswers` decides nothing.** In `oats-local.yaml`, a block
  with only `awebDevelopmentChannel: true` entries, an empty block, or
  `workspaceTrust`, is ignored with one warning per command saying to remove it.
  A home entry `awebDevelopmentChannel: false` is an operator's refusal this
  kernel cannot honour, so it is refused (`E_WORKSPACE_SCHEMA`, reason
  `removed-key`, at that entry), naming the two settings that keep the prompt
  unanswered. Remove the block.

## Provider updates

- **Minimum provider: oats.aweb 1.27.0** (`compatibility.oats >=0.52.0`). It
  reads `launchPrompts.status` for its `channel-dev-confirmation` readiness
  warning, which stays quiet for a home whose last start completed the
  confirmation and warns for one recorded as blocked. It treats `flag-ignored`
  as not confirmed and warns that the channel is unavailable.

- **oats.framework 1.9.2: oats.core 2.5.2, oats.setup 2.5.1.** Instruction
  text only; no kernel, schema or provider contract changes, and the
  capability floors are unchanged.
  - `oats-operate` (oats.core) says that from OATS 0.52.0 one stop or retire
    of an instance runs at a time, which code each refusal answers
    (`E_INSTANCE_RETIRING`, `E_LIFECYCLE_BUSY`) and what to do after each
    (#866).
  - `oats-onboarding` (oats.setup) follows oats.aweb 1.26 and oats.okf 5.x:
    `oats aweb resident create` for a GLOBAL resident, and harvest as
    proposals with the soul's own opt-out in place of the removed host
    setting (#901, #904).
  - `oats-workspace-config` (oats.setup) says that from OATS 0.52.0 OATS
    itself confirms development mode's prompt, and lists
    `E_LAUNCH_CONFIG_AMBIGUOUS` with its remedy (#886).
  A deployment takes it at the tag `oats-framework/v1.9.2`; a running
  instance keeps the text it was spawned with until it is respawned.
