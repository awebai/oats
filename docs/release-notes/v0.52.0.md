# OATS 0.52.0

Unreleased

## Fixed

- **A lifecycle command never answers with a code that is not a kernel code
  (#892, #874 item 3; the raw inner code of #891).** `oats retire`, `oats
  instance stop`, `oats session` and `oats worktree add|remove` answered any
  error that had a `code` with that code, so a file the system refused to
  read, an entry removed while a retire walked the home, a claim directory
  that could not be made or a home removed under a stop came back as `EACCES`,
  `ENOENT`, `EEXIST` or `ENOTEMPTY`, with no statement of what the command had
  done. Such an error is now answered with a documented kernel code
  (`E_WORK_INSPECTION_FAILED` for an entry a retire's inspection cannot read
  or no longer finds; `E_LIFECYCLE_FAILED` for the rest; `E_SESSION_FAILED`
  for `oats session`; `E_SESSION_STOP_FAILED` inside a stop receipt and a
  retire's `childrenStopped`), with the system's own code in the new
  `error.details.cause` (`{code, syscall}`; or `{name}` for a defect of the
  kernel, a `TypeError` and its like, whose stack goes to stderr). A refusal
  the kernel words without a code, and a `tmux` or `git` command that fails,
  are answered as before: the command's general code and the message alone.
  `unsafe-config-key` and `unsafe-config-value` keep their own names. A
  retire's message ends with
  what it had done when it failed, and every error of a retire apply says the
  same as data in the new `error.details.reached`: `{phase,
  sessionStopAttempted, hooksStarted, home, recovery}`. A removal that fails
  after a complete recovery names that recovery. No existing kernel code
  changes its meaning, no exit status changes, and no receipt or plan gains a
  field. `oats version --json` lists the feature `lifecycle-kernel-codes`
  for all of this: the rule about codes, `details.cause`, `details.reached`
  and what its absence means. A client that matched on a system error's name
  in one of these answers reads `details.cause.code` instead when the probe
  lists the feature, and keeps its guard for a system code when it does not.
  See
  [The envelope](../desktop-cli-api.md#kernel-codes) and
  [`error.details.reached`](../desktop-cli-api.md#retire-reached).
- **A claim no longer refuses for ever, or spins, about a holder that will
  never act again (#870, #874 items 1 and 2).** The claim is the file that
  lets one `oats retire` of a home, and one `oats worktree add|remove` of a
  purpose, run at a time. Three of its edges are closed:
  - **A holder that has exited or was killed and that its parent has not
    reaped (a zombie) is gone.** It was read as running, so the command
    answered `E_LIFECYCLE_BUSY` "… is already running … wait for it to
    finish" until the parent reaped it, which a parent that never waits does
    not do. Its claim is now taken over as any dead holder's is. The same
    holds for the three other records that name a command by pid and start
    time: a tree record in state `creating` (the next `add` or `remove`
    recovers it), a self-retire's pending marker (the next retire does what
    the completion owed), and a spawn's `inProgress` marker. **A changed
    answer of `oats status --json`:** a spawn whose process is a zombie
    reads as `rollbackIncomplete`, no longer as `spawnInProgress: true`, and
    `oats retire` completes it. A process group that a killed command left
    is still proven by its leader while that leader is a zombie, and its
    members are still ended. The start token a record names (`proc:<ticks>`,
    `ps:<lstart>`) is unchanged, so a claim or a marker written by an older
    kernel still names its live holder.
  - **A path that exists and never reads as a claim is refused, not
    retried without end.** A dangling symbolic link where the claim belongs
    made `oats retire` and `oats worktree add|remove` loop without a pause
    and without an end. Every attempt now pauses, and the command answers
    `E_LIFECYCLE_BUSY` "`<file>` is not a readable claim; inspect it and
    remove it …; nothing was done": a retire, which does not wait, after
    five retries (a quarter of a second); a worktree command, and a
    self-retire's completion, the same five retries after its 3 s wait.
  - **A gone holder whose claim cannot be taken over is said to be gone.**
    A claim file whose holder is gone and whose `nonce` is not the 32
    hexadecimal digits a claim carries (written or damaged by hand) was
    answered as a live holder, to wait for. It, and the claim at the end of
    a chain of dead takeovers too long for the file system to name one
    more (answered until now as `E_LIFECYCLE_FAILED` with `ENAMETOOLONG`
    about a file that does not exist), now answer `E_LIFECYCLE_BUSY` "the
    process that held `<file>` (pid `<pid>`) is gone, and this file is not a
    claim this kernel can take over (`<why>`); nothing was done — inspect
    `<file>` and remove it if no oats retire holds it, then retry".
  `E_LIFECYCLE_BUSY` keeps its meaning (refused before any effect) and no
  JSON shape changes: what changes is when it is answered and, in the two
  cases above, its message. `details.lock` of a worktree command's "not a
  readable claim" and "this process's start time cannot be read" refusals
  now names the file the message names, as a retire's does; it was always
  the purpose's claim, which differs only for the claim of a takeover
  (`<purpose>.lock.reclaim-<nonce>`).
  **One changed answer in a rare race, `oats worktree` only:** a command
  whose takeover ended a dead command's git step and that was then refused
  the claim (another command took it first) answered `E_LIFECYCLE_BUSY`
  "… nothing was done". It now answers `E_LIFECYCLE_FAILED`, naming the git
  group it ended first and then the refusal, with "nothing else was done";
  `details` are the refusal's. The same holds when the system refuses to
  remove that dead command's claim: "… was ended, and the claim it left is
  kept; nothing else was done", where the answer said that nothing was done.
  See
  [`oats worktree`](../desktop-cli-api.md#oats-worktree) and
  [One retire of a home at a time](../desktop-cli-api.md#retire-one-at-a-time).
- **One instance home whose record cannot be read no longer breaks the others
  (#896, first half).** A home whose `instance.json` was there and could not
  be read as a JSON object (a write cut off, a file kept from the user, JSON
  that is not an object) made `oats status` end with a stack and no answer,
  and made every other instance's stop and retire fail, because the listing
  read every record without a guard. Now that home decides only for itself.
  `oats status` lists every instance, and that home's row has the fields of a
  home with no `instance.json`, with `running: null`, `runtimeState:
  "unreachable"` and `runtimeError: "E_UNIDENTIFIED_INSTANCE_HOME:
  <home>/instance.json cannot be read (<reason>)"`. Every command about
  another instance answers as if that home were not there. The home's own
  `oats retire` (`--plan` and `--force` included), `oats instance stop` and
  `oats session start|restart` are refused with
  `E_UNIDENTIFIED_INSTANCE_HOME` before anything is read, stopped, run or
  removed; a stop and a session start did not answer that code before.
  Restoring the file from a copy makes the home usable again. A home whose
  `instance.json` is there and cannot be read cannot be removed through OATS
  yet, `--force` included. A parent whose record cannot be read has no
  recorded children for a stop or a retire: they are listed and act on their
  own. A home with no `instance.json` answers as before, and so does every
  command when every record can be read; no answer gains a field, and there
  is no new feature name. See
  [A home whose `instance.json` cannot be read](../desktop-cli-api.md#unreadable-record).
