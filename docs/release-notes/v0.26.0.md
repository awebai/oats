# OATS 0.26.0

The workspace model is the only model the kernel knows ("v2 becomes the
classic"). The 0.24-era classic path is removed, not flagged: a 0.24.x kernel
keeps running 0.24.x deployments, and a 0.25.x deployment is already v2
([rebuild-to-v2.md](../rebuild-to-v2.md)).

## Removed

- **Package approval** (human decision, 2026-09-24). People install a package
  only when they trust it: declaring it in the workspace's `packages:` IS the
  trust decision, so there is no second, per-version approval step.
  - `oats sync` resolves, fetches, verifies integrity, writes the lock and exits
    `0` on success. No exit `2` for pending approvals, no interactive prompt, no
    `approvalNeeded` in the report and none on `changes[]` rows.
    `oats sync --approve …` is `E_BAD_ARGS` naming the decision.
  - `oats onboard` has no approval-pending outcome and no "approve first" hint.
  - The lock (v3) drops the per-entry `approved` record. A lock that still
    carries it is read with the field ignored, and the next write drops it.
    **A kernel before 0.26.0 cannot read a lock 0.26.0 wrote** (`E_LOCK_SCHEMA`
    on the missing `approved`): keep every kernel that reads one deployment on
    0.26.0 or later.
  - The lock still pins each package to its exact commit and content integrity.
    `oats sync` refuses a moved tag, drifted content and a lock whose capability
    list no longer matches the package (`E_PACKAGE_INTEGRITY`) —
    reproducibility, not approval.
    **Where integrity is checked:** `oats sync` recomputes each package's
    content digest and refuses drift. At spawn, the kernel checks the lock's
    capability list against the package and trusts the locked commit plus
    materialize's fetch-versus-copy self-check. The lock's integrity is
    recorded in each module's `from`, not recomputed per spawn. (The removed
    per-spawn executables-digest check was an approval binding, not an
    integrity guarantee.)
  - Spawn, `--preview` and operator dispatch never raise `E_PACKAGE_UNAPPROVED`;
    the executables-digest gate is gone. At spawn a package capability must come
    from a package the workspace **still declares** (a stale lock entry for a
    package removed from `packages:` is `E_PACKAGE_MISSING { reason:
    "undeclared" }` until `oats sync`), and the lock's capability list must match
    what the package declares at the locked commit (`E_PACKAGE_INTEGRITY { why:
    "capabilities" }`). A package capability agent is found only in a declared
    package.
  - `oats workspace status` loses its `approval` object and column; `oats
    capabilities` package rows lose `approved`; `oats doctor` prints each locked
    package's integrity instead of its approval.
  - `oats version --json` advertises `packages-no-approval`. `syncApi`,
    `workspaceStatusApi` and `capabilitiesApi` are NOT bumped: a consumer that
    reads the removed fields gates on this feature string.
- **The `soul` link in instance homes.** A home no longer carries
  `<home>/soul`: its composed `AGENTS.md` already holds the soul's
  instructions. The soul directory an instance incarnates is recorded as
  `instance.json` `soulDir` (a workspace soul's per-commit copy
  `<deployment>/agents/<soul>/souls/<commit12>`, or the read-only soul inside a
  capability package) and is handed to every classic lifecycle hook — spawn,
  launch, retire — and to every capability command dispatched inside a home as
  `OATS_SOUL` (captured lifecycle hooks set no `OATS_SOUL`, unchanged). Launch
  and retire hooks, and in-home commands such as `oats okf harvest`, previously
  received no `OATS_SOUL`; `oats operation run`
  previously handed the swappable `agents/<soul>/soul` pointer. Captured
  (portable) scaffolds no longer create the link either; their curriculum check
  compares the retained `AGENTS.md` and skills as before. `oats session
  recompose` reads the recorded `soulDir`. A spawn that is rolled back into
  quarantine records the soul in its cleanup descriptor, so a retried retire
  hook sees the spawn's soul. A capability command dispatched with no recorded
  soul gets no `OATS_SOUL`, never one inherited from the invoking process.
  - **Homes spawned before 0.26.0** record no `soulDir`. They keep their
    existing `soul` link (0.26.0 neither reads nor removes it). Their retire
    hooks get the soul pointer `agents/<soul>/soul` (today's soul, not
    necessarily the spawn's commit). They are degraded: their launch hooks and
    in-home commands get no `OATS_SOUL` (a provider that requires it, such as
    oats.okf 2.1.5, refuses with `E_OATS_SOUL_MISSING`), and `oats session
    recompose` refuses them (`E_SOUL_UNKNOWN`). Re-spawn to get a recorded
    `soulDir`.

## Added

- **`oats spawn <soul> --name <slug>`** (human decision, 2026-09-24): an
  explicit, unprefixed instance name. The name is exactly `<slug>`, with no
  `<soul>-` prefix. Derived naming (`--purpose`, `<soul>-<n>`) stays the
  default.
  - `--name` and `--purpose` are mutually exclusive (`E_BAD_ARGS`).
  - The name is never rewritten: a non-slug, or a soul name of the deployment,
    is `E_INSTANCE_NAME_INVALID`.
  - A name that any soul of the deployment already holds, or that a live tmux
    window carries, is `E_INSTANCE_NAME_TAKEN`; never a silent `-2`.
  - `--preview` reports the final name and the same refusals, and
    `--expect-decision` binds the name.
  - Feature `spawn-name`.
- **Instance names are at most 64 characters**, explicit and derived (the
  messaging alias allows 1–64). A longer name is `E_INSTANCE_NAME_INVALID` in
  preview and apply, and is never truncated. A derived name that would exceed
  64 (a long purpose, or the `-2` suffix on a long one) is refused, naming the
  purpose to shorten. A spawn schedule whose run names
  (`<agent>-<purpose|id>-<YYYYMMDDHHMM>`) would exceed 64 is refused when it is
  saved (`E_SCHEDULE_INVALID`). Previously such a name passed the kernel and
  failed only at the messaging join.

## Changed

- **`oats inspect`, `oats readiness` and `oats operation run` read the
  workspace model** on a workspace deployment and for every home whose
  `instance.json` records `modules`. They never read the classic config chain.
  The probe integers are the gate: `operationsApi: 2`, `soulsApi: 2` (the
  inspect soul rows) and `readinessApi: 2`. `oats souls --json` keeps
  `soulsApi: 1`, since its shape is unchanged. Shapes and examples are in
  [desktop-cli-api.md](../desktop-cli-api.md#inspect-readiness-and-operation-run-on-the-workspace-model-operationsapi-2-soulsapi-2-readinessapi-2-oats-0260).
  - The subject is an instance (`--home`: `{kind:"instance", instance, home,
    soul}`) or a soul (`--soul`: `{kind:"soul", soul, repoKey, commit,
    team}`). A workspace deployment with neither is `E_BAD_ARGS`; the
    scope-wide lists are `oats souls` and `oats capabilities`.
  - Payloads lose `scope` (`chain`, `team`, `agentsRoots`), config `levels`,
    `activation`, `currentConfig`, `snapshot`, `health.trusted` and the
    portable `sources`. A capability's origin is its module's `from`; its
    settings are the merged provider payload.
  - Readiness checks are `installed | configured | member | providers`:
    - `trusted` is removed, and `--verify-signatures` is `E_BAD_ARGS` on a
      workspace deployment.
    - `enrolled` is now `member`: the soul's member repository confirmed in
      the workspace (`oats-membership.yaml`), never `oats.yaml`.
    - `providers` is new: each bound provider's own binding check, relayed
      verbatim (`{status: "ready" | "needs-configuration", problems}`).
    - A soul whose packages the lock does not provide fails `installed` with
      the typed code and an `oats sync` remedy.
  - `readiness --policy` is kept, with the same shape. The selector echo moves
    from `subject.selector` to a top-level `selector`.
  - `oats operation run` runs the module that fills the layer for the home or
    the soul. There is no trust gate, and the result carries
    `operationsApi: 2`. Remote routing accepts a destination advertising
    `operationsApi` 1 or 2.

## Fixed

- **Instance names are unique across the deployment.** A derived name used to
  de-duplicate only within its own soul's `instances/`, so soul `a` with
  `--purpose b-c` and soul `a-b` with `--purpose c` both got `a-b-c`. Derived
  names now skip every instance and soul name in the deployment (`-2`, `-3`, …).
