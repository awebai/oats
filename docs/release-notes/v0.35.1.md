# OATS 0.35.1

## Fixed

- **The remote cache no longer leaves a background git maintenance running
  after a fetch** (awebai/oats#451). Since Git 2.47, a `git fetch` starts
  `git maintenance run --auto --detach`, a daemon that outlives the fetch.
  Every fetch the kernel made into its remote cache (`<cache>/<hash>`)
  started one, which could still be repacking the cache after the command
  that fetched had returned. The cache is the kernel's own repository and
  never runs gc, so its git now runs with `maintenance.auto=false` as well.
  The same daemon, started by a test's commit, was what made a retire test
  fail its cleanup with `ENOTEMPTY` in CI; the test fixtures' repositories
  turn it off too.
- **Desktop's folder pickers open in a sensible place** (awebai/oats#460).
  **Add workspace → Browse…** opened wherever macOS last was, often
  ~/Downloads. It now opens in the folder holding the workspace most
  recently added or opened, remembered across launches, and in the home
  directory before the first one. **Choose oats…** opens in the directory
  of the chosen or discovered CLI.

- **A tree object the remote cache cannot read is a problem, never an empty
  directory, and the cache heals** (awebai/oats#455). A fetch into the cache
  that failed partway (on one host, one run by hand) left a member's commit
  without its `souls/` tree. git answers "names no tree" the same way for an
  absent path and for a tree object it cannot read, and the kernel took both
  as an absent directory. So the member enumerated to zero souls with no
  problem, the parsed cache (`<cache>/.parsed/`) kept that answer, and every
  later command hid the member's souls (`E_SOUL_UNKNOWN`). Because a present
  commit is never refetched, the cache stayed broken. Now:
  - an absent directory is confirmed against the commit's own listing;
  - a tree the commit lists but that cannot be read is `E_REMOTE_UNREADABLE`
    (reason `cache`). It is shown as a problem and never kept in the parsed
    cache;
  - the read marks that cache repository damaged, and the next command
    rebuilds it and fetches afresh.

  Upgrading also stops a bad answer kept by an earlier kernel from being
  served: the parsed cache is keyed by the kernel's own code.

  Never fetch into `~/.cache/oats/remotes` by hand. It is the kernel's cache,
  written only under its own locks.

- **A Desktop workspace never waits silently on "Reading the deployment…",
  and a folder that is not a deployment never drops the open ones**
  (awebai/oats#461). With three or more deployments open, the third and later
  ones were never read: the server started every deployment's reads at once
  past the observer's two-read bound, and kept the refused ones on their
  first "pending" forever. Deployments are now read two at a time, each one
  every cycle. A launch from a folder that is not a deployment (a parent such
  as `~/Agents` as the cwd or `--dir`), at a moment when no saved deployment
  could be opened, saved that folder as the whole open set; only deployments
  are saved now, and the saved set is never replaced with nothing. Add
  workspace → Browse… on a folder without `oats-local.yaml` is refused with
  an explanation and lists the deployments in it (or the one it is inside)
  as one-click adds; setting up a new deployment there is a secondary
  action. A workspace the Desktop's server does not serve, or does
  not answer for within 45 s, shows an error naming it, with Retry and
  Re-add workspace. Behaviour change in the Desktop's own server: an explicit
  `?ws=` it does not serve (any id) on `/api/panel` and `/api/agents` is now 404
  `E_WORKSPACE_NOT_SERVED` instead of the first workspace's answer.
