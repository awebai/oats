# OATS 0.42.1

## Changed

- **Remote roster rows carry the local row's work, repository, branch,
  model-from, soul and module drift facts**
  ([#675](https://github.com/awebai/oats/issues/675)). A remote instance
  row (`oats server roster --json`, and the Desktop's remote roster) now
  relays `work`, `repo`, `branch`, `modelFrom`, `soul` and `modules` from
  the host's own `oats status --json` row, with the same names and meaning
  as on a local row. `soul` and `modules` are the host's own drift
  observation, relayed as it answered; nothing is recomputed on this side,
  and `repo` is the host's path. Each is always present, `null` from a host
  that doesn't report it (an older host, a fact it never recorded, or a saved
  route the host no longer lists). See
  [the remote roster](../desktop-cli-api.md#the-remote-roster-oats-server-roster---json).

- **The `worktree` and `checkout` briefings allow extra trees, and give the
  command** ([#674](https://github.com/awebai/oats/issues/674)). Both
  briefings forbade extra Git worktrees: `worktree` said "Don't create extra
  worktrees; `work/` is your one tree", and `checkout` said to ask for a
  worktree-mode instance for work that needs its own branch. That
  contradicted the shipped `oats.engineering` package, whose developer
  briefing and `/worktrees` skill say "your work-mode briefing has the
  command", with `.work-<purpose>` in the home as the default place. No
  briefing gave that command. The case that needs it is a developer whose
  one task touches several repositories of the deployment.

  Both briefings now carry the same short paragraph. An extra tree is created
  in the home, from any clone of the deployment (`oats-local.yaml` `clones:`,
  or `<deployment>/<repo>`), from the remote's current state:

  ```bash
  git -C <clone> worktree add --detach "$OATS_INSTANCE_HOME/.work-<purpose>"
  git -C "$OATS_INSTANCE_HOME/.work-<purpose>" fetch --refmap= origin <base>
  git -C "$OATS_INSTANCE_HOME/.work-<purpose>" switch -c <branch> FETCH_HEAD
  ```

  The fetch runs inside the new tree, which has its own `FETCH_HEAD`, so
  creating it moves none of the clone's refs. The paragraph also covers
  branch names (the repository's rules, else `agents/<instance>-<purpose>`;
  never `-C` or `-B`), pushing a tree without an upstream
  (`git push origin HEAD:<remote-branch>`), and closing: merge each tree into
  the PR branch or push it and name it in the hand-back, then
  `git -C <clone> worktree remove`. `git switch` needs Git 2.23 or later.

  `worktree` mode now says never to work in a shared checkout (the main
  checkout, or any clone others use), and that changes happen in `work/` or
  in the extra trees. It drops "Parallel work means your human spawns
  another instance". `checkout` mode now says that work needing its own
  branch goes in an extra tree, not in `work/`. The `workspace`, `directory`
  and `attached` briefings do not change, and there is no new `oats`
  command. The instance-boundary block every instance receives said repository
  work happens in `work/` "and only there"; it now says "there, or in the
  extra trees your mode block grants, and nowhere else", so the two blocks
  no longer disagree. Instances spawned before the upgrade keep the briefing
  they were spawned with. See
  [souls and instances](../souls-and-instances.md#extra-trees).

- **Retire protects extra trees in the home**
  ([#674](https://github.com/awebai/oats/issues/674)). An extra tree is a
  top-level `.work-*` entry of the home that Git confirms is a linked
  worktree of some repository. Before, retire treated it as home bytes: it
  copied it to recovery and removed it with the home, leaving the
  repository's admin entry behind. Now, in every work mode:

  - A verified extra tree is not copied to recovery. `workRecovery.notCopied`
    lists it with `owner: "kernel:extra-worktree"`. A `.work-*` entry that
    does not verify (a plain directory, a symbolic link, a full clone), or
    that belongs to a repository inside the home, is copied as before.
  - When the home is removed, the retire handles each tree after its hooks
    and before the `work/` worktree step. A clean tree (empty status,
    ignored and untracked files included; no operation in progress; HEAD
    reached by a ref of its repository, not only by the tree's own) is
    removed with `git worktree remove` and pruned. Its branch is kept. Any
    other tree is moved, as `work/` is retained, to
    `<deployment>/.agents/worktrees/<repo>/<branch>`.
  - A locked tree refuses the retire with `E_WORK_PRESERVATION_FAILED`
    before anything runs: no session is stopped and no retire hook runs. A
    move or removal Git refuses refuses it after the hooks. Either way the
    home is kept. `--force` does not bypass it, and `--discard-worktree` does
    not apply to extra trees.
  - With `--keep-dir`, or when the home is kept for a retry, the trees stay
    where they are.

  `oats retire <instance> --plan` adds `facts.extraWorktrees` (`[{path, repo,
  branch, detachedAt, disposition, movedTo, reason}]`, empty when there are
  none) and one `notes` string per tree. The trees are part of
  `planRevision`: a tree created, removed, dirtied or cleaned between the plan
  and the apply refuses the apply with `E_PLAN_STALE`. The retire receipt adds
  `extraWorktrees` (the plan's row plus `outcome`), present when a tree was
  handled. The `worktree-removed` and `worktree-retained` events for an extra
  tree carry `extra: true` and its `path`. All keys are additive. See
  [souls and instances](../souls-and-instances.md#extra-trees-at-retire) and
  [the CLI API](../desktop-cli-api.md#retire).

## Fixed

- **The context panel shows the soul and teams of an instance on a server**
  ([#675](https://github.com/awebai/oats/issues/675)). The Soul tab and the
  Messaging & Teams list were empty for an instance on a registered server.
  They now read through the server by the instance's home, as the soul page
  does, and say "Reading from <server>…" while they wait. The Soul tab's
  header shows the soul's description from the server's roster. The Work
  card, the "model from" line and the "older build" chip show the facts the
  server relays. When a part can't be shown, it says why and what to update:
  this computer's OATS when it can't route the read or doesn't relay the
  facts, the server's OATS when it lacks the feature or doesn't report them.
  A server's other refusals show its code and message, as the rest of the
  panel does.
