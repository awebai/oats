# OATS 0.69.5

Unreleased

0.69.5 makes the commands OATS runs most often start faster, and it shows a
lost session as `LOST` in `oats status` and `oats server roster`. A restart
whose relaunch fails no longer comes back on the next resume. The catalog
moves to oats.okf 5.6.0 and oats.cloning 1.1.0, whose one-shot service souls
are listed under Background, and to oats.aweb 1.32.1 and oats.framework
1.16.3.

## Upgrade

- **Install the Desktop first and the CLI second,** as
  [Upgrading](../upgrading.md) says. The 0.69.5 Desktop accepts OATS CLIs
  `>=0.26.0 <0.70.0`.
- **OATS 0.69.2 or later on every host that shares a workspace, before any of
  them syncs:** oats.okf 5.6.0 and oats.cloning 1.1.0 require it. On an older
  kernel, `oats sync` still locks them, but their souls are dropped and new
  spawns that compose them are refused (`E_CAPABILITY_INCOMPATIBLE`, naming
  the re-pin) (Provider updates, below). Where oats.okf is the workspace's
  default knowledge slot, that is nearly every new spawn.
- **Package moves:** the official catalog pins oats.okf 5.6.0, oats.cloning
  1.1.0, oats.aweb 1.32.1 and oats.framework 1.16.3. A deployment takes them
  with `oats sync`. Running instances keep the modules they were spawned
  with: new spawns get the new ones, and a stopped home moves with
  `oats instance upgrade`.
- **A new cache directory:** every `oats` command keeps Node's compile cache
  in `~/.oats/compile-cache` (Changed, below). It is safe to delete.

## Changed

- **`oats` commands start faster: the CLI keeps Node's compile cache.** Node
  no longer recompiles the kernel on every command: each command starts
  faster, by about a quarter for a cheap read such as `oats version`, and the
  status polls the Desktop and the TUI make cost less. The cache is a new
  directory, `~/.oats/compile-cache` (`$OATS_HOME_DIR/compile-cache`),
  created mode 0700. It is safe to delete at any time. `NODE_COMPILE_CACHE`
  moves it, and `NODE_DISABLE_COMPILE_CACHE=1` turns it off
  ([configuration](../configuration.md#the-compile-cache)). Nothing a command
  prints changes.

- **The reads OATS makes most often load only what they use.** `oats version`,
  `session inspect`, `status`, `workspace status`, `instance events` and
  `instance waiting clear` no longer load the whole kernel. `oats version` takes
  less than half its time and `session inspect` about half; `status` takes about
  an eighth less and `workspace status` about a fifth less; `instance events` and
  the waiting hook a Claude instance runs every turn take about a quarter less.
  Nothing a command prints changes.

## Fixed

- **A restart whose relaunch fails no longer reads `lost`, so a resume does not bring back the session you were restarting.** `oats session restart` stopped the running harness and then relaunched it, without recording the stop. When the relaunch failed, or the restart died between the two, the home read `sessionEnd: "lost"`, and the next resume sweep (OATS Desktop or `oats tui` opening) started the old launch again. A restart now records the stop before it asks the harness to end, as a retire does, so such a home reads `stopped` and stays down; a successful relaunch records a new start, which reads as before. A restart whose stop is refused keeps that record, so its harness, should it die later, reads `stopped` rather than `lost` ([awebai/oats#1601](https://github.com/awebai/oats/issues/1601); [Resume after a shutdown](../execution-targets.md#resume-after-a-shutdown)).

- **`oats tui` no longer replaces the answer to what you did with its own line.** When the add of the deployment a run started in to this computer's list fails, the line that says so waits again until a line answering your own act has gone, as it did before 0.69.2. The add answers in the run's first moments, so this shows only when you act before it does: a correctness restore, rarely visible ([awebai/oats#1603](https://github.com/awebai/oats/issues/1603); [Start it](../tui.md#start-it)).

- **The pi bridge loads the kernel that launched its instance first**
  ([#1604](https://github.com/awebai/oats/issues/1604)). Pi instances were
  never affected: each home's own `oats` link is first on the PATH pi
  launches with, so the bridge found the launching kernel with no global
  install. Now the bridge reads that link directly, after `OATS_PKG_ROOT`
  and before any PATH or global lookup, so a home loads its own kernel
  whatever PATH pi has. A pi started outside any instance, on a host with no
  global install and an `oats` that is a script rather than a link to the
  kernel, failed with "the pi adapter needs the oats CLI installed
  globally". It now says "OATS kernel not found" and names the three ways
  out: `npm install -g @awebai/oats`, an `oats` on PATH that links to the
  kernel's `bin/oats.mjs` (`npm link` in a checkout), or `OATS_PKG_ROOT`
  ([the bridge's README](../../packages/pi/README.md)).

- **`oats status` printed a lost session as `idle`**
  ([#1617](https://github.com/awebai/oats/issues/1617)). The text views of
  `oats status` and `oats status --server <id>` printed every row that does
  not run as `idle`, so a session lost to a reboot or a dead tmux server read
  the same as one stopped on purpose. A row whose `sessionEnd` is `lost` now
  prints `LOST`, with one line under it naming the way back: `oats session
  start --resume --home <home>`, or the next `oats session resume` (run when
  OATS Desktop or `oats tui` opens) when it can vouch for the loss. A
  `--server` row names the host to run them on. A stopped, exited or
  never-launched row, and a row from a host whose kernel reports no
  `sessionEnd`, still print `idle`.
  The JSON is unchanged
  ([How a session's end is read](../execution-targets.md#how-a-sessions-end-is-read)).

- **`oats server roster` printed a lost session as `idle`**
  ([#1628](https://github.com/awebai/oats/issues/1628)). Its rows did not
  relay the host's `sessionEnd`, so the roster could not tell a session lost
  to a reboot or a dead tmux server from one stopped on purpose. A roster row
  of `server roster --json` now carries `sessionEnd` when the host's row has
  it, with the host's value: `lost`, `stopped` or `exited`. A host whose
  kernel reports no `sessionEnd` gives rows as before. The roster line prints
  a lost row as `LOST`, with one line under it naming the way back on that
  host, as `oats status --server <id>` does
  ([`sessionEnd` on a roster row](../desktop-cli-api.md#the-remote-roster-oats-server-roster---json)).

## Provider updates

- **oats.aweb 1.32.1: recover pi mail lost on an interrupted turn.** The
  catalog and this workspace pin `oats.aweb: v1.32.1`, from 1.32.0. It is
  guidance only, cut from 1.32.0 with this one change: with `@awebai/pi`
  0.4.0, mail that arrives during a turn can be lost when the human
  interrupts it (awebai/aweb#68). The inject and `/oats-aweb` section 4 now
  have affected pi instances scan `aw mail inbox --show-all --json` after any
  interrupted turn and at task boundaries, and reconcile by message id. The
  workaround goes once a fixed `@awebai/pi` is pinned. OATS >=0.68.0 and the
  aw floor are unchanged.

- **oats.cloning 1.1.0: cloners are background instances.** The catalog and
  this workspace pin oats.cloning `v1.1.0`, from 1.0.1. The `cloner` soul says
  `background: true`, so the Desktop and `oats tui` list a new cloner under
  their Background section (oats-cloning#6, awebai/oats#1579). The clone
  itself is placed as its own soul says.
- **Upgrade:** 1.1.0 requires **OATS >=0.69.2** (was >=0.34.0): an older
  kernel drops the soul, so `oats cloning request` refuses with
  `E_SOUL_UNKNOWN`. Upgrade OATS first, then `oats sync`.

- **oats.framework 1.16.3: oats.setup 2.9.4.** oats.setup's `/oats-onboarding`
  pins `oats.okf: v5.6.0` in its knowledge section and names its kernel floor,
  OATS 0.69.2 (text only). The other capabilities are unchanged.
- **Upgrade:** `oats sync` locks it once the workspace or the catalog pins
  `oats.framework: v1.16.3`. New spawns get it, and a stopped home moves with
  `oats instance upgrade`.

- **oats.okf 5.6.0: knowledge harvesters and knowledge maintainers are
  background instances.** The catalog and this workspace pin
  `oats.okf: v5.6.0`, from 5.5.0. Both package souls say `background: true`,
  so the Desktop and `oats tui` list new harvesters and knowledge maintainers
  under their Background section (oats-okf#113, awebai/oats#1579). Existing
  instances do not move, and harvest and review behave as before.
- **Upgrade:** 5.6.0 requires **OATS >=0.69.2** (was >=0.49.0): an older
  kernel refuses the `background:` key, so it drops both souls and refuses
  new spawns that compose oats.okf (`E_CAPABILITY_INCOMPATIBLE`, naming the
  re-pin). Upgrade OATS on every host that shares the workspace first, then
  `oats sync`.

## Documentation

- **Which losses come back** names one more limit: the 24-hour gap of clause
  4 does not reach across a reboot, so after a quiet spell of more than a day
  with no OATS read, the first sweep after a restart can bring back a session
  lost during it ([Which losses come back](../execution-targets.md#which-losses-come-back)).
