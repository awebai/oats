# OATS v0.25.2 — operator-rebuild round

Kernel/Pi **0.25.2**. Tag `v0.25.2` → the commit carrying these notes; the
version-bump commit lands after the tag. Consumers gate on `oats version --json`
`features[]` names and API integers — never on the version.

**No API change.** `workspaceApi: 2`, every other API integer and the
`features[]` list are exactly those of [0.25.1](v0.25.1.md). The only surface
additions are **additive fields**: `oats spawn --preview` gains `providers` and
`settings`, `oats status --json` gains `instances[].soul`; `oats sync` gains
the `--approve` flag. Every item below comes from an operator's first rebuild
of a real two-team deployment on 0.25.0, following `docs/rebuild-to-v2.md`
literally — the guide is a contract the kernel honours. Normative record:
"0.25.2 operator-rebuild round" in
`docs/design/2026-09-23-workspace-module-contracts.md` and the matching
clarifications in
`agents/oats-expert/soul/knowledge/decisions/workspace-model-v2.md`.

## Kernel

- **R1 — member clones are found as the guide says.** For a `work: worktree |
  checkout` soul: `--repo`, then `oats-local.yaml` `clones:` (keys normalised
  through `parseRepoRef`), then `<deployment>/<member name>` (a member named
  `agents` → `agents-repo`); none → `E_CLONE_MISSING` naming the three
  remedies; a directory whose remotes name another repo → `E_CLONE_MISMATCH`.
- **R2 — `oats sync` creates `<deployment>/agents/` when absent.**
- **R3 — one "You run on OATS" block.** With `oats.core` resolved as a module
  the kernel's legacy block is suppressed; the module's inject is the briefing.
- **R4 — `oats status` shows soul-source drift.** `soul: <name> from <member>
  @ <c7>  [member moved since …]` beside the module rows; `--json`
  `instances[].soul { repoKey, commit, current, status }`.
- **R5 — `spawn --preview` shows the payload.** `providers` (the `--provider`
  map as given) and `settings.<cap>` (the merged payload each provider
  receives).
- **R9 — non-interactive approval.** `oats sync --approve <id>@<version>`
  (repeatable) approves exactly the locked entry at that version; the digest is
  always computed, never typed; an id/version not in the resolution is
  `E_BAD_ARGS`. Ctrl+D at the interactive prompt is a decline (exit `2`).
- **R10 — `oats onboard` lists the host** among the clones to make, like any
  member; an explicit `standalone:` header is named as such in the next steps.

## Documentation

- **R6** — the rebuild guide's work-mode section states that a coordination
  soul's (`work: workspace`) `./work` is the deployment directory (0.25.1 B2).
- **R7 — where the team `.aw` lives now.** Rebuild guide §8b: oats.aweb 1.11.2
  finds `.aw` among the home, the home's git repo, the soul's work repo and the
  deployment directory — never the 0.24 team root; place it inside the member
  clone (gitignored) or at the deployment directory. **`messaging.byTeam` is
  kernel-merged but a no-op for oats.aweb 1.11.2**, which does not read `team`
  from its payload; per-repo `.aw` placement is the working alternative
  (`workspaces.md` byTeam paragraph updated accordingly).
- **R8 — OKF 2.1.3 reads `okf.json`, not a soul payload.** The guide, `workspaces.md`,
  `souls-and-instances.md` and `knowledge.md` no longer show `knowledge: { owns,
  reads }` / `{ store, root }` on `soul.yaml`: the soul's declaration is
  `souls/<name>/okf.json` (`version`, `owner`, `owns`, `reads`); the `knowledge:`
  payload may carry only the binding's settings (`bindings-file`, `state-dir`,
  `harvest-runtime`, `harvest-model`); a base's `root` is the bindings file's.
  Decision 24's example is corrected. §7b (fresh `state-dir`) confirmed.
- `configuration.md` `clones` row states the R1 order; `workspaces.md` and
  `souls-and-instances.md` describe the R4/R5 fields and the per-commit soul
  cache paths.

## Provider follow-ups (not kernel)

- **oats.aweb follow-up:** read `team` from the spawn payload (so
  `messaging.byTeam` yields per-label identities) and accept the deployment
  directory as a first-class aweb root. Until that release, 1.11.2 behaves as
  §8b describes.
- **oats.okf follow-up:** a soul-payload grammar (`owns`/`reads` on
  `soul.yaml`), declared in the binding when it lands; owner pin re-based on
  identity rather than path, and per-soul harvest opt-out (2.1.4 items, unchanged).

## Known follow-ups (unchanged from 0.25.1)

- The classic (no `oats-local.yaml`) spawn path still runs the pre-v2 compose.
- The readiness quartet (`readinessApi: 1`) is still produced by the 0.24 tier
  observers.
- `oats-local.yaml` `transport:` needs a schema addition before it can be
  written.
