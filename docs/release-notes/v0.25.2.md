# OATS v0.25.2 — operator-rebuild round

Kernel/Pi **0.25.2**. Consumers gate on `oats version --json` `features[]`
names and API integers, never on the version.

**No API change.** `workspaceApi: 2`, every other API integer and the
`features[]` list are those of [0.25.1](v0.25.1.md). The surface additions
are additive: `oats spawn --preview` gains `providers` and `settings`, `oats
status --json` gains `instances[].soul`, and `oats sync` gains `--approve`.
Every item comes from an operator's first rebuild of a real two-team
deployment on 0.25.0, following the [rebuild guide](https://github.com/awebai/oats/blob/bdd7e55e1b798a97b8b5486001d7c17e522792a7/docs/rebuild-to-v2.md) literally.

## Kernel

- **Member clones are found as the guide says.** For a `work: worktree |
  checkout` soul: `--repo`, then `oats-local.yaml` `clones:`, then
  `<deployment>/<member name>` (a member named `agents` → `agents-repo`). None
  is `E_CLONE_MISSING` naming the three remedies; a directory whose remotes
  name another repo is `E_CLONE_MISMATCH`.
- **`oats sync` creates `<deployment>/agents/` when absent.**
- **One "You run on OATS" block.** With `oats.core` resolved as a module, the
  kernel's own block is suppressed.
- **`oats status` shows soul-source drift**: `soul: <name> from <member> @
  <c7>  [member moved since …]`; `--json` `instances[].soul { repoKey, commit,
  current, status }`.
- **`spawn --preview` shows the payload**: `providers` (the `--provider` map
  as given) and `settings.<cap>` (the merged payload each provider receives).
- **Non-interactive approval.** `oats sync --approve <id>@<version>`
  (repeatable) approves exactly that locked entry; the digest is always
  computed. An id or version not in the resolution is `E_BAD_ARGS`. Ctrl+D at
  the interactive prompt is a decline (exit `2`).
- **`oats onboard` lists the host** among the clones to make; an explicit
  `standalone:` header is named as such in the next steps.

## Documentation

- A coordination soul's (`work: workspace`) `./work` is the deployment
  directory.
- **Where the team `.aw` lives.** oats.aweb 1.11.2 finds `.aw` in the home,
  the home's git repo, the soul's work repo or the deployment directory, never
  the 0.24 team root: place it in the member clone (gitignored) or the
  deployment directory. **`messaging.byTeam` is a no-op for oats.aweb
  1.11.2**, which does not read `team` from its payload; per-repo `.aw`
  placement is the working alternative.
- **OKF 2.1.3 reads `okf.json`, not a soul payload.** A soul's knowledge
  declaration is `souls/<name>/okf.json` (`version`, `owner`, `owns`,
  `reads`); the `knowledge:` payload carries only the binding's settings
  (`bindings-file`, `state-dir`, `harvest-runtime`, `harvest-model`).
- [configuration.md](../configuration.md), [workspaces.md](../workspaces.md)
  and [souls-and-instances.md](../souls-and-instances.md) describe the clone
  order, the new status and preview fields, and the per-commit soul cache.

## Known limitations

- oats.aweb 1.11.2 does not read `team` from the spawn payload and does not
  treat the deployment directory as an aweb root.
- OKF 2.1.3 has no soul-payload grammar (`owns` / `reads` on `soul.yaml`),
  pins owners by path, and has no per-soul harvest opt-out.
- A deployment without `oats-local.yaml` still spawns through the classic
  compose path; readiness (`readinessApi: 1`) is still produced by the 0.24
  tier; `oats-local.yaml` has no `transport:` key.
