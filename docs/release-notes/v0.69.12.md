# OATS 0.69.12

0.69.12 moves the official catalog to `oats.okf` 5.8.0, `oats.aweb` 1.37.0 and
`oats.framework` 1.22.1. `oats.okf` checks every harvest publication's content
before it is pushed. `oats.aweb` lets a person join a team by pasting one
invite, keeps every invite token off the command line, names the cause of a
refused join, warns when whatever keeps a home's aweb task claims present is
too old, and on macOS restarts its launchd jobs so they come back after an aw
upgrade. The setup expert and getting started take a second round of fixes
from newcomer runs on fresh machines.

## Upgrade

- **Either order of the Desktop and the CLI works.**
  [Upgrading](../upgrading.md) installs the Desktop first, and a host that
  installed the CLI first is fine too: the 0.69.12 Desktop accepts OATS CLIs
  `>=0.26.0 <0.70.0`, as the 0.69.11 and 0.69.10 Desktops do.
- **Package moves:** the official catalog pins oats.okf 5.8.0 (from 5.7.0),
  oats.aweb 1.37.0 (from 1.35.0, crossing 1.36.0) and oats.framework 1.22.1
  (from 1.21.0, crossing 1.22.0). None changes its OATS floor: oats.okf stays >=0.69.2,
  oats.aweb >=0.68.0 with aw >=1.36.33 (tested with 1.36.53). A deployment
  takes each by raising its own pin (`/oats-package-pins`), then `oats sync`.
  Running instances keep the modules they were spawned with: new spawns get
  the new ones, and a stopped home moves with `oats instance upgrade`. A
  knowledge harvester spawned after the sync publishes through oats.okf
  5.8.0's content gate.
- **Where `oats.aweb-tasks` is composed, readiness may warn** (oats.aweb
  1.37.0) `wake-daemon-outdated` (a home the host wake daemon serves, while
  the daemon runs aw below 1.36.54), `aweb-channel-outdated` (a Claude home,
  below aweb-channel 1.8.2) or `pi-extension-outdated` (a pi home, below
  @awebai/pi 0.4.1). These are warnings, not refusals: an older component
  still delivers, but a claim it doesn't heartbeat can be taken over once it
  goes stale. Messaging-only homes get none of them.
- **aw 1.36.54 is on npm's `next` tag; `latest` is still 1.36.53.** Install
  it by version, `npm install -g @awebai/aw@1.36.54`: a plain
  `npm install -g @awebai/aw`, and `oats aweb setup --install-aw`, install
  1.36.53. Then rerun `oats aweb wake install` to restart the host wake
  daemon on it. On macOS that rerun now unloads and reloads the daemon
  (bootout, then bootstrap), because launchd refuses to respawn a job whose
  binary an upgrade replaced; before oats.aweb 1.37.0 it left the daemon
  down. Against a server other than the aweb Cloud, aw 1.36.54 is newer than
  the tested aw, so oats.aweb also warns `aw-newer-than-tested` there.
- **Known issue (macOS): a running custody job is not restarted for you
  after an aw upgrade.** Reload each one by hand:
  `launchctl bootout gui/$(id -u)/<label>`; wait until
  `launchctl print gui/$(id -u)/<label>` no longer finds it; then
  `launchctl bootstrap gui/$(id -u) ~/Library/LaunchAgents/<label>.plist`;
  then rerun `oats aweb resident create <name>` to verify (oats.aweb 1.37.0's
  CHANGELOG).
- **`oats aweb setup --invite` or `--invite-stdin` without `--join` is no
  longer a usage error** (exit 2, "requires --join <label>"). From oats.aweb
  1.36.0 it is setup from the invite alone: it needs aw 1.36.53 or later,
  refuses with `E_SETUP_AW_VERSION` on an older one, and refuses every other
  problem before anything is redeemed. `--join <label>` works as before.
  Every invite acceptance now reads the token on stdin, so a malformed token
  fails as an aw usage error (exit 2) before anything is redeemed.

## Changed

- **oats.okf 5.8.0: a content-safety gate on every harvest publication.**
  Harvest and maintenance screen what they would publish (the outgoing
  history, paths, blobs and text) before any push, comment or merge, and
  report only the location, line and rule. A harvest PR left behind the
  accepted tip is rewritten onto it for a fresh exact-head verdict, never
  merged on an approximate squash. Structural OKF validation is unchanged
  ([awebai/oats-okf#121](https://github.com/awebai/oats-okf/pull/121)).
- **oats.aweb 1.36.0: setup from one pasted invite.** `oats aweb setup --soul
  <soul> --invite-stdin --name <alias>`, without `--join`, reads the invite's
  team and service with aw's `team invite inspect` (redeeming nothing),
  derives the label from the team's name, joins into a per-team root, and
  ends with one next step. `oats aweb invite --json` answers that command at
  `result.joinCommand`, with no token in it. A refused `oats aweb join` and a
  failed `aw team invite` name their cause and fix, and new team roots go
  beside the default team's root
  ([awebai/oats-aweb#56](https://github.com/awebai/oats-aweb/issues/56),
  [#52](https://github.com/awebai/oats-aweb/issues/52),
  [#45](https://github.com/awebai/oats-aweb/issues/45)).
- **oats.aweb 1.37.0: claim floors for aweb tasks, and launchd restarts.**
  oats.aweb-tasks's readiness warns per home on the component that keeps its
  claims present (above). `oats aweb wake install` and
  `oats aweb resident create` restart a loaded launchd job with bootout and
  bootstrap, never `kickstart`
  ([awebai/oats-aweb#196](https://github.com/awebai/oats-aweb/pull/196),
  [#198](https://github.com/awebai/oats-aweb/pull/198)).
- **`oats.framework` 1.22.0 ships the second round of newcomer fixes to the setup expert.** `oats.setup` 2.13.0's `/oats-setup-expert`, `/oats-setup-model` and `/oats-package-pins`, `oats.onboarding` 1.2.0's `/oats-tailor-workspace`, and the `oats-setup-expert` soul carry them: the hand-over and hand-back, the tasks rule for each case, human attribution, both instance-name forms, and a harness entry for each new soul whose declared harness differs (#1726, #1729). The onboarding round-two entry in these notes describes each fix. The per-soul launch lines say from OATS 0.53.0. Apart from `oats tui` (OATS 0.52.0), which the hand-back leaves unversioned, no other command they name needs a newer OATS than each capability already admits ([awebai/oats#1665](https://github.com/awebai/oats/issues/1665)).
- **`oats.framework` 1.22.1: `oats.setup` 2.13.1's `/oats-onboarding` names `oats.okf` 5.8.0**, the release the catalog pins, as what knowledge operations need beside kernel 0.69.2 or later, and its workspace example pins `oats.okf: v5.8.0`. No other change.

- **Getting started and the setup expert: fixes from further newcomer runs on fresh machines** ([awebai/oats#1665](https://github.com/awebai/oats/issues/1665)).
  - **`oats-getting-started`, the machine's round is always asked:** on a machine found-list, the round's one yes, naming the changes, is asked even when the prompt that started the run says to ask for nothing more. It is the consent the harness's permission check reads; without it, each change (the repository, the aweb signup, the folder trust) was refused on its own and cost the person a round. After it, nothing more is asked.
  - **`oats-getting-started`, the Desktop's system libraries on Linux x64** are checked with step 2's other checks, before step 1's message, so a missing ALSA library goes on the one-yes list as a system package (dropped if the person declines the Desktop) and the Desktop's install needs no second yes.
  - **`oats-getting-started`, the harness for every soul:** the skill records the chosen harness with `oats soul launch set '*' --harness <harness>` (plan first), for every soul on the machine without an entry of its own, in place of the setup soul alone. Package souls the setup expert or the steward spawns later no longer fall back to pi. `'*'` wins over a soul's own `launch:` on that machine, so each soul whose declared harness differs, and is installed and logged in on that machine, gets its own entry with that harness (and its model), by the `key` `oats souls --json` prints, plan first; a declared harness the machine lacks stays under `'*'`, so the soul can run, and the hand-over names it. The setup soul is the exception: it keeps the harness the person chose. Souls added later are covered when they declare no `launch:` of their own; one that declares one gets its own entry from the skill that adds it (`/oats-tailor-workspace`, `/oats-package-pins`) ([Launch preferences](../configuration.md#launch-preferences)).
  - **`/oats-tailor-workspace` (oats.onboarding), tasks, one rule per case:** with aweb's task list by default, it keeps it. Beside a tracker the agents already use (`tasks: none`), the setup expert offers to make a tasks capability of the workspace's own for it, from how the team works (its labels and states, who files and closes issues, what agents may do), holds that conversation itself and builds it with the person (over `gh issue` for GitHub issues, a manifest with `"layer": "tasks"`), and makes it the tasks default on their yes. The getting-started skill's tasks line now says the setup assistant offers to connect the tracker. It never leaves `none` without asking and pins no generic provider in its place ([Official providers](../integrations.md#official-providers)).
  - **`/oats-tailor-workspace`, human attribution:** the step where the person typed a deployment-agent command and a passphrase at a terminal is gone, as #1665 decided. Agents run every command, and the person's one act is a click in their aweb dashboard; agents already running are attached in place, with no respawn. The setup expert first looks for the step in the messaging capability's own skill; until `oats.aweb` ships it, and for a self-custodial key or an account off aweb Cloud, it runs nothing, and its brief says the agents stay unattributed and keep working. A declined or expired request is reported, never re-prompted.
  - **`/oats-setup-expert` (oats.setup):** its list of what the hand-over holds matches the getting-started template (the host and its type, the steward lines, the channel mode, Tasks, and what the person may want later), and step 1 reads the tasks default. Its hand-back names no versions and no commands unless the person asks, and when a session spawned before messaging should be replaced, on the person's yes the setup expert spawns the new one as `<its name>-2`, checks that it runs and is in the team, tells the person its name, asks before its retirement would stop any of the person's agents, writes its state and only then retires itself; if a check fails it keeps its session. The person runs none of it. It describes the workspace's tasks capability as made beside a tracker on the person's yes.
  - **`/oats-setup-model` (oats.setup)** describes the setup expert as `oats.framework`'s package soul `oats-setup-expert`, chosen by `oats onboard` after a workspace's own `<workspace>-oats-setup-expert` and before the first by name, and lists `oats.aweb-tasks` among the tasks providers. It, `/oats-setup-expert` and the `oats-setup-expert` soul's own instructions name both instance-name forms, `<workspace>-oats-setup-expert` and `<workspace>-<machine>-oats-setup-expert`, and the kernel's `<workspace>-oats-setup` when a soul holds the first name.
  - **`oats-getting-started`, a person without a GitHub account:** step 1 asks whether they have one when gh is not logged in. Without one, step 3 opens GitHub's sign-up page in their browser (they create the account there, never in the conversation), then runs the usual device login; gh is installed like any missing tool, on the one yes.
  - **`oats-getting-started`, a join never runs `aw team ensure`:** on a join, `ensure` would silently make a new team of the person's own for the same repository rather than find the teammate's. It stays step 5's, for a new workspace, and a test pins every `ensure` line there.
