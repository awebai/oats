# OATS 0.37.0

## Added

- **The Desktop opens one window per workspace** (awebai/oats#481). Each
  workspace has at most one window, titled with its name (a workspace on a
  server: `name — server`). Choosing a workspace in the switcher shows it in the
  current window, or brings its own window to the front when it has one.
  Each workspace in the switcher has an **Open in new window** button
  (keyboard: Right Arrow then Enter, or ⌘Enter / Ctrl+Enter). On macOS,
  **File → New Window** (⌘⇧N) opens a window with no workspace that asks you
  to choose one, and ⌘\` cycles the windows; on Linux and Windows the command
  palette has **Window: new window**, with no default chord. Quitting and
  relaunching brings every window back with its size and place; a window
  whose workspace isn't served at launch stays remembered until you close it
  while it is served. Launching the app again with `--dir <deployment>`
  brings that deployment's window to the front, adding the deployment if
  needed. An unfocused window re-reads its instance list at the server's
  blurred cadence (30 s). A window's requests always carry its own
  workspace: one the server doesn't serve is refused with
  `E_WORKSPACE_NOT_SERVED`, never answered with another workspace's data.
  Window positions are kept in `windows.json` in the app's data folder.

## Changed

- **The Desktop accepts OATS CLIs `>=0.25.8 <0.38.0`**, so it runs against
  this release's kernel. Install the CLI and the Desktop 0.37.0 together: the
  Desktop 0.36.x refuses a 0.37 CLI.

- **Team model 3 is OATS 0.38.0, not 0.37.0.** 0.37.0 keeps 0.36.1's
  behaviour: the new `oats-workspace.yaml` keys are validated but not applied,
  and the `team-model-3-migration` warning, which now names 0.38.0, says what
  0.38.0 will refuse. The migration steps in the 0.36.1 notes apply unchanged.

- **oats.framework 1.4.3** (oats.setup 2.2.2): the `oats-teams` and
  `oats-workspace-config` skills say team model 3 is 0.38.0, and that 0.36.x
  and 0.37.x keep applying the local team keys. Remove them only when the
  deployment moves to 0.38.0.

- **oats.aweb 1.18.1** (catalog and workspace pin, and the bundled mirror):
  how mail reaches a session now depends on the runtime. Under the default
  `delivery: channel`, Claude Code takes mail and chat through its
  `aweb-channel` plugin and pi through the `@awebai/pi` extension, and
  neither goes through the host wake broker. Codex keeps the wake broker. A
  Codex home under `channel` is now registered with it at every start, where
  before it got no wake at all. Every start of a home re-decides the path for
  that start's runtime and leaves the home on exactly one path. A start that
  cannot register or deregister the home is refused. Existing instances keep
  the delivery they were spawned with until they are respawned.
  `delivery: session` still sends every runtime through the broker.

  oats.aweb 1.18.1 declares `launchPreview` (see Fixed below). A launch
  preview, including Desktop's start dialog, and a start refused by
  preflight change no broker registration: the hook calls `aw` only in the
  real run, after preflight has passed.

## Fixed

- **Launch hooks no longer have side effects under a preview, or before a
  start's preflight has passed** (awebai/oats#500). A launch hook may register
  a home with its provider; oats.aweb's registers it with the host wake
  broker. But `oats launch-config preview`, which Desktop's start dialog
  calls for running homes, ran every hook for real. A start refused by
  preflight, including a start of a home that was already running, had also
  run them. Previewing a running Claude home with another harness could
  therefore change how that live session is woken.

  A capability now declares that its launch hook is preview-aware, with
  `"launchPreview": true` at the top level of its manifest. The kernel reads
  the declaration from the home's own module copy. A preview-aware hook
  runs twice per start:
  - **As a preview,** with `OATS_LAUNCH_PREVIEW=1` in the hook environment
    (a new, additive hook environment variable). This run's contribution
    drives the preflight and the rendered command.
  - **For real, without the flag,** only once every check has passed, and
    before a restart stops the running harness.

  A preview runs only the first pass. A preview-aware hook must change
  nothing under the flag. It must also return the same contribution either
  way, apart from the values of the env names its preview answer lists in
  `volatileEnv` (below). If the real run's contribution differs otherwise,
  the start is refused with `E_LAUNCH_PREPARATION` and nothing is stopped or
  started.

  A hook that doesn't declare `launchPreview` runs as it did in 0.36: once
  per start, for real, during preflight. `oats launch-config preview` never
  runs it; the preview shows its recorded contribution and says so. The
  kernel never passes on an `OATS_LAUNCH_PREVIEW` inherited from the
  environment.

  **Provider authors:** declare `launchPreview` once your launch hook
  honours `OATS_LAUNCH_PREVIEW`, and expect it to run twice per start
  (docs/capabilities.md). oats.aweb 1.18.1 does. A kernel before 0.37
  ignores the key and runs the hook once, as before.
- **Existing homes whose launch hook renews a credential at every start
  start again** (awebai/oats#504). The first version of the two-pass rule
  above ran every launch hook twice. A hook from before the preview flag
  then really ran under the preview too, and a hook that answers new values
  at every call failed the comparison. That covers oats.aweb homes with
  `identity.mode: global` and `renew: launch`, which mint a grant at each
  start: their starts were refused with `E_LAUNCH_PREPARATION`. Two passes
  are now opt-in, through `launchPreview`.

  A preview-aware hook can also name, in its preview answer, env whose
  values only the real run can know, such as `"volatileEnv":
  ["AWEB_IDENTITY_HOME"]`. The start takes those values from the real run
  and leaves them out of the comparison. Each must be a name the same hook
  returned. A harness configuration selector (`CLAUDE_CONFIG_DIR`,
  `CODEX_HOME`, `PI_CODING_AGENT_DIR`) is refused as volatile, because the
  package probe reads it before the real run.
