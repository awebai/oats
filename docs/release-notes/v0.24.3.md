# OATS v0.24.3 — `prepare` usability fixes

Kernel/Pi/Desktop **0.24.3**. Fixes five usability problems met when adopting a shared workspace definition on 0.24.1 and 0.24.2. No contract, schema or authority change.

- **Attributed provider problems.** Every preparation problem carries `slot`, `capability` and its `origins`, with kernel-fixed text (for example `oats.aweb@1.10.3 declares no binding interface; messaging cannot be prepared`). For a provider's own `needs-configuration` the kernel names the slot, capability and phase but not the missing setting unless the provider sends it (OKF 2.1.1 sends only a code). One unqualified slot no longer hides another slot's diagnostics. Provider free text still never crosses the wire.
- **`oats trust <capability> --dir <deployment>` on a lock v3 deployment** returns a typed problem with the working command (`oats trust <cap> --deployment <abs> --artifact-set <sha256-…>`) instead of `unsupported lockfileVersion 3`. Nothing is approved automatically.
- **Help** documents `--artifact-set` and how it pairs with `prepare`'s `selections[].artifactSet` and `approvalRequired[]`.
- **`prepare` on an absent deployment path** returns a typed explicit-provisioning hold instead of a raw `ENOENT`.
- **One request file for both commands.** `prepare --request` accepts the explicit `workTarget` that `inspect --request` requires, and `oats inspect --request <f> --emit-prepare-request <out>` writes the converted preparation request.
