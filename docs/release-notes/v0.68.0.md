# OATS 0.68.0

Unreleased

## Upgrade

- **Install the Desktop first and the CLI second,** as
  [Upgrading](../upgrading.md) says: a 0.67 Desktop refuses a 0.68.0 CLI. The
  0.68.0 Desktop accepts OATS CLIs `>=0.26.0 <0.69.0`.

- **Package moves:** the official catalog pins oats.framework 1.14.1,
  oats.okf 5.3.0, oats.engineering 1.11.0 and oats.aweb 1.31.0 (Provider
  updates, below). A deployment that pins them takes them with `oats sync`;
  new spawns use them, and existing homes move with the step below. No floor
  changes: oats.aweb 1.31.0 still needs OATS >=0.52.0 and aw >=1.36.33.

- After bumping a package pin and running `oats sync`, stop each existing home
  that should adopt it and review `oats instance upgrade <instance> --plan`.
  Apply with the plan revision and an idempotency key, then start the session.
  Providers with state must support the `upgrade` adoption hook; a provider
  refusal names the remedy. oats.aweb's hook ships after this release, in
  oats.aweb 1.32.0: until a deployment pins that, a plan that moves oats.aweb
  refuses and names respawn. See [the deploy step](../upgrading.md#moving-existing-homes-to-locked-package-versions).
  This command requires a kernel advertising `instance-upgrade`; older
  kernels keep their existing spawn-only behavior.

## Added

- `oats instance upgrade` moves a stopped local home's package modules to the
  deployment lock, recomposing skills, instructions and hooks while keeping
  the recorded soul and member modules. Plans show provider adoption and
  composition changes and whether the home changed since spawn. Dirty homes
  retain their original retirement baseline for recovery, including with older
  kernels; work-tree baselines never change. Apply checks the revision and supports idempotent
  retries. Undo verifies the latest saved state and asks the restored version
  to adopt it. Before commit, a partial upgrade after a successful provider
  hook or an interrupted hook with an uncertain outcome finishes forward
  with the same key and blocks start with
  `E_UPGRADE_PARTIAL`. After commit, a cleanup failure permits start with a
  warning and the same-key retry finishes event publication and cleanup; another move waits
  until cleanup finishes.
- Start and restart report package drift and the command to move those
  modules. Their JSON includes `drift`; they keep the recorded copies. An
  unreadable lock yields one warning and no `drift`, without blocking launch.
  `modules.<cap>.previous` records the latest move, and `modules-upgraded`
  records its completion in instance events. Desktop tolerates the additive
  `previous` field and labels the new events: `modules-upgraded`, and
  `upgrade-refused` with its failed step and reported reason.

- **Desktop: a spawn on another machine is named from its task.** With Name
  left empty, a spawn on a server whose OATS takes an exact name is now named
  from its Opening instruction, as a spawn on this computer is: the Desktop
  asks this computer's harness and model for a name (OATS here with feature
  `instance-suggest-name`), shows it in the field and under it, and the
  server spawns under it. When this computer can't name it, the server names
  it from its task if its OATS can (feature `spawn-apply-suggest-name`), and
  otherwise numbers it as before. The help under an empty Name says which,
  before you press Spawn, and a notification says why when the instance was
  numbered instead. Naming never stops a spawn
  ([desktop.md](../desktop.md)).

- **Desktop: Workspace › Capabilities shows the workspace's defaults.** A new
  **Workspace defaults** section, above Workspace owned, shows what every soul
  starts with unless it turns one off:
  - **Core capabilities**: Knowledge, Messaging and Tasks, at most one of
    each per soul. A filled slot shows the capability and where it comes
    from, and opens its page. An empty one says there is no workspace
    default and each soul chooses its own.
  - **Additional capabilities**: any number per soul, the other capabilities
    the workspace gives every soul, shown the same way. One the workspace
    turned off is struck through.
  - A workspace with no defaults, such as a standalone deployment, says so in
    one line. The search and the repository pills never hide the section,
    and the section jump starts with **Defaults**. With an OATS that does not
    report the defaults, the section is not shown.
- **Desktop: "What capabilities are".** The round **i** button after the
  section jump explains what a capability gives a soul's instances, the three
  places one comes from, which capabilities are core and which are
  additional, and what workspace defaults are and why they matter.
  Workspace › Souls has the same button, **About souls**, which explains what
  a soul is
  ([Desktop](../desktop.md#capabilities-and-spawning)).

- `oats instance suggest-name --soul <soul> --task-file <f> --json`
  (feature `instance-suggest-name`) chooses the name a `--suggest-name` spawn
  of a soul would get, on this machine, for a spawn that may land on another:
  the soul only gives the role and needn't exist here. It resolves no
  workspace, writes nothing, records nothing and reserves no name; it reads
  only this machine's launch configurations and the OATS tmux server's
  environment. Its model call is bounded as the preview's is, and the task
  text goes to this machine's harness and model, as the preview's naming
  does. [A name for a spawn elsewhere](../desktop-cli-api.md#a-name-for-a-spawn-elsewhere-oats-instance-suggest-name).
  The name is not made unique: the host the spawn lands on does that.
  A naming failure answers a numbered result with its reason, never an error.
  It is never routed: `--server` is refused.
- `oats spawn <soul> --suggest-name` on an apply (feature
  `spawn-apply-suggest-name`): without `--preview`, the machine that spawns
  names the instance `<descriptive>-<role>`, made unique as today, and
  numbers it on any failure. The result carries `naming`. The naming call
  can add up to 20 s to the apply. A spawn without the flag is unchanged.
  Routed, the host needs the feature (`E_REMOTE_INCOMPATIBLE`, nothing sent).
  [Desktop CLI API](../desktop-cli-api.md#on-an-apply-feature-spawn-apply-suggest-name)

## Changed

- **The `oats-getting-started` agent does more of the setup itself,
  instead of handing it to the person**
  ([#1314](https://github.com/awebai/oats/issues/1314)). A clean-machine trial of the skill
  showed it handing back work at the end. Now:
  - It adds `~/.local/bin` to the shell's startup file when it set a
    per-user npm folder.
  - It opens the GitHub device page in the browser.
  - It opens the person's terminal with the exact command in it, for each
    step that needs a password or token typed there (a `sudo` or Homebrew
    password, an aweb invite token) and for the TUI. The person types only
    the secret.
  - On Linux it starts OATS Desktop on the new deployment through the
    session manager (`systemd-run --user`), so it gets the desktop session's
    environment rather than the agent's. It checks that it is running.
  - It quits a running Desktop before installing over it.
  - Without FUSE it uses `--appimage-extract-and-run`, which needs no
    `sudo`.

- **Desktop: an instance's card on the Deployments page has two buttons.**
  Clicking an instance shows what it reports, as before, and two buttons:
  - **Go to instance** opens the instance's terminal tab. For a stopped
    instance, which has no terminal, it reads **Start…** and opens the Start
    dialog. Double-click, Enter and `T` do the same.
  - **Go to soul** opens the soul the instance was spawned from on the
    Workspace page: that exact soul, never another of the same name. When it
    can't be told exactly, the button is disabled and says why, for example
    when the soul is no longer among the deployment's souls, or the instance
    is on a deployment other than the one the Workspace page shows.

  The card's Git, Restart with…, Brain and Workspace buttons are gone, and so
  is the `B` key there, which only said Brain was unavailable. Restart with…
  is in the instance's menu and its panel, Git on the panel's Developer page,
  and Workspace in the rail and on `S`
  ([desktop.md](../desktop.md),
  [desktop-keyboard.md](../../packages/desktop/docs/desktop-keyboard.md)).

- **Desktop and TUI: pressing the leader (Ctrl+X) shows nothing.** The panel
  of keys at the bottom of the Desktop's main area, and the TUI's leader hint
  in place of its cheat sheet, are gone. The leader still waits for its key
  exactly as before. Its table is in the Desktop's shortcuts editor (`?` after
  the leader, or ⌘, / Ctrl+,) and in the TUI's help (`?`). In the Desktop, a
  screen reader still hears that a key is awaited, and a key that cannot act
  still says why in one quiet line
  ([desktop-keyboard.md](../../packages/desktop/docs/desktop-keyboard.md),
  [TUI](../tui.md)).

- **Desktop: the spawn dialog's section keys follow the form.** The Opening
  instruction, the form's first field, is now ⌘1 / Ctrl+1, and Name, its last
  before **Developer settings**, ⌘6 / Ctrl+6 (they were the other way round).
  ⌘2–⌘5 and ⌘7 are unchanged. A shortcut you rebound is kept, and where one of
  yours now shares a key with a section's new default, yours is the one that
  runs, as the shortcuts editor says
  ([desktop-keyboard.md](../../packages/desktop/docs/desktop-keyboard.md)).
- **Desktop: the instance name is proposed sooner.** Once the Opening
  instruction holds seven words, the Desktop asks OATS for a name as you type
  (it waited for three words and a pause of about a second and a half). The
  Name field's placeholder shows the proposed name alone, without "will be
  named". ([Desktop](../desktop.md))

- **TUI: each workspace keeps its tabs, layout and place across a switch.**
  - Opening another workspace still closes the open terminals' viewers (the
    agents keep running), but coming back opens them again: the tabs in their
    order and groups, the split, each group's shown tab, and where the focus
    was, zoom included.
  - A tab whose instance is gone or stopped is dropped; another machine's tab
    is asked first again.
  - The selection, the scroll and, new, the filter come back with their
    workspace. Before, the filter was dropped on every switch, and a filter
    still being typed in is kept as `Enter` keeps it.
  - The palette (Ctrl+X then `k`) keeps each workspace's own recency, its last
    50 instances, so working in another workspace leaves it as it was.
  - Nothing is kept after the TUI exits ([TUI](../tui.md)).

- **Desktop and TUI on Linux and Windows: the shortcuts are Alt chords by
  default.**
  - Alt+K is the palette, Alt+P Quick Open (a spawn, in the TUI), Alt+O the
    list of workspaces, Alt+Z focus mode, Alt+W close the tab, Alt+E /
    Alt+Shift+E split, and Alt+F the filter.
  - Alt+← / → move between tabs, and Alt+Shift+← / → between split groups.
  - Alt+↑ / ↓ move between workspaces.
  - Alt+1–9 go to a tab.
  - Alt+Shift+↑ / ↓ still open the previous / next instance.
  - In a focused terminal, the family takes these keys from the program,
    among them Alt+F (readline's forward-word) and Alt+O, which #1433 had
    left to the program.
- **macOS: ⌥ with an arrow moves.** ⌥← / → go between tabs, ⌥⇧← / → between
  split groups, and ⌥↑ / ↓ between workspaces. ⌥⌘↑ / ↓ still open the
  previous / next instance, and the letters and digits stay on ⌘. ⌥⌘← / →
  no longer move between tabs, and ⌥⌘A no longer goes to the next group.
  - A text field keeps its ⌥ arrows for moving the cursor; a focused
    terminal does not. To give them back to the shell, rebind them in the
    Desktop's shortcuts editor.
  - The TUI takes them only where the terminal sends ⌥ arrows as such
    (iTerm2, kitty, WezTerm, Alacritty). Terminal.app, Ghostty and VS Code
    send ⌥← / → as word moves unless set otherwise; the docs give each
    setting. The leader moves everywhere.
  - The TUI on macOS shows no tab numbers, since no key there reaches a tab
    by number. The Desktop does (⌥⌘1–9).
- **Ctrl+Alt is still there, for programs that need Alt.** Choose it in the
  Desktop's Shortcuts page, or in `keys.json` (`"chords": "ctrl+alt"`), which
  both clients share. If you already chose Ctrl+Alt or Ctrl+Shift, you keep
  it; only those who never chose move to Alt.
  - Ctrl+Alt and Ctrl+Shift leave Alt+↑ / ↓ to the program. Ctrl+X then ↑ / ↓
    moves between workspaces in every family.
  - In the Alt family, Esc then the key reaches the program where the program
    reads Esc as Meta (readline, zsh, Emacs, irssi). Otherwise choose
    Ctrl+Alt.
  - The docs list each key the family takes from Claude Code, Codex, pi, the
    shell and the others, and how to reach it.
- **Each tab shows a small number**, the N that Alt+N goes to: 1–8, then 9 on
  the last tab of a strip with nine or more. In a split, each group numbers
  its own tabs. The Desktop's tab tooltip names the key. In the TUI, the
  numbers are the first thing dropped when the tab bar is too narrow for
  every name.
- **Ctrl+X then Shift+Tab** goes to the previous split group, as Ctrl+X then
  Tab goes to the next.
- On AltGr keyboard layouts, AltGr still types its characters and never fires
  an Alt chord.
  ([desktop-keyboard.md](../../packages/desktop/docs/desktop-keyboard.md),
  [TUI](../tui.md))

- **Desktop: the Workspace tabs read Souls, Capabilities, Teams, Setup.**
  Teams was first. The page still opens on Souls, and the arrow keys, Home
  and End follow the new order
  ([desktop-keyboard.md](../../packages/desktop/docs/desktop-keyboard.md)).

- **New workspaces get aweb tasks.** The getting-started skill's workspace
  file pins `oats.aweb` at v1.31.0 or later and sets
  `defaults.tasks: { oats.aweb-tasks: { from: package } }` when the
  workspace has messaging, so agents assign, claim and hand off work as aweb
  tasks. A workspace on Jira or Linear writes that provider instead. An
  existing workspace opts in as [integrations.md](../integrations.md#official-providers)
  describes.

- `--suggest-name` with `--expect-decision`, which a preview accepted and
  ignored, is refused (`E_BAD_ARGS`): the decision already binds a name.

- **Desktop and TUI: a list of workspaces at the top of the sidebar.** It
  replaces the workspace menu and is always shown: one line per workspace you
  can open, by name, whatever machines it is on. The current one is marked.
  A click, or Enter on a row, shows that workspace in the same window. The
  workspace's own pages show its machines and deployments.
  - Each workspace keeps its own tabs, layout, selection and recency, as
    before, so Ctrl+X then `k` (⌘K) still lists its instances, the most
    recently selected first.
  - In the Desktop, a workspace another window shows moves to this window,
    with its terminals and its split. Its file, brain and view tabs close in
    the other window. **Open in new window** is ⌘Enter / Ctrl+Enter on a row,
    or the row's context menu.
  - `w` in the sidebar, Ctrl+X then `o`, and the palette's
    **Workspace: switch…** focus the list.
- **A yellow dot on a workspace where an instance needs input**, after its
  name. Screen readers also get it as words, "needs input", and the TUI's help
  explains the dot. A workspace that hasn't been read recently shows no dot,
  never an old one.
- **Ctrl+X ↑ / ↓ move to the previous / next workspace of the list**, in both
  clients. They don't wrap. They used to open the previous / next instance.
  That move keeps its chords, Alt+Shift+↑ / ↓ (⌥⌘↑ / ⌥⌘↓ in the Desktop on
  macOS), and the roster's own arrow keys. On macOS the TUI has no chords, so
  there it's the roster's ↑ / ↓ then Enter.
- **Desktop: this computer's deployments that aren't opened yet are in
  Add local workspace…**, not in the list.
  - One click adds and opens one.
  - Deployments that can't be opened (missing, not a deployment any more,
    can't be checked) are listed after them, each with its **Remove**.
  - While the Desktop has no workspace at all (a first launch), a new window
    opens with this dialog.
- **TUI:** this machine's deployments that aren't opened yet stay in the
  switcher (`w` `w`).
  ([desktop.md](../desktop.md),
  [desktop-keyboard.md](../../packages/desktop/docs/desktop-keyboard.md),
  [TUI](../tui.md))

## Fixed

- `oats worktree remove` completes Git's partial deletion of a clean extra
  tree containing read-only ignored output, such as a Go module cache. A
  retry of an unregistered tree with a dangling `.git` file verifies its
  surviving files against the recorded branch before deletion, refusing
  modified or nonignored untracked paths even when tracked `.gitignore`
  files were deleted. Permission changes stay within the tree and never
  follow symlinks. Cleanup preserves `.git` until other entries are gone.
  Incomplete removal keeps the record and reports partial deletion
  accurately, with a manual recovery step when Git removed `.git` too.

- **Desktop: the tab and instance keys no longer skip a press.**
  - In a split, the tab keys (Ctrl+Tab, Alt+Shift+←/→, ⌥←/→, the leader's
    ←/→ and ⌥⌘1–9 / Ctrl+Alt+1–9) went through every tab in the order they
    were opened, across both groups. They now stay in the focused group, in
    the order its strip shows.
  - Moving to the previous or next instance (the leader's ↑/↓,
    Alt+Shift+↑/↓, ⌥⌘↑/↓) could re-open the instance already being opened
    when pressed again before its terminal arrived. Each press now moves one
    instance on.

- **Desktop: a spawn on another machine keeps the name you give it.** Spawning
  onto a server (Where to run, or a soul listed from a server) named the
  instance `<soul>-<what you typed>`, while the same name typed for this
  computer became exactly `<what you typed>-<role>`. Now a spawn on a server is
  named the same way as a local one when that machine's OATS can take an exact
  name (feature `spawn-name`, OATS 0.26.0 and later, as its last roster answer
  reports it): no `<soul>-` prefix in the field, the final name on the line
  under it, and a name that machine refuses as taken or invalid is explained
  there too. With an older OATS on either side, or a machine this computer has
  not heard from, what you type is still a purpose, with its prefix shown
  ([desktop.md](../desktop.md)).
- **Routed spawns check `--name` against the host.** `oats spawn --server <id>
  --name <name>` is refused with `E_REMOTE_INCOMPATIBLE`, before anything is
  sent, when the host does not advertise `spawn-name`, and with
  `E_ROUTE_EXISTS` when a saved route here already holds that name
  ([servers.md](../servers.md#run-there)).

- **Desktop: Electron 43.8.3, from 43.2.0, for Electron's security fixes.**
  It carries the fixes for
  [CVE-2026-102674](https://github.com/electron/electron/security/advisories/GHSA-gr2m-v5gq-v685)
  (windows opened from a sandboxed top-level document did not inherit its
  sandbox restrictions; fixed in 43.4.1) and
  [CVE-2026-102677](https://github.com/electron/electron/security/advisories/GHSA-qmv3-fv6v-rmhq)
  (the sandboxed preload code cache did not check that a cached entry matched
  its preload; first released in 43.5.0), the block of the compromised
  eMudhra intermediate certificates
  ([GHSA-jr5w-w6x2-84p9](https://github.com/electron/electron/security/advisories/GHSA-jr5w-w6x2-84p9),
  43.8.1), and the other Electron advisories fixed on the 43 line since
  43.2.0. Neither CVE was reachable in the Desktop: it refuses every window a
  page tries to open, its windows load only its own local files, and its
  preload does not run sandboxed. Electron 43.8.3 bundles Node.js 24.22.0, so
  the Node.js security release of 2026-10-21 (24.22.1) is not in it yet. The
  Desktop's own code on that Node.js, its main process and its backend, makes
  no TLS, DNS or outbound network connections: it reaches its backend over
  127.0.0.1 only.

- **Desktop: opening a new version while an older one runs says so.**
  Installing a new Desktop (an AppImage, a DEB, another copy) while an older
  one was running used to open a window of the old one, silently: the new
  version's features seemed missing. Now the running Desktop opens or focuses
  the window as before, then says which version you opened and which is still
  running, and offers **Restart into** the new one (it closes Desktop's
  windows and starts the version you opened; your agents keep running in their
  sessions) or **Keep** the running one. When the copy you opened can't be
  started again, it says to quit Desktop and open it again. This takes effect
  once the running Desktop is this version or later: an older running Desktop
  still opens its own window, so quit it once, by hand
  ([desktop.md](../desktop.md#updating)).

## Provider updates

- **oats.framework 1.14.1: oats.core 2.7.0, oats.setup 2.9.1.** Text only:
  neither floor (`compatibility.oats`) changes. (1.14.0 was tagged but never
  pinned by a release; 1.14.1 adds the last item below.)
  - **`/oats-upgrade` reaches deployments.** oats.setup carries the skill
    for "upgrade OATS" and "update to the latest": it reads the upgrade page
    and release notes at the latest release's tag, not the installed copy,
    and the setup inject lists it. `/oats-setup-model` points at it for an
    upgrade ([#1440](https://github.com/awebai/oats/issues/1440)).
  - **`/oats-operate` teaches moving a stopped home's package modules.** A
    new section covers `oats instance upgrade`: stop, plan, apply with the
    plan's revision and an idempotency key, then start; a partial move that
    must finish forward; and `--undo` for the latest move. Its lines name
    their version, "from OATS 0.68.0"
    ([#1450](https://github.com/awebai/oats/issues/1450)).
  - **`/oats-operate` on a half-done `oats worktree remove`.** From OATS
    0.68.0, `remove` finishes a deletion Git left half done on read-only
    ignored output, and checks an unregistered residue against its branch
    before removing it ([#1451](https://github.com/awebai/oats/issues/1451)).
  - **`/oats-onboarding` pins `oats.okf: v5.3.0`** and describes its harvest
    checkpoints and named harvesters.

- **oats.aweb 1.31.0: an official aweb provider for the tasks slot.** The
  catalog and this workspace pin `oats.aweb: v1.31.0`. The package now ships
  `oats.aweb-tasks` (`layer: tasks`) beside `oats.aweb` (messaging), and the
  catalog aliases `oats.aweb-tasks` to it.
  - A workspace selects it with
    `defaults.tasks: { oats.aweb-tasks: { from: package } }` (or a soul's
    `capabilities:`). Tasks use the instance's own oats.aweb identity in its
    default team: the `/aweb-tasks` skill covers finding work, claims,
    assignment, status, dependencies as blockers, handoff and epics through
    `aw task` and `aw work`, with every prose field read from a file.
  - The oats.aweb messaging instructions now point task state at the
    selected tasks layer; `aw lock` and `aw roles` stay outside OATS.
  - Readiness has no tasks-slot item for this provider. Its spawn hook adds a
    fixed brief line and makes no aw calls.
  - The floors are unchanged (OATS >=0.52.0, aw >=1.36.33). A pinned
    `oats.aweb: v1.31.0` selects `oats.aweb-tasks` on older CLIs too, without
    this alias (verified on 0.67.1). A deployment gets it by pinning the
    version and running `oats sync`; only new spawns use it.

- **oats.okf 5.3.0: named harvest checkpoints; instances name their
  harvesters.** The catalog and this workspace pin `oats.okf: v5.3.0`
  (floor unchanged, OATS >=0.49.0).
  - The checkpoints are a PR handed over for review, a finished task and, in
    a long-lived role such as a maintainer's, a feature ready, a release or
    deploy shipped, and a direction decision taken with the human. Each gets
    one proposal carrying only what no earlier proposal carried, and a line
    in `log.md` even when there is nothing to propose.
  - The available-memory gate before a harvester spawn is gone. A proposal
    held back by a harvester that is still listed launches at the next
    checkpoint.
  - The proposer names each harvester:
    `oats spawn oats.okf/knowledge-harvester --name <harvester-name> …`,
    with a name **okf-propose** prints from the source's name and a fresh
    UUID. The kernel's numbered default could land on an alias that a
    retired harvester's messaging certificate still holds, and the spawn
    then failed at identity minting. `E_INSTANCE_NAME_TAKEN` and identity
    failures stop and are reported, with no automatic rename.
  - See [Knowledge](../knowledge.md#the-flow).
- **oats.engineering 1.11.0: the release lane.** The catalog and this
  workspace pin `oats.engineering: v1.11.0` (floor unchanged). One
  maintainer lane is the release lane: it plans and tags every release and
  keeps the lane map, which says when another lane's merge needs its
  sign-off. A maintainer the map doesn't name asks for a lane before it
  acts. The maintainer's harvest checkpoints defer to the knowledge layer's
  rules.
- **Upgrade:** `oats sync` locks both; only new spawns get them, or a
  stopped home moved with `oats instance upgrade` (from OATS 0.68.0).
  Peer maintainers name the release lane and the sign-off rule in their
  lane map.
