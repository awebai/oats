# OATS 0.53.0

2026-10-13

## Upgrade

[Upgrading OATS on a host](../upgrading.md) has the steps that are the same
for every release: the CLI, then `oats update` in each deployment, then
`oats doctor`. It also says when a change of Node version leaves something
to do on a host, and what: restart the instances and, where schedules run,
install the host timer again; before that, install the CLI again where it is
installed inside the Node version.

- **Where the Desktop is installed, install Desktop 0.53.0 before the CLI
  ([#1107](https://github.com/awebai/oats/issues/1107)).** A 0.52.0 Desktop
  refuses a 0.53.0 CLI and lists no instance until it is replaced. Desktop
  0.53.0 accepts the older CLI in the meantime. This includes an
  `oats update` whose plan installs the CLI.

- **A host that comes from 0.51 or earlier does 0.52.0's
  [Upgrade steps](v0.52.0.md#upgrade) first, in their order.** One of them is
  easy to miss because it is a host tool and not OATS: aw 1.36.33 or later,
  before `oats sync`. The sync to this release's catalog locks oats.aweb
  1.27.1, which refuses every new spawn below that version. After the sync,
  `oats readiness --soul <name>` shows it as a failed provider check, with
  the install that cures it.

- **Once the CLI is 0.53.0, run `oats update` in each deployment that
  launches pi instances.** It now moves the pi bridge in every pi folder that
  deployment's launch configurations name, and `oats doctor` warns about each
  one that is behind
  ([#991](https://github.com/awebai/oats/issues/991)). An `oats update` run
  by 0.52 or earlier moves the bridge of the default pi folder only, so the
  one that upgraded the CLI is not enough.

- **Claude Code instances on a Homebrew node: a restart rewrites their
  waiting hooks, and a respawn makes that last
  ([#997](https://github.com/awebai/oats/issues/997)).** A home's hooks in
  `<home>/.claude/settings.json` are written again at every `oats session
  start` and `restart`, by the copy of oats.core in that home, which a start
  does not refresh. A home spawned before the oats.framework that carries
  this fix keeps writing the path of the versioned keg, so it is repaired by
  a restart after each Node upgrade, and gets the lasting path when it is
  respawned. Between a Node upgrade and that restart, such an instance does
  not report that it waits on you. A home spawned with the fixed oats.core
  gets the lasting path at its first start under this kernel, whichever
  kernel spawned it.

- **On every host where `oats setup` was run, run `oats setup` once more
  after upgrading the CLI, as the same user
  ([#1003](https://github.com/awebai/oats/issues/1003)).** The capture hooks
  in `~/.claude*/settings.json` and the capture watcher's unit still name the
  `node` that ran the earlier setup, and nothing else rewrites those files:
  no `oats update`, spawn, start or restart. The run replaces its own hooks
  and unit and adds no second one. `oats setup --dry-run` first prints the
  `node` it would record and changes nothing. The same step follows a change
  of Node version wherever the recorded path does not outlast it
  ([Upgrading](../upgrading.md#after-a-change-of-node-version)).

  A run that prints `already installed` for the watcher's unit has not
  checked that the watcher is enabled
  ([#1099](https://github.com/awebai/oats/issues/1099)). On Linux,
  `systemctl --user is-enabled turn-record-capture.service` says whether it
  is. Where an earlier `oats setup` could not enable it, enable it by hand:
  `systemctl --user enable --now turn-record-capture.service`.

- **Existing resident custody units: after updating to oats.aweb 1.27.1, run
  `oats aweb resident create <name>` again from the deployment**, with the same
  `--root` if one was used. An existing unit changes only on that rerun; an
  OATS upgrade or seat restart alone does not refresh it. OATS 0.53.0 supplies
  the kernel-selected Node path; supported older kernels retain the previous
  fallback. If the recorded `aw` path lives inside a Node version that will
  be removed, install aw in the new version and rerun before removing the old
  one. See [the provider's upgrade steps](https://github.com/awebai/oats-aweb/blob/v1.27.1/docs/resident-create.md#after-changing-node-or-aw).

- **After upgrading, run `oats doctor`: it lists each key of `souls.launch`
  that matches no soul, with the command that fixes it.** Until then a spawn
  that would fall through is refused and says the same
  (`E_LAUNCH_PREFERENCE_UNMATCHED`, under **Changed** below). This reaches
  scheduled jobs, triggers and agents' own spawns: before 0.53.0 such a key
  was never read.

  To check before upgrading: every key of `souls.launch` other than `"*"` is
  the name of a soul that `oats souls` lists, bare for a member's soul and
  `<package>/<soul>` for a package's. For a script, on 0.51.0 or 0.52.0:

  ```
  oats souls --json | node -e 'const r=JSON.parse(require("fs").readFileSync(0,"utf8")).result;const p="oats-local.yaml#/souls/launch/";console.log([...new Set(r.souls.map(s=>s.launch&&s.launch.at).filter(a=>a&&a.startsWith(p)).map(a=>a.slice(p.length).replace(/~1/g,"/").replace(/~0/g,"~")))].sort().join("\n"))'
  ```

  It prints the keys of `souls.launch` that decide some soul's launch. A key
  in the file that it does not print, other than `"*"`, names no soul.

- **A host on 0.52.0 or earlier that is refused with
  `E_REMOTE_UNREADABLE` in a second or two, on a network that is fine, needs
  only this upgrade ([#1059](https://github.com/awebai/oats/issues/1059)).**
  The refusal names the reason `network`, or `auth`, and neither is the
  cause: see Fixed. Installing the CLI goes through npm and not through the
  remote cache, so the fault does not block the upgrade, and the first read
  by 0.53.0 fetches the commit. To run a command on the old kernel before
  that, put three Git variables in front of it, for that command only:

  ```
  GIT_CONFIG_COUNT=1 GIT_CONFIG_KEY_0=fetch.negotiationAlgorithm GIT_CONFIG_VALUE_0=noop oats sync
  ```

  The same prefix works on any `oats` command that fetches: a spawn, a
  preview, `oats souls`, `oats workspace status`. Do not run Git inside
  `~/.cache/oats` and do not move a cache entry aside: the old kernel
  rebuilds it and fails the same way. In that state `oats souls` can also
  print its list without a package's souls, with no error and exit 0
  ([#1098](https://github.com/awebai/oats/issues/1098)); `oats souls --json`
  names them in `problems`.

- **The official catalog's versions in this release** are oats.framework
  1.9.4, oats.okf 5.0.3, oats.aweb 1.27.1 and oats.engineering 1.9.1: see
  Provider updates. Pin what your workspace uses, then run `oats sync`.

## Added

- **`oats tui` (preview) shows a deployment's instances (#855).** In 0.52 the
  preview drew a frame and read nothing from the kernel. **This version shows
  a workspace's instances, on this machine and on the other machines
  registered on it, and changes nothing.** The list
  is the roster the Desktop draws, with the same groups, order and states,
  from the same code, and it follows the deployment every few seconds. Beside
  it is the detail of the selected instance, with what it needs from you. `/`
  filters by name, soul and repository. **It cannot yet** open an agent's
  terminal, stop, start, restart, retire or spawn one, show souls or
  capabilities, or add, check or remove a machine: its help screen
  names the `oats` command for each. It is still a preview: its screens and its configuration
  file may change without notice. [docs/tui.md](../tui.md) has the rest.
  - **Start it in or under a deployment**, or name one: `oats tui --dir
    <path>`. With no `oats-local.yaml` at or above the start, and, when no
    `--dir` was given, no deployment directly inside `~/Agents` to offer, it
    prints one line (`E_NO_DEPLOYMENT`) and exits 1. Started inside an agent's pane it
    still reads the deployment it was asked about: it removes the instance's
    variables from its own environment first.
  - **It runs the kernel it shipped with**, never an `oats` found on `PATH`,
    and only to read (`oats status` and `oats workspace status`, then a probe
    of the terminals, and `oats server roster` for the other machines). A
    kernel it cannot accept stops the start with
    `E_TUI_KERNEL`. Start it again after upgrading OATS.
  - **Every key can be changed** in `$XDG_CONFIG_HOME/oats/tui.json` (else
    `~/.config/oats/tui.json`). A file it cannot honour stops the start, one
    line per problem (`E_TUI_CONFIG`): it resolves no conflict between two
    actions and guesses nothing.

- **`oats soul launch set|remove` writes a soul's launch preference
  ([#990](https://github.com/awebai/oats/issues/990)).** Until now the only
  way to pin a soul to a launch on a machine was to edit `oats-local.yaml`
  `souls.launch` by hand, the edit everyone is told not to make.

  ```
  oats soul launch set <soul>|'*' (--launch-config <name>|none | --harness pi|claude|codex [--model <id>])
  oats soul launch remove <soul>|'*'|<exact key>
  ```

  each with `--plan` (every check, nothing written), `--dir <deployment>` and
  `--json`. `set` names the soul as a spawn does and writes the key that soul
  has, so it cannot write a key that names no soul. `remove` also takes the
  exact text of a key in the file, and that form works when the workspace's
  souls cannot be read. Both answer what the next spawn of the soul selects
  and every key of `souls.launch` that still names no soul. **The file is
  rewritten, and every other entry keeps its value and its comments.** A
  client gates on the feature `soul-launch`; the answer is `soulLaunchApi: 1`
  ([docs/desktop-cli-api.md](../desktop-cli-api.md#oats-soul-launch)). New
  code: `E_LAUNCH_PREFERENCE_UNKNOWN`, a `remove` of an entry the file does
  not have. Not in this release: a `list` verb (`oats souls` shows each
  soul's launch), and a lock for `oats launch-config set|remove`, which
  writes the same file without the one this verb and `oats teams` hold
  ([#998](https://github.com/awebai/oats/issues/998)).

- **`OATS_NODE_BIN`: the node a capability writes down
  ([#997](https://github.com/awebai/oats/issues/997)).** Every hook, every
  provider check and operation, and every dispatched command now receives
  `OATS_NODE_BIN` beside `OATS_CLI_BIN`: the node to write into anything that
  outlives the process (a harness's settings, a unit, a script). It is the
  node running the kernel, by the rule the host timer's unit already follows
  (#916): the Homebrew `opt` link for a keg, else the same node found on the
  kernel's `PATH`, else the path as it is. A version manager's shim is another
  program, so it is never the answer; with mise the answer is the version's
  own path (measured), and other version managers were not measured. Like
  `OATS_CLI_BIN`, a launch configuration cannot set it and it is not part of
  the environment OATS starts a session with. A capability that must also run
  under an older kernel falls back to `process.execPath` when the variable is
  absent. See [Capabilities](../capabilities.md#the-node-a-hook-writes-down).
  - **When the rule has no stable answer, a spawn and a start say so.** Each
    carries one more line in `warnings`, for every harness: `the node path
    <path> is not stable (no Homebrew opt link and no node on PATH resolves to
    it): what this home's hooks record with it stops working when it goes
    away; install a node with a stable path and restart the instance`. A
    preview carries none. No other answer changes.

- **`oats tui` (preview) shows a workspace's other machines, and switches
  between workspaces (#855).** It is still a preview: its screens and its
  configuration file may change without notice, and it still changes
  nothing. **This version adds the instances a workspace runs on the other
  machines registered on this machine**, in the same list as this
  machine's: each deployment under a heading of its own, a machine's
  heading with the time its rows were read. A row of another machine shows
  what its host reported at that time, not what is true at this moment. A
  machine that is not reached keeps its heading and the rows it last
  reported, and they read `unknown`: nothing reads as stopped that is only
  not reached. **`w` opens a switcher of workspaces**: the workspaces this
  run knows, what was matched to no workspace, and the deployments directly
  inside `~/Agents`, which `Enter` opens in the same run. **Started outside
  every deployment, with no `--dir`, it starts with that switcher** when
  `~/Agents` holds a deployment, where it printed the `E_NO_DEPLOYMENT`
  line; with none there, and with a `--dir` that is in no deployment, it
  prints that line and exits 1. It keeps nothing on disk, so a machine it
  has not reached in this run is listed by its own name, in no workspace.
  **It cannot yet** open an agent's terminal (`oats session attach --home
  <home>`), stop one (`oats instance stop <instance>`), start or restart one
  (`oats session start --home <home>`), retire one (`oats retire
  <instance>`), show souls or spawn an agent (`oats souls`, `oats spawn
  <soul>`), show capabilities (`oats capabilities`), add, check or
  remove a machine (`oats server connect`, `oats server check`, `oats server
  remove`), or open from its switcher a deployment outside `~/Agents` (`oats
  tui --dir <path>`): its help screen names the same commands.
  [docs/tui.md](../tui.md) has the rest.
  - **The other machines are one more read**, `oats server roster --json`,
    by the kernel it shipped with. It never holds this machine's rows, one
    runs at a time, and the next begins no sooner than 15 seconds after the
    last one ended unless you ask for it (`r`).
  - **Two new actions can be given other keys** in `tui.json`: `workspaces`
    (`w`) and `open-workspace` (`enter`). A `tui.json` that gives `w` or
    `enter` to another action stops the start, as any key given to two
    actions does (`E_TUI_CONFIG`): give that action of the switcher another
    key, or none.

- **A retire plan says as a fact whether `work/` is the instance's own tree
  (#988).** `facts.ownWorktree` in `oats retire --plan --json`, and in the
  fresh plan of an `E_PLAN_STALE` and an `E_CHILDREN_RUNNING` refusal, is a
  boolean: `true` exactly when `work/` is the instance's own work tree, the
  one the retire retains or removes. It is the answer of the reading the
  retire acts on. `facts.workMode` is the record's value, which the
  instance can write, and `facts.work` is an observation through any link,
  so neither says it: a link or a directory of the home under a record that
  says `worktree`, and an attached instance over a tree on another branch,
  have `false`. `defaults.retainWorktree` is unchanged and follows the fact
  today; it is the default of an option, not the place to learn what
  `work/` is. Feature word `retire-plan-own-worktree`: without it the key
  is absent and says nothing. A stop plan does not carry it. The plan's
  revision, notes and text, and the receipt, are unchanged. See [the retire
  plan](../desktop-cli-api.md#retire).

## Changed

- **`oats teams add|remove|default` no longer re-wrap a long line of
  `oats-local.yaml`.** These verbs rewrite the file, and a value past 80
  columns elsewhere in it came back folded over two lines. Values are
  unchanged, before and now: only the line breaks differ. The file is now
  written the same way by every verb that shares this write, `oats soul
  launch` included.

- **Desktop: a row keeps its roster group under a filter and a collapse**
  ([#971](https://github.com/awebai/oats/issues/971)). A relation group is
  now decided on the whole roster, not on the rows left on screen. With a
  filter, one match out of a group of five is listed under its group's name,
  where it stood under "independent"; the same holds for a query in the
  command palette. With a collapse, a root collapsed over its whole group
  stays under the group's name and at its place, where it moved to
  "independent" at the press and came back on expand, taking the keyboard's
  selected row with it. A group with no row on screen is not drawn, and
  "independent" lists only instances with no relation. A header still counts
  the rows shown under it.

- **The Desktop accepts OATS CLIs `>=0.25.8 <0.54.0`.** The compatibility band
  admits 0.53. Upgrade the CLI and the Desktop together: a 0.52.0 Desktop
  refuses a 0.53.0 CLI. No new gate on the band. `oats tui` runs the kernel it
  ships with and is held to the same band.

- **Desktop: when a spawn works but Claude Code ignores the channel option,
  Desktop says after the spawn that mail and chat will not wake the instance,
  with what OATS reported (#886).** From 0.52.0 a launched spawn's successful
  answer carries `launchPrompts` in the start's shape. With the status
  `flag-ignored` the spawn worked and the instance has no channel delivery.
  After a Start or Restart the Desktop already said so in a notice; a local
  spawn now shows the same notice, from the same reader. It is shown once per
  spawn, also for a replayed one, beside any other notice of that spawn. While
  another workspace is on screen it is held, and shown on return. A
  `--no-launch` spawn, any other status and an answer without `launchPrompts`
  read as before. A spawn routed to a server shows none.
  - The creation receipt of a local spawn (`spawnCreationReceipt` in
    `packages/client/`, and the apply reply of the Desktop's `/api/spawn`)
    gains the optional key `flagIgnored`: `{reason, warnings, omitted}`. It is
    additive. An older side that does not know the key drops it, and the
    receipt stands.

- **Desktop: the notice that Claude Code ignored the channel option shows at
  most 16 of the warnings OATS reported, and at most 4096 characters of them,
  and says how many more there are (#886).** After a Start, a Restart or a
  spawn, the notice's Details hold the warnings of the kernel's answer in the
  order given while both bounds hold, each whole, and with more a last line
  such as "3 more not shown." The cut is by position: no warning is picked,
  matched or dropped by its words. OATS puts its own sentence last, so
  warnings that fill the bound before it leave it out: the notice still says
  what happened, without OATS's own advice on what to check.

- **`oats update` and `oats doctor` cover every pi folder of the deployment**
  ([#991](https://github.com/awebai/oats/issues/991)). Until now they read the pi
  bridge (`@awebai/oats-pi`) of `~/.pi/agent` only. A launch configuration
  that sets its own `PI_CODING_AGENT_DIR` has its own folder, so a pi
  instance launched through it kept an old bridge against a new kernel, with
  nothing saying so. Now both look at the default folder, at this shell's
  `PI_CODING_AGENT_DIR`, and at the folder of each pi launch configuration of
  the deployment; two names for one folder are one folder.
  [docs/upgrading.md](../upgrading.md) is the new page that owns this.
  - **`oats doctor` prints one `version skew` warning per folder**, naming
    the folder and why it is looked at (`the default`, `launch configuration
    work`). A folder it cannot look at is a warning too; one that does not
    exist or holds no bridge is not. `oats doctor --json` is unchanged.
  - **`oats update` lists the folders in its plan**, each with the bridge
    found there and what it does: move it, leave it alone, or not touch it,
    with the reason and the command to run there. It does not touch a folder
    it cannot resolve (a `{fromEnv: NAME}` not set where it runs, a path that
    is not absolute), a bridge it cannot read, or a folder named only by
    launch configurations that run their own `executable`: it runs no
    wrapper. It creates no folder and installs no first bridge.
  - **`oats update --dir <deployment>`** names the deployment from anywhere.
    With no deployment at or above the working directory it still moves the
    default folder and this shell's, and its last line says that no launch
    configuration was looked at.
  - The text of the warning and of the plan changed. Nothing in OATS parses
    either.

- **Desktop: the rules for other machines and the switcher's words are in
  `packages/client/`.** What an answer of `oats server roster --json` becomes
  when it fails or cannot be read, how a machine that stops answering keeps
  its place in its workspace, and the words the workspace switcher shows for
  a view are now functions in `packages/client/` that keep nothing, where a
  second client can call them. The Desktop shows and stores what it did:
  `/api/panel`, `/api/workspaces`, `remote-identity.json` and every sentence
  are unchanged. The panel's functions there now read no clock at all: a
  remote deployment's panel takes the time of its call.

- **Desktop: a deployment the kernel refuses to read says so in the kernel's
  words, attributed.** When `oats status` or `oats workspace status` answers
  with an error, the deployment's line now reads "OATS answered with an error
  (`<code>`). It says: `<message>`", where it read "`<code>`: `<message>`".
  The message is shown as one line, and withheld whole ("[Detail withheld]")
  when it looks like a credential or holds control characters. The Desktop's
  own failures to read a deployment (no compatible CLI, a timeout, an answer
  it cannot read) read as before. `oats tui`, which reads a deployment from
  this version on, shows the same sentence in its notice.

- **Desktop: the Spawn dialog says an unmatched launch preference in its own
  words, and quotes OATS under Details**
  ([#1015](https://github.com/awebai/oats/issues/1015)). From 0.53.0 OATS
  refuses a spawn that names no launch while `oats-local.yaml` `souls.launch`
  holds a key that names no soul. The dialog read "OATS couldn't work out this
  soul's defaults. Try again, or see Details.", with OATS's message under
  Details and its fix nowhere. It now reads "This machine's launch
  preferences name a soul this workspace doesn't offer, so OATS won't choose
  a launch for this soul. To spawn now, pick a harness above, or a launch
  configuration in Developer settings. To fix it for every spawn, correct
  the preference (Details)." Details hold the code, then "OATS says:
  `<message>`", then the fix on its own line. Each text is one line and
  whole; one that looks like a credential reads "[Detail withheld]", and
  "OATS says:" then stands before the other.
  - **At a press**, when the key appeared after the dialog had read its
    preview, the notice read "OATS couldn't complete the spawn. Try again, or
    see Details. Nothing was created." It now reads "This machine's launch
    preferences name a soul this workspace doesn't offer, so OATS won't
    choose a launch for this soul. To spawn now, pick a harness or a launch
    configuration for this spawn. To fix it for every spawn, correct the
    preference. Nothing was created.", with the code under its details. A
    dialog still open reads the preview again and shows the first sentence.
  - **Unchanged:** a spawn routed to another machine shows that host's
    refusal as before, and a spawn already sent that OATS then refuses with
    this code still reads as an outcome to check.
  [The spawn dialog](../../packages/desktop/docs/desktop-spawn-preview.md#an-unmatched-launch-preference)
  has the whole of it.

- **Desktop: a soul's launch problem says who is speaking**
  ([#1015](https://github.com/awebai/oats/issues/1015)). The soul page and
  the soul panel show a box when a spawn of that soul with no launch chosen
  would be refused: a harness that is not installed, a launch configuration
  that is gone or ambiguous, and from 0.53.0 a launch preference that names
  no soul, which every soul with no entry of its own then carries. The box
  showed OATS's message and its fix as two paragraphs, with no word on whose
  they were. It now starts with the Desktop's own line, "A spawn of this soul
  with no launch chosen would be refused here.", then reads "OATS says:
  `<message>`" and the fix under it, with the code under Details as before.
  Each of OATS's two texts is one line and whole; one that looks like a
  credential reads "[Detail withheld]", and "OATS says:" then stands before
  the other. This is so for every launch problem, not only the new one.

- **A pull request writes its release-notes entry in a file of its own**
  ([#1018](https://github.com/awebai/oats/issues/1018)). The entry goes in
  one file under `docs/release-notes/next/` and no longer into the version's
  notes file, so two pull requests that share no code no longer conflict over
  their entries. `node scripts/assemble-release-notes.mjs --tag vX.Y.Z`, run
  in the release-prep pull request, moves the entries into the notes file and
  removes the entry files. **A tag is refused while an entry file exists**,
  by the release workflow and by `scripts/release-lane.mjs build`, before
  anything is built or published.
  [Release-notes entries](../release-lane.md#release-notes-entries) has the
  rule.

- **On btrfs, a retire that went through with an empty directory where its
  recovery copies one file is now refused
  ([#1029](https://github.com/awebai/oats/issues/1029)).** With an empty
  directory at `info/attributes`, at the stash's log or at the log of a
  nested repository's branch, `oats retire` completed there. It now answers
  `E_WORK_PRESERVATION_FAILED`, the code every other file system already
  gave for it. On every file system, such a path whose parent directory
  cannot be searched is refused the same way, where it was left out of the
  copy. See the entry under Fixed.

- **A retire that was refused for a work tree with no index file now
  completes ([#1048](https://github.com/awebai/oats/issues/1048)).** For an
  instance whose own tree has no index file, `oats retire` answered
  `E_WORK_PRESERVATION_FAILED`, with `--force` and with
  `--discard-worktree` as without them. It now completes and writes a
  recovery whose `repo/` has no index file either. No code, no key of the
  receipt and no warning is new. See the entry under Fixed.

- **The `fix` of a launch refusal names `oats soul launch`, not the file**
  ([#1049](https://github.com/awebai/oats/issues/1049)). Three answers still
  told the operator to change `souls.launch` in `oats-local.yaml`, the hand
  edit that `oats soul launch set|remove` replaced: `E_HARNESS_UNAVAILABLE`
  (a harness that is not installed), `E_LAUNCH_CONFIG_UNKNOWN` as a soul's
  `launch.problem`, and `E_LAUNCH_CONFIG_AMBIGUOUS`. Their `fix` now gives the
  command, for example "install codex, or pin this soul to another launch
  (oats soul launch set <soul> --launch-config <name> | --harness <h>)", and
  where `souls.launch."*"` decided the launch it gives the command for `'*'`
  first. The message of `E_HARNESS_UNAVAILABLE` and of
  `E_LAUNCH_CONFIG_AMBIGUOUS` ends with its `fix`, so it changed with it. No
  code, no `details` field and no API version changed. A `fix` is a sentence
  for a person: its wording may change between releases, so a client shows it
  and never parses it
  ([Launch preferences](../desktop-cli-api.md#launch-preferences)). The
  function that renders the command also holds one rule for every text of a
  launch answer: none carries a character the kernel never prints, whatever
  key it is handed

- **A stop whose claim cannot be written reads it instead, and stops (#946).**
  Since 0.52.0 a stop holds the home's claim, so a stop whose claim could
  not be written was refused before it signalled anything
  (`E_LIFECYCLE_FAILED`). A full disk is the likely case, and one of the
  reasons a person presses Stop. Now `oats instance stop --apply`, and it
  alone, reads the claim where it cannot write it, and goes on when nobody
  holds it.

    `EDQUOT` (the quota is spent), `EROFS` (it is read-only), or `EACCES` or
    `EPERM` (the claims directory is not writable by this user). What stops
    this stop from writing there stops a retire or another stop of the same
    user as well. Any other failure is refused as before.
  - **Beside a holder nothing changes:** a retire or a stop that holds the
    claim, a holder whose liveness cannot be read, and a file that is no
    readable claim are answered with the same code, sentence and `details`
    as for a stop that can write, and nothing is signalled. The claim is
    read once more just before the first signal.
  - **It says so.** One line per such target on stderr, in text and in JSON
    mode: `oats: warning: <instance>: stopping without its claim: <lock>
    could not be written (<CODE>), and nobody holds it. A retire or a stop
    of <instance> that starts while this one runs will not see it.` The
    receipt has no new field. Through `--server` the warning does not reach
    the caller, as no warning of a stop does (#952).
  - **The limits.** Nothing on the home shows such a stop, so a retire or a
    stop that starts while it runs and that can write its claim is not
    refused: space freed a moment later, or a process of another user. If
    the warning says `EACCES` or `EPERM`, fix the permissions of the claims
    directory (`<instances>/.oats-retirement/claims`); do not live with the
    warning.
  - **On a full disk** the stop cannot write its own record and receipt
    either. The session is stopped, and that target's row is `ok: false`,
    `E_SESSION_STOP_FAILED`, `… its harness was signalled (SIGTERM) and has
    exited`, `stillRunning: []`: read `stillRunning`. The receipt is not
    stored, so the same key is not replayed: the same apply again answers
    `E_PLAN_STALE`, and with the fresh revision `alreadyIdle`.
  - A retire, and a retire's stop of a recorded child, need their claim as
    before.
  - A claim that could not be written leaves no private file
    (`<lock>.tmp-<pid>-<nonce>`) behind when its write fails after the file
    was created, as on a full disk.

- **A scheduled self-retire that does not complete says so, and no longer
  leaves the instance reading as retiring when nothing of its home was
  changed (#954).** `oats retire <instance> --self` only schedules: a
  detached completion runs the retire a few seconds later, with nobody at a
  terminal. A completion that was refused or that failed left its pending
  marker behind, so the instance read `RETIRING` in `oats status`, and `oats
  instance stop --apply` and `oats session start` answered
  `E_INSTANCE_RETIRING`, for a retire that was not happening.
  - **The marker follows how far the retire got.** It stays when a retire
    hook was started or the removal of the home began: the home is owed a
    retire, and `oats retire <instance>` continues. Otherwise the completion
    removes it, and the instance is a stopped or a running instance like
    any other: a start works, and a wake schedule may start it.
  - **The outcome stays, as before:** `.oats-retired-<instance>.json` and
    its log beside the home, listed by `oats status` (`retireFailures`)
    until a retire of the instance completes. Nothing retries by itself.
  - **A new event kind, `retire-refused`,** `data: {code, homeChanged,
    reason}`, written once by such a completion and by nothing else.
    `code` is a kernel code, or `null` for a cleanup that did not finish.
    `reason` is the sentence the retire answered, on one line and at most
    2048 UTF-16 code units. The row is in the workspace's log. A client
    that does not know the kind reads the row as any unknown kind.
  - **A scheduling that the host held up** for longer than its completion
    waited for it (3 s) made that completion give up: the self-retire did
    not happen, and the marker, written afterwards, stayed. A completion now
    waits for its own scheduling for up to ten minutes, then retires the
    instance. A `--self` whose completion has already ended when the
    marker is written (it was killed, or the ten minutes passed and its
    retire was refused) answers `E_SELF_RETIRE_SCHEDULE_FAILED`, removes
    the marker it wrote, and schedules nothing.
  - **A retire hook of a scheduled self-retire no longer inherits
    `OATS_RETIRE_INTENT`:** the variable is the completion's own input, and
    the completion takes it out of its environment before it runs anything.
  - **Homes already stuck by a completion refused under 0.52.0 or earlier**
    keep their marker. To retire such an instance after all, run `oats
    retire <instance>`. To keep it, no command does this: once the
    completion the marker names is gone (its pid is `completionPid` in the
    marker), remove by hand `.oats-retire-pending-<instance>.json`,
    `.oats-retired-<instance>.json` and `.oats-retired-<instance>.log`
    beside the home. The kernel does not do this for a home whose refusal
    it cannot date.

  [A completion that does not complete](../souls-and-instances.md#self-retire-not-completed),
  [the `retire-refused` event](../desktop-cli-api.md#retire-refused-event).

## Fixed

- **`oats update` removes nothing it cannot replace**
  ([#852](https://github.com/awebai/oats/issues/852)). It ran `pi uninstall`
  and then `pi install`: run right after a release, the install failed on a
  version the registry did not list yet, and the host was left with no bridge
  at all. Now:
  - **It runs one `pi install` over the installed bridge, and no
    `pi uninstall`.** pi replaces a package it already holds, and an install
    that fails leaves the old one in place.
  - **Before any step, the CLI's own install included, it asks the registry
    for the bridge's exact version**, with npm told to revalidate its cache.
    If the version does not resolve, it stops with nothing changed and says
    to run it again in a few minutes. `--check` does not make this lookup.
  - **A failed step names the folder and the exact step to run again**, says
    what the folder holds now (the old bridge, or none) and lists the folders
    not reached. It stops at the first failure.
  - A pi folder whose path has a space in it is one argument: the steps are
    run as arguments, never as a split line.
- **`oats retire --plan`: the text no longer reads as if another instance's
  tree were removed (#959).** For an instance with no work tree of its own,
  the plan's `defaults:` line printed `retain worktree false`. For an
  attached instance that read as if its owner's tree were removed. It is
  not. The line now says what is true of the work mode: `no work tree of its
  own (work/ links to its owner's tree and that tree is not touched)` for an
  attached instance, the same of the shared checkout and of the deployment
  directory for a checkout and a workspace instance, and `no work tree
  (work/ is the home's own directory: copied to recovery when not empty and
  then removed with the home)` for a directory instance. A record with no
  work mode says `work mode not recorded`, and one with a work mode the
  kernel does not know says `work mode not known to this kernel`, without
  the value, unless `work/` is the instance's own tree or a real directory
  of the home: the line then says that, whatever the mode (#962). A
  `worktree` instance's line is unchanged (`retain worktree true`), unless
  its `work/` is a link, which the line then says (#973). The rest of the
  line and the plan's JSON are unchanged too: `defaults.retainWorktree` is
  the default of one option, whether the instance's own work tree is
  retained, and is `true` only when `work/` is that tree: in `worktree`
  mode unless `work/` is a link (#973), and for a record with no work mode
  whose `work/` Git confirms is a registered linked worktree (#962). See
  [the retire plan](../desktop-cli-api.md#retire).

- **`oats teams add|remove|default` and `oats soul launch set|remove` write
  an `oats-local.yaml` that is JSON.** The kernel reads a file that opens
  with `{` as strict JSON. A `teams` write to such a file ended in a decoder
  error with no answer, and nothing was written. Both verbs now write it
  back as JSON: the keys keep their order, the final newline stays as it
  was, and the indentation becomes two spaces. A rewrite the kernel could
  not read back is refused (`E_WORKSPACE_SCHEMA`) and nothing is written.

  `<home>/.claude/settings.json`. On Homebrew that is the versioned keg

  of a live home then called a node that was gone, and failed without a
  word, so the Desktop and `oats status` no longer showed the instance as
  waiting. **oats.core now writes `OATS_NODE_BIN`**, which on Homebrew is the
  `opt` link that an upgrade repoints. It is also the kernel's own node, where
  the hook's could be another one found first on `PATH`. It needs this kernel
  and the oats.framework that carries the change; under an older kernel the
  same oats.core writes what it wrote before. For homes that already exist,
  see Upgrade above.

- **`oats update` moves forward only, and checks what the registry answers
  before it uses it**
  ([#1011](https://github.com/awebai/oats/issues/1011)).
  - **It proposed a downgrade.** From a CLI ahead of the version npm lists (a
    checkout, a build not published yet), the plan held
    `npm install -g @awebai/oats@<the older version>`, and `--yes` ran it. A
    bridge ahead of that version was moved back the same way. Now the CLI is
    installed only when npm lists a newer version, one line says when the
    installed one is ahead, and a bridge ahead of the version the CLI has
    after the run is left alone. `oats doctor` still warns about such a
    bridge, and says what ends the skew instead of "run `oats update`".
  - **What `npm view` printed went into the steps and onto the screen as it
    came.** Now each of the two lookups must answer one version and nothing
    else. Any other answer stops the update before any step, with nothing
    changed, and the message shows it cut short, with its control characters
    made visible. npm's error output of a lookup is shown the same way, never
    as it came.
  - **A pi folder named only by launch configurations with different
    executables** got a by-hand command with the first one's executable. Now
    the plan prints one command per executable, with the configurations it
    is for.

- **`oats setup` records a `node` that survives an upgrade of Node, and
  quotes what it writes
  ([#1003](https://github.com/awebai/oats/issues/1003)).** It wrote the path
  of the `node` it ran under into the capture hooks of every
  `~/.claude*/settings.json` and into the capture watcher's unit. On Homebrew
  that is the versioned keg, which `brew upgrade node` removes: the hooks
  then failed at every stop of every Claude Code session of that user, and
  launchd or systemd kept restarting a watcher that could not start. Now:
  - **It records the path the kernel hands every hook (`OATS_NODE_BIN`):** on
    Homebrew the `opt` link, else a `node` on `PATH` that is the same file,
    else the path as it is.
  - **When there is no stable path it says so,** once, a dry run included:
    the capture hooks and the watcher stop when that `node` goes away, and
    `oats setup` is to be run again after installing a `node` with a stable
    path.
  - **Each path is quoted for what reads it:** a shell word in the hook's
    command, systemd's quoting in `ExecStart`, XML text in the launchd plist.
    A `node` or an install under a path with a space in it no longer splits.
    A path of plain characters is written as before.
  - **A hook is taken for setup's own only when the whole command reads as
    one plain command of its shape.** A command that also carries a second
    command, an operator or a redirection was overwritten, and that part
    lost. It is now left as it is, and setup's hook is added beside it.
  - `turn-record setup`, run without the kernel, records the `node` it runs
    under, as before, with the same quoting.
  - For installs that already exist, see Upgrade above.

- **A retire no longer keeps a clean extra tree for a Git operation that has
  ended ([#1008](https://github.com/awebai/oats/issues/1008)).** Git leaves
  `REBASE_HEAD` behind a rebase that stopped on a conflict and was continued,
  and `AUTO_MERGE` or `MERGE_MSG` behind others. A retire read each as "an
  operation is in progress", so the tree stayed on the host under
  `.agents/worktrees/` with its branch. A retire now reads what `git status`
  reads: an open rebase, `git am`, merge, cherry-pick, revert or bisect keeps
  the tree as before, and a tree that holds only such leftovers is removed,
  its branch kept. The recovery of an instance's own worktree and `oats
  doctor` use the same answer.
  [What counts](../souls-and-instances.md#git-operation-in-progress).

- **Desktop: the fix OATS sends with a refused preview reaches the Spawn
  dialog** ([#1015](https://github.com/awebai/oats/issues/1015)). When OATS
  refuses the preview of a spawn it may send, beside its message, a fix: what
  to do about it. The Desktop's reader of the CLI's answer kept the code and
  the message and dropped the fix, so no fix reached the dialog from an
  installed OATS. It now keeps the fix beside OATS's own message, as one
  printable line of at most 1,024 characters, and nothing else of the
  refusal's details. What a person sees differently today is in one place:
  the three lines under Details for an unmatched launch preference (under
  Changed) are read from it. A harness that is not installed reads as it did,
  since OATS's message for it already holds its fix.

- **Whether a retire refuses no longer depends on the file system
  ([#1029](https://github.com/awebai/oats/issues/1029)).** A recovery copies
  the index, `info/attributes`, the stash's log and a nested repository's
  reflogs each as one file. With an empty directory at one of the last three
  the copy failed on most file systems and the retire refused, but on btrfs
  it wrote an empty file and the retire went through. Nothing was lost
  there: an empty directory at such a path holds nothing that Git reads. A
  retire now looks before it copies and refuses on every file system with
  `E_WORK_PRESERVATION_FAILED`, naming the path and what is there. A link
  at such a path is still followed, as Git follows it.
  [The rule](../souls-and-instances.md#copied-as-one-file).

- **An instance whose work tree has no index file can be retired
  ([#1048](https://github.com/awebai/oats/issues/1048)).** A tree made by
  `git worktree add --no-checkout`, or one whose index file was removed,
  reads to Git as a tree whose index lists nothing: every committed file is
  a staged deletion. A retire copies such a tree, as any tree that holds
  work, and the copy refused it: it copies the index as one file, and none
  was there. The instance could not be retired until someone ran
  `git reset` in its tree. The recovery now carries "no index" as no index:
  its `repo/` has no index file, and Git reads it as it read the tree, file
  for file. The same holds for a nested repository that has a commit and no
  index file. `git reset` in the recovery makes an index from `HEAD`. An
  extra tree with no index file was never refused: a retire re-homes it as
  it is, as before.
  [The rule](../souls-and-instances.md#no-index-file).

- **A commit is fetched into the remote cache whatever the cache already
  holds** ([#1059](https://github.com/awebai/oats/issues/1059)). A spawn, a
  preview, `oats souls` or `oats workspace status` could fail with
  `E_REMOTE_UNREADABLE … (network)` in a second or two, every time, on a
  network that was fine: the fetch of a pinned package's commit, or of a
  member's new head, into a cache that held another commit of the same
  repository. It needed one file under 64 KiB at the wanted commit whose
  version at a commit the cache held was over 64 KiB, which a file that grows
  or is split produces in any repository. Git then received a pack it could
  not complete and the fetch died; a cache in that state could stay in it, and
  a deleted cache came back to it. The kernel now makes that fetch once more,
  whole, and it succeeds. Nothing needs to be done on a host that was
  affected: the next read fetches the commit.
- **The pack of a fetch that failed no longer stays in the cache for good**
  ([#1059](https://github.com/awebai/oats/issues/1059)). Each failed fetch
  left a temporary pack file in the cache's object store, which nothing
  removed; a host that retried for an hour held dozens. Every fetch into a
  cache now first removes the temporary files there that are older than the
  longest fetch (11 minutes). It goes by age and not at once, because a file
  that appeared during a fetch cannot be told from one another Git process
  is still writing.

- **A work tree that holds a repository with no commit can be retired
  ([#1078](https://github.com/awebai/oats/issues/1078)).** `git init` in a
  directory of the work, and no commit in it, was enough to make an
  instance impossible to retire: the copy of a nested repository read the
  commit at its `HEAD` before anything else, and that `HEAD` has none. The
  same held after `git switch --orphan` in a repository that has commits.
  The recovery now rebuilds such a repository as any other: its `HEAD` is on
  the same branch with no commit, its other branches, their commits and
  their logs are there, and its index, what is staged in it and its files
  are the source's. A `HEAD` with no commit that names no local branch (a
  ref outside `refs/heads/`, or a branch whose name is not UTF-8) is still
  refused: a commit there, or `git switch -c <branch>`, makes the work tree
  retirable.
  [The rule](../souls-and-instances.md#nested-no-commit).

- **`oats retire`: a real directory at `work/` is no longer removed without
  a copy, and is no longer read as a work tree (#962).** A retire decided
  that an instance had a work tree of its own from any real directory at
  `<home>/work`, whatever the work mode. For a home that was given a link
  (an attached, a checkout or a workspace instance) or whose record held no
  work mode, most retires then refused, and two shapes lost what the
  directory held: under a record that named no repository, a directory that
  was a Git repository of its own, or the registered worktree of a spawn
  that had not finished, was removed with the home and nothing of it was
  copied. What `work/` is now comes from one reading, which the retire and
  its plan share:
  - A real directory that is not the instance's own tree is a directory of
    the home. The retire copies it to recovery (`workRecovery.path/work`,
    class `directory work bytes`), checks the copy, and removes it with the
    home, a `.git` in it included. It is never moved or removed through
    Git. Three refusals of such a home are now a completed retire with a
    recovery copy. An entry the copy cannot take (a FIFO, a socket) still
    refuses before anything is touched.
  - The instance's own tree is retained as before, under a record with no
    work mode too when Git confirms that `work/` is a registered linked
    worktree (its plan's default is under Changed). When the record names no
    repository, the retire uses the one Git names for the tree, does not
    write it into the record, and says so in the plan's note and the
    receipt's `warnings`.
    What such a tree holds uncommitted is copied to recovery as a `worktree`
    instance's is. An own tree with no repository at all is refused
    (`E_WORK_PRESERVATION_FAILED`, nothing stopped, run or removed) and
    never removed with the home.
  - A registered worktree that is a directory of the home leaves its entry
    in its repository until a prune: the receipt's `warnings` name the
    repository and the command, and its branch and commits are untouched.
  - The plan's notes and its text's `defaults:` line say the above. No key
    of the plan or of the receipt is new, and no code.
  - The plan of a `directory` instance whose `work/` is a Git repository of
    its own no longer has the note `N changed and M untracked file(s) would
    be retained with the worktree`: nothing of it is retained. Its bytes are
    copied to recovery and removed with the home, as the plan's recovery
    note and its text's `defaults:` line say. The plan's `facts.work` for
    that home is unchanged.

  See [what `work/` is at retire](../souls-and-instances.md#what-work-is-at-retire).
- **`oats instance git` and the plans no longer read an enclosing checkout
  as an instance's work (#962).** Git answers for any directory inside a
  work tree, so a plain `work/` in a home whose deployment directory is a
  Git checkout was reported with that checkout's branch and files. A real
  directory at `work/` is now the instance's work tree only when it is the
  top level Git names for it (what is answered otherwise is under Changed).
  The rule is the path, in every work mode. A `directory` instance in such a
  deployment has no work tree observed (its retire is unchanged: its bytes
  are copied to recovery and removed with the home); one whose `work/` is
  the top level of a repository of its own is observed as before. A `work/`
  that is a link is read as what it leads to, as before: a `workspace`
  instance's deployment directory included.

- **A stop on a full disk leaves no private file in the home (#963).**
  `oats instance stop --apply` writes its record (`.oats-stop.json`) and the
  receipt of its key (`.oats-stop-receipt.<key>.json`) through a private file
  beside each, renamed into place. On a file system with no space the private
  file was created, its write failed, and nothing removed it: the home kept
  `.oats-stop.json.tmp-<pid>` and `.oats-stop-receipt.<key>.json.<pid>.tmp`,
  both empty, and one more of the second for each later apply. Both writers
  now remove their private file when the write or the rename fails. The error
  is the one they gave before, and so is the receipt: its row for such a stop
  is unchanged. An upgrade does not remove the files an earlier version left
  in a home.

  The record's writer is shared: an `instance.json` or a restart record that
  cannot be written leaves no `<name>.tmp-<pid>` beside it either.
- **The text of a stop no longer says that something is still running when
  nothing is (#963).** A stop that is not `ok` closed its text with `some
  targets are still running; nothing was escalated`, also under a row that
  said `its harness was signalled (SIGTERM) and has exited`: a stop on a full
  disk, which stops the session and cannot write its record. The closing
  sentence is now chosen from the rows'
  [`stillRunning`](../desktop-cli-api.md#still-running), as a client reads
  them. It is the sentence above when a row that is not `ok` names a process
  or establishes nothing (`null`, or no `stillRunning`), and `the stop did
  not complete its record; nothing is still running` when every such row
  says `[]`. The exit status is 1 in both cases, as before, and the JSON
  receipt is unchanged.

  See [a stop whose claim cannot be written](../desktop-cli-api.md#stop-claim-write).

- **`oats retire`: a link at `work/` is never the instance's own tree
  (#973).** For anything at `<home>/work` that was not a real directory, a
  retire went by the record's work mode. A home whose record said `worktree`
  and whose `work/` was a symbolic link was then read as holding the
  instance's own tree: its plan said `defaults.retainWorktree: true`, and
  its retire was refused (`E_WORK_PRESERVATION_FAILED`) by a comparison
  written for something else. Nothing was lost, by accident. The record is
  a file the instance can write; what the link leads to is not the
  instance's. Now a link is a link, whatever the record says:
  - The plan of such a home has `defaults.retainWorktree: false`, the note
    `the record says work mode worktree, but work/ is a link and not a work
    tree of the instance's own: the retire removes the link with the home
    and does not touch what it leads to, with --discard-worktree as well`
    (a plan takes no option, so the note names the flag), and in its text's
    `defaults:`
    line `no work tree of its own (work/ is a link, though the record says
    worktree: what it leads to is not touched)`. Its `planRevision` binds
    it: a plan read by an older kernel, or while `work/` was the instance's
    own tree, is stale.
  - The retire completes, with every flag (it was refused: see Changed):
    the link goes with the home, and what it led to is not copied, moved,
    removed or read through Git, and no branch is deleted. The receipt's `warnings` say where the link led
    (`<home>/work was a link though the record says work mode worktree:
    nothing was retained or removed as a work tree, and what it led to
    (<path>) was not touched`), or that it led nowhere that could be read.
    The receipt holds the path as the system gave it; the retire's text
    spells a character a terminal would act on (see Changed).
    A registered worktree that was moved elsewhere, with a link left in its
    place, stays registered in its repository.
  - A link at `work/` that is a directory or a file by the time the retire
    inspects the home again after its hooks refuses the retire
    (`E_WORK_INSPECTION_FAILED`) and keeps the home, in every work mode:
    the home's removal would have taken what replaced the link, uncopied.
    The message says what is there now and how it ends: for a directory,
    that `oats retire <instance> --plan` shows what a retire would do with
    it and that running the retire again does that; for a file, or an entry
    that is neither a link, a directory nor a file, that no retire removes
    it, and to move it out of the home or remove it, then run the retire
    again; for an entry that cannot be read, that the retire reads it again
    when it is run again.
  - The two notes about a worktree that is retained are given for the
    instance's own tree alone (see Changed).
  - No key of the plan or of the receipt is new, and no code. A `worktree`
    record whose `work/` is gone, or is a file, answers as before.

  See [what `work/` is at retire](../souls-and-instances.md#what-work-is-at-retire).

- **One long text with no space no longer slows the Desktop and the TUI
  ([#976](https://github.com/awebai/oats/issues/976)).** Both show the
  kernel's free text through one filter, which withholds a text that looks
  like a credential. Its check for a URL with credentials took time that grew
  with the square of a run of letters: one 8192-letter message with no space
  cost from a tenth of a second to most of a second each time it was shown,
  depending on the machine, in the Desktop on each render and in the TUI on
  each paint. The check now takes time that grows with the length of the
  text: the same message takes about a millisecond or less. The filters of
  the readiness view and of an instance's activity had the same check and
  take the same fix. **What is withheld and what is shown are the same as
  before.**

- **Two commands that rewrite `oats-local.yaml` no longer drop each other's
  change ([#998](https://github.com/awebai/oats/issues/998)).** `oats
  launch-config set|remove` read the file when it started and wrote it back
  without the file's lock, and `oats schedule|trigger enable|disable` took no
  lock either. Either could overwrite what `oats teams`, `oats soul launch`
  or the other had written in between: a team, a soul's launch preference, a
  launch configuration or an opt-out was gone, with no error. All of them
  now write under one lock, each from the file as it is then.
- **`oats schedule|trigger enable|disable` of a workspace item writes
  `oats-local.yaml` whole, and leaves its long lines alone
  ([#998](https://github.com/awebai/oats/issues/998)).** The file was written
  in place, so a command killed during the write could leave half of it; it
  is now written beside and renamed in. A line longer than 80 columns
  elsewhere in the file was folded onto several lines by the write, and
  stays as written now. A deployment whose `oats-local.yaml` is written as
  JSON could not opt out at all (the command failed with
  `invalid-declaration` and wrote nothing): the opt-out is now written, and
  the file stays JSON.
- **A kernel command that rewrites `oats-local.yaml` keeps the file's
  permission bits ([#998](https://github.com/awebai/oats/issues/998)).**
  `oats teams`, `oats soul launch` and `oats launch-config set|remove`
  replace the file by a rename, and the new file got the bits the process's
  umask gives: a file its operator had made private (`0600`) came back
  readable by others (`0644` under the usual umask). The new file now has
  the bits of the one it replaces, from before its first byte is written.
  `oats schedule|trigger enable|disable` keeps them too, as it did when it
  wrote in place.
