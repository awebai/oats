# OATS 0.53.0

Unreleased

## Upgrade

- **A host that runs pi instances moves the pi bridge with the kernel.**
  `oats update` does both for the default pi folder, and `oats doctor` warns
  of a kernel and a bridge at different versions there. A launch configuration
  that sets its own `PI_CODING_AGENT_DIR` has a pi folder of its own, which
  neither command reaches yet
  ([#991](https://github.com/awebai/oats/issues/991)): in each such folder,
  run the two commands `oats update` prints (`pi uninstall
  npm:@awebai/oats-pi@<old>`, then `pi install npm:@awebai/oats-pi@<new>`).
  This was already so in 0.52 and earlier; no notes said it.

## Added

- **`oats tui` (preview) shows a deployment's instances (#855).** In 0.52 the
  preview drew a frame and read nothing from the kernel. **This version shows
  one deployment's instances on this machine and changes nothing.** The list
  is the roster the Desktop draws, with the same groups, order and states,
  from the same code, and it follows the deployment every few seconds. Beside
  it is the detail of the selected instance, with what it needs from you. `/`
  filters by name, soul and repository. **It cannot yet** open an agent's
  terminal, stop, start, restart, retire or spawn one, show souls or
  capabilities, or read another machine: its help screen names the `oats`
  command for each. It is still a preview: its screens and its configuration
  file may change without notice. [docs/tui.md](../tui.md) has the rest.
  - **Start it in or under a deployment**, or name one: `oats tui --dir
    <path>`. With no `oats-local.yaml` at or above the start it prints one
    line (`E_NO_DEPLOYMENT`) and exits 1. Started inside an agent's pane it
    still reads the deployment it was asked about: it removes the instance's
    variables from its own environment first.
  - **It runs the kernel it shipped with**, never an `oats` found on `PATH`,
    and only to read (`oats status` and `oats workspace status`, then a probe
    of the terminals). A kernel it cannot accept stops the start with
    `E_TUI_KERNEL`. Start it again after upgrading OATS.
  - **Every key can be changed** in `$XDG_CONFIG_HOME/oats/tui.json` (else
    `~/.config/oats/tui.json`). A file it cannot honour stops the start, one
    line per problem (`E_TUI_CONFIG`): it resolves no conflict between two
    actions and guesses nothing.

## Changed

- **Desktop: a row keeps its roster group under a filter and a collapse**
  ([#971](https://github.com/awebai/oats/issues/971)). A relation group is
  now decided on the whole roster, not on the rows left on screen. With a
  filter, one match out of a group of five is listed under its group's name,
  where it stood under "independent"; the same holds for a query in the
  command palette. With a collapse, a root collapsed over its whole group
  stays under the group's name and at its place, where it moved to
  "independent" at the press and came back on expand, taking the keyboard's
  selected row with it. A group with no row on screen is not drawn, and
  "independent" lists only instances with no relation. A header still counts
  the rows shown under it.

- **The Desktop accepts OATS CLIs `>=0.25.8 <0.54.0`.** The compatibility band
  admits 0.53. Upgrade the CLI and the Desktop together: a 0.52.0 Desktop
  refuses a 0.53.0 CLI. No new gate on the band. `oats tui` runs the kernel it
  ships with and is held to the same band.

## Provider updates

- **oats.okf 5.0.3: installing the host timer is the operator's step in
  `okf-trigger-setup` (awebai/oats-okf#73, awebai/oats-okf#74).** The agent checks with
  `oats schedule host status` and hands a missing timer's install command to
  the operator, to run in their own terminal from the deployment directory
  and outside every instance home. It checks status again after installation
  and reports what is waiting if no operator is present. The agent must not
  install the timer or offer its own `--print` output as a preview. The
  generated mirror and package pins move together to the released tag;
  compatibility remains OATS >=0.29.0.

- **oats.framework: installing the host timer is the operator's step in the
  `oats-automations` and `oats-onboarding` skills (#967).** Both skills had the
  agent run `oats schedule host install`. The unit records the `PATH` and the
  node of the shell that installs it, and an agent's shell can carry a
  session's own. The skills now have the agent hand the operator the exact
  command, with the flags they want, to run in their own terminal, outside
  every instance home, and check the result afterwards with
  `oats schedule host status`. Until the operator runs it, the timer stays as
  it is. The skills' other schedule and trigger steps are unchanged.
