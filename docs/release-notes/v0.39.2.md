# OATS 0.39.2

## Added

- **oats.cloning 1.0.0**, a new official package (catalog entry, workspace
  member and pin, and the bundled mirror): clone an instance for a new goal.
  `oats cloning request <source>` spawns the package soul
  `oats.cloning/cloner`, which reads the source and writes a curated,
  redacted brief, then spawns the clone with it attached and a fresh
  identity. The clone gets no raw transcript, notes or work content. See
  [instance cloning](../design/2026-10-01-instance-cloning.md).
  - The framework's oats-expert, oats-kernel-expert, oats-desktop-expert,
    integrations-expert, oats-operator-expert and oats-setup-admin souls take
    it (`oats.cloning: { from: package }`); there is no workspace default.
  - The workspace pins it as `git:github.com/awebai/oats-cloning@v1.0.0`
    until every deployment's CLI carries this catalog entry; then the pin
    becomes the bare `v1.0.0`.
  - Operators: run `oats sync` to lock the package; new spawns of those
    souls get the capability. Running instances keep what they were spawned
    with.

## Changed

- **Desktop: terminal text in the White and Solarized themes renders at the
  stroke weight of a native macOS terminal with font smoothing.** Chromium
  draws dark text on a light background lighter, so these themes' terminal text
  looked fainter than the same font in a native terminal. Each theme now sets
  its own text weight; Dark is unchanged, and bold text stays bold.
- **oats.engineering 1.8.0** (catalog and workspace pin, and the bundled
  mirrors; includes 1.6.0 and 1.7.0):
  - **New capability `oats.maintainer`**: the whole maintainer job, generic.
    It covers the overview of what's open, launching work, a direction and
    architecture gate, review and merge at an exact head, release planning
    and shipping with a verification checklist, cross-review between peer
    maintainers, keeping the project clean, and a living roadmap,
    architectural calls and coherence rules kept in the maintainer's
    knowledge. Skills: `/maintainer-intake`, `/launch-work`,
    `/direction-gate`, `/pr-review`, `/plan-release`, `/ship-release`,
    `/cross-review-peer`, `/keep-it-clean`.
  - **A maintainer is not an expert; no soul holds both roles.** The
    maintainer launches work without leading it: `/launch-work` delegates it
    to a live expert whose work it continues, or spawns the best-suited expert
    with `--relation unrelated` as the effort's lead, never as its own child.
    The lead coordinates the developers and experts it needs.
  - **Knowledge and state.** Maintainers and experts consult their knowledge
    before deciding, and keep their instance state accurate.
  - **Experts tell a standing maintainer what they start** when a human
    launches them directly.
  - **Experts give unrelated work to a new expert** (1.6.0). New work goes to
    a live expert only when it continues that expert's work or that expert's
    context helps. Otherwise the expert spawns a new one: as its child when
    the work is part of its effort, or with `--relation unrelated` when it is
    independent, reporting to whoever asked.
  - **Developers prefer this machine's reviewer override** (1.7.0). When
    picking the reviewer's model, `/run-the-review-loop` reads what the
    machine will launch (`launch.effective`, including an `oats-local.yaml`
    `souls.launch` override), not only the soul's default. It keeps the
    override when that runs on another harness than the developer's.
