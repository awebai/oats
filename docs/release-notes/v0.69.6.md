# OATS 0.69.6

Unreleased

0.69.6 makes the Desktop and `oats tui` refresh without starting a new CLI
process for every read. Both now read through one warm `oats reader --stdio`,
and under the new feature `status-liveness` they take each instance's
liveness from `oats status` instead of running their own terminal probe.
`oats status` and `oats workspace status` also do less work per read. A
working instance no longer reads idle when the process scan can't see it.
The catalog moves to oats.okf 5.7.0, whose knowledge maintainer never parks a
harvest PR for a human, and to oats.framework 1.16.4.

## Upgrade

- **Either order of the Desktop and the CLI works.**
  [Upgrading](../upgrading.md) installs the Desktop first, and a host that
  installed the CLI first is fine too: the 0.69.6 Desktop accepts OATS CLIs
  `>=0.26.0 <0.70.0`, and so does the 0.69.5 Desktop. The warm reader needs
  both: a Desktop or TUI uses it only with a CLI that lists feature
  `warm-reader`, and otherwise reads through the CLI, as before.
- **Package moves:** the official catalog pins oats.okf 5.7.0 and
  oats.framework 1.16.4, with no change to their OATS floors. A deployment
  takes them with `oats sync`. Running instances keep the modules they were
  spawned with: new spawns get the new ones, and a stopped home moves with
  `oats instance upgrade`.
- **Knowledge PRs parked on `okf-needs-human`:** on the review host of the
  workspace's harvest-review trigger, once its lock has oats.okf 5.7.0,
  re-review each one as Provider updates (below) says. A label left in place
  does nothing, and no new review starts on its own.

## Added

- The warm reader, `oats reader --stdio` (feature `warm-reader`,
  `readerApi: 1`, #1630). A client starts it as its own child, from the same
  install it runs its CLI reads with, and sends it `oats status --json` and
  `oats workspace status --json` reads over its stdin and stdout, one JSON
  line each way, many times. It answers with the kernel's own read code, kept
  loaded: warm code, not warm data. Every request reads the deployment
  afresh, and each answer's `exit` and `answer` are what the same CLI read
  prints and exits with, with cwd = `--dir`. What it cannot answer that way it
  refuses (`E_READER_BAD_REQUEST`, `E_READER_UNSUPPORTED`), and the client
  runs the CLI. A reader whose install changed under it (an upgrade, a Node
  upgrade) answers nothing more from the old code: it refuses with
  `E_READER_STALE` and exits. It ends when its client closes its stdin or
  dies. Bare `oats reader` is `E_USAGE`. The protocol and the client rules
  are in [The warm reader](../desktop-cli-api.md#the-warm-reader); the
  decisions in [the design record](../design/2026-10-29-warm-reader.md).
- Feature `status-liveness`: `oats status --json` instance rows' `running`
  and `runtimeState` are the complete local liveness reading, read live at
  every call under the kernel's pane rule, so a client that sees the feature
  in the probe needs no liveness probe of its own beside the roster
  ([The roster](../desktop-cli-api.md#the-roster-oats-status---json)).

## Changed

- **OATS Desktop: the poll's reads go through the warm reader** (#1630).
  Where the installed CLI lists `warm-reader` (`readerApi: 1`), the Desktop's
  bundled server starts one `oats reader --stdio` from that CLI. It answers
  the background `oats status` and `oats workspace status` reads of every
  refresh cycle (`--max-age` above 0) with the kernel's read code kept
  loaded, instead of a Node start per read. The answers are the CLI's own and
  are checked the same way. A live read (the first cycle, a refresh after a
  change, Refresh) still runs the CLI. Whenever the reader is absent, refuses,
  times out, stops answering or exits, that read runs the CLI as before.
  After repeated failures the Desktop uses the CLI until the CLI changes. A
  reader whose install was upgraded under it makes the Desktop probe the CLI
  again. The reader dies with the server that started it, also when the app
  or the server is killed. Nothing about it is shown. `/api/cli` reports its
  state as a diagnostic.
- **OATS Desktop: no liveness child under `status-liveness`.** With a CLI
  that lists `status-liveness`, the refresh cycle no longer starts its
  terminal-liveness child. A local row's running state, reason and tmux
  record are the ones `oats status` reports, and a reason on a local row is
  always the kernel's. As a result, an instance home with no tmux record
  (every spawn records one) has no terminal for the Desktop to open, where
  the child used to fill in the default session. With an older CLI the child
  runs as before.

- `oats tui` reads its deployments in the background through one warm
  `oats reader --stdio` of its own kernel, when that kernel lists feature
  `warm-reader`, in place of two kernel commands per deployment each cycle.
  Its answers are the commands' own, and a live read (`r`), every read
  before the reader is ready and every read it does not answer still run
  the commands, as before. Under feature `status-liveness` the TUI no
  longer runs its probe of the terminals: each instance's running state,
  reason and tmux record are the ones `oats status` reports. As a result,
  an instance home with no tmux record (every spawn records one) has no
  terminal for the TUI to open, where the probe used to fill in the default
  session. With an older kernel the probe runs as before (#1630; [What it
  reads, and what it runs](../tui.md#what-it-reads-and-what-it-runs)).
- The warm reader (`oats reader --stdio`, #1630) starts with only the code
  its reads use: the CLI no longer loads its whole command set for it first.
  On a real deployment its hello comes in about 140–180 ms instead of about
  300, and it holds about 20 MiB less memory while it answers a poll. Its protocol, its answers
  and its install stamp are unchanged; a client needs no change
  ([The warm reader](../desktop-cli-api.md#the-warm-reader)).

- `oats status` and `oats workspace status` do less work per read, with the same answers ([awebai/oats#1630](https://github.com/awebai/oats/issues/1630)). `status` shares each instance home's `instance.json`, as its listing read it, with its legacy-home check and its waiting-claim read instead of each parsing it again, and `workspace status` asks git for a member clone's remotes once, where it verified the clone an automation lives in twice. Nothing is kept between reads, in the CLI or in the warm reader (`oats reader --stdio`).

- **`oats workspace status --max-age <s>` reuses the host's `gh` login, for display only** ([awebai/oats#1630](https://github.com/awebai/oats/issues/1630); [Observation reuse](../desktop-cli-api.md#the-gh-login-display-only)). To show where each workspace trigger and schedule runs, `workspace status` asks `gh api user` which account this host acts as: a GitHub API call on every read, which a client polling every few seconds made every few seconds, and most of each read's time. Under `--max-age <s>` it now reuses a login observed at most `<s>` seconds ago, as it reuses remote heads, and counts it in the `observation` block (`reused`, `observedAt`). A login is reused only under the same `gh` context (host, `gh` binary, which token variables are set, `GH_HOST`, the config directory and its `hosts.yml`); no token or digest of one is kept; a failed answer is never reused and ends the reuse of the one before it. Without `--max-age`, or with `0`, it asks every time. What runs does not change: a schedule tick, `oats trigger poll` and every run still ask `gh` live. Within `<s>`, a token revoked on GitHub still shows the login, as a moved head shows unmoved.
- **A `gh` that hangs costs `oats workspace status` 5 s, not 30.** The display waits at most 5 s for `gh api user` (ticks and runs keep 30 s); a `gh` that does not answer in time reads `owner-mismatch`, as one that is not logged in does.


## Fixed

- **A working instance no longer reads idle when the process scan cannot see it.** tmux names the launch's own shell as a pane's command while the harness runs below it, so `oats status` and `oats session inspect` decide such a pane from the process table. A table that could not establish the fallback prompt still read it: a `ps` that could not see the pane's process (another PID namespace, a pane respawned between the two reads), a process in the pane with no command name, or a line that is not a process each made a running harness read `running: false` (idle) in the Desktop and the TUI. `false` now needs the pane's own shell in the table with no non-shell process below it; anything else reads `running: null` with the reason as `runtimeError` (`session inspect`: `E_SESSION_UNAVAILABLE`), and a lifecycle command refuses rather than taking the pane for a fallback shell. A pane at its fallback prompt still reads `running: false` with `runtimeState: "shell"` ([awebai/oats#1641](https://github.com/awebai/oats/issues/1641); [The roster](../desktop-cli-api.md#the-roster-oats-status---json)).

## Provider updates

- **oats.okf 5.7.0: the knowledge maintainer never parks a harvest PR**
  ([awebai/oats-okf#118](https://github.com/awebai/oats-okf/issues/118)).
  When a deployment pins oats.okf 5.7.0, a PR that would supersede a
  human-accepted decision is settled at review instead of waiting for a
  human under the `okf-needs-human` label. The OATS floor is unchanged.
  - It is closed when it cites no acceptance (who accepted the change, when
    and where).
  - A cited record on GitHub (an issue or PR comment, or a commit) is
    checked: it must exist at the cited link, under the account the citation
    names, and say the cited thing. Confirmed, the PR merges as an explicit
    supersession with the acceptance recorded as verified at its link, which
    shows the account and the record, not that the human typed it: agents
    may post under their human's account. Otherwise it is closed.
  - A relay on GitHub (a record that presents itself as an agent reporting
    the human's words) is checked the same way: it must exist at the cited
    link and say that the relaying agent reported the human's acceptance of
    this change. Confirmed, the PR merges as an explicit supersession with
    the acceptance recorded as `source-reported (relay at <link>)`, never as
    verified; otherwise it is closed.
  - A cited record the maintainer cannot read (mail, a session, a call) is
    trusted without a check: the PR merges as an explicit supersession with
    the acceptance recorded as source-reported.
  - `oats okf-maintenance review-context` no longer reports `blocked`, and
    `settled` now means only that the PR is not open.
  - **Re-review each parked PR.** A label left in place is inert, but the
    PR is reviewed again only on a new `harvest-review` event. The trigger
    polls: a close it never saw is no reopen. On the trigger's review host,
    once its lock has 5.7.0:
    1. Retire the knowledge-maintainer instances left from older reviews,
       running or stopped: a retained home holds a concurrency slot (`max`
       2, `perKey` 1), and one composed from an older package keeps the old
       behaviour.
    2. Remove `okf-needs-human` from each parked PR, then close it.
    3. Wait until `oats trigger status <id> --json` shows a `lastPoll`
       after the closes with `ok: true` and `prs` under 100 (every 2m). Only
       such a poll records a close: a failed poll records none (keep
       waiting), and one that fetched 100 open PRs may be truncated (stop
       and report the poll cap; do not reopen). `oats trigger test` does not
       count: it records nothing.
    4. Reopen each PR, and check that `oats trigger status <id> --json`
       lists a `pending` or `fired` entry with `event: "reopened"` for each
       PR's number. At most two reviews run at once; the rest wait as `held`
       until a maintainer retires.

    Never clear the trigger's dedup state.
  - [Knowledge operations: the flow](../knowledge.md#the-flow), step 4,
    says what holds before and after 5.7.0.

- **oats.framework 1.16.4: oats.setup 2.9.5.** oats.setup's `/oats-onboarding`
  pins `oats.okf: v5.7.0` in its knowledge section (text only), so a new
  deployment sets up knowledge operations whose review never parks a harvest
  PR. The floors and the other capabilities are unchanged.
- **Upgrade:** `oats sync` locks it once the workspace or the catalog pins
  `oats.framework: v1.16.4`. New spawns get it, and a stopped home moves with
  `oats instance upgrade`.
